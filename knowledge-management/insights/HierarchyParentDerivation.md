# HierarchyParentDerivation — Technical Insight Document

## What It Is

`HierarchyParentDerivation` centers on `deriveAncestryFromStorePath()` in `integrations/unified-viewer/src/graph/D3GraphCanvas.tsx`, the function responsible for reconciling a locally-computed ancestry path with the Zustand store's authoritative `pathToSelected` set. It is the mechanism by which the dynamic, force-directed knowledge graph (a sibling concern of `ForceDirectedLayout`) determines which nodes count as "ancestors" of a selected node for visual dimming/tiering purposes. As a child concept under both `KmCoreAdapter` and `GraphVisualRendering`, it sits at the intersection of graph traversal logic and rendering-tier assignment, and its correctness directly affects what the D3 canvas visually presents as hierarchy.

## Architecture and Design

The core design is a **fast-path/slow-path reconciliation pattern**: an inline BFS (`computeAncestryPath`) computes ancestry locally, and this result is compared against the store's `pathToSelected`. When the two agree, the BFS result is returned unmodified (fast path). When they diverge, the function must adjudicate — nodes present in the store but unreached by the BFS are still included but pinned to `maxDepth` (the dimmest visual tier), while BFS-reached-but-not-store-tagged nodes are dropped entirely. This is a deliberate trust hierarchy that favors "writer's intent" (the store's authoritative path) over locally-derived graph traversal, even at the cost of potentially hiding real graph relationships from the visualization when a filter change causes divergence.

This derivation logic lives inside `D3GraphCanvas.tsx`, which as the parent `GraphVisualRendering` context notes, has no shared rendering abstraction with the sibling static SVG renderer `multi-agent-graph.tsx` (`MultiAgentGraphSvg`). The ancestry derivation is therefore a concern unique to the dynamic knowledge-graph rendering path — there is no equivalent concept in the fixed-topology workflow diagram, since that diagram's hierarchy (`WAVE_AGENTS`, `KG_OPERATOR_CHILDREN`) is hand-authored and static rather than derived from live selection state.

## Implementation Details

The mechanics hinge on two independently-produced sets of ancestry information: (1) the inline BFS traversal `computeAncestryPath`, which walks graph edges directly, and (2) `pathToSelected`, a set maintained by the Zustand store representing the "official" path to the currently selected node. The reconciliation logic treats agreement as the default/fast case, only invoking the more expensive comparison-and-merge logic on divergence. Divergence handling is asymmetric by design: store-only nodes are demoted to `maxDepth` rather than excluded, while BFS-only nodes are excluded rather than included at some default depth. This asymmetry encodes a policy choice, not just a technical shortcut — it explicitly prioritizes consistency with the store's semantic notion of ancestry over path-completeness from raw graph structure.

This derivation function operates within a broader file whose selection/viewport behavior is governed by explicitly "locked" contracts — notably "Locked Contract #3" (viewport stability), enforced by keeping a `selectionSource` subscription out of the main render `useEffect`'s dependency array. While `deriveAncestryFromStorePath` itself is not the contract enforcement mechanism, it operates in the same file and under the same general engineering culture of encoding invariants via comments and structural omission rather than types or tests — a pattern worth understanding before modifying adjacent selection/ancestry logic.

## Integration Points

`deriveAncestryFromStorePath` depends on the Zustand store's `pathToSelected` as its authoritative source, and integrates with the visual tiering system that assigns depth-based dimming (via `maxDepth`) to graph nodes. It is downstream of `useGraphData` (live entity/relation data) and works in concert with the color/shape resolution layer (`ClassColorFallback`'s `nodeFillColor`/`nodeShapeFor`, and the `isOnlineLearned` classifier from `learning-source.ts`), since visual tier and color/shape are separate but complementary axes of node styling in the D3 canvas. It has no counterpart in the static `MultiAgentGraphSvg` rendering path, reinforcing the broader architectural split described at the `GraphVisualRendering` level: no shared node/edge type or common ancestry/hierarchy abstraction exists between the two "graph" surfaces.

## Usage Guidelines

Developers modifying this function should recognize that its divergence-handling behavior is a deliberate trade-off, not a bug: silently dropping BFS-only nodes and demoting store-only nodes to `maxDepth` can hide legitimate graph relationships whenever filters cause the BFS and store views to disagree. Any change to filtering logic elsewhere in the unified-viewer should prompt re-examination of whether divergence frequency/impact has changed. Because this logic is entangled with the same file's locked viewport-stability contract, changes to dependency arrays or subscription wiring nearby should be made cautiously and with reference to the in-file comments describing prior UX reversals. Finally, given the absence of a shared hierarchy/ancestry abstraction with `MultiAgentGraphSvg`, any future unification effort for graph rendering across `GraphVisualRendering` should treat ancestry derivation as one of the concerns needing an explicit shared contract, alongside the already-consolidated color resolution layer in `color-fallback.ts`.
