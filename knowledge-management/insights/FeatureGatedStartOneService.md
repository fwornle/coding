# FeatureGatedStartOneService — Technical Insight Document

## What It Is

FeatureGatedStartOneService represents the per-service gating logic that lives inside its parent, `DashboardServiceWrapper`, and is realized concretely in `scripts/start-services-robust.js`'s `SERVICE_CONFIGS` catalogue and the container-level equivalent in `docker/entrypoint.sh`. At its core, this is the mechanism by which an individual service (dashboard, transcript monitor, graphify, etc.) is either started, retried, or suppressed based on a feature flag, with the actual "start one service" operation wrapped in structured retry/liveness logic rather than a bare spawn call. The entity sits between two independently implemented gating layers — one host-side (Node.js, driven by `lib/features/index.mjs` and `SERVICE_CONFIGS`) and one container-side (`docker/entrypoint.sh`'s `PROGRAM_FEATURES` map) — that communicate only through a mounted JSON snapshot file rather than shared code.

## Architecture and Design

The design follows a retry-with-timeout, graceful-degradation pattern applied uniformly across every entry in `SERVICE_CONFIGS`, per the module's own header comment. Each service config is a plain data literal (`required`, `maxRetries`, `startFn`, `healthCheckFn`), and this "single service" unit is what `startServiceWithRetry` (imported from `../lib/service-starter.js`) operates on. Sibling entity `ServiceRequiredFlagAsymmetry` documents that the required/optional split for a given service — most consequentially for the `transcriptMonitor`/`liveLoggingCoordinator` pair defined in this parent module — lives entirely in that data literal with no schema enforcement, meaning FeatureGatedStartOneService's "start one service" behavior for a misconfigured entry could silently degrade from required to optional with only a test catching the drift.

Ordering is likewise externalized as a tested contract rather than implicit array order: sibling `SERVICE_ORDER_Contract` shows `tests/features/service-gating.test.mjs` asserting `SERVICE_ORDER` and `SERVICE_CONFIGS` cover each other exactly, and pinning `SERVICE_ORDER.slice(0, 2)` to `['transcriptMonitor', 'liveLoggingCoordinator']` because later per-service start operations register against them. This is directly relevant to FeatureGatedStartOneService because any single-service start function that assumes those two are already running depends on this externally-tested ordering invariant, not on anything enforced at the point of starting a single service.

At the container boundary, sibling `DockerEntrypointFeatureSnapshot` implements a parallel but philosophically inverted gating mechanism: `docker/entrypoint.sh` fails open on both a missing snapshot and an unknown feature key, deliberately choosing "runs too much" over "silently runs nothing." This is a two-tier fail-open policy that contrasts with the host-side test suite's fail-closed stance (`'an unknown feature on a config is a loud failure, not a silent skip'`), illustrating that the same conceptual operation — deciding whether to start one gated service — is handled with opposite risk postures depending on which side of the host/container boundary it executes on.

## Implementation Details

Within `scripts/start-services-robust.js`, starting one service typically involves more than a single check. The `transcriptMonitor.startFn` exemplifies a layered liveness-verification pattern: it calls `psm.isServiceRunning('transcript-monitor', 'global')`, then `psm.isServiceRunning('enhanced-transcript-monitor', 'per-project', {...})`, then falls back to an OS-level `isProcessRunningByScript('enhanced-transcript-monitor.js')` via `pgrep`. Only the third, ground-truth check re-registers with PSM via `psm.registerService(...)`, forming a trust hierarchy where each earlier check is weaker evidence than the last, and the final check exists to self-heal PSM's own bookkeeping.

Resource acquisition before starting a service is similarly two-phased: `killProcessOnPortAndWait()` escalates SIGTERM to SIGKILL while polling `lsof -ti:<port>`, and only once the port is confirmed free does `waitForPortBindable()`'s throwaway `net.createServer().listen()` probe become meaningful — checking bindability before clearing the port would trivially fail during a TIME_WAIT-like window. The inline comments explicitly tie this networking-layer code to `maxRetries` economics: a wasted EADDRINUSE spawn burns a retry slot, coupling low-level socket handling directly to the retry-budget semantics of `startServiceWithRetry`.

On the container side, `docker/entrypoint.sh` implements the equivalent single-service gate through a hand-maintained `PROGRAM_FEATURES` whitespace-delimited string (8 program:feature pairs), parsed via `${pair%%:*}`/`${pair##*:}` parameter expansion, and resolved by shelling out to a `node -e` one-liner that must emit exactly `"true"`/`"false"`. Gated programs are suppressed via an additive `autostart=false` override written to a separate supervisor.d include rather than by rewriting `supervisord.conf` directly.

## Integration Points

FeatureGatedStartOneService's host-side implementation depends on `lib/service-starter.js` (`startServiceWithRetry`), PSM (process/service-manager) APIs (`isServiceRunning`, `registerService`), and OS-level tools (`pgrep`, `lsof`). It is exercised and constrained by `tests/features/service-gating.test.mjs`, which directly mutates the `SERVICE_CONFIGS` singleton (e.g., overriding `startFn` or `maxRetries` in a `try/finally`) rather than using mocking or dependency injection — a convention rather than an enforced isolation boundary. Its container-side counterpart integrates with `supervisord.conf`'s `[program:...]` sections and is validated only externally by `tests/features/container-gating.test.mjs`, with no runtime cross-check inside `entrypoint.sh` itself. Both gating mechanisms cross the host/container boundary via a mounted JSON feature snapshot rather than shared code or env vars at container-create time. Separately, `docker/entrypoint.sh` also filters `*_API_KEY|*_TOKEN|*_MANAGEMENT_KEY` when sourcing `/coding/.env`, a defense-in-depth boundary complementing but independent of this service-starting logic.

## Usage Guidelines

Developers modifying a `startFn` for a given service should preserve the layered liveness-check ordering (trust weakest evidence first, verify with OS-level ground truth last) and must not check `waitForPortBindable()` before `killProcessOnPortAndWait()` has confirmed the port is clear. Changes to `required`/`maxRetries` flags, especially for `transcriptMonitor`/`liveLoggingCoordinator`, must keep `tests/features/service-gating.test.mjs`'s ordering and coverage assertions passing, since these are the only guards against silent observability collapse. Any new supervisord program added in the container must get a corresponding `PROGRAM_FEATURES` entry in `docker/entrypoint.sh`, verified only by `tests/features/container-gating.test.mjs` — there is no runtime safety net. Test authors mutating `SERVICE_CONFIGS` must always wrap changes in `try/finally` to restore original state given the shared ESM module singleton. Finally, the legacy `start-services.sh` (`ROBUST_MODE=false`) path remains a parallel, less structured implementation using emoji-string status tracking (`CONSTRAINT_MONITOR_STATUS`) rather than the structured config object model used here — new work should target the robust path.
