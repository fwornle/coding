# SERVICE_ORDER_Contract: Technical Insight Document

## What It Is

`SERVICE_ORDER_Contract` is the executable specification, enforced in `tests/features/service-gating.test.mjs`, that governs the relationship between two data structures in `scripts/start-services-robust.js`: the `SERVICE_ORDER` array (which dictates startup sequencing) and `SERVICE_CONFIGS` (which declares each service's feature dependency, retry behavior, and required-ness). Rather than treating these as independently maintained arrays, the contract asserts that they must "cover each other exactly" — every key in `SERVICE_ORDER` must have a matching entry in `SERVICE_CONFIGS` and vice versa. This is the host-side half of a broader gating system whose container-side analogue lives in `docker/entrypoint.sh`'s `PROGRAM_FEATURES` map (tested separately by `container-gating.test.mjs`). As a child concern of `DashboardServiceWrapper`, this contract is what guarantees that the wrapper's asymmetric optional/required service model (dashboard/graphify as optional, Live Logging pair as required) actually holds at runtime rather than merely in intent.

## Architecture and Design

The core architectural pattern is **contract-as-test**: structural invariants that would traditionally live in documentation or code comments are instead encoded as executable assertions (`tests/features/service-gating.test.mjs:47-52`, `55-61`). This converts two classes of bugs — a service registered in `SERVICE_CONFIGS` but absent from `SERVICE_ORDER` (never started), and the inverse (an order entry pointing at a deleted config, throwing at runtime) — into CI-time failures instead of production incidents.

A second pattern, **three-state outcome classification**, prevents a subtler failure: conflating "disabled" (feature intentionally off) with "degraded" (feature on, service attempted, partial failure) and "failed" (hard failure). The sibling entity `ServiceRequiredFlagAsymmetry` documents how this classification protects a pared-down `coding-features` profile like `proxy-only` from reporting spurious failures for services the user never wanted running.

A third pattern is **deliberate fail-open/fail-closed asymmetry across a host/container boundary**. `startOneService` fails *closed* on an unknown feature name (`assert.rejects(..., /unknown feature 'nope'/)`), while the sibling `DockerEntrypointFeatureSnapshot` and `FeatureGatedStartOneService` describe how `docker/entrypoint.sh` fails *open* on the same category of input — both documented as intentional, not accidental, inversions of posture at different layers of the system.

Finally, the **strangler/migration-seam pattern** is visible in `start-services.sh`, which retains a full legacy startup path gated by `ROBUST_MODE` (defaulting to `true` but overridable), running alongside the structured `SERVICE_ORDER`/`SERVICE_CONFIGS` replacement.

## Implementation Details

`startOneService`, imported and exercised via `../../scripts/start-services-robust.js`, is the decision point where the contract's runtime behavior is enforced. Critically, the ordering of its internal checks matters: it must evaluate feature-enablement *before* required-ness, because `SERVICE_CONFIGS.transcriptMonitor.required = true` must not block startup when the `lsl` feature is explicitly disabled (`service-gating.test.mjs:107-113`). This conditional-required-ness — "required" as a property gated by feature state rather than a static flag — is called out explicitly as fragile to a naive refactor, which is precisely why a test pins the check ordering.

The pinned ordering test (`service-gating.test.mjs:55-61`) locks `SERVICE_ORDER.slice(0, 2)` to `['transcriptMonitor', 'liveLoggingCoordinator']`, because, per the test's own comment, later services register against this pair. As `DashboardServiceWrapper`'s parent-level notes emphasize, a bug in `startServiceWithRetry()` (from `../lib/service-starter.js`) that mis-marks this pair's required flag would silently break the observability pipeline the rest of the system depends on.

The "required failure blocks downstream" test (`service-gating.test.mjs:116-131`) deliberately collapses `maxRetries` from its production value to `1`, trading fidelity for speed — the comment notes this "asserts the blocking contract, not the backoff schedule," leaving the real retry/backoff timing inside `service-starter.js` unverified by this particular test.

## Integration Points

This contract integrates directly with `DashboardServiceWrapper`, whose asymmetric treatment of required (`transcriptMonitor`, `liveLoggingCoordinator`) versus optional (dashboard, graphify) services depends on this contract holding true. The sibling `ServiceRequiredFlagAsymmetry` notes that the required/optional split is a plain data literal in `SERVICE_CONFIGS` with nothing structural preventing drift — the single `assert.deepEqual` in this test file is the only guard.

It also has a structural counterpart, not a shared mechanism, in the container-side gating implemented by `docker/entrypoint.sh` and validated by `container-gating.test.mjs`. As sibling `DockerEntrypointFeatureSnapshot` details, that gate operates by writing `autostart=false` for supervisord, versus the host-side gate skipping a function call — meaning a bug in one contract's test suite would not catch a bug in the other's, despite both protecting against the same conceptual risk (an entity declared but not gated, or gated against a nonexistent feature).

Finally, `start-services.sh`'s legacy `ROBUST_MODE=false` path is a live but uncovered integration seam: it duplicates Docker/Qdrant/Redis startup with bash string-typed status variables and manual port cleanup, entirely outside the reach of `service-gating.test.mjs`.

## Usage Guidelines

Any new service must be added to both `SERVICE_ORDER` and `SERVICE_CONFIGS` simultaneously; the mutual-coverage test will fail otherwise, in either direction. When marking a service `required: true`, developers must remember this only has effect while its owning feature is enabled — it is not a blanket guarantee. Anyone modifying `startOneService`'s internal check order must preserve feature-check-before-required-check, since this is asserted but not visually obvious in the source. When adding tests for retry/backoff behavior, note that existing tests intentionally use reduced `maxRetries` values for speed and do not validate the real backoff schedule — a separate, slower test is needed for that. Finally, changes to feature-gating semantics should be mirrored (or deliberately diverged, with justification) in `docker/entrypoint.sh`, since the two gating mechanisms are independently tested and not automatically kept in sync. The legacy `start-services.sh` path should either be actively maintained/tested or scheduled for removal, since it currently sits as an untested but reachable fallback.
