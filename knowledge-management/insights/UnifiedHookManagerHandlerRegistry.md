# UnifiedHookManagerHandlerRegistry — Technical Insight Document

## What It Is

UnifiedHookManagerHandlerRegistry is the registry-and-dispatch core embodied in `lib/agent-api/hooks-api.js`'s abstract `HooksManager` class, together with its runtime counterpart `lib/agent-api/hooks/claude-bridge.js`. It is the mechanism by which hook handlers are registered against unified `HookEvent` values, stored in priority order, and later invoked when Claude Code (or another agent host) triggers an event such as `PreToolUse`/`PostToolUse`. As the parent entity, **KnowledgeInjectionHooks**, already establishes, the defining behavioral trait of this registry is that `registerHook()` re-sorts each event's handler array on every insertion rather than deferring that cost to dispatch time — a design decision that ripples through every other part of this component.

## Architecture and Design

The registry is built on several composed patterns (per Architectural Patterns observations): a **Template Method / Abstract base class** pattern, where `HooksManager` supplies `registerHook()`, `triggerHook()`, and `unregisterHook()` as concrete algorithm skeletons but forces subclasses to implement `getAgentType()`, `loadNativeHooks()`, and `saveNativeHooks()`; an **Observer/Publish-Subscribe** pattern, where each `HookEvent` maintains its own subscriber list invoked in priority order; and an **Adapter/Bridge** pattern realized by `claude-bridge.js`, which translates Claude Code's native stdin/stdout JSON hook protocol into the unified `HookContext`/`HookEvent` vocabulary consumed by the registry.

A central and deliberate trade-off is the **eager-sort-on-write** strategy analyzed in sibling entities HooksManagerRegisterHook and KnowledgeInjectionHookGating: `registerHook()` performs `eventHooks.sort((a, b) => a.priority - b.priority)` on every call, amortizing sort cost onto the low-frequency, startup-time registration path so that `triggerHook()` — invoked on every single tool call — remains a cheap linear scan. This is explicitly the correct place to pay algorithmic cost given the relative call frequencies of the two operations.

Layered on top of this is a **fail-open error-handling** pattern spanning three independent failure surfaces: `claude-bridge.js`'s `readStdin()` resolves to `{}` after a 1000ms timeout guarding against a hung host process; `triggerHook()` wraps each `hook.handler(fullContext)` invocation in try/catch with an explicit "Continue with other hooks even if one fails" comment; and `main()` in `claude-bridge.js` wraps the entire pipeline (`transformContext()`, `getHookManager()`, `manager.initialize()`, `manager.executeHooks()`) in an outer try/catch. All three converge on the same observable outcome — `process.exit(0)` with `{decision: 'allow', ...}` — meaning correctness bugs anywhere in the chain degrade to a warning rather than a block, a deliberate security/safety trade-off favoring availability over strict gating.

## Implementation Details

The registry's construction enforces an abstract-class contract: the `HooksManager` constructor throws if `new.target === HooksManager`, and `getAgentType()`, `loadNativeHooks()`, `saveNativeHooks()` throw hard errors unless overridden. This creates a striking **two-tier reliability policy** within the same file: construction-time contract violations are unrecoverable programmer errors that fail loud immediately, while runtime handler failures inside `triggerHook()` are treated as recoverable operational events — logged via `logger.error` and simultaneously collected into a `messages` array as human-readable strings (`'Hook error (${hook.id}): ${error.message}'`). That string is then threaded through `claude-bridge.js`'s `transformResponse()` into the JSON payload written to stdout, so a single internal exception produces both a structured log entry and chat-visible text via two separate channels.

As detailed in sibling HooksManagerRegisterHook, the registration path does more defensive work than necessary: `this.hooks.get(event) || []` and the trailing `this.hooks.set(event, eventHooks)` are dead-code safety nets, since `this.hooks` is a `Map<string, RegisteredHook[]>` pre-populated for every `HookEvent` in the constructor — the fallback and re-set are effectively no-ops given that invariant.

Hook identity is purely string-based: `registerHook()` generates default IDs via `hook-${event}-${Date.now()}-${Math.random().toString(36).substr(2, 9)}` rather than a monotonic counter or UUID, and `unregisterHook(hookId)` performs a linear `findIndex` scan across `this.hooks.entries()`. Collision risk is acceptable only because registration is a low-frequency, mostly-startup operation.

## Integration Points

The registry's agent-agnostic vocabulary (`HookEvent`, `HookContext`) is isolated from agent-native event names via the `EVENT_MAPPINGS` translation table in `hooks-api.js`, which returns `null` for `PRE_PROMPT`/`POST_PROMPT`/`ERROR` under the `claude` agent type. This is only loosely coupled to `claude-bridge.js`'s own `EVENT_MAP`, which independently translates native strings like `'PrePrompt'` into unified names in the opposite direction — and notably includes `'PrePrompt'`/`'PostPrompt'` mappings that `EVENT_MAPPINGS.claude` declares unsupported, a latent asymmetry that only surfaces if code assumes the two tables agree. Sibling entity ClaudeBridgeEventTranslation further shows that `transformContext()` falls back to `nativeEvent.toLowerCase()` for unrecognized events, producing unified strings that will never match the hyphenated `HookEvent` enum values — a silent-drop risk consistent with, but distinct from, the fail-open philosophy elsewhere.

`claude-bridge.js` is stateless per invocation, lazily importing the shared singleton via `await import('./hook-manager.js')` inside `main()` rather than holding its own hook state — centralizing registration while keeping the bridge a pure protocol translator. ## Usage Guidelines

Developers extending `HooksManager` must implement `getAgentType()`, `loadNativeHooks()`, and `saveNativeHooks()` or face an immediate construction-time throw — this is intentional and should not be worked around. When registering hooks, rely on the registry's own priority-ordering guarantee rather than re-sorting externally; the eager-sort-on-write design (shared across KnowledgeInjectionHooks, HooksManagerRegisterHook, and KnowledgeInjectionHookGating) already keeps arrays sorted. Do not assume handler exceptions will halt execution or propagate structurally — they are absorbed into `messages` strings, so any caller needing structured error detail must inspect logs, not the returned messages array. When adding new native event types, ensure `EVENT_MAPPINGS` (hooks-api.js) and `EVENT_MAP` (claude-bridge.js) are updated in tandem, and verify that `transformContext()`'s fallback lowercase conversion actually matches a real `HookEvent` value — otherwise hooks for that event will silently never fire.
