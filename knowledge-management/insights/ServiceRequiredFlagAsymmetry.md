# ServiceRequiredFlagAsymmetry

## What It Is

`ServiceRequiredFlagAsymmetry` names a structural weak point in `scripts/start-services-robust.js`: the entire required/optional classification for services lives as a plain boolean field (`required: true`) inside object literals in `SERVICE_CONFIGS` — e.g. `transcriptMonitor: { required: true, maxRetries: 3, ... }` and `liveLoggingCoordinator: { required: true, maxRetries: 3, ... }`. There is no type system, schema, or runtime validator enforcing that this flag is set correctly or even present; the only thing standing between a typo and a silently disabled observability pipeline is a single hand-written assertion in `tests/features/service-gating.test.mjs` that pins `SERVICE_ORDER.slice(0, 2)` to `['transcriptMonitor', 'liveLoggingCoordinator']`. As a child concept of `DashboardServiceWrapper`, this asymmetry explains why the wrapper pattern treats services so unevenly: the Live Logging pair is hard-blocking by convention, while the dashboard and similar services are optional by the same convention, with nothing but test coverage keeping the two categories from being confused.

## Architecture and Design

The design follows a data-driven service registry pattern — configuration as data (`SERVICE_CONFIGS`/`SERVICE_ORDER`) rather than hand-written per-service start blocks — which is efficient but pushes all correctness burden onto tests rather than the language. This is reinforced by the sibling `SERVICE_ORDER_Contract`, which treats `SERVICE_ORDER` and `SERVICE_CONFIGS` as two halves of one contract verified by a diff-based test, and by the ordering pin that guarantees the live-logging pair starts first because "later services register against them."

A second architectural theme is fail-open vs. fail-closed asymmetry by boundary. The host-side orchestrator fails closed: the test `an unknown feature on a config is a loud failure, not a silent skip` proves `startOneService` rejects on an unrecognized feature name. The container-side `docker/entrypoint.sh` (sibling `DockerEntrypointFeatureSnapshot` / `FeatureGatedStartOneService`) fails open by design — its `node -e` ternary (`value === false ? "false" : "true"`) treats any unrecognized feature key as enabled, justified by the inline comment that a silently-disabled container is worse than an over-permissive one. Both defaults are intentional but never cross-referenced, so the asymmetry is only discoverable by reading both files side by side.

A third layer of design intent is the decoupling between orchestration and low-level mechanics: `waitForPortBindable()` and `killProcessOnPortAndWait()` are fully service-agnostic, applying identical TIME_WAIT-avoidance and SIGTERM→SIGKILL escalation regardless of whether the port belongs to a required or optional service. The required/optional distinction is deliberately confined to the orchestration layer (`startOneService`), keeping a bug in retry mechanics from masquerading as a required-service policy bug, and vice versa.

## Implementation Details

Each required service embeds a bespoke dual health-check strategy directly in its `startFn` rather than through a shared helper: `transcriptMonitor.startFn` calls `psm.isServiceRunning('transcript-monitor', 'global')`, falls back to OS-level `isProcessRunningByScript('enhanced-transcript-monitor.js')`, and self-heals orphaned processes via `psm.registerService({...})`. `liveLoggingCoordinator.startFn` duplicates this same pattern with its own service names. This duplication means "required" correlates with extra defensive code but does not derive from it structurally — an optional service added later could copy the pattern or skip it, with no enforcement either way. `healthCheckFn` for `transcriptMonitor` is likewise bespoke (`result.skipRegistration ? true : createPidHealthCheck()(result)`), reinforcing that per-service logic is hand-maintained rather than generated from the `required` flag.

Critically, `required: true` no longer means unconditionally blocking. The test `a REQUIRED service whose feature is off does not block startup` shows `out.blocked` is `false` when `lsl: false` is passed via `featureSet` — required-ness is now conditional on the owning feature being enabled at all. This is a layer added on top of the original file-header policy comment ("REQUIRED: Must start successfully or block coding startup"), which was never updated to reflect the new feature-gating semantics, creating a documentation/behavior mismatch for readers.

## Integration Points

This entity integrates directly with its parent `DashboardServiceWrapper`, which frames the wrapper-script asymmetry between required (Live Logging) and optional (dashboard, graphify) services, and depends on `startServiceWithRetry()` from `../lib/service-starter.js`. It shares infrastructure with sibling `SERVICE_ORDER_Contract`, which enforces that `SERVICE_ORDER` and `SERVICE_CONFIGS` cover each other exactly and that the live-logging pair leads the start order. It also stands in direct contrast with siblings `FeatureGatedStartOneService` and `DockerEntrypointFeatureSnapshot`, which implement the opposite (fail-open) default for unknown feature keys on the container side via `docker/entrypoint.sh`'s `PROGRAM_FEATURES` parsing.

Additionally, `start-services.sh` introduces a parallel integration surface: `ROBUST_MODE="${ROBUST_MODE:-true}"` selects between the Node.js robust path and a legacy bash path whose Constraint Monitor degrades through string states (`CONSTRAINT_MONITOR_STATUS="⚠️ DEGRADED MODE"`) with no `maxRetries` or `required` equivalent at all. Because `ROBUST_MODE` defaults true, this legacy branch is normally dormant but remains reachable, meaning the entire required-flag asymmetry described here can be bypassed if an operator or stale CI job sets `ROBUST_MODE=false`.

## Usage Guidelines

Anyone modifying `SERVICE_CONFIGS` must treat `required: true`/`false` as a load-bearing convention, not a cosmetic flag — flipping it, or adding a new service entry that omits it, will not be caught by any type system, only by the `tests/features/service-gating.test.mjs` assertions. Developers should update that test suite whenever adding, removing, or reclassifying a service, and should not assume the `required` flag means "always blocks startup" — check the feature-gating state, since a required service with its feature off will not block. When reasoning about failure defaults, remember the two boundaries disagree on purpose: host-side (`start-services-robust.js`) fails closed on unknown config, container-side (`docker/entrypoint.sh`) fails open on unknown feature keys — do not port one file's default into the other without explicit justification. Finally, treat `ROBUST_MODE=false` as effectively disabling this entire required/optional model in favor of a coarser legacy scheme, and avoid relying on it in environments where required-service blocking is expected to hold.
