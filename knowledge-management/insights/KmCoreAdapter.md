# KmCoreAdapter — Technical Insight Document

## What It Is

KmCoreAdapter is a SubComponent of KnowledgeManagement that sits conceptually adjacent to GraphifyGraph, the code-structure knowledge reader implemented in `integrations/semantic-analysis/src/agents/graphify-graph.ts`. Where GraphifyGraph normalizes raw graph edges and entities from a static `graph.json` artifact, KmCoreAdapter's two children — OntologyHierarchyColorPalette and HierarchyParentDerivation — implement the corresponding *presentation-layer* normalization, concretely realized in `integrations/unified-viewer/src/graph/color-fallback.ts`. Its role is to adapt an ontology class hierarchy (an arbitrary, potentially deep set of registered classes with parent links) into a small, fixed vocabulary of visual attributes (color, shape) usable by rendering code such as `D3GraphCanvas.tsx`.

![KmCoreAdapter — Architecture](images/km-core-adapter-architecture.png)

## Architecture and Design

The dominant pattern here is **lossy canonicalization via parent-walk**, mirrored directly from GraphifyGraph's `mapRelation()` approach to edge-label collapsing. Both KmCoreAdapter's children and GraphifyGraph take a richer, more varied input space — ontology class hierarchies on one side, raw graphify edge labels on the other — and normalize them down to a small fixed set of outputs for downstream simplicity. In KmCoreAdapter's case, the output space is the five-tier hierarchy System/Project/Component/SubComponent/Detail, split further across two orthogonal families: BATCH_PALETTE (teal-to-light-blue, for batch/manually-imported/migrated entities) and ONLINE_PALETTE (red-to-pink, gated by `isOnlineLearned()` reading `metadata.source`).

This directly parallels the sibling GraphViewerHierarchy/GraphVisualRendering layer's needs and is consumed downstream by `D3GraphCanvas.tsx`, whose ancestry-trace reconciliation logic (`computeAncestryPath` via BFS vs. `deriveAncestryFromStorePath` trusting a store-authoritative path) is architecturally analogous: both prefer a fast, cached/precomputed answer and fall back to local recomputation only when the authoritative source is stale or absent. KmCoreAdapter's parent-walk falls back similarly — first checking a class's own declared style, then a static palette table, then walking to `reg.parent` — before terminating at a hardcoded default.

## Implementation Details

The concrete mechanics live in `color-fallback.ts`'s `nodeFillColor()` and `nodeShapeFor()`, both operating over a `ClassRegistryEntry` map (`registry: ReadonlyMap<string, ClassRegistryEntry>`). Given a `className`, each function resolves through three ordered tiers: (1) an explicit `display.color`/`display.shape` on the class itself, (2) the static `BATCH_PALETTE`/`SHAPE_PALETTE` lookup table, (3) a walk to `reg.parent` repeating the same checks, guarded by a `seen` Set to prevent infinite loops on cyclic registries. If no ancestor yields a match, resolution terminates at `DEFAULT_BATCH` (`#94a3b8`, slate) or `'circle'`.

This is precisely what HierarchyParentDerivation formalizes as a component: visual attributes are resolved not from a node's own declaration but by walking an externally-defined inheritance chain (`ClassRegistryEntry.parent`). OntologyHierarchyColorPalette supplies the actual color/shape tables and online/batch distinction that HierarchyParentDerivation's walk consults at each step. Notably, the two functions are structurally near-identical, and observations flag them as ripe for collapsing into a generic `resolveViaParentWalk(className, registry, extractor, palette, fallback)` higher-order function — a concrete refactor opportunity rather than a speculative one.

## Integration Points

![KmCoreAdapter — Relationship](images/km-core-adapter-relationship.png)

KmCoreAdapter's output feeds directly into GraphVisualRendering and the D3GraphCanvas selection/ancestry model, meaning any change to the ClassRegistryEntry schema or palette tables has immediate, visible downstream effects in the unified-viewer UI. It sits alongside GraphifyGraph (source-of-truth graph data) and CodeGraphAgent within KnowledgeManagement, though notably its normalization logic is implemented entirely independently of the backend's own taxonomy simplification performed by LevelDbMigrationScripts (`migrate-graph-db-entity-types.js`, `migrate-leveldb-to-kmcore.mjs`). There is no shared type definition between the frontend registry-based hierarchy and backend entity-type taxonomy — a drift risk explicitly called out in the observations. Additionally, the wave-based persistence concept (WaveInsightPersistence's w1/w2/w3 substeps, `wave-controller.ts`) and dashboard AGENT_SUBSTEPS entries reflect a related but separate cross-cutting convention that KmCoreAdapter's rendering path does not itself participate in, though both are examples of the same project-wide provenance/classification philosophy (see also `ukbSlice.ts`'s provenance fields).

## Usage Guidelines

Developers modifying the ontology class registry should register `display.color`/`display.shape` explicitly for any new top-level class rather than relying on parent-walk fallback, since unregistered classes silently inherit ancestor styling — a deliberate anti-"grey blob" design, but one that can mask missing registrations. When extending BATCH_PALETTE/ONLINE_PALETTE, maintain the five-tier hierarchy consistently with backend entity-type taxonomy to avoid the drift risk noted above, given there is no enforced shared schema between `color-fallback.ts` and the backend's `kindOf`/`nameOf` migration logic. Given the near-duplication between `nodeFillColor` and `nodeShapeFor`, any future consolidation into a shared `resolveViaParentWalk` helper should preserve the `seen`-guarded cycle protection, as malformed or accidentally-cyclic registry data is the primary correctness risk in this component.


## Hierarchy Context

### Parent
- [KnowledgeManagement](./KnowledgeManagement.md) -- [LLM] The GraphifyGraph reader (integrations/semantic-analysis/src/agents/graphify-graph.ts) represents a deliberate architectural simplification: rather than maintaining a live graph database connection (Memgraph via Cypher), the component now treats a static graph.json artifact produced by the graphify service as the source of truth for code-structure knowledge. This file, a NetworkX node-link JSON export, can be tens of megabytes, so GraphifyGraph implements mtime-based lazy caching — it stat()s the file and only re-parses when the mtime has changed since the last load. This pattern trades real-time graph mutation capability for drastically simpler deployment (no separate DB process) and fast repeated reads, at the cost of only picking up graph changes when the underlying analysis pipeline re-writes graph.json.

### Children
- [OntologyHierarchyColorPalette](./OntologyHierarchyColorPalette.md) -- [LLM] color-fallback.ts implements a five-tier ontology hierarchy palette (System/Project/Component/SubComponent/Detail) split across two orthogonal color families: BATCH_PALETTE (teal-to-light-blue, for batch/manual/migration-imported entities) and ONLINE_PALETTE (red-to-pink, for entities where `isOnlineLearned()` returns true based on `metadata.source`). - [HierarchyParentDerivation](./HierarchyParentDerivation.md) -- [LLM] `nodeFillColor` and `nodeShapeFor` in integrations/unified-viewer/src/graph/color-fallback.ts implement an identical two-function parent-walk pattern: each takes a `className`, a `registry: ReadonlyMap<string, ClassRegistryEntry>`, walks `cur = reg?.parent` in a `while (cur && !seen.has(cur))` loop with a `seen` Set guarding against cycles, and resolves through three tiers in strict order — explicit `display.color`/`display.shape` on the class or an ancestor, then the static `BATCH_PALETTE`/`SHAPE_PALETTE` table on the class or an ancestor, then a hardcoded terminal fallback (`DEFAULT_BATCH` slate / `'circle'`). This is a textbook 'HierarchyParentDerivation' component: it resolves a node's effective visual attribute not from its own declaration but by walking an inheritance chain defined externally in `ClassRegistryEntry.parent`, and the two functions are close enough in structure that a future refactor could trivially collapse them into one generic `resolveViaParentWalk(className, registry, extractor, palette, fallback)` higher-order function.
