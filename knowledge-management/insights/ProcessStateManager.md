# ProcessStateManager: Technical Insight Document

## What It Is

`ProcessStateManager` is a class defined in `process-state-manager.js`, functioning as the in-memory registry of process/service liveness state for the host-native (non-Docker) service startup path. It is consumed primarily by `scripts/start-services-robust.js`, which instantiates it exactly once at module scope (`const psm = new ProcessStateManager();`, line ~38/44) and shares that single instance across every service definition in `SERVICE_CONFIGS`. As the parent component `DockerizedServices` documentation notes, this reflects one half of a dual-mode execution model: services either run as supervisord-managed processes inside a container, or as host-native Node subprocesses tracked via PID through ProcessStateManager. PSM is the mechanism that makes the latter mode possible.

## Architecture and Design

PSM embodies several distinct, deliberate patterns. First, it is a **singleton state manager** — one instance per run of `start-services-robust.js`, meaning any internal registry (e.g., PIDs keyed by service) is effectively process-global for the script's lifetime. This is not dependency-injected; consumer code accesses it via closure capture, a pattern formalized in its child component `ProcessStateManagerConsumerPattern`.

Second, PSM's query/registration API is built on **composite-key scoping**: `isServiceRunning(name, scope, options?)` accepts `'global'` or `'per-project'` scopes, with `'per-project'` requiring a `projectPath` option. This lets the same script (e.g., `enhanced-transcript-monitor.js`) run once globally or once per project without registration collisions — visible in calls like `psm.isServiceRunning('transcript-monitor', 'global')` versus `psm.isServiceRunning('enhanced-transcript-monitor', 'per-project', { projectPath: TARGET_PROJECT_PATH })`.

Third, and most important architecturally, PSM is explicitly treated as a **fallible cache, not a source of truth**. Its child component `ServiceRegistrationLifecycle` documents the cascading liveness check used by `transcriptMonitor.startFn`: a PSM global check, then a PSM per-project check, then an OS-level `pgrep` fallback (`isProcessRunningByScript('enhanced-transcript-monitor.js')`). This is a **self-healing registry** pattern — when the OS-level check finds a process PSM doesn't know about, the code calls `psm.registerService(...)` to repair PSM's state rather than treating the discrepancy as an error ("Re-registering orphaned process with PSM").

## Implementation Details

The two observable async methods are `isServiceRunning(name, scope, options?)` and `registerService({name, pid, type, script})`. The registry schema appears to be `{name, type, pid, script, ...}` — the inclusion of `script` alongside `pid` strongly suggests PSM disambiguates stale-PID reuse by also checking that a live PID's command line matches the expected script, rather than trusting `kill(pid, 0)` alone. This is consistent with other defensive, layered-verification code in the same file (`killProcessOnPortAndWait`, `waitForPortBindable`), none of which trust a single cheap signal.

Each check in the three-tier cascade short-circuits and returns either `{ pid: 'already-running', skipRegistration: true }` or a real PID with `skipRegistration: true`; downstream `healthCheckFn` logic must special-case `skipRegistration` to avoid re-validating a process it didn't itself spawn.

Notably, there appears to be an inconsistency in *how* registration happens across service types: wrapper scripts like `scripts/api-service.js` and `scripts/dashboard-service.js` call `registerService()` immediately after spawn as a normal step, whereas in `start-services-robust.js`, `psm.registerService` is only invoked defensively inside the orphan-recovery branch — the normal transcript-monitor path simply returns `{ pid: child.pid, service: 'transcript-monitor' }` with no visible explicit registration call. This may mean registration happens implicitly inside `startServiceWithRetry` (from `lib/service-starter.js`, sibling `ServiceStarter`), but this should be confirmed rather than assumed uniform.

## Integration Points

PSM sits beneath `start-services-robust.js` (sibling `StartServicesRobust`) and is tightly coupled to it — imported and instantiated directly rather than injected. It shares the "PID+lifecycle tracking" role with sibling `ServiceStarter`'s `lib/service-starter.js`, and its output feeds the same overall health story as sibling `ServiceProbe`, though `service-probe.js` is deliberately blind to process ownership and only checks HTTP/TCP reachability — the two are complementary but architecturally separate oracles of "is this running."

Within `DockerizedServices`, PSM is the host-native counterpart to the container path's supervisord + `docker/entrypoint.sh` feature-gating mechanism (see siblings `SupervisordRuntime`, `APIServiceWrapper`). Its child `ServiceRegistrationLifecycle` implements the concrete cascading check logic, and child `ProcessStateManagerConsumerPattern` documents the closure-based singleton access pattern used throughout `SERVICE_CONFIGS`.

## Usage Guidelines

Developers extending `SERVICE_CONFIGS` should recognize that PSM state is shared and process-global for the duration of a `start-services-robust.js` run — a stale or leaked registry entry for one service can silently corrupt `isServiceRunning` checks for an unrelated service later in the same run. Any new service integrating with PSM should follow the established defense-in-depth pattern: check PSM (global and/or per-project scope as appropriate), then fall back to an OS-level check before concluding a service isn't running, and re-register orphaned processes rather than erroring out.

Critically, **`tests/features/service-gating.test.mjs` provides no coverage of PSM's internal registration/query correctness** — it stubs `SERVICE_CONFIGS.transcriptMonitor.startFn` wholesale, bypassing PSM entirely. Regressions in PSM's PID-matching or scope-collision logic would not be caught by existing tests. Because PSM is accessed via closure rather than dependency injection, any future test of PSM's actual behavior would require monkeypatching the module import rather than passing a mock through a public API — a maintainability gap worth addressing if PSM's correctness becomes a priority. Given that `transcriptMonitor` and `liveLoggingCoordinator` are `required: true` services that others register against (per sibling `DashboardServiceWrapper`'s notes), bugs in PSM's bookkeeping for these specific services carry outsized blast radius.
