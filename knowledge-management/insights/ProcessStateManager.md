# ProcessStateManager: Technical Insight Document

## What It Is

`ProcessStateManager` is a class defined in `process-state-manager.js` that functions as a shared, in-process registry for tracking running services across the DockerizedServices system. It exposes a small API — `initialize()`, `registerService({name, pid, type, script, metadata})`, and `unregisterService(name, type)` — that is consumed identically by two wrapper scripts, `scripts/api-service.js` and `scripts/dashboard-service.js`. Both wrappers dynamically import it (`(await import('./process-state-manager.js')).default`), instantiate it with `new ProcessStateManager()`, register their spawned child process immediately after spawn, and unregister it symmetrically in the child's `exit` handler. As a child of ProcessStateManager, `ServiceRegistration` models the register/unregister data contract itself, while `PsmIntegrationInStartupOrchestration` captures how (and where) this registration mechanism sits relative to the rest of the startup pipeline.

## Architecture and Design

The dominant pattern here is a **shared registry** consumed by decoupled wrapper scripts instead of bespoke IPC — both `api-service.js` and `dashboard-service.js` register/unregister against the same PSM instance-per-process rather than communicating with each other directly. Layered on top of that is a **best-effort side-channel pattern**: registration and unregistration calls are wrapped in try/catch blocks whose failure handling is explicitly non-fatal, logging errors and continuing ("Continue anyway - not critical") or silently swallowing them ("Ignore cleanup errors"). This mirrors the asymmetric strictness philosophy seen in sibling component `ServiceStarter`, where core lifecycle concerns (SIGTERM/SIGINT handling, child process management) are treated as critical, while PSM visibility is treated as disposable telemetry.

![ProcessStateManager — Architecture](images/process-state-manager-architecture.png)

Structurally, PSM registration is strictly downstream of feature gating performed in `docker/entrypoint.sh:100-140`, which reads `/coding/.coding/runtime/features.json` and disables supervisord programs by feature name before they ever spawn. A feature-disabled service never invokes its wrapper script, and therefore never reaches PSM at all — meaning PSM's registry reflects only "services that were both feature-enabled AND successfully spawned," not the full configured service set. This same fail-open bias (`value === false ? "false" : "true"` in entrypoint.sh) is philosophically consistent with PSM's own tolerance of registration failures: both layers favor keeping visible services running over strict registry/gating completeness — contrasted with the fail-closed `required: true` path in sibling `ServiceStarter`.

## Implementation Details

The registration call sites are concrete and mirrored: `scripts/api-service.js:60-84` registers the `constraint-api-child` process with metadata including port/service, while `scripts/dashboard-service.js:59-83` performs the analogous registration for `constraint-dashboard-child`. Both use the literal type string `'global'`, and the corresponding unregister calls (`scripts/api-service.js:44-53`, `scripts/dashboard-service.js:43-52`) hardcode that same string rather than deriving it from the registration call — an implicit, convention-over-enforcement contract that PSM itself does not validate.

Both wrappers perform registration inside a fire-and-forget async IIFE that runs *after* the startup log line and *after* SIGTERM/SIGINT handlers are already attached. This creates a real, if benign, race: a child process can exist, and even receive a shutdown signal, before PSM has recorded it. Because the unregister call is a separate try/catch keyed by name, it fires regardless, presumably no-op'ing against an unregistered service. PSM is loaded via dynamic `import()` rather than static import in both scripts, likely to avoid module-load ordering/cost at wrapper startup.

## Integration Points

![ProcessStateManager — Relationship](images/process-state-manager-relationship.png)

PSM sits within `DockerizedServices` alongside siblings `ServiceStarter`, `ServiceProbe`, `DockerEntrypoint`, `LLMMockService`, `StartServicesRobust`, and `ServiceWrapperScripts`. Notably, PSM is architecturally orthogonal to `ServiceStarter`'s `startServiceWithRetry()`/`withDeadline()` machinery — the Node-based Global Service Coordinator's health-check function is supplied by the coordinator itself, not sourced from PSM, and PSM registration is never referenced in `entrypoint.sh`'s `PROGRAM_FEATURES` gating. As `PsmIntegrationInStartupOrchestration` documents, this produces two disjoint bookkeeping systems in the containerized path: supervisord owns actual process lifecycle for supervisord-launched wrappers, while PSM independently performs its own register/unregister dance describing overlapping but not identical facts about the same children.

At the parent level, `DockerizedServices` enforces SPEC R6 via `ServiceProbe`'s pessimistic three-state probing (`healthy` is never asserted directly by probes); PSM's registration state is one of the signals a higher-level health-coordinator can combine with probe results to determine true health, though PSM does not itself perform health checks.

## Usage Guidelines

Developers extending or adding new wrapper scripts must manually replicate the full register/unregister pattern — nothing in PSM enforces that a spawned child gets registered, or that the type string used at registration matches the one used at unregister. Given the hardcoded `'global'` literal duplicated across call sites, any new service type should ideally reference a shared constant rather than repeat the string, to avoid silent unregistration drift. Because registration happens asynchronously after signal handlers attach, developers should treat PSM state as eventually-consistent, not authoritative at the instant of spawn. Most importantly, PSM failures must never be allowed to block a wrapper's real responsibility (serving `dashboard-server.js` or the Next.js dev server) — this non-fatal, best-effort posture is a deliberate design invariant, not an oversight, and should be preserved in any future service wrapper.

### Siblings
- [ServiceStarter](./ServiceStarter.md) -- [LLM] The core resilience primitive in lib/service-starter.js is withDeadline(), which wraps Promise.race() around a work promise and a timeout-rejecting promise, then clears the timer in a finally block regardless of which promise wins. This is not the naive Promise.race() pattern seen in many codebases — the naive version leaves the losing setTimeout timer armed on the event loop even after the work promise resolves, which is a classic cause of hung Node.js processes (a test runner or one-shot CLI that never exits cleanly, or a long-lived service that leaks a timer handle per retry attempt). startServiceWithRetry() calls withDeadline() twice per attempt (once wrapping startFn() with the attempt's `timeout` option, once wrapping healthCheckFn() with a hardcoded 10000ms), so the leak-avoidance matters doubly under the exponential-backoff retry loop where dozens of timers could otherwise accumulate across maxRetries attempts.
- [ServiceProbe](./ServiceProbe.md) -- [LLM] service-starter.js's startServiceWithRetry() (lib/service-starter.js) implements a three-layer resilience wrapper around arbitrary async start/health-check function pairs: an outer retry loop (default maxRetries=3) with exponential backoff (retryDelay * 2^(attempt-1)), an inner withDeadline() timeout guard applied separately to both the start call and the health check call (30000ms and 10000ms respectively by default), and post-failure cleanup that SIGTERMs then SIGKILLs an unhealthy child process before the next attempt. The withDeadline() helper is deliberately written with a try/finally that calls clearTimeout(timer) regardless of whether the race was won by the work or the timer — the accompanying comment explains this exists specifically to avoid leaving a dangling setTimeout handle that would hold the Node.js event loop open in short-lived callers like test runners or one-shot CLIs, even though in the long-lived service-starter context itself the leak would be invisible.
