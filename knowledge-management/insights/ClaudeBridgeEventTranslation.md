# ClaudeBridgeEventTranslation

## What It Is

`ClaudeBridgeEventTranslation` refers to the bidirectional translation layer implemented in `lib/agent-api/hooks/claude-bridge.js`, which sits between Claude Code's native hook protocol and the unified hook format defined in `lib/agent-api/hooks-api.js`. Its core responsibilities are split across four functions: `transformContext()` converts Claude's native stdin payload into the unified `HookContext` shape; `transformResponse()` converts the unified `{allow, messages}` result back into Claude's expected `{decision, message}` shape; `readStdin()` reads and bounds the incoming payload; and `main()` orchestrates the whole request lifecycle as a CLI entrypoint. As the Detail child of the parent component KnowledgeInjectionHooks, this bridge is the concrete mechanism by which the abstract `HooksManager` (defined in the parent) is made reachable from an actual Claude Code process.

## Architecture and Design

The dominant pattern is a classic Adapter/Bridge: `EVENT_MAP` in claude-bridge.js and `EVENT_MAPPINGS.claude` in hooks-api.js each independently encode a mapping between Claude's native event vocabulary (PreToolUse, PostToolUse, Startup, Shutdown, PrePrompt/PostPrompt/Error) and the unified `HookEvent` enum's hyphenated names (e.g., `pre-tool`). Notably these two tables are not identical — `EVENT_MAPPINGS.claude` explicitly nulls out PRE_PROMPT/POST_PROMPT/ERROR — so the bridge and the manager maintain overlapping but non-identical contracts with no compile-time or test-time link forcing them to stay in sync.

A second major pattern is fail-open error handling: `main()` wraps its entire body in a single try/catch, degrading any failure — JSON parse errors, a missing `hook-manager.js` module, or a genuine hook rejection — into an `{decision: 'allow', ...}` response. This mirrors the fail-open philosophy at the outer boundary while `HooksManager` itself enforces fail-loud construction-time contracts internally, producing an architectural asymmetry where the same class of error is treated differently depending on which layer it surfaces in.

The module also embodies the dual-purpose "testable CLI entrypoint" pattern: it exports `main`, `transformContext`, `transformResponse`, and `EVENT_MAP` for unit testing, while guarding actual execution behind `if (process.argv[1] === fileURLToPath(import.<COMPANY_NAME_REDACTED>.url))`. Finally, `main()` uses dynamic/lazy import of `./hook-manager.js` and conditionally calls `manager.initialize(projectPath)` only when `!manager.initialized`, deferring module resolution cost until dispatch is actually needed.

## Implementation Details

`transformContext()` performs lossy, one-way translation: it looks up `nativeEvent` in `EVENT_MAP` for five known events, falling back to `nativeEvent.toLowerCase()` for anything unrecognized — a fallback that doesn't actually match the unified format's hyphenated naming convention, so unrecognized events silently produce unified strings that will never match any `HookEvent` key. It also spreads the entire raw `claudeContext` object into `metadata` after explicitly copying `cwd` and `project_path`, making every Claude-sent field visible to handlers without requiring bridge changes, at the cost of an untyped, version-dependent `metadata` contract.

`transformResponse()` reverses the process, joining `unifiedResult.messages` (an array produced by `HooksManager.triggerHook()`/`executeHooks()`) into a single newline-delimited string via `.join('\n')`. This narrowing operation destroys per-hook attribution — if multiple hooks fire and one blocks, Claude's native format cannot indicate which hook produced which message.

`nativeEvent` itself is resolved from three fallback sources — `process.env.HOOK_EVENT || process.argv[2] || 'PreToolUse'` — while the corresponding context payload arrives exclusively via `readStdin()`. These two channels are never cross-validated, so a caller supplying a mismatched event name and payload produces a silently mistranslated context. `readStdin()` compounds this fragility: its 1000ms `setTimeout` only resolves early `if (!data)`, so any partial byte received before the deadline disables the timeout entirely, weakening the bridge's "never hang" guarantee for partially-hung callers.

## Integration Points

The bridge's primary integration point downstream is `HooksManager` in `lib/agent-api/hooks-api.js`, obtained via lazy import of `./hook-manager.js` and `getHookManager()`. It consumes `HooksManager.triggerHook()`'s `{allow, messages}` output and depends on the sibling behaviors documented in HooksManagerRegisterHook and UnifiedHookManagerHandlerRegistry — namely that `registerHook()` eagerly sorts each event's handler array by priority on every registration, keeping `triggerHook()` a cheap linear scan on the hot per-tool-call path. Upstream, it integrates with the Claude Code process via stdin/stdout and process.env/argv, forming the two disjoint input channels (env/argv for event name, stdin for payload) noted as a structural coupling risk.

## Usage Guidelines

Developers extending Claude's event vocabulary must update `EVENT_MAP` and `EVENT_MAPPINGS.claude` together, since nothing enforces their consistency — a change to one without the other reintroduces the silent-drop risk already present for PrePrompt/PostPrompt/Error handling. Anyone relying on `metadata` in a hook handler should treat it as untyped and Claude-version-dependent, since it's a raw spread of `claudeContext`. Callers driving the bridge programmatically must ensure `HOOK_EVENT`/argv and the stdin payload are always set consistently, as no runtime check will catch a mismatch. Finally, because errors from broken infrastructure (e.g., a missing `hook-manager.js`) and errors from malformed input are indistinguishable at the response level, debugging failures requires inspecting `logger.error('Bridge execution failed', ...)` output rather than trusting the returned decision.


## Hierarchy Context

### Parent
- [KnowledgeInjectionHooks](./KnowledgeInjectionHooks.md) -- [LLM] lib/agent-api/hooks-api.js defines an abstract `HooksManager` base class whose `registerHook()` method pushes a new hook into `this.hooks.get(event)` and then immediately calls `eventHooks.sort((a, b) => a.priority - b.priority)` on every single registration. This re-sort-on-insert strategy means the handler array is always kept in priority order rather than being sorted lazily at dispatch time in `triggerHook()`. The cost is O(n log n) per registration instead of amortizing the sort to a single O(n log n) pass before the first dispatch, which is a reasonable trade-off only because hook registration is a low-frequency, mostly-startup-time operation while `triggerHook()` (invoked per tool call) stays a cheap linear scan.
