# HooksManagerRegisterHook — Technical Insight Document

## What It Is

`HooksManagerRegisterHook` refers to the `registerHook()` method implemented in `lib/agent-api/hooks-api.js` as part of the abstract `HooksManager` base class. This method is the write-path entry point for the priority-ordered event listener registry that underlies the entire `KnowledgeInjectionHooks` system (its parent component). Concretely, `registerHook()` validates an event/handler pair, assigns a default ID if none is supplied, inserts the resulting hook into a per-event array, and re-sorts that array by priority on every call: `const eventHooks = this.hooks.get(event) || []; eventHooks.push(hook); eventHooks.sort((a, b) => a.priority - b.priority); this.hooks.set(event, eventHooks);`.

Because `this.hooks` is a `Map<string, RegisteredHook[]>` pre-populated for every `HookEvent` value in the constructor, the `|| []` fallback and the trailing `this.hooks.set(event, eventHooks)` are defensive no-ops — the array reference always already exists, so re-setting it mutates nothing new. This is a small but real bit of redundant work layered on top of an invariant the constructor already guarantees.

## Architecture and Design

`registerHook()` sits at the center of an Observer/Pub-Sub pattern: it and `triggerHook()` together implement a priority-ordered event listener registry keyed by `HookEvent`. The class as a whole follows a Template Method / abstract base class pattern — `HooksManager` defines the registration/trigger/unregistration algorithm skeleton, while `getAgentType()`, `loadNativeHooks()`, and `saveNativeHooks()` are abstract hooks that concrete subclasses must implement (enforced via the constructor's `new.target === HooksManager` throw).

The defining trade-off of `registerHook()` is **eager sort-on-insert**: every registration call pays an O(n log n) sort cost so that `triggerHook()` — invoked per tool call on the hot path — can do a cheap linear scan of an already-sorted array. This is explicitly a deliberate asymmetry, not an oversight, mirrored identically across sibling entities `UnifiedHookManagerHandlerRegistry` and `KnowledgeInjectionHookGating`, both of which describe the same code path from slightly different angles: registration is low-frequency/startup-time work, while `triggerHook()` fires on every PreToolUse/PostToolUse event. A lazy sort-on-read strategy would instead impose an O(n log n) penalty (or dirty-flag bookkeeping) on the hot path — the wrong place to spend cycles in a per-tool-call-latency-sensitive system.

This eager-sort design creates a subtle inconsistency with `getRegisteredHooks()`, a related method that flattens all per-event arrays into one list via `allHooks.push(...hooks)`. Because this flattening only concatenates already-sorted segments in `Map` iteration order without a global re-sort, the result is locally sorted per event but not globally priority-ordered — a caller who assumes `getRegisteredHooks()` returns one globally prioritized execution order would be wrong. Only `triggerHook(event, ...)`, which reads a single event's sorted array, gets correct priority ordering.

## Implementation Details

`registerHook()` enforces two fail-loud runtime contracts before touching the registry: `Object.values(HookEvent).includes(event)` rejects unknown event names, and `typeof handler !== 'function'` rejects non-callable handlers. Both throw synchronously and immediately, consistent with a broader "fail loud at registration, fail open at execution" philosophy also visible in the constructor's abstract-class guard and abstract-method throws in `getAgentType()`/`loadNativeHooks()`/`saveNativeHooks()`.

Default hook IDs are generated via `hook-${event}-${Date.now()}-${Math.random().toString(36).substr(2, 9)}` — a timestamp-plus-random-suffix scheme rather than a monotonic counter or `crypto.randomUUID()`. Collision probability is negligible in practice, but the use of the deprecated `String.prototype.substr` (rather than `.slice`/`.substring`) is a minor style smell likely to trip stricter lint configurations.

The counterpart `unregisterHook(hookId)` takes an O(events × hooks-per-event) approach, iterating `this.hooks.entries()` and calling `findIndex(h => h.id === hookId)` per event rather than maintaining a secondary `Map<hookId, event>` index. This mirrors `registerHook()`'s bias toward simplicity over performance — defensible given hook counts stay small per-agent, per-event, but it does mean removal cost scales with the total number of distinct events (7, per `HookEvent`) rather than being O(1).

## Integration Points

The hooks registered via `registerHook()` are consumed by `triggerHook(event, context)`, which builds a `fullContext` object by spreading the caller-supplied `context` *last* — `...context` — after computing `event`, `agentEvent`, `agentType`, `sessionId`, and `timestamp` authoritatively via `translateEvent()` and `getAgentType()`. This ordering means a caller can silently override those computed fields, a contract looseness worth knowing about since a handler branching on `context.agentType` could be misled by a stale or mismatched caller-supplied context.

`triggerHook()`'s per-handler try/catch (logging errors and appending `'Hook error (<id>): <message>'` to `messages`, then continuing the loop) implements fail-open at hook granularity, nested inside the process-level fail-open in `claude-bridge.js`'s `main()` (which wraps the entire bridge run and writes `{decision: 'allow', ...}` on any uncaught failure). This two-tier design means an exception anywhere in the hook pipeline degrades to a logged warning rather than a blocked tool call, at both layers.

Upstream, sibling entity `ClaudeBridgeEventTranslation` (`claude-bridge.js:transformContext()`) translates Claude's native event payloads into the unified `HookContext` shape that `registerHook()`/`triggerHook()` expect, using `EVENT_MAP` for known events and falling back to `nativeEvent.toLowerCase()` otherwise — a fallback that doesn't align with `HookEvent`'s hyphenated naming convention, meaning hooks registered for such events would silently never fire.

## Usage Guidelines

Developers registering hooks should rely on `registerHook()`'s synchronous validation errors (unknown event, non-function handler) as immediate feedback — these are programmer errors and will not be silently tolerated, unlike runtime handler failures inside `triggerHook()`. Callers should avoid passing pre-populated `context` objects into `triggerHook()` that include `event`, `agentEvent`, `agentType`, `sessionId`, or `timestamp` keys, since these will silently override the manager's authoritative computed values. When consuming `getRegisteredHooks()`, do not assume global priority ordering across events — only per-event arrays accessed through `triggerHook()` guarantee correct dispatch order. Given hook volumes are expected to remain small and per-agent/per-event scoped, the current O(n log n)-per-registration and O(events × hooks) unregistration costs are acceptable; they should be revisited only if hook counts or dynamic registration/unregistration frequency grow substantially beyond current assumptions.
