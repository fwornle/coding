# DeriveAncestryFromStorePath — Technical Insight Document

## What It Is

`deriveAncestryFromStorePath` is a function defined in `integrations/unified-viewer/src/graph/D3GraphCanvas.tsx`, taking `(selectedId, storePath, relations)` as arguments. It is a reconciliation function that resolves discrepancies between two independently-derived ancestry computations: the Zustand store's `pathToSelected` set (read via `useViewerStore((s) => s.pathToSelected)`, written by whichever selection writer last fired — graph click, history click, or LSL timeline tick) and a local, fresh BFS traversal produced by `computeAncestryPath()` (imported from `./ancestry`). Rather than treating either source as sole authority, the function merges them, returning the same `AncestryPathResult` shape (`{ edges, nodeDepths, pathLength }`) that `computeAncestryPath` itself produces, making it a transparent drop-in wrapper rather than a new type in the ancestry API surface.

As a child of the `GraphViewerHierarchy`, this function is the clearest embodiment of that parent's central tension: D3GraphCanvas.tsx is a port of a Redux-based `GraphVisualization.tsx` component into a Zustand-driven architecture, but the port had to re-derive selection/ancestry logic to keep two independently-maintained rendering engines — this D3/SVG canvas and a parallel Sigma/WebGL canvas (`graph-builder.ts:461,487`, referenced only in comments) — consistent against one shared store.

## Architecture and Design

The dominant pattern is **reconciliation between two independently-derived data sources**: a store-authoritative selection set versus a locally-recomputed graph traversal. This is layered with a **fast-path/slow-path optimization**: an equality check (`inline.nodeDepths.size === storePath.size` plus a membership scan) short-circuits to the cheap inline BFS result when both sources agree, falling into an O(n) pruning path only when they diverge. The design assumes agreement is the common case and divergence the exception, triggered specifically by filter changes occurring between a writer's click and the current render.

The reconciliation itself follows a **"writer's intent wins, but degrade gracefully" policy** rather than a strict source-of-truth swap. Nodes present in `storePath` but unreachable by the local BFS are still added to `prunedNodeDepths`, pinned at `maxDepth` so they render at the dimmest end of the gradient instead of vanishing — a graceful-degradation pattern favoring visual completeness over strict graph correctness. Conversely, nodes the BFS reaches but the store doesn't acknowledge are silently dropped by omission. Edge filtering is stricter still: `prunedEdges` retains an inline-derived edge only if both endpoints (split via `e.split('||')`) exist in `storePath`, so an orphaned "phantom" node renders as an isolated dot rather than a connected trace.

This entire structure functions as a **cross-rendering-engine consistency shim** — one BFS implementation whose output is constrained to match what the Sigma/WebGL engine presumably also derives from the same store field.

## Implementation Details

The comment block preceding the function attributes its existence to a named audit (`state-flow audit 'b29bdb34c' §6.4/§6.6`, "audit finding S3") that identified duplicated source-of-truth logic between the D3 canvas and the Sigma canvas. Notably, the fix does not eliminate duplication — it reintroduces the inline BFS as a fallback/producer, with the comment explicitly conceding: "the inline BFS is still the producer; we just constrain its output." This means ancestry BFS logic still runs in at least two places: `computeAncestryPath` here, and presumably an equivalent implementation in `graph-builder.ts`.

The function does not resolve the underlying race condition it documents — it absorbs it. The docstring explains mismatches arise "if a filter dropped some intermediate ancestor between the writer's click and this render," i.e., `pathToSelected` was computed against a different `visibleRelations` set than the one currently passed in. Rather than coordinating a recompute across every writer (graph click, history click, timeline tick), the function locally degrades affected nodes to `maxDepth` — a cosmetic fix for a data-freshness problem.

No divergence telemetry exists: the function silently absorbs mismatches with no logging, counter, or flag exposed to callers, making it impossible from outside to detect how often the slow-path pruning actually triggers in production.

## Usage Guidelines

Developers modifying this function should preserve the uniform `AncestryPathResult` return contract, since downstream consumers rely on not needing to distinguish reconciled from unreconciled results. Any change to `pathToSelected` writers (graph click, history click, timeline tick) must consider its effect on reconciliation timing, since the fix does not eliminate the underlying race — it only cosmetically degrades stale nodes to `maxDepth`. Given the "Locked Contract #3" constraint, this function must never be invoked as an independent effect keyed on selection state; it must ride along with the existing render cycle.

The duplication pattern here recurs elsewhere in the codebase: siblings **DeriveParentsHierarchyReduction** and **HierarchyCycleBreaking** both document near-identical parent-walking loops in `color-fallback.ts` (`nodeFillColor`/`nodeShapeFor`), where "derive X from ancestor chain" is repeatedly solved via a fresh per-consumer loop rather than a shared reducer — the same structural instinct visible in this function's choice to keep the inline BFS rather than consolidate with `graph-builder.ts`. Anyone attempting a true consolidation should treat both the ancestry duplication and the color/shape hierarchy duplication as instances of the same systemic pattern, and any fix should consider whether a shared traversal/reduction utility could serve both the D3 and Sigma canvases, as well as the color-fallback walks.
