# APIServiceWrapper — Technical Insight Document

## What It Is

APIServiceWrapper is the umbrella SubComponent that normalizes how heterogeneous services (Express APIs, Next.js dev servers, Python services) are started, monitored, and stopped, spanning both container-side and host-side orchestration paths. Its concrete implementations live in `docker/entrypoint.sh` (container-boot feature gating), `scripts/start-services-robust.js` (host-native orchestration), and the legacy `start-services.sh` (bash fallback). It sits under DockerizedServices, which itself is architected around a dual-mode execution model — supervisord-managed processes in a single container versus host-native Node subprocesses tracked by ProcessStateManager — and APIServiceWrapper is the layer that makes both modes speak a common start/stop/health contract. Its two named children, FeatureGatingOverride and ApiServiceChildWrapper, both describe the same `docker/entrypoint.sh` mechanism from complementary angles: one as an additive supervisord-include generator, the other as a pure translation layer with no decision-making authority.

## Architecture and Design

The dominant pattern is wrapper/adapter: a single lifecycle contract (start/stop/health) wraps disparate service types, letting ServiceProbe (a sibling) remain a "pure protocol-level health <COMPANY_NAME_REDACTED>" blind to process ownership. Feature gating is deliberately layered *on top of* existing orchestration rather than rewritten into it — `docker/entrypoint.sh` never touches `supervisord.conf`'s `[program:...]` blocks; it only emits `autostart=false` overrides into `/etc/supervisor/features.d/disabled.conf`, consumed via supervisord's `[include]` directive. This is the FeatureGatingOverride child's core insight: an additive-diff design that regenerates the override directory unconditionally (`rm -f *.conf` then rebuild) rather than diffing against previous state, keeping the blast radius of a bug small.

A second major pattern is the coexistence of legacy and current implementations in the same tree: `start-services.sh` dispatches into `scripts/start-services-robust.js` when `ROBUST_MODE` (default true) is set, with ~150 lines of bash-based docker-compose/manual-container fallback logic retained purely as an escape hatch — dead code under normal operation but not deleted.

A third pattern, shared with sibling ServiceStarter, is required-vs-optional service classification enabling graceful degradation: `transcriptMonitor` and `liveLoggingCoordinator` are `required: true` with hard-fail retry semantics, while dashboard/graphify-type services are optional, per DashboardServiceWrapper's documented asymmetry.

## Implementation Details

On the container side, `docker/entrypoint.sh:79-140` parses `/coding/.coding/runtime/features.json` and iterates the `PROGRAM_FEATURES` mapping (`semantic-analysis:knowledge`, `graphify:codegraph`, `constraint-monitor:constraints`, etc.), using `node -e` rather than `jq` (not installed in the image) to evaluate each flag. The ApiServiceChildWrapper framing is explicit that this loop is a translation layer only — it reads a pre-computed boolean, it does not compute feature resolution itself, because the real logic (layered defaults → `config/features.yaml` → `~/.coding/features.yaml` → `CODING_FEATURE_*` env vars) lives entirely on the host and is structurally unreachable from inside the container.

On the host side, `scripts/start-services-robust.js` implements `SERVICE_CONFIGS`/`SERVICE_ORDER`, each service declaring a mandatory `feature` field checked against `FEATURE_IDS` from `lib/features/catalogue.cjs`. Liveness checking is triple-layered — PSM (`psm.isServiceRunning()`), then OS-level `isProcessRunningByScript()` via `pgrep -lf`, then re-registration of any OS-level orphan back into ProcessStateManager — treating PSM as an eventually-consistent cache rather than ground truth. Port lifecycle races are handled by `killProcessOnPortAndWait()` (SIGTERM, then SIGKILL after half of `maxWaitMs`, polling `lsof -ti:<port>`) and `waitForPortBindable()` (a throwaway `net.createServer().listen()` probe to dodge a lingering-socket EADDRINUSE race) — both added reactively per inline comments, not part of original design.

## Integration Points

APIServiceWrapper's status/error semantics interlock tightly with test infrastructure: `tests/features/service-gating.test.mjs` asserts `SERVICE_ORDER` and `SERVICE_CONFIGS` "cover each other exactly," and separately enforces that `transcriptMonitor`/`liveLoggingCoordinator` must be the first two entries in `SERVICE_ORDER` since later services register against them — a load-bearing ordering constraint enforced only in CI, not at runtime. The orchestrator also distinguishes `results.disabled` from `results.degraded`, mirroring the project-wide fail-open/fail-closed asymmetry: display/status surfaces fail open toward "intentionally off," while start actions fail closed.

Container-side gating (JSON snapshot) and host-side gating (`lib/features/catalogue.cjs`/`FEATURE_IDS`) are two separate enforcement points reading different sources, coordinated only by shared naming convention and cross-checking tests rather than one schema — a drift risk explicitly called out by sibling ServiceStarter. The retry/backoff mechanics delegate to `service-starter.js`'s `startServiceWithRetry`/`withDeadline`, and health reachability is deliberately kept separate from declared config (as in `prompt-classifier-service.mjs`'s `runtime` Map vs `config`), reflecting the broader convention of not conflating "declared" with "currently reachable" — consistent with ServiceProbe's protocol-agnostic health checking.

## Usage Guidelines

Any new feature flag must be wired into both the container path (`PROGRAM_FEATURES` in `docker/entrypoint.sh`) and the host path (`SERVICE_CONFIGS`/`FEATURE_IDS`), or the two deployment modes will drift silently. When adding or reordering entries in `SERVICE_ORDER`, remember the <AWS_SECRET_REDACTED>-first constraint is only test-enforced — misclassifying either as optional or moving them later would silently break the observability pipeline other services register against. Prefer treating PSM lookups as advisory rather than authoritative; the orphan-reconciliation pattern (`pgrep` fallback + re-registration) exists because PSM bookkeeping can miss crashes. Avoid deleting the legacy `start-services.sh` bash path casually — it's retained deliberately as a `ROBUST_MODE=false` escape hatch. Finally, respect the fail-open default in feature gating (absent/unreadable snapshot or unknown key = enabled) as an intentional debuggability trade-off, not a bug to "fix" toward stricter defaults.
