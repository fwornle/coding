## Architecture and Design

The architectural shape attributed to APIServiceWrapper is the **wrapper-process pattern**: lifecycle management (spawn, signal handling, PID registration) is kept separate from actual HTTP API logic, which is delegated entirely to the child process (`dashboard-server.js`). This separation of concerns is corroborated structurally, though not directly, by `scripts/start-services-robust.js`, which implements the identical idiom for a different service — `SERVICE_CONFIGS.transcriptMonitor.startFn` checks `psm.isServiceRunning()`, falls back to an OS-level `pgrep` check via `isProcessRunningByScript()`, and only then spawns the real process and hands its PID to ProcessStateManager. This duplication across ServiceStarter (the sibling component implementing `start-services-robust.js`) suggests that "spawn, then register PID with a global process registry" is a repo-wide convention rather than a bespoke design in the constraint-monitor wrapper.

![APIServiceWrapper — Architecture](images/apiservice-wrapper-architecture.png)

Layered above any individual wrapper is container-level feature gating, implemented in `docker/entrypoint.sh` via a `PROGRAM_FEATURES` mapping (e.g., `constraint-monitor:constraints`, `constraint-dashboard-api:constraints`) that is read at boot and converted into supervisord `[program:...]` overrides with `autostart=false` for disabled features. Notably, an unrecognized or missing feature snapshot defaults to **enabled**, a fail-open design choice. This means APIServiceWrapper's autostart behavior, if run under supervisord in the same container, is governed externally rather than by logic inside the wrapper script — a clean separation, but one that makes the wrapper's observable behavior partly opaque to someone reading only its own source.

Health assessment for such wrappers is expected to use a three-state contract (`running`/`stopped`/`unknown`) from `lib/utils/service-probe.js` rather than a binary up/down check, per the parent's DockerizedServices health-verification workflow.
