# KnowledgeInjectionHookGating — Technical Insight Document

## What It Is

`KnowledgeInjectionHookGating` is the cross-cutting gating layer that determines *whether* and *how* feature-gated CLI commands and agent hook events are allowed to execute, spanning three implementation surfaces: the runtime hook dispatch machinery in `lib/agent-api/hooks-api.js` (`HooksManager`, `EVENT_MAPPINGS`, `translateEvent`), the process-boundary bridge in `lib/agent-api/hooks/claude-bridge.js`, and the shell-level feature guard `lib/features/require-feature.sh` exercised by `tests/features/cli-and-rules-gating.test.mjs`. As a child of `KnowledgeInjectionHooks` — which defines the abstract `HooksManager` skeleton — this component specifically embodies the *gating* concern: refusing or permitting actions (tool calls, CLI invocations, cross-agent events) based on feature flags and configuration, while guaranteeing the refusal mechanism itself cannot become a worse failure mode than what it protects against.

## Architecture and Design

The dominant architectural theme is **layered fail-open containment**, applied at three nested levels of a single call chain. At the innermost level, `HooksManager.triggerHook()` wraps each registered hook execution in a try/catch that logs and continues rather than propagating — one bad handler cannot stop others from running. One level up, `claude-bridge.js:main()` wraps the entire bridge invocation (stdin parse, dynamic `import('./hook-manager.js')`, `executeHooks()`) in a catch-all that always resolves to `{decision: 'allow', ...}` and calls `process.exit(0)`, so no internal defect can hang or block the parent Claude Code process. At the outermost level, the shell guard `require-feature.sh` fails open with `[ -n "$repo" ] || return 0` and `command -v node ... || return 0` when its own resolution logic breaks. This is the same reliability philosophy as `triggerHook()`'s per-hook containment, just applied one layer earlier — a design choice explicitly called out as intentional (a broken gate defaulting to "allow" rather than "block everything").

This coexists with an inverted philosophy for *programmer* errors: `HooksManager`'s constructor throws hard if instantiated directly (`if (new.target === HooksManager) throw ...`), and its abstract methods (`getAgentType`, `loadNativeHooks`, `saveNativeHooks`) throw unconditionally if not overridden — a Template Method pattern enforcing subclass contracts at construction time, sibling in spirit to `ClaudeBridgeEventTranslation`'s adapter role, which implements the concrete translation `HooksManager` defers.

The gating layer's exit-code contract (`exit 2` for "feature disabled," distinct from generic `exit 1` failures) is an implicit cross-file API: any script wrapping a hook-gated CLI can branch on exit code alone without parsing stderr. Stdout is kept clean of gating noise on refusal, isolating gate messaging entirely to stderr.

## Implementation Details

`EVENT_MAPPINGS` and `translateEvent()` (`return mapping[event] || null`) implement a Strategy/lookup-table pattern where `null` is an intentionally overloaded but accepted signal: for `claude`, `PRE_PROMPT`/`POST_PROMPT`/`ERROR` map to `null` (handled elsewhere, e.g., a launcher script or `EXIT` trap); for `copilot`, `POST_PROMPT` is explicitly commented `// Not supported`. Both collapse to the same `null` return, meaning consumers must treat `null` as normal "not wired for this agent," not exceptional — the gating contract absorbs this ambiguity rather than exposing it.

`registerHook()` (shared with sibling `HooksManagerRegisterHook`/`UnifiedHookManagerHandlerRegistry`) eagerly sorts `eventHooks` by priority on every insertion rather than lazily before dispatch, trading a marginally more expensive low-frequency write (registration, startup-time) for a guaranteed-cheap `triggerHook()` read (hot path, invoked per tool call). This directly serves the gating layer's need for predictable, low-latency dispatch ordering when deciding whether a call proceeds.

The test suite (`tests/features/cli-and-rules-gating.test.mjs`) enforces the gating contract primarily through **source-inspection assertions** — regex-matching that each CLI in `GUARDED` (`bin/semantic`→knowledge, `bin/graphify`/`bin/codegraph`→codegraph, `bin/constraints`→constraints, `bin/log-session`→lsl) sources `require-feature.sh` and invokes `require_feature <name>`. Only a small subset of tests actually spawn subprocesses via `execFile`/`exec()` against a sandboxed `CODING_HOME`, since — per the file's own comment — shell exit-status/stream/wording behavior "does not survive being mocked."

## Integration Points

This gating logic sits downstream of `HooksManager`'s dispatch skeleton and upstream of agent-specific bridges like `claude-bridge.js`, which performs Claude-native event translation via `transformContext()` (documented under sibling `ClaudeBridgeEventTranslation`) — including its known silent-drop risk when unrecognized events fall through to `nativeEvent.toLowerCase()`, producing strings that never match the hyphenated `HookEvent` enum. Any hook-gated CLI integrates via the shared `require-feature.sh` guard and the `GUARDED` feature-name contract; new CLIs must replicate the exit-code-2 convention to remain compatible with anything branching on process exit codes.

Notably, the same "avoid ambiguous absent-state" instinct recurs in the UI layer, in `usePolledFetch.ts` (`paused`/`wasPaused`, immediate refetch on tab-return) and `useWorkflowDefinitions` (Redux-with-constants-fallback) — independent implementations echoing the backend's null-as-explicit-signal design, though not directly coupled to this component.

## Usage Guidelines

Developers extending gating behavior should preserve the layered fail-open guarantee: any new guard, bridge, or hook handler must degrade to "allow and log," never to a hang or hard block. New hook-gated CLIs must call `require_feature` with the correct feature name and preserve the exit-code-2/empty-stdout contract. When adding new native event types to `claude-bridge.js`, avoid relying on the naive lowercase fallback in `transformContext()` — it silently fails to align with the unified `HookEvent` naming convention. Finally, treat `translateEvent()`'s `null` return as an expected, non-exceptional value throughout consuming code, consistent with the system's broader "no silent ambiguity, but no hard crash either" design ethos.


## Hierarchy Context

### Parent
- [KnowledgeInjectionHooks](./KnowledgeInjectionHooks.md) -- [LLM] lib/agent-api/hooks-api.js defines an abstract `HooksManager` base class whose `registerHook()` method pushes a new hook into `this.hooks.get(event)` and then immediately calls `eventHooks.sort((a, b) => a.priority - b.priority)` on every single registration. This re-sort-on-insert strategy means the handler array is always kept in priority order rather than being sorted lazily at dispatch time in `triggerHook()`. The cost is O(n log n) per registration instead of amortizing the sort to a single O(n log n) pass before the first dispatch, which is a reasonable trade-off only because hook registration is a low-frequency, mostly-startup-time operation while `triggerHook()` (invoked per tool call) stays a cheap linear scan.

This is a minor but real inefficiency: the method does more defensive work than the invariant it establishes in the constructor requires.
- [UnifiedHookManagerHandlerRegistry](./UnifiedHookManagerHandlerRegistry.md) -- [LLM] lib/agent-api/hooks-api.js's `HooksManager.registerHook()` performs `eventHooks.sort((a, b) => a.priority - b.priority)` on every call, keeping each event's hook array continuously sorted rather than deferring the sort to first dispatch in `triggerHook()`. Since `triggerHook()` is invoked per tool call (PreToolUse/PostToolUse fire on every single agent action) while `registerHook()` only runs during initialization, this eager-sort-on-write design correctly amortizes cost onto the cold path — a lazy-sort-on-read strategy would instead pay an O(n log n) penalty (or require a dirty-flag check) on every hot-path `triggerHook()` call, which is the wrong place to spend cycles in a system built around per-tool-call latency.
- [ClaudeBridgeEventTranslation](./ClaudeBridgeEventTranslation.md) -- [LLM] lib/agent-api/hooks/claude-bridge.js:transformContext() performs a lossy, one-way translation from Claude's native hook payload into the unified HookContext shape used by hooks-api.js. It hardcodes a lookup into EVENT_MAP for five specific events (PreToolUse, PostToolUse, Startup, Shutdown, PrePrompt/PostPrompt/Error) but falls back to `nativeEvent.toLowerCase()` for anything unrecognized, meaning an unexpected Claude event name silently produces a made-up unified event string that will never match a key in hooks-api.js's own `HookEvent` enum (which uses hyphenated names like 'pre-tool', not 'pretooluse'). This is a subtle translation gap: the bridge's own fallback doesn't actually align with the unified format's naming convention, so any hook registered for such an event would never fire, and no error would surface anywhere in the pipeline — consistent with the fail-open philosophy but a real silent-drop risk for future event types.
