# CopilotEventsTail — Technical Insight Document

## What It Is

`CopilotEventsTail` is implemented in `lib/lsl/live/copilot-events-tail.mjs` and is the Copilot-side realization of the `LiveTranscriptWatchers` component. Its core mechanism is a polling-based file tail: `tailEventsFile()` runs a `statSync`-driven interval loop (`TAIL_POLL_INTERVAL_MS = 200`) against `~/.copilot/session-state/<uuid>/events.jsonl`, detecting file growth and incrementally reading new bytes rather than subscribing to OS-level file-change notifications (`fs.watch`/inotify). It works in concert with sibling logic `scanForLiveSessions()` (attributed to the `LiveSessionScanner` component) which discovers candidate session directories, and `buildStubObservation()`, which synthesizes a plausible transcript when no real content exists yet. Together these functions turn raw, partially-written Copilot session artifacts into structured LSL observations in near-real time.

## Architecture and Design

The defining architectural decision here is **polling over push**: a `statSync`-based interval loop stands in for a file watcher, justified in the file's own header comment as "comfortable for human-interactive Copilot sessions" given that growth is only a few KB per turn. This is explicitly bounded by a documented threat-model note (T-51-09-RL) assuming "typically 1-5" concurrent sessions — an acknowledged scalability ceiling rather than an unbounded design. This stands in sharp architectural contrast to its sibling `OpencodeTokenRows`, which implements a fundamentally different consistency model: a single bounded SQLite query (`MESSAGE_SCAN_LIMIT = 4000`, `ORDER BY rowid DESC`) executed once at measurement-stop, trading live latency for zero background CPU cost. The parent `LiveTranscriptWatchers` therefore is not a unified abstraction but a loose umbrella over two structurally incompatible models — polled push-like tailing vs. on-demand pull — with no shared interface; a developer adding a third agent must choose a model based on that agent's on-disk artifact shape rather than reuse a common watcher base class.

Several cross-cutting patterns recur: a fail-closed ownership guard (`isOwnedByMe()`), a stub/synthetic-data adapter (`buildStubObservation()`), a heuristic liveness check via mtime staleness (`findLiveLockFile()`), and dedicated error-isolation catch paths (the Phase 69 D-08 discipline). Each represents a deliberate simplicity/robustness trade-off documented inline in the source rather than an accidental gap.

## Implementation Details

`tailEventsFile()` performs manual byte-offset tracking using `lastSize` and a `residual` buffer to handle partial JSONL lines split across poll boundaries: each tick computes `curr.size - lastSize`, reads only the delta via `fs.openSync`/`fs.readSync`, splits on `\n`, and re-buffers any trailing incomplete line into `residual` for the next iteration. This hand-rolled tail-follow logic is a deliberate substitute for an external tailing library, consistent with a stated "Zero new package installs" constraint (T-51-09-SC), and is functionally equivalent to `tail -f` but reimplemented in JS so lifecycle event dispatch (started/completed/failed) can happen inline in the same read loop.

`scanForLiveSessions()` gates candidate sessions using two independent filters before expensive work occurs: `isOwnedByMe()` (a `statSync` + `process.getuid()` comparison, fail-closed with a `process.stderr.write` diagnostic on rejection) and `findLiveLockFile()`, which checks an `inuse.<pid>.lock` file's `mtimeMs` against `LOCK_STALE_GRACE_MS` (10 minutes) rather than signaling the PID directly (e.g., `process.kill(pid, 0)`). This is explicitly documented as "RESEARCH landmine #5" — a legitimately idle session untouched for 10+ minutes will be incorrectly excluded, a known correctness/simplicity trade-off. `projectMatches()` adds a further early-exit, skipping sessions whose `workspace.yaml` resolves to `sessionProject === 'unknown'` when project filtering is active.

`buildStubObservation()` fabricates a synthetic user/assistant exchange from lifecycle metadata (`agentName`, `agentDescription`, `started_at`, `completed_at`, `completion_status`) when no real transcript exists, tagging the result with `lsl_incomplete: true` and the locked constant `COPILOT_LSL_INCOMPLETE_NOTE` — explicitly "Locked by Test 6," meaning its exact shape is contractually pinned and any change requires coordinated test updates.

The Phase 69 `onTokenRow` hook grafted onto `tailEventsFile()` follows the D-08 error-isolation discipline: failures in the token-row callback are caught and logged via a distinct `[copilot-events-tail] onTokenRow threw (non-fatal)` stderr prefix, kept separate from the pre-existing `onError` path used for subagent lifecycle failures, so a bug in token accounting cannot mask or break the older observation pipeline.

## Integration Points

`CopilotEventsTail` reuses parsing logic from `lib/lsl/adapters/copilot-events.mjs` (`parseWorkspaceYaml`, `projectFromWorkspace`, `stripToolCallIdPrefix`) — labeled "D-Reuse" — showing intentional avoidance of duplicating the Phase 51-04 parsing logic even as it duplicates ownership-check logic elsewhere. The `onTokenRow` hook integrates it with the token-accounting pipeline (`lib/lsl/token/token-db.mjs:insertTokenRow()`), bridging the live-tail loop to token bookkeeping without merging failure domains. Architecturally it sits beside `OpencodeTokenRows` under `LiveTranscriptWatchers`, and shares (but does not code-share) the ownership-guard pattern with `opencode-token-rows.mjs`'s `ownedDbPath()` — both implement identical `statSync`/uid-check/stderr-diagnostic logic independently, and reportedly a third variant exists in `copilot-token-rows.mjs`. `tailEventsFile()` also maintains a strict forward-only read boundary, deliberately excluding historical backfill responsibility, which is instead handled out-of-band by the Plan 51-04 sweep process.

## Usage Guidelines

Developers should treat the 200ms poll interval and 10-minute lock staleness window as tunable but load-bearing constants tied to documented assumptions (1-5 concurrent sessions, KB-scale per-turn growth); scaling well beyond that envelope would require revisiting the polling model. Any change to `buildStubObservation()`'s output shape must be coordinated with the pinned "Test 6" contract. Because the uid-ownership check is duplicated (not shared) across `copilot-events-tail.mjs`, `opencode-token-rows.mjs`, and likely `copilot-token-rows.mjs`, any future fix to ownership semantics (e.g., ACL or group-based access) must be manually propagated to every callsite — there is no compiler or test enforcing consistency. Extending token-source coverage requires respecting the `BYPASS_PROVIDERS` allowlist design (in the sibling `OpencodeTokenRows`) — treat it as default-safe/undercounting rather than risk silent double-counting. Finally, when adding a new agent to `LiveTranscriptWatchers`, evaluate its on-disk artifact model first; do not assume `tailEventsFile()`'s polling design is universally appropriate versus the pull-based SQLite model used by `OpencodeTokenRows`.
