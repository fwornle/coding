# KnowledgeManagement — Technical Insight Document

## What It Is

KnowledgeManagement is the foundational data layer of the Coding project, implementing a graph-based knowledge storage architecture documented in `docs/architecture/memory-systems.md`. At its core is the VKB (Virtual Knowledge Base) server, which acts as the sole runtime interface for querying and mutating the knowledge graph. The component represents a transition point in the project's history: it replaced or augments a prior LevelDB-based store with a newer graph backend referred to as KMCore, and this migration is significant enough to warrant its own dedicated correctness testing.

As a component within the broader Coding hierarchy, KnowledgeManagement is a sibling to LiveLoggingSystem, LLMAbstraction, DockerizedServices, CodingPatterns, and ConstraintSystem, but it functions differently from these — rather than being a pipeline or service layer, it is the persistent substrate that other subsystems (like the agent abstraction API and LLM routing) depend on for shared context. Within the Coding project's scale (1982 files, 17280 code references), KnowledgeManagement anchors two child components: ManualLearning and OnlineLearning, both of which write into the same graph rather than maintaining independent storage.

## Architecture and Design

The defining architectural decision is strict separation of concerns around the VKB server as a single choke point. Downstream agents — notably `code-graph-agent.ts` — do not talk to the storage layer directly; instead, they route all entity persistence operations through VKB. This centralizes consistency guarantees, caching behavior, and decay tracking logic in one place, meaning any schema change to entities must be coordinated through the VKB server rather than through ad-hoc script access to the graph.

A second key pattern is the **dual-path write architecture**: one path is transactional and incremental, driven by the runtime agent (`code-graph-agent.ts`) performing per-entity updates during normal operation; the other is batch and administrative, driven by the standalone script `scripts/migrate-graph-db-entity-types.js` performing full-database schema sweeps. This is a deliberate boundary — schema migrations are treated as offline maintenance operations rather than something the live agent process executes, which reduces the risk of runtime corruption during schema evolution but introduces an operational cost: schema changes require manual script execution as part of deployment, and the script must be kept synchronized with whatever entity type definitions `code-graph-agent.ts` currently expects. Because both paths operate on the same graph database, operational discipline matters — running the bulk migration script concurrently with an active agent risks race conditions on entity type fields, so maintenance windows should quiesce the VKB server and agents before batch operations run.

## Implementation Details

The migration from LevelDB to the graph-based KMCore backend is validated by a dedicated test suite, `migrate-leveldb-to-kmcore.test.ts`, which serves as the authoritative specification for what "correct migration" means — preserving entity IDs, relationships, and decay metadata during the storage transition. This isolation from general unit tests signals that data integrity during migration was treated as a significant, standalone risk.

Knowledge decay tracking is an explicit responsibility of the graph store: entities carry temporal relevance metadata (e.g., last-accessed or confidence-decay timestamps) rather than being persisted statically. This has direct implications for the VKB server's query logic, which must incorporate decay-aware filtering or ranking to distinguish "fresh" from "stale" knowledge for consuming agents. Any storage migration — including the LevelDB-to-KMCore move — must faithfully carry forward these decay fields, since silently resetting them would corrupt the relevance semantics agents depend on.

Bulk schema evolution is handled by `scripts/migrate-graph-db-entity-types.js`, which updates entity type schemas directly against the graph database out-of-band from the running agent process, reinforcing the offline-maintenance design philosophy described above.

## Integration Points

KnowledgeManagement sits within a much larger documented system that includes cross-project knowledge sharing (`docs/architecture/cross-project-knowledge.md`) and a broader ontology integration effort (`docs/RELEASE-2.0.md`). This positions it as infrastructure that other architectural concerns — the agent abstraction API and LLM routing among them — rely on for shared context, rather than an isolated subsystem.

Its two children implement distinct ingestion paths into the same graph: **ManualLearning** persists entities through the VKB server's entity persistence operations rather than via direct storage writes, adhering to the same choke-point discipline described in `docs/architecture/memory-systems.md`. **OnlineLearning**, by contrast, produces entities via a batch analysis pipeline that ingests git history, LSL session logs, and code analysis output. Both ultimately converge on the same underlying graph store and its VKB access boundary, even though their entity-origination mechanisms differ substantially.

As the root of the hierarchy, Coding treats KnowledgeManagement as one of its seven major components, alongside LiveLoggingSystem, LLMAbstraction, DockerizedServices, CodingPatterns, and ConstraintSystem — none of which appear to write directly into the knowledge graph based on current observations, but which may consume knowledge context indirectly through the agent abstraction layer.

## Usage Guidelines

Developers modifying entity schemas or query interfaces should first consult `docs/architecture/cross-project-knowledge.md` and the Release 2.0 ontology notes in `docs/RELEASE-2.0.md` to understand downstream consumers before altering graph structure — changes ripple beyond this component. Any change touching entity serialization format must be validated against `migrate-leveldb-to-kmcore.test.ts`, which functions as the correctness contract for migration behavior, particularly around preserving decay metadata.

Schema changes to entity types should go through `scripts/migrate-graph-db-entity-types.js` as an explicit, offline maintenance step — not through direct manipulation of the graph or through the live agent process. Operational runbooks should schedule such script executions during maintenance windows with the VKB server and agents quiesced, to avoid race conditions between the batch and transactional write paths. Finally, all new entity persistence logic — whether for ManualLearning-style manual entries or OnlineLearning-style pipeline output — should route through the VKB server's persistence operations rather than bypassing it, preserving the single-choke-point consistency model this component is built around.

- [LiveLoggingSystem](./LiveLoggingSystem.md) -- [LLM] The LiveLoggingSystem is structured as a pipeline with distinct, separable stages: configuration validation, session windowing, file routing, classification, and transcript capture. This separation is evident in the presence of scripts/validate-lsl-config.js as a standalone pre-flight check that runs independently of the main logging.ts pipeline, meaning developers can validate configuration changes (session window durations, file routing rules) without triggering the full logging pipeline. This design supports fail-fast behavior: catching misconfiguration before any live session data is captured, rather than discovering issues mid-capture when data loss or malformed logs could occur.
- [LLMAbstraction](./LLMAbstraction.md) -- [LLM] The LLMAbstraction component implements a mode-resolution hierarchy that is critical for understanding how any given agent call is actually dispatched. getLLMMode() in llm-mock-service.ts checks, in strict order: a per-agent override (allowing individual agents to be pinned to mock/local/public independently of global state), then a global mode setting, then a legacy mockLLM boolean flag (retained for backward compatibility with older config schemas), and finally falls back to 'public' as the safe default. This layered precedence means a developer debugging unexpected LLM behavior for a specific agent must check all four levels rather than assuming the global setting applies uniformly—per-agent overrides silently win even if the global mode says otherwise, which is a common source of confusion during multi-agent experiments.
- [DockerizedServices](./DockerizedServices.md) -- DockerizedServices provides the containerization and process-management layer that wraps Coding's various services (semantic analysis MCP, constraint monitor API/dashboard, graphify, LLM services) so they can run reliably both inside Docker containers and as standalone Node processes managed by a Global Service Coordinator. The layer combines Docker artifacts (docker-compose.yml, Dockerfile.coding-services, supervisord.conf, entrypoint.sh) with a set of Node.js wrapper scripts (api-service.js, dashboard-service.js) that spawn actual backend processes, forward signals, and register/unregister with a ProcessStateManager (PSM) for lifecycle tracking.

A core architectural pattern is robust startup with retry/backoff and health verification, implemented in lib/service-starter.js's startServiceWithRetry(), which wraps a start function and a health-check function with timeouts (via withDeadline) and exponential backoff, distinguishing required vs optional services for graceful degradation. Complementing this, lib/utils/service-probe.js implements liveness probes (probeHttpHealth, probeTcpPort) used by scripts/health-coordinator.js to poll services every 5 seconds per config/health-verification-rules.json, strictly avoiding false-positive 'healthy' states per its SPEC R6 invariant.

Service wrappers such as api-service.js and dashboard-service.js follow a consistent pattern: resolve CODING_REPO-relative paths, verify target files/directories exist, spawn the real process with stdio inherited, forward SIGTERM/SIGINT, and asynchronously register/unregister with ProcessStateManager for centralized process tracking across the dockerized/global service fleet. Mock-mode support (llm-mock-service.ts) allows service behavior (LLM calls) to be swapped for deterministic mocks driven by a shared workflow-progress.json state file, aiding testing inside containers where CODING_ROOT may differ from host paths.
- [CodingPatterns](./CodingPatterns.md) -- [LLM] CodingPatterns has no dedicated source directory or module of its own within the Coding project; it exists purely as a conceptual grouping label applied during component analysis to catch conventions that recur across many subsystems but are not owned by any single one. - [ConstraintSystem](./ConstraintSystem.md) -- The ConstraintSystem provides rule-based validation and enforcement for tool calls and file operations during Claude Code sessions, plus a hook infrastructure that lets agent-agnostic events (pre-tool, post-tool, startup, shutdown, etc.) trigger scripts, commands, or modules. It is composed of a hook configuration layer (lib/agent-api/hooks/hook-config.js) that loads and merges user-level (~/.coding-tools/hooks.json) and project-level (.coding/hooks.json) configs, and a central UnifiedHookManager (lib/agent-api/hooks/hook-manager.js) that registers, prioritizes, and dispatches handlers per event across all supported agents. Violations detected during live sessions are captured and persisted via the ViolationCaptureService (scripts/violation-capture-service.js), which writes JSONL logs and maintains rolling statistics for dashboard consumption.

Architecturally, the system favors a layered configuration-merge pattern (defaults → user → project) with validation warnings rather than hard failures, and a priority-sorted handler registry keyed by event name. Constraint violations flow from live session monitoring into a persistent JSON store capped at 1000 entries, with statistics (severity breakdown, most common violation, per-session averages) computed on write. The system also integrates with content/documentation validation (ContentValidationAgent in integrations/semantic-analysis) which, while primarily about entity staleness, shares the same validation-issue/severity taxonomy pattern used elsewhere in constraint reporting, and with the System Health Dashboard's workflow visualization hooks (React-side, distinct from the agent-api hook system) for rendering constraint/violation data.
- [SemanticAnalysis](./SemanticAnalysis.md) -- [LLM] The batch-analysis workflow is structured as a multi-stage pipeline where semantic-analysis-agent.ts is responsible for extracting raw entities and relationships from git history and LSL (likely 'Language/Session Log') session data, while ontology-classification-agent.ts takes those extracted entities and maps them into a hierarchical ontology structure. This separation of concerns means the extraction logic (identifying what something is—a function, a decision, a bug fix) is decoupled from the classification logic (determining where that entity fits in a broader knowledge hierarchy), allowing each agent to be independently tuned, tested, and potentially swapped out without affecting the other stage's implementation.
