# KnowledgeManagement — Technical Insight Document

## What It Is

KnowledgeManagement is the L2 subsystem within the Coding ontology (sibling to LiveLoggingSystem, LLMAbstraction, DockerizedServices, CodingPatterns, ConstraintSystem, and SemanticAnalysis) responsible for representing, storing, migrating, and serving code-structure and pattern knowledge as a graph. Its implementation spans several concrete files: the reader `integrations/semantic-analysis/src/agents/graphify-graph.ts` (GraphifyGraph), the compatibility shim `code-graph-agent.ts` (CodeGraphAgent), and a pair of migration scripts — `migrate-graph-db-entity-types.js` and `integrations/semantic-analysis/scripts/migrate-leveldb-to-kmcore.mjs`. Its children — GraphifyGraph, CodeGraphAgent, KmCoreAdapter, LevelDbMigrationScripts, WaveInsightPersistence, ManualLearning, OnlineLearning, GraphViewerHierarchy, GraphVisualRendering, and UkbWorkflowDashboard — together cover the full lifecycle: producing graph artifacts, adapting/querying them, migrating legacy storage formats, persisting insights from analysis waves, and visualizing the resulting graph.

## Architecture and Design

The defining architectural decision in this component is a deliberate move away from a live graph database (Memgraph via Cypher) toward a static, file-based artifact: `graph.json`, a NetworkX node-link JSON export produced by the graphify service. GraphifyGraph treats this file as the system of record, implementing mtime-based lazy caching — stat()-ing the file and re-parsing only when its mtime changes. This is a classic read-heavy optimization that trades real-time graph mutation and query capability for simpler deployment (no separate DB process to run) and fast repeated reads, at the cost of batch-consistency: code-structure changes are invisible to the system until graphify finishes rewriting `graph.json`.

To preserve backward compatibility during this migration, CodeGraphAgent implements a Strangler Fig pattern: it exposes the exact pre-migration API (CodeEntity, CodeRelationship types, `checkMemgraphConnection`, and query methods) while internally delegating everything to GraphifyGraph. This let consumers throughout the codebase continue importing CodeGraphAgent unchanged even though the storage backend was completely replaced.

The knowledge model's ontology has itself evolved toward simplification, mirroring the taxonomy-flattening pattern seen elsewhere in Coding (e.g., LiveLoggingSystem's L1/L2 ontology carriers). `migrate-graph-db-entity-types.js` collapses over-specified legacy types (TransferablePattern, WorkflowPattern, TechnicalIssue) down to three canonical categories — System, Project, Pattern — directly against the live GraphDatabaseService Graphology in-memory graph.

## Implementation Details

Because graphify's node-link JSON carries no explicit type/name attributes, GraphifyGraph derives semantic meaning from each node's `label` field via two helper functions, `kindOf()` and `nameOf()`. This makes the entity "schema" interpreted rather than stored data, creating an implicit, unenforced coupling between graphify's label format and GraphifyGraph's parsing logic — any change to graphify's labeling convention requires corresponding parser updates.

Edge semantics undergo a similar normalization: `mapRelation()` collapses graphify's fine-grained raw relation strings (`indirect_call`, `inherits`, `re_exports`, etc.) onto six canonical CodeRelationship types (calls/imports/extends/implements/uses/defines). This lossy compression simplifies downstream pattern-matching at the cost of losing fine distinctions irrecoverably.

The migration path from legacy LevelDB storage to km-core's canonical shape is handled by two sequential, non-idempotent scripts under LevelDbMigrationScripts. First, `migrate-graph-db-entity-types.js` performs the taxonomy consolidation described above. Then `migrate-leveldb-to-kmcore.mjs` restructures each entity with a UUIDv7 identifier, a `layer='evidence'` classification, a `legacyId.system='B'` backward-reference tag, and a `provenance` stamp (`provider='phase-42-migration'`). This second script enforces a strict error budget, aborting if more than 5% of entities are malformed — a safety gate designed for production-scale data where manual verification is infeasible. Critically, these two scripts form an implicit ordering contract: the km-core migration assumes the three-category taxonomy already exists, and running it prematurely silently corrupts type data with no runtime error.

Insight persistence, handled by WaveInsightPersistence, occurs across three sequential sub-steps (w1/w2/w3 corresponding to L0/L1, L2, and L3+embeddings entities respectively), all pure storage operations (`llmUsage: 'none'`, `GraphDB + LevelDB storage`) with no LLM calls of their own — upstream analysis does the semantic work. Wave 3 uniquely performs "direct attribute merge," reconciling operator-enriched fields onto entities that may already exist from earlier waves.

The wave-controller.ts anchoring logic addresses an orphan-entity bug: relation lookups must call `queryIncomingRelations(e.name, e.entityType)`, parameterized by both name and type, since multiple entities can share a name across different types. The anchor pass falls back through `findBestParent(...)` and ultimately to a hardcoded `projectAnchorName` of `'Coding'`, guaranteeing every Insight node is connected via an explicit edge and never left unreachable.

## Integration Points

KnowledgeManagement sits under the Coding root and interacts closely with SemanticAnalysis, which supplies the graphify pipeline output that GraphifyGraph consumes. CodeGraphAgent's preserved API surface means broader codebase consumers depend on it without knowledge of the underlying migration. Downstream, KmCoreAdapter's output (graph.json, entity types, relationship taxonomy) feeds visualization layers in the system-health-dashboard and unified-viewer packages, notably D3GraphCanvas and GraphViewerHierarchy/GraphVisualRendering. However, a documentation-drift artifact exists here: `AGENT_SUBSTEPS['code_graph']` in `multi-agent-graph.tsx` still labels its query sub-step `techNote: 'Cypher queries on Memgraph'`, contradicting the actual GraphifyGraph-backed implementation — a stale label surfaced to operators via UkbWorkflowDashboard's `ukb-workflow-modal.tsx`.

## Usage Guidelines

Developers should never assume `checkMemgraphConnection` on CodeGraphAgent performs a real connectivity check — it is a preserved but likely stubbed method retained only for API compatibility. Anyone modifying graphify's node labeling scheme must update `kindOf()`/`nameOf()` in GraphifyGraph accordingly, since no shared type definition enforces this coupling. Migration scripts under LevelDbMigrationScripts must be run in strict order (entity-type consolidation before the km-core restructuring); running them out of order fails silently rather than raising errors. When persisting Insight entities, always query relations by both name and entityType to avoid orphan or duplicate nodes, relying on the `'Coding'` anchor fallback only as a last resort. Finally, treat dashboard-facing labels like the Memgraph techNote as potentially stale documentation artifacts rather than ground truth about the current backend.

This duality means developers must understand that 'starting a service' has two entirely separate code paths depending on deployment target, and that health-checking logic (service-probe.js) is written to be agnostic to which path is in effect — it only cares about HTTP/TCP reachability, not process ownership. This design avoids needing separate health-monitoring logic for containerized vs local services, but it also means Docker-specific failures (e.g., supervisord misconfiguration killing a service inside the container) surface identically to host-side crashes, requiring log inspection to disambiguate.

Concretely, each script accepts the same positional arguments and environment variables (e.g., LLM_PROXY_URL, CODING_OPENCODE_MODEL), performs argument translation specific to its backend binary, and emits output in a shared format consumable by the orchestrator layer. This lets the rest of the system (e.g., wave-controller.ts or any dispatcher invoking these scripts) remain agnostic to which underlying agent CLI is actually installed—new agents can be onboarded by adding a new script that satisfies the same contract rather than modifying core dispatch logic, as described in docs/architecture/adding-new-agent.md.
- [ConstraintSystem](./ConstraintSystem.md) -- [LLM] The configuration merging strategy in HookConfigLoader (lib/agent-api/hooks/hook-config.js) implements a three-tier cascade — DEFAULT_CONFIG baked into the code, user-level settings from ~/.coding-tools/hooks.json, and project-level settings from .coding/hooks.json — resolved through mergeConfigs(). This design lets individual developers set personal defaults (e.g., preferred logging verbosity or disabled hooks) while allowing a project to enforce mandatory constraints that override user preferences, but not vice versa. A new developer extending this system needs to understand that the merge is not a deep recursive merge in all cases; array-type handler lists are typically concatenated or replaced depending on the key, so adding a new hook type requires checking mergeConfigs() logic to avoid silently dropping user-level handlers.
- [SemanticAnalysis](./SemanticAnalysis.md) -- [LLM] The classification pipeline in OntologyClassificationAgent embodies a deliberate 'deterministic-first, LLM-as-fallback' philosophy that recurs throughout SemanticAnalysis. Before any LLM call is made, classifySingleObservation() checks the observation's name against the hard-root-guard set (CollectiveKnowledge, Coding, DynArch, Timeline, Normalisa) imported from @fwornle/km-core's HIERARCHY_ROOTS. If matched, the method immediately assigns classificationMethod='hard-root-guard' and returns without ever invoking classifier.classify() or touching the LLM. This is a defensive engineering decision: because these 5 names anchor the entire hierarchy, any LLM-driven misclassification of them would cascade corruption through the whole ontology tree, so the developers chose to hardcode an escape hatch rather than trust probabilistic classification for structurally critical nodes.
