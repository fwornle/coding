## Architecture and Design

The dominant architectural pattern is layered evolution: a legacy Memgraph/Cypher-backed graph store has been replaced by GraphifyGraph, a lazy, mtime-cached reader over a static `graph.json` file produced by the graphify tool. This is a read-oriented design — there is no live mutation path through GraphifyGraph itself; updates only occur when graphify regenerates `graph.json` and the cache is invalidated on file mtime change, introducing a staleness window that any consumer must tolerate.

To avoid breaking existing call sites, CodeGraphAgent (`code-graph-agent.ts`) exists purely as a compatibility shim, preserving the original `CodeEntity`, `CodeRelationship` types and `checkMemgraphConnection` method while delegating internally to GraphifyGraph — a deliberate trade-off of naming clarity (the method no longer touches Memgraph) for backward compatibility.

Entity typing is a second architectural throughline: GraphifyGraph infers `EntityKind` ('function'|'class'|'method'|'file'|'variable') purely from node label strings since raw nodes carry no explicit type field, while the km-core migration path (KmCoreMigration) consolidates many legacy, ad-hoc entity types down to exactly three canonical types — System, Project, Pattern — via a static `ENTITY_TYPE_MAPPING` table in `migrate-graph-db-entity-types.js`, persisted through `GraphDatabaseService._persistGraphToLevel()`.

## Implementation Details

`migrate-leveldb-to-kmcore.mjs` enforces a hard error budget: migration aborts if more than 5% of source nodes cannot be converted to km-core's canonical shape (UUIDv7 ids, `layer='evidence'`, provenance stamps), and supports a `--dry-run` mode to preview conversion counts without touching the target `dataDir`.

A significant correctness fix lives in `km-core-adapter.ts`: `findEntityByName` previously resolved purely by name with "oldest wins" semantics, which caused a new Detail-typed entity to silently inherit 24 edges from an unrelated older SubComponent sharing the same name. The fix threads an optional `entityType`/`endpointTypes` parameter through `queryIncomingRelations` and `storeRelationship`, establishing entityType disambiguation as mandatory discipline anywhere name-based entity lookup occurs.

WaveInsightPersistence addresses a parallel divergence bug: Wave 4 batch analysis wrote 73 insight documents to storage but zero corresponding Insight-typed graph nodes, rendering them invisible to the History UI (which filters strictly on `entityType='Insight'`). The fix explicitly creates Insight entities stamped with `source`/`subsystem='wave-analysis'` at write time.

## Usage Guidelines

Developers must treat document persistence and graph-node persistence as two distinct steps that are never automatically synchronized — the WaveInsightPersistence incident shows this divergence occurs silently. Any name-based entity lookup must pass `entityType` (or `endpointTypes`) explicitly; bare-name lookup via `findEntityByName` is unsafe under the current schema. Code relying on legacy fine-grained entity types (TransferablePattern, WorkflowPattern, TechnicalIssue, etc.) must be updated to query against the canonical System/Project/Pattern taxonomy post-migration, since the rewrite is in-place and one-way. Consumers of GraphifyGraph must account for its staleness window rather than assuming real-time graph updates, and operators running km-core migrations should use `--dry-run` first to validate the malformed-node error budget (5%) before committing.
