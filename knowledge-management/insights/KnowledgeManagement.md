# KnowledgeManagement

**Type:** Component

## What It Is

KnowledgeManagement is the component governing the persistent knowledge graph and its supporting pipelines within the Coding project hierarchy. Its implementation spans several concrete artifacts: `src/knowledge-management/GraphDatabaseService.js` (the live mutable graph store), `integrations/semantic-analysis/src/agents/graphify-graph.ts` and `code-graph-agent.ts` (a code-graph query layer), and a set of migration scripts (`scripts/migrate-graph-db-entity-types.js`, `migrate-leveldb-to-kmcore.mjs`) that evolve the graph's schema and storage format over time. It is the parent for four child components — WaveInsightPersistence, OnlineLearning, GraphAttributionAudit, and UnifiedGraphViewerRendering — though OnlineLearning's supplied files turned out to be viewer/testing scaffolding unrelated to actual learning logic, an important caveat for anyone navigating that child.

## Architecture and Design

![KnowledgeManagement — Architecture](images/knowledge-management-architecture.png)

The architecture layers a live, mutable graph atop a durable but lazily-flushed store, alongside a separate read-oriented code-graph query path. GraphDatabaseService uses a Graphology in-memory graph backed by LevelDB, but persistence is explicitly deferred: an `isDirty` flag and `_persistGraphToLevel()` method mean writes accumulate in memory until a flush is triggered. This is a deliberate throughput-over-durability trade-off, and it is what makes batch migrations like `migrate-graph-db-entity-types.js` cheap — they rewrite node attributes directly on the live Graphology object and persist once, rather than paying per-node LevelDB costs.

A second, structurally different pattern appears in the code-graph query stack: CodeGraphAgent is a compatibility shim preserving the exact interface of a former code-graph-rag Memgraph/Cypher backend while internally routing reads through GraphifyGraph, which caches graphify's NetworkX node-link `graph.json` keyed on file mtime rather than content hash. This "hollow out and rewire" pattern minimizes consumer churn but leaves CodeGraphAgent carrying legacy Cypher-shaped API surface that must be reimplemented case-by-case against the new file-based structure.

## Implementation Details

GraphifyGraph's caching avoids reparsing multi-megabyte graph.json files unless mtime changes, but entity "kind" derivation has no dedicated type field — `nodeToCodeEntity()` infers semantic type (e.g., graphify's 'file' kind → CodeEntity 'module') from structural cues, forming an implicit, fragile contract with graphify's export vocabulary.

The migration scripts illustrate two different rigor levels. `migrate-graph-db-entity-types.js` performs a straightforward, atomic in-memory taxonomy collapse — nine legacy types (TransferablePattern, WorkflowPattern, TechnicalIssue, AnalysisInsight, etc.) reduced to System/Project/Pattern — accepting that a crash between mutation and persistence loses the work entirely. `migrate-leveldb-to-kmcore.mjs` is more elaborate: it assigns UUIDv7 identifiers, preserves originals as `legacyId`, stamps provenance, retains existing embeddings, and enforces a hard 5% malformed-record error budget, validated in `migrate-leveldb-to-kmcore.test.ts` via 1-of-20 (pass) versus 2-of-20 (fail) fixtures — a deliberate tolerance for isolated corruption but a hard stop against systemic data problems.

Entity resolution itself was a fragility point: `findEntityByName` previously used "oldest wins" with no type filter, once causing a Detail-typed entity to inherit 24 edges from an unrelated older SubComponent of the same name. The fix threads `entityType` through `queryIncomingRelations(e.name, e.entityType)` and `storeRelationship`'s `endpointTypes` parameter, converting name-only lookup into a name+type composite key.

## Usage Guidelines

Callers must treat entity identity as name+type, not name alone, given the historical edge-inheritance bug. Anything intended to be queryable from the History sidebar or similar graph-filtered UI must be written as an actual graph node, not merely a document — WaveInsightPersistence's 73-document/0-node incident is the cautionary precedent. Migration authors should follow the established pattern of batching mutations in-memory before a single `_persistGraphToLevel()` call, but must be aware of the crash-window durability risk, and should consider adopting `migrate-leveldb-to-kmcore.mjs`'s error-budget approach for any future large-scale rewrites. Finally, since GraphifyGraph's type inference depends on an implicit schema contract, changes to graphify's node-kind vocabulary require coordinated updates to `nodeToCodeEntity()` rather than assuming silent compatibility.
