# KnowledgeManagement: Technical Insight Document

## What It Is

KnowledgeManagement is the component within the Coding project responsible for storing, querying, and aging knowledge graph entities that describe the codebase and its evolving semantic context. Its center of gravity is the VKB (Virtual Knowledge Base) server (implemented as the `VKBServer` class in `index.js`, corresponding to the child component VkbServer), which sits atop KMCore, a graph database backend that replaced an earlier LevelDB-based storage engine. Rather than being a thin passthrough to the database, the VKB server implements query logic, caching, and decay scheduling as first-class server responsibilities—logic that must survive any future storage backend swap.

As the parent Coding node's component breakdown makes clear, KnowledgeManagement is one of seven major subsystems in the project, sitting alongside siblings like SemanticAnalysis, LLMAbstraction, and ConstraintSystem. Its four children—ManualLearning, OnlineLearning, VkbServer, and UkbUnifiedCli—represent distinct access paths and operator-facing surfaces built on top of the same underlying graph substrate.

## Architecture and Design

The architecture reflects a deliberate separation between three concerns: storage/query (VKB server + KMCore), knowledge construction (owned by the SemanticAnalysis integration, not by this component), and lifecycle/decay tracking. Graph construction—populating the knowledge graph with entities and relationships—is explicitly handled outside the core VKB server, in `integrations/semantic-analysis/src/agents` via `code-graph-agent.ts` and `graphify-graph.ts`. This means KnowledgeManagement owns storage, query, and lifecycle management, while the sibling SemanticAnalysis component owns extraction and construction, feeding entities into the graph rather than manipulating it directly.

A second architectural decision is the decoupling of graph database implementation from higher-level knowledge semantics (entity types, relationships, decay curves). This is reinforced by `migrate-graph-db-entity-types.js` existing as a standalone, independently runnable script rather than inline migration logic embedded in the live server—anticipating further backend evolution and making schema migrations independently testable outside the running VKB process.

However, the ManualLearning child component reveals an architectural tension: at least three distinct code paths can mutate the same knowledge entities—`lib/ukb-database/cli.js` writing directly to SQLite + Qdrant via `DatabaseManager`/`UKBDatabaseWriter`, `lib/ukb-unified/cli.js` orchestrating incremental workflows via `WorkflowOrchestrator`, and `VkbApiClient.js` talking to the same data over HTTP against a running VKB server. Nothing shown enforces mutual exclusion across these paths, representing a latent race/divergence risk that developers should be aware of when reasoning about consistency.

## Implementation Details

Entity persistence follows a two-stage lifecycle: raw entity extraction/creation, followed by decay tracking. Decay is not a passive TTL—`ukb-trace-report.ts` provides diagnostic visibility into how VKB queries interact with aging entities, implying a temporal relevance score or decay curve that actively influences query results rather than simple expiration.

The migration path from LevelDB to KMCore is validated by `migrate-leveldb-to-kmcore.test.ts`, which exercises the actual transformation logic in `migrate-graph-db-entity-types.js`. This test suite functions as the authoritative definition of a "successfully migrated" entity record and relationship set; if it breaks, either the migration script's transformation logic or the target KMCore schema has drifted.

On the child-component side, UkbUnifiedCli implements a safety-first incremental philosophy: `UKBCli.defaultCommand()` in `lib/ukb-unified/cli.js` checks for a `TeamCheckpointManager` checkpoint and refuses to run a full analysis if none exists, directing users to `ukb --full` instead—guarding against unbounded first-run cost. OnlineLearning's `calculateDynamicEta()` (in `integrations/system-health-dashboard/src/components/ukb-workflow-modal.tsx`) implements an online-learning-style ETA estimator, blending a live `learnedAvgBatchMs` with a `linearEtaMs` sanity-clamped fallback, including a conservative 1.2x multiplier for single-batch samples to avoid overfitting.
