# KnowledgeManagement — Architectural Insight Document

## What It Is

KnowledgeManagement is the component of the Coding project responsible for capturing, storing, migrating, and surfacing code-derived and analytical knowledge as a graph. Its implementation spans `integrations/semantic-analysis/src/agents/graphify-graph.ts` (GraphifyGraph), `integrations/semantic-analysis/src/agents/code-graph-agent.ts` (CodeGraphAgent), a GraphDatabaseService backed by LevelDB, and a family of migration scripts (`scripts/migrate-graph-db-entity-types.js`, `migrate-leveldb-to-kmcore.mjs`). Its children — ManualLearning, OnlineLearning, GraphDatabaseService, GraphifyGraphReader, CodeGraphAgent, KmCoreMigrationTooling, EntityTypeConsolidation, DuplicateNameAnchoring, GraphAttributionAudit, GraphVisibilityFiltering, and SigmaGraphRenderer — represent the distinct concerns of this domain: writing insights, reading/rendering graphs, resolving entity identity, and migrating schema over time. As a child of Coding, it sits alongside SemanticAnalysis and other infrastructure components but owns the durable knowledge-graph representation that those pipelines feed into.

## Architecture and Design

The dominant pattern here is the Facade/Adapter used to decouple backend migrations from consumer code: CodeGraphAgent retains its full historical public interface — `CodeEntity`, `CodeRelationship`, `checkMemgraphConnection` — from when it queried a live Memgraph/Cypher backend, but now delegates internally to GraphifyGraph's static `graph.json` reads. This is a deliberate trade-off: callers' old guard clauses (`if (!connectionCheck.connected)`) keep working, at the cost of a permanently misleading "connection" concept in the API surface.

A second structural theme is derived-rather-than-declared schema: GraphifyGraph treats a NetworkX node-link `graph.json` export as sole source of truth, with no explicit `type`/`name` fields — `kindOf()` and `nameOf()` parse these out of a `label` string at read time. This makes the entire entity taxonomy hostage to upstream label-formatting conventions, with no schema validation layer to catch drift.

Persistence follows a manual dirty-flag model rather than transparent auto-save: GraphDatabaseService requires every in-memory Graphology mutation to be paired with `dbService.isDirty = true`, with actual LevelDB writes deferred until `_persistGraphToLevel()` is invoked — batching for performance at the risk of silent data loss if a mutation path forgets to mark dirty.

## Implementation Details

Entity identity resolution has historically been a weak point. The anchor pass originally used `findEntityByName`, a name-only lookup, which caused a newly created Detail-type node to silently inherit 24 incoming edges from an unrelated, same-named SubComponent node created weeks earlier (documented in the Wave Insight Persistence record, and reflected in the DuplicateNameAnchoring child). The fix threads `entityType` through `queryIncomingRelations` and `storeRelationship` so lookups disambiguate by (name, type) pairs, with a fixed fallback `projectAnchorName = 'Coding'` ensuring unresolvable nodes attach to a known anchor rather than becoming orphans.

Schema evolution is handled through explicit, sometimes lossy migration scripts. `scripts/migrate-graph-db-entity-types.js` consolidates six historically distinct types — TransferablePattern, WorkflowPattern, TechnicalPattern, TechnicalIssue, SystemImplementation, AnalysisInsight — into a single canonical `Pattern` type via a hardcoded `ENTITY_TYPE_MAPPING`, and is permissive-by-default: unmapped types also collapse to `Pattern` rather than being flagged, a risk if the mapping drifts from the live schema (this is the substance of EntityTypeConsolidation). `migrate-leveldb-to-kmcore.mjs`, validated by `migrate-leveldb-to-kmcore.test.ts`, encodes an explicit error-budget policy — up to 5% malformed entities tolerated with exit 0, 10% triggers a halt — and supports `--dry-run` to preview migration counts before committing (KmCoreMigrationTooling).

A separate, significant gap surfaced in the Wave Insight Persistence record: Wave 4 wrote 73 insight documents to storage but created zero corresponding graph nodes of `entityType 'Insight'`. Because the viewer's History sidebar filters strictly on `entityType == 'Insight'` to render a Batch badge, this broke traceability between completed analysis runs and their visible conclusions, even though the underlying data existed on disk — illustrating how ManualLearning and OnlineLearning can produce documents that never get anchored as graph entities (GraphAttributionAudit).

## Usage Guidelines

Any new code path that mutates the GraphDatabaseService's in-memory graph must be audited to confirm it sets `isDirty = true` and eventually triggers `_persistGraphToLevel()` — omitting this causes silent data loss on process exit. Entity lookups should always resolve by (name, type) pairs, not name alone, per the DuplicateNameAnchoring fix; code still calling raw `findEntityByName`-style lookups risks cross-contaminating edges between unrelated same-named entities. When extending `ENTITY_TYPE_MAPPING` in `migrate-graph-db-entity-types.js`, new entity types must be added explicitly — the permissive fallback to `Pattern` will otherwise silently reclassify anything unmapped. Migration scripts should be run with `--dry-run` first to assess blast radius, and their 5%/10% malformed-data thresholds should be treated as real operational gates, not arbitrary constants. Finally, any pipeline that produces insight documents (ManualLearning, OnlineLearning) must be checked to confirm it also writes corresponding `Insight`-typed graph nodes, since GraphVisibilityFiltering's UI surfaces (like the History sidebar's Batch badge) depend on that entityType being present, not merely on the document existing on disk.
