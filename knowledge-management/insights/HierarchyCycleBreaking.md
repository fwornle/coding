# HierarchyCycleBreaking — Technical Insight Document

## What It Is

HierarchyCycleBreaking is the defensive traversal logic guarding the ontology-class parent-walk in `integrations/unified-viewer/src/graph/color-fallback.ts`, specifically inside two functions: `nodeFillColor()` and `nodeShapeFor()`. Both functions resolve a rendered node's visual styling — fill color and shape, respectively — by walking up a `ReadonlyMap<string, ClassRegistryEntry>` class registry via `cur = reg?.parent`, looking for the nearest ancestor that carries an explicit `display.color` or `display.shape` override before falling through to static palettes (`BATCH_PALETTE`, `SHAPE_PALETTE`). The cycle-breaking mechanism itself is a `Set<string>` named `seen`, gating the walk with `while (cur && !seen.has(cur))`, so that a malformed registry (e.g., class A declaring parent B, and B declaring parent A) cannot infinite-loop the walk. Because these functions run per-node inside D3GraphCanvas's render path, an unguarded cycle would not just misrender a single node — it would hang the entire canvas.

## Architecture and Design

The core pattern is a visited-set-guarded graph walk: a `seen` Set accumulates visited class names, and the loop condition `cur && !seen.has(cur)` terminates the ascent the moment a previously-visited node reappears. This is paired with a fail-safe default fallback — on either a genuine cycle or simple chain exhaustion (reaching a class with no styled ancestor), control falls out of the loop identically and returns `DEFAULT_BATCH` or `'circle'`. This is a deliberate design choice: cyclic registry data is made structurally indistinguishable from legitimately-unstyled data, trading diagnostic visibility for implementation simplicity and guaranteed termination.

This traversal sits within a broader family of hierarchy-walk safety mechanisms in the same rendering subsystem. Its sibling, `DeriveAncestryFromStorePath` (in D3GraphCanvas.tsx), solves a structurally analogous problem — don't trust a single-source ancestry traversal — but for a different domain: entity-instance selection-ancestry rather than ontology-class-ancestry. There, `deriveAncestryFromStorePath()` reconciles a locally-computed BFS (`computeAncestryPath()`) against the store's authoritative `pathToSelected` set, capping unreached-but-store-tagged nodes at a synthetic `maxDepth` (`inline.pathLength`) rather than allowing unbounded recursion. Both mechanisms share the same defensive posture — bound or reconcile an ancestor walk against unreliable input — but are implemented completely independently, with no shared abstraction. This reflects the parent component GraphViewerHierarchy's broader pattern, noted in relation to D3GraphCanvas.tsx's role as a Redux-to-Zustand port: rather than trusting one canonical traversal implementation, the codebase re-derives ancestry/traversal logic per consumer to keep independently-maintained rendering paths (this D3/SVG canvas and the parallel Sigma/WebGL `graph-builder.ts`) in sync.

## Implementation Details

`nodeFillColor()` and `nodeShapeFor()` are structurally near-identical: both accept a `className` and the registry, initialize `const seen = new Set<string>()`, and loop `while (cur && !seen.has(cur))`, adding each visited node to `seen`, checking the registry entry's override field, then consulting a static palette, before ascending via `cur = reg?.parent`. The only divergence is which field/palette each consults — `display.color`/`BATCH_PALETTE` versus `display.shape`/`SHAPE_PALETTE`. This duplication directly mirrors the sibling entity DeriveParentsHierarchyReduction's characterization: an entity's ontology class is reduced to the nearest ancestor carrying an actual styling assignment (e.g., `LiveLoggingSystem` inheriting Component's blue rather than falling to slate default).

Notably, unlike most of color-fallback.ts's defensive logic — such as the heavily-annotated `isOnlineLearned` migration note (shared with sibling LearningSourceClassifier) or the UI-SPEC §14 fallback-rule comments surrounding it — the `seen` Set guard carries no dated comment explaining its origin. Given this codebase's practice of using comments as a decision log, this absence suggests the guard was written preventively against a hypothetical bad registry rather than in response to an observed production cycle.

## Integration Points

This logic is invoked per-node from D3GraphCanvas's render path, making it a hot-path dependency: any registry entry consulted by `nodeFillColor`/`nodeShapeFor` must terminate its parent chain, either through the `seen` guard or through legitimately reaching an unparented root. It depends on the `ClassRegistryEntry` structure (specifically the `parent` and `display` fields) and on the static `BATCH_PALETTE`/`SHAPE_PALETTE` tables consulted only after the guarded walk exits.

Architecturally, it sits alongside — but does not share code with — `DeriveAncestryFromStorePath`/`ComputeAncestryPathExtraction`, which perform the analogous reconciliation for selection-ancestry rendering. Both are children/siblings under GraphViewerHierarchy, and both independently embody the "don't trust one traversal source" philosophy without a common `walkAncestryChain`-style helper — an explicitly noted missed consolidation opportunity, especially given color-fallback.ts's own header commentary describing its five-rule fallback chain as a deliberate unification of previously-divergent D3/Sigma/Legend color logic. Here, the unification stopped one level short: the two resolvers share behavior but not code.

## Usage Guidelines

Developers extending or modifying the class registry should be aware that cyclic parent references will not throw or log — they will silently degrade to `DEFAULT_BATCH`/`'circle'`, identical to an intentionally unstyled class. Any future debugging of "why does this class render with default styling" should include checking for registry cycles as a candidate cause, since there is currently no runtime signal distinguishing the two cases. When adding new per-node ancestor-walk logic (color, shape, or otherwise), maintainers should consider factoring the walk into a shared helper rather than replicating the `seen`-guarded `while` loop a third time — the codebase's stated preference for consolidating divergent per-consumer logic (as done for the five-rule color fallback chain) has not yet been extended to this walk. Finally, if a genuine production cycle is ever observed, it would be worth adding the dated decision-log comment this guard currently lacks, consistent with the module's otherwise thorough self-documentation practice (e.g., the `isOnlineLearned` migration note).
