# ProjectFiltering — Technical Insight Document

## What It Is

ProjectFiltering is the project-scoping mechanism implemented in `lib/lsl/live/copilot-events-tail.mjs`, centered on the predicate function `projectMatches(workspaceYaml, projectRoot)`. It determines whether a discovered Copilot session belongs to the project a caller is currently interested in, so that live event tailing can be scoped to "this project" rather than every Copilot session running on the host. As a child concern of its parent component, CopilotLiveTail, ProjectFiltering does not touch the data-loss/degraded-parity problem that CopilotLiveTail's header documents (see DegradedParityStub) — it operates purely at the session-selection layer, deciding *which* sessions get tailed, not what fidelity their events carry.

The mechanism reads a session's `workspace.yaml` via `readWorkspace(sessionDir)`, resolves a project identity from it using the imported `projectFromWorkspace()`, and compares that identity against a caller-supplied `projectRoot` (full path or bare basename) using `path.basename()` normalization. A match, a non-match, or an unresolved/malformed workspace file all funnel through the same simple boolean predicate.

## Architecture and Design

The dominant pattern is **fail-closed filtering with opt-in activation**: `projectMatches()`'s first line, `if (!projectRoot) return true;`, makes the entire mechanism a caller-invoked narrowing rather than a structural default — omit `projectRoot` and the pipeline reverts to host-wide scope. But once a filter *is* supplied, the function flips to a strict, under-inclusive posture: any session whose resolved project is falsy or the sentinel `'unknown'` is rejected, explicitly to "save resources for stray Copilot sessions that don't belong to this project." This is a deliberate trade-off favoring missed matches over false positives.

ProjectFiltering is also a clear instance of a **layered gate pipeline**, sitting downstream of and subordinate to `scanForLiveSessions()`. That function first applies security/liveness gates — `isOwnedByMe()` (see sibling UidOwnershipGuard) and `findLiveLockFile()` freshness checks against `LOCK_STALE_GRACE_MS` (see sibling LockStaleDetection) — before any session is even considered for project matching. This ordering means project-identity comparison, the cheapest and most semantically specific check, runs last, and a foreign-uid or stale-lock session never reaches `readWorkspace()`/`projectMatches()` at all.

A third pattern is the **adapter reuse boundary**: `parseWorkspaceYaml` and `projectFromWorkspace` are imported from `../adapters/copilot-events.mjs` rather than reimplemented, per the module's documented "D-Reuse" policy. Notably, this reuse is asymmetric — vendor-specific parsing/identity helpers from Plan 51-04 are shared, while the broader Phase 50 LSL windowing primitives are deliberately not imported into this file, keeping project filtering decoupled from windowing/conversion concerns.

## Implementation Details

`projectMatches(workspaceYaml, projectRoot)` is a pure, synchronous function with no filesystem or session-lock dependency — it operates purely over its two arguments. It normalizes `projectRoot` with `path.basename()`, permitting callers to pass either an absolute path or a bare directory name, and compares that against the value returned by `projectFromWorkspace(workspaceYaml)`. This basename-only comparison is a deliberate ergonomic trade-off: it removes the burden of absolute-path bookkeeping from callers but introduces a latent ambiguity, since two distinct projects sharing a basename (e.g., `~/work/coding` vs `~/archive/coding`) are indistinguishable to the filter.

`readWorkspace(sessionDir)` is the I/O-bound counterpart, separated out as its own single-purpose function. It gates on `fs.existsSync` (returning `null` for a missing file) and wraps `fs.readFileSync` + `parseWorkspaceYaml` in a try/catch (returning `null` on any parse error). This collapses "file absent" and "file malformed" into an identical `null` result — and because `projectFromWorkspace(null)` yields a falsy/sessionProject value, both cases produce the same silent exclusion when a filter is active. Unlike the sibling UidOwnershipGuard's `isOwnedByMe()`, which writes a stderr warning on rejection, this path surfaces no diagnostic at all, making "why isn't my session being tailed due to a bad workspace.yaml" invisible to an operator — echoing the same observability asymmetry noted in LockStaleDetection's silent staleness path.

There is no caching layer: `readWorkspace()` re-reads and re-parses `workspace.yaml` on every invocation. This is deemed acceptable because it is invoked once per session during discovery scanning rather than per poll cycle, so the cost is bounded by session count rather than by tail frequency.

## Integration Points

ProjectFiltering's primary dependency is `../adapters/copilot-events.mjs`, which supplies `parseWorkspaceYaml` and `projectFromWorkspace` — making that adapter the single source of truth for "what project does this Copilot session belong to." Within `copilot-events-tail.mjs`, it integrates downstream of `scanForLiveSessions(sessionStateDir, myUid)`, which in turn depends on the sibling concerns UidOwnershipGuard (`isOwnedByMe`) and LockStaleDetection (`findLiveLockFile`, `LOCK_STALE_GRACE_MS`). Only sessions surviving those two gates are passed into `readWorkspace()`/`projectMatches()`, and only sessions surviving *that* gate proceed to the expensive per-file `tailEventsFile()` work under the parent CopilotLiveTail component. Structurally, this makes ProjectFiltering the final, most semantically meaningful filter in a three-stage pipeline: ownership → liveness → project identity.

## Usage Guidelines

Callers that want project-scoped tailing must explicitly pass a `projectRoot` (path or basename); omitting it silently yields host-wide scope, which is easy to overlook when writing new call sites. Because the filter is fail-closed once active, a session with a missing or corrupted `workspace.yaml` will be silently dropped with no stderr signal — developers debugging "missing session" issues should check `readWorkspace()`'s null-return conditions before assuming a matching bug in `projectMatches()`. Given the basename-only comparison, callers operating in environments with same-named project directories under different parents should be aware that ProjectFiltering cannot disambiguate them; a full-path-aware match is not currently implemented and would require deliberate extension of `projectMatches()`. Any future diagnostic improvements should add stderr signaling to `readWorkspace()`'s null paths, mirroring the pattern already established by `isOwnedByMe()`, rather than altering the fail-closed matching logic itself.
