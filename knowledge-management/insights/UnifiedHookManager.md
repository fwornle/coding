# UnifiedHookManager: Technical Insight Document

## What It Is

UnifiedHookManager is a class defined in `lib/agent-api/hooks/hook-manager.js` that serves as the central runtime dispatcher for agent lifecycle hooks (PreToolUse/PostToolUse-style events) within the ConstraintSystem. It is instantiated as a singleton accessed via `getHookManager()`, and it is responsible for the core registry logic — priority sorting, agent-scoping, and handler invocation — that agent-specific adapters delegate to rather than implement themselves. As a child of ConstraintSystem, it composes several subcomponents that divide its responsibilities: `UnifiedHookConfigLoader` (configuration resolution), `HandlerRegistry` (the priority-ordered `Map<event, Handler[]>` registry), `ClaudeBridgeAdapter` (agent-specific translation), and `HookMigrationTool` (transition tooling, presumably for reconciling legacy hook definitions).

## Architecture and Design

The dominant pattern is Adapter/Bridge: `claude-bridge.js` translates Claude Code's native hook payloads into a unified event contract and hands them to UnifiedHookManager via `manager.executeHooks(unifiedContext.event, unifiedContext, 'claude')`. The bridge itself is deliberately thin — handling only stdin parsing, event-name mapping via `EVENT_MAP`, and response shaping via `transformResponse()` — while all registry complexity (priority sorting, handler dispatch) lives in UnifiedHookManager. This keeps agent adapters free of duplicated logic and centralizes behavior in one place.

![UnifiedHookManager — Architecture](images/unified-hook-manager-architecture.png)

A Registry pattern underlies the design: UnifiedHookManager maintains a `Map<event, Handler[]>`, mirroring the abstract `HooksManager` base class in `lib/agent-api/hooks-api.js`, which seeds the same map structure from `Object.values(HookEvent)` and sorts handlers by priority immediately on registration (`registerHook()`). This raises an open architectural question — flagged repeatedly across observations — of whether UnifiedHookManager actually extends `HooksManager` or is a parallel reimplementation; no `extends` clause has been confirmed. Given that its siblings `HookConfigLoader`, `KnowledgeInjectionHooks`, and `HealthPromptHook` sit alongside it under ConstraintSystem, and its own children (`HandlerRegistry`, `UnifiedHookConfigLoader`) replicate concepts found in hooks-api.js, this duality should be resolved to avoid maintaining two divergent hook execution paths.

## Implementation Details

UnifiedHookManager exposes an idempotent `initialize(projectPath)` method guarded by an `initialized` flag, allowing `claude-bridge.js`'s `main()` to lazily initialize the manager only once per relevant lifetime — important because each PreToolUse/PostToolUse event spawns a fresh Node process. Its `executeHandlers`/`executeHooks` path is invoked per event with the event name, unified context, and originating agent type (`'claude'`) as arguments. Configuration resolution is delegated to its child `UnifiedHookConfigLoader`, which mirrors the three-tier cascade (DEFAULT_CONFIG, user `~/.coding-tools/hooks.json`, project `.coding/hooks.json`) described at the ConstraintSystem parent level via `mergeConfigs()`.

Handler storage and ordering are managed by `HandlerRegistry`, consistent with the priority-sort-on-registration strategy seen in `hooks-api.js`'s `registerHook()` (`eventHooks.sort((a,b) => a.priority - b.priority)`), trading O(n log n) per-registration cost for cheap linear dispatch at call time. The `ClaudeBridgeAdapter` child component encapsulates the Claude-specific translation logic that `claude-bridge.js` invokes, while `HookMigrationTool` presumably assists in moving handlers/configuration between the older `HooksManager` abstraction and the current unified implementation.

## Integration Points

![UnifiedHookManager — Relationship](images/unified-hook-manager-relationship.png)

UnifiedHookManager's primary external integration is with `claude-bridge.js`, which performs event-name translation via `EVENT_MAP` and passes raw `claudeContext` into `metadata` via `transformContext()` without sanitization — meaning any redaction of sensitive fields (tool_input, etc.) must occur inside UnifiedHookManager's `executeHooks()` or downstream in ViolationCaptureService's `sanitizeParams()`, not at the bridge layer. This is a notable open question for maintainers auditing security boundaries.

At the ConstraintSystem level, UnifiedHookManager coexists with `HookConfigLoader`, `KnowledgeInjectionHooks`, and `HealthPromptHook` as siblings, and structurally parallels the abstract `HooksManager` in `hooks-api.js`, which defines `getAgentType()`, `loadNativeHooks()`, and `saveNativeHooks()` as methods that concrete per-agent classes must implement. The presence of a second, independently-maintained event mapping table (`EVENT_MAPPINGS`, nested per agentType including `'copilot'`) alongside `claude-bridge.js`'s flat `EVENT_MAP` creates a synchronization burden: adding new lifecycle events likely requires updates in both places (and possibly a third mapping inside `hook-manager.js` itself, plus any future `copilot-bridge.js`).

## Usage Guidelines

Developers extending UnifiedHookManager should treat the bridge layer as a poor location for mandatory, non-bypassable policy checks: the system-wide fail-open philosophy — visible in both `claude-bridge.js`'s `main()` (defaulting to `{decision: 'allow', message: 'Hook bridge error: ...'}` with `process.exit(0)` on any failure) and `HooksManager.triggerHook()`'s fail-soft per-handler try/catch — means infrastructure failures are indistinguishable from legitimate approvals. Enforcement logic belongs inside registered handlers within UnifiedHookManager, not the adapter.

Before adding new hook types, confirm whether UnifiedHookManager and `HooksManager` in `hooks-api.js` are meant to converge (verify inheritance) to avoid maintaining duplicate registries. When adding new lifecycle events, update all known event-mapping tables (`EVENT_MAP`, `EVENT_MAPPINGS`, and any internal mapping in `hook-manager.js`) together. Finally, be aware that `metadata` passed through the Claude bridge is unsanitized — any handler consuming context data should not assume prior redaction has occurred. Lastly, note that "hooks" terminology is overloaded in this codebase — React hooks in `system-health-dashboard` (`hooks.ts`, `usePolledFetch.ts`) are unrelated to this agent lifecycle hook dispatch system and should not be conflated during searches or refactors.
