# OnlineLearning — Technical Insight Document

## What It Is

OnlineLearning, a child concept of `KnowledgeManagement`, is not a distinct entity or ontology class within the system — it is a cross-cutting metadata concern that describes *how* a knowledge-graph entity was learned (online/incremental vs. batch), rather than *what* the entity is. It is implemented primarily in `integrations/unified-viewer/src/graph/color-fallback.ts` and `integrations/unified-viewer/src/graph/D3GraphCanvas.tsx`, with its classification logic centralized in `learning-source.ts` — the realization of the child component `LearningSourceClassifier`. Entities carry a `source` field (`'auto'` or `'online'`) in their metadata, and this field is interpreted uniformly across the visualization stack to determine coloring, ring overlays, legend grouping, filter-rail behavior, and history-sidebar display.

On the operational/dashboard side, OnlineLearning also surfaces in `integrations/system-health-dashboard` as the `LLMMode` type (`'mock' | 'local' | 'public'`) and per-substep `llmUsage` tiers in `multi-agent-graph.tsx`, which together model the cost and invocation mode of the pipeline that produces online-learned knowledge.

## Architecture and Design

The defining architectural decision is that "online-learned" is a **metadata flag riding on any entity**, not a structural type. `color-fallback.ts` defines two parallel palettes — `BATCH_PALETTE` and `ONLINE_PALETTE` — keyed by the same hierarchy levels (System/Project/Component/SubComponent/Detail), and `classColor()` selects between them based on `isOnlineLearned()`. This decouples provenance from taxonomy: an entity's class/type is unaffected by whether it was learned online or in batch.

A deeper design pivot, documented inline as an "operator decision (Hybrid)," moved provenance encoding from full node **fill** color to a **ring overlay**. The canonical `nodeFillColor()` resolver is now explicitly source-independent, deriving fill purely from `ontologyClass` via a parent-walk (registry `display.color` → `BATCH_PALETTE` → ancestor lookup → slate fallback). Online provenance is instead layered on top via `ONLINE_RING_COLOR` (`#f472b6`), drawn as a ring in `D3GraphCanvas.tsx`. This is a deliberate separation-of-concerns pattern — "what kind of entity" vs. "how it was learned" — avoiding a combinatorial explosion of class × source color pairs.

A single-source-of-truth predicate, `isOnlineLearned()`, is shared across `classColor()`, `D3GraphCanvas.tsx`'s ring-overlay logic, the Legend, the filter rail, and the History sidebar — this consolidation is the entire reason `LearningSourceClassifier` exists as a concept, preventing render surfaces from drifting apart in their classification logic.

## Implementation Details

`D3GraphCanvas.tsx` is a near-verbatim port of the original VKB component (`integrations/memory-visualizer/src/components/KnowledgeGraph/GraphVisualization.tsx`), re-platformed onto `useGraphData` and a Zustand store (`useViewerStore`) instead of Redux, because attempts to replicate the force-directed layout using sigma + graphology-layout-* drifted from the reference. The `d3.forceSimulation` with `forceLink(150)` and `forceManyBody(-500)` is preserved verbatim, which matters directly for OnlineLearning presentation since this physics is what visually clusters online-learned (red/pink) vs. batch-learned (blue) nodes.

The classification bug history is instructive: prior to a documented fix, `classColor()` inlined `source === 'auto'` directly, undercounting online-learned nodes because the real pipeline stamps `source: 'online'` far more often than `'auto'`. The fix consolidated all checks behind `isOnlineLearned()` in `learning-source.ts`.

On the dashboard side, `ukbSlice.ts` types `UKBProcess.llmMode` as optional (`llmMode?: LLMMode`) rather than a legacy boolean `mockLLM`, explicitly to distinguish "server stated no mode" from "server stated public" and to express `'local'` invocation used during online/local LLM-driven knowledge-graph learning. `multi-agent-graph.tsx` extends this with `AGENT_SUBSTEPS` per-substep `llmUsage` tiers (`none`/`fast`/`standard`/`premium`) across agents like `kg_operators`, `semantic_analysis`, and `insight_generation`, modeling the cost/quality trade-off of the pipeline at fine granularity — pure graph operations (`embed`/`merge`) are `none`, while `generate` steps are `premium`. `WAVE_AGENTS` and `KG_OPERATOR_CHILDREN` are hoisted to module scope specifically to avoid silently defeating a status `useMemo`'s dependency tracking.

## Integration Points

OnlineLearning sits under `KnowledgeManagement`, sharing its ecosystem with siblings such as `GraphifyGraph` (which supplies the static `graph.json` consumed downstream by visualization), `CodeGraphAgent`, `GraphViewerHierarchy`, and `GraphVisualRendering`. Its child, `LearningSourceClassifier`, is not a standalone file but a distributed convention centered on `learning-source.ts`'s `isOnlineLearned()`, consumed by `color-fallback.ts:70` and `D3GraphCanvas.tsx` (~line 30).

The `WaveInsightPersistence` sibling clarifies where online-learned entities enter storage: its w1/w2/w3 substeps persist L0–L3 entities via "GraphDB + LevelDB storage" with `llmUsage: 'none'`, with w3 uniquely performing a "direct attribute merge" — suggesting duplicate-entity reconciliation for online-learned/refined entities happens at persistence time rather than during insight generation.

A known integration gap exists: `multi-agent-graph.tsx`'s `AGENT_SUBSTEPS['code_graph']` still labels its `query` substep with `techNote: 'Cypher queries on Memgraph'`, even though `CodeGraphAgent` and `GraphifyGraph` have migrated to a static graph.json reader — meaning the dashboard's `MultiAgentGraph` visualization presents stale technology labels to operators inspecting the live pipeline.

## Usage Guidelines

Developers extending provenance-aware visualization should route all "is this online-learned" checks through `isOnlineLearned()` in `learning-source.ts` rather than reimplementing `source` field checks — this is the explicit lesson from the pre-fix bug where `source === 'auto'` silently undercounted nodes stamped `'online'`. New render surfaces (legend entries, filters, sidebars) must consume this shared predicate to avoid classification drift.

When adding visual encodings, respect the fill/ring separation: entity class/taxonomy should drive fill color via `nodeFillColor()`'s ontology-registry parent-walk, while learning provenance should be layered as an overlay (ring), not baked into fill, per the established Hybrid pattern. When modifying `D3GraphCanvas.tsx`, preserve the ported force-simulation parameters (`forceLink(150)`, `forceManyBody(-500)`) — deviations risk drifting from the VKB visual reference. For LLM-mode-related UI/state work, use the optional `LLMMode` tri-state pattern rather than reintroducing boolean flags, and keep constants like `WAVE_AGENTS`/`KG_OPERATOR_CHILDREN` at module scope to avoid defeating memoization. Finally, the `code_graph` `techNote` documentation drift should be corrected when touched, and pagination-style assumptions (as seen in `HISTORY_PAGE_SIZE`) should be checked against actual server-side parsing cost before assuming a fix is "free."

- [KnowledgeManagement](./KnowledgeManagement.md) -- [LLM] The GraphifyGraph reader (integrations/semantic-analysis/src/agents/graphify-graph.ts) represents a deliberate architectural simplification: rather than maintaining a live graph database connection (Memgraph via Cypher), the component now treats a static graph.json artifact produced by the graphify service as the source of truth for code-structure knowledge. This file, a NetworkX node-link JSON export, can be tens of megabytes, so GraphifyGraph implements mtime-based lazy caching — it stat()s the file and only re-parses when the mtime has changed since the last load. This pattern trades real-time graph mutation capability for drastically simpler deployment (no separate DB process) and fast repeated reads, at the cost of only picking up graph changes when the underlying analysis pipeline re-writes graph.json.
