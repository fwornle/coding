# OnlineBatchPaletteSplit — Technical Insight Document

## What It Is

OnlineBatchPaletteSplit is implemented in `integrations/unified-viewer/src/graph/color-fallback.ts`, and it is the concrete visual mechanism by which the graph viewer distinguishes knowledge learned "online" (interactively, via ETM/consolidator activity) from knowledge learned through the batch wave-analysis pipeline. As a Detail-level child of ManualLearning, it operationalizes the parent's conceptual online/batch split into actual pixels: node fill colors, palette selection, and (in the newer scheme) a ring overlay. The split is driven entirely by a single shared predicate, `isOnlineLearned()`, imported from `./learning-source` (the sibling LearningSourceClassifier) and consumed consistently across `color-fallback.ts`'s `classColor()` and directly inside `D3GraphCanvas.tsx`.

## Architecture and Design

The core architectural pattern here is **single-source-of-truth classification**: rather than each rendering surface (D3 canvas, Legend, filter UI, History sidebar) independently inspecting a node's `source` field, they all defer to `isOnlineLearned()`. This was a deliberate fix for a prior bug where a naive `=== 'auto'` check under-counted online-learned nodes, because ETM/consolidator output is actually stamped `'online'` far more often than `'auto'`. Centralizing the check in one classifier (owned by the sibling LearningSourceClassifier) means the palette split can't drift per-consumer — but it also means correctness of the *entire* visual online/batch distinction now hinges on that one function staying in lockstep with any new provenance tag a data source might introduce.

Layered on top of this classifier, the module is mid-migration between two competing color-resolution schemes. `classColor()` is the legacy, **source-dependent** scheme: it swaps between `BATCH_PALETTE` and `ONLINE_PALETTE` based directly on `isOnlineLearned()`. `nodeFillColor()` is the new, **source-independent** scheme: it walks a `ClassRegistryEntry` parent chain and never looks at `source` at all, instead delegating provenance signaling to a separate `ONLINE_RING_COLOR` ring overlay. The design intent, per an "operator decision (Hybrid)" comment, is that online Insights should be "purple-filled with a pink ring, not solid pink" — i.e., ontology-class color is orthogonal to learning-provenance color, and the two should be composited rather than conflated. `classColor()` remains exported "for callers that genuinely hold a string," so both models currently coexist, and which one governs a given render path depends on whether that path calls `classColor()` or `nodeFillColor()`.

## Implementation Details

`nodeFillColor()` and its shape counterpart `nodeShapeFor()` both implement the same fallback-chain algorithm: a loop guarded by a `seen` Set (to prevent infinite loops on cyclic ancestry), checking registry display → static palette → `reg.parent` → default. This shared algorithm shape is currently duplicated rather than factored into a generic "resolve up the ontology chain" helper — an intentional near-copy justified by fixing the same bug class (L2 classes like `LiveLoggingSystem` falling back to defaults instead of inheriting ancestor styling). Notably, `borderStyleFallback()` in the same file is *not* ancestor-aware — it ignores `_className` and only checks `hasRelations` — showing the ancestor-walk pattern hasn't yet been applied uniformly to every visual attribute.

On the classifier side, `isOnlineLearned()` is small and pure, elevated to its own module specifically to be importable independently by rendering code (`color-fallback.ts`), predicate/visibility code (`D3GraphCanvas.tsx`'s `useGraphVisibility` dependency chain), and inferred consumers like the Legend and History sidebar.

## Integration Points

OnlineBatchPaletteSplit sits directly downstream of LearningSourceClassifier (`isOnlineLearned()`), its primary dependency, and is a sibling concern to DynamicEtaLearning (`calculateDynamicEta()`) — both are Detail-level manifestations of the broader ManualLearning distinction between operator-driven and pipeline-driven state, though ETA estimation lives in the dashboard (`ukb-workflow-modal.tsx`) while the palette split lives in the viewer (`D3GraphCanvas.tsx`, `color-fallback.ts`). Within the viewer, it integrates with node rendering across at least two render surfaces (D3 canvas and, by implication, Sigma's `buildGraph`), and its ring-overlay design must ultimately reconcile with `ClassRegistryEntry`-based ancestry resolution shared with `nodeShapeFor()`.

## Usage Guidelines

Any future data source introducing a new `source`/provenance tag must update `learning-source.ts` in lockstep, or the palette split risks silently reverting to the pre-fix under-classification bug. When adding new render paths, prefer `nodeFillColor()` + `ONLINE_RING_COLOR` (the intended end state) over `classColor()`, which is retained only for callers holding a raw string and should be treated as deprecated. Given the duplicated parent-walk logic between `nodeFillColor()` and `nodeShapeFor()`, any third ancestor-aware attribute (e.g., extending `borderStyleFallback()` to be ancestry-aware) should prompt refactoring both into a shared generic ancestor-resolution utility rather than adding a third copy.
