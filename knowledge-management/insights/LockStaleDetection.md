# LockStaleDetection

## What It Is

LockStaleDetection is the time-windowed liveness heuristic implemented in `lib/lsl/live/copilot-events-tail.mjs`, specifically in the function `findLiveLockFile(sessionDir)`. It determines whether a Copilot CLI session is still "live" by regex-matching lock filenames against `^inuse\.\d+\.lock$` and comparing the lock file's `fs.statSync(lockPath).mtimeMs` against `Date.now()`, using a module-level constant `LOCK_STALE_GRACE_MS` hardcoded to `10 * 60 * 1000` (10 minutes). It is one of two composed predicates consumed by `scanForLiveSessions(sessionStateDir, myUid)`, the entry point that discovers which sessions under a session-state directory are eligible for live tailing. As a child concept of the parent component CopilotLiveTail, LockStaleDetection exists specifically to work around the "RESEARCH landmine #5" scenario referenced in its own inline comment: a hard-crashed Copilot session leaves its lock file orphaned on disk with no explicit crash signal.

## Architecture and Design

The defining architectural pattern here is composition-by-short-circuit: `scanForLiveSessions()` runs the sibling UidOwnershipGuard check (`isOwnedByMe`) *before* LockStaleDetection's freshness check, meaning ownership is a harder gate than freshness. A non-owned session is skipped with an explicit `process.stderr.write` warning, while an owned-but-stale session is dropped silently — no log line at all. This creates an observability asymmetry: security-relevant skips are loud, staleness-relevant skips are mute, which directly harms operator debuggability ("why isn't my session being tailed") when the cause is staleness rather than permissions.

A second key decision is that LockStaleDetection is a pure, side-effect-free predicate, decoupled from the polling loop (`tailEventsFile()`, with its own `TAIL_POLL_INTERVAL_MS = 200`) that would consume its result. There is no shared state machine linking a staleness transition to stopping an active tail — the two poll cadences (session-discovery-level staleness at whatever cadence the caller invokes `scanForLiveSessions`, and 200ms content-level tailing) are entirely uncoordinated. Any wiring between them, if it exists, lives outside this file.

Notably, this staleness/grace-window pattern is bespoke to Copilot's `inuse.<pid>.lock` filesystem convention and is *not* shared with sibling token-adapter files `lib/lsl/token/opencode-token-rows.mjs` and `lib/lsl/token/token-db.mjs`, which use one-shot `ownedDbPath()` uid checks with no time-based liveness window because they read completed SQLite records rather than tailing a potentially-orphaned live lock. This confirms Phase 50's generic LSL primitives (`lib/lsl/window.mjs`, `lib/lsl/scan-and-convert.mjs`) were deliberately not reused, since no sibling module needed an equivalent liveness distinction.

## Implementation Details

`findLiveLockFile(sessionDir)` is a pure function of two inputs: `Date.now()` and `fs.statSync` results. It cannot distinguish "session idle 11 minutes between turns" from "process hard-crashed 11 minutes ago" — both yield an identical `null` return and both are silently excluded from the live-session list. This is a precision/recall trade-off compressed into a single constant: shortening `LOCK_STALE_GRACE_MS` risks false negatives (dropping legitimately idle-but-live sessions), while lengthening it risks false positives (tailing a dead session's lock well past actual death). There is no mid-run adaptive signal — no re-check after an initial miss, no PID-alive probe — to recover from either failure mode.

The constant itself is a magic number, justified only by an inline comment, with no config or environment override — tying operational tuning to a code edit and redeploy. This is compounded by `isOwnedByMe()`'s platform-dependent behavior (sibling UidOwnershipGuard): on non-POSIX platforms it returns `true` unconditionally (`if (myUid == null) return true;`), making the uid gate a no-op on Windows. In that scenario, LockStaleDetection's mtime-freshness window becomes the *sole* remaining discriminator between the current user's sessions and any other session directory physically present under `sessionStateDir` — a security responsibility the timing heuristic was never designed to bear.

Because `scanForLiveSessions()` re-reads the directory (`fs.readdirSync`) and re-stats every candidate lock (`fs.statSync`) on every invocation, the "fresh vs. stale" answer for a given session can flip between two consecutive scans with no transition event recorded anywhere.

## Integration Points

LockStaleDetection sits directly upstream of, and gatekeeps, the entire degraded-parity pipeline described by sibling DegradedParityStub: a session judged stale is excluded from `scanForLiveSessions()`'s return list before `tailEventsFile`, `buildStubObservation()`, or `lsl_incomplete` stamping ever run for it. This makes the 10-minute grace window not merely a liveness heuristic but a data-loss amplifier — a crashed session's final `subagent.failed` event in events.jsonl may never be tailed once the window elapses, compounding the already-accepted "inner reasoning FOREVER LOST" gap (per parent CopilotLiveTail) with a second, narrower gap on the lifecycle bookends themselves.

It also composes directly with sibling ProjectFiltering and UidOwnershipGuard within `scanForLiveSessions()`'s gate sequence, and is one of the module's several fail-permissive vs. fail-closed asymmetries alongside `isOwnedByMe()`'s non-POSIX/stat-failure split.

## Usage Guidelines

Treat `LOCK_STALE_GRACE_MS` as an operational tuning knob currently baked into code — any change requires a redeploy, and adjustments should be weighed explicitly against the false-negative/false-positive trade-off described above. Developers debugging missing live sessions should be aware that stale-lock drops produce no stderr signal, unlike non-owned-session drops; adding logging parity here would materially improve debuggability. On Windows deployments, do not rely on `isOwnedByMe` for isolation — the staleness window is effectively the only session discriminator, so OS-level ACLs must carry the security burden. Finally, any future work on crash-detection precision should consider a direct liveness signal (e.g., PID-alive check) rather than further tuning the grace constant, since the current design has no adaptive fallback if the mtime heuristic guesses wrong.
