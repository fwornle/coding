# FeatureGatingOverride — Technical Insight Document

## What It Is

FeatureGatingOverride is the mechanism by which feature enablement decisions are translated into concrete runtime behavior across two distinct execution boundaries: the containerized supervisord runtime and the host Node.js orchestrator. It manifests in two parallel implementations: `docker/entrypoint.sh`, which regenerates `/etc/supervisor/features.d/disabled.conf` on every container boot, and `scripts/start-services-robust.js`, whose `startOneService()` function consults a live `loadFeatures()` result to decide whether a host-spawned service should run. As the parent entity APIServiceWrapper's description makes clear, this is fundamentally an override layer sitting *on top of* pre-existing static configuration (supervisord.conf's `[program:...]` blocks) rather than a rewrite of that configuration — the gate only ever emits `autostart=false` stanzas, never touches command/logging definitions.

## Architecture and Design

The dominant pattern is an **additive override/decorator** approach: `docker/entrypoint.sh` does `rm -f "$FEATURES_DIR"/*.conf` and rebuilds `features.d/disabled.conf` from scratch every boot rather than diffing against prior state, keeping the override surface deliberately small and stateless. This pairs with a **snapshot/live-object duality** at the process boundary — the container consumes a flat, pre-resolved `/coding/.coding/runtime/features.json` snapshot (as also described by sibling ApiServiceChildWrapper, which frames entrypoint.sh as a pure translation layer, not a decision-maker), while the host consumes a richer `{features, enabled, disabled, warnings}` object with per-feature `.reason`/`.source`. This split is not a stylistic choice but a **deployment-boundary constraint**: `~/.coding/features.yaml` lives on the host and is never mounted into the container, so the container is structurally incapable of being its own source of truth.

The most striking design decision is the **asymmetric failure philosophy** between the two halves. The container path is fail-open at every layer — unknown feature, missing snapshot, and JSON parse errors all default to "enabled" — because a container that silently runs nothing is harder to diagnose than one that runs too much. The host path, exercised by `tests/features/service-gating.test.mjs`, is fail-loud: an unknown feature identifier causes `startOneService()` to reject explicitly. Same concept, opposite blast-radius reasoning: boot-time robustness versus developer-facing correctness.

A secondary pattern is **legacy escape-hatch retention**: `start-services.sh`'s `ROBUST_MODE` branch `exec`s into `start-services-robust.js` under default configuration, making ~150 lines of legacy bash (docker-compose polling, manual Qdrant/Redis fallback, the "DOCKER NOT RUNNING" banner) dead code that is nonetheless kept rather than deleted.

## Implementation Details

In `docker/entrypoint.sh`, the `PROGRAM_FEATURES` string (`semantic-analysis:knowledge embedding-listener:knowledge graphify:codegraph constraint-monitor:constraints ...`) is split via bash parameter expansion (`${pair%%:*}` / `${pair##*:}`) into program/feature pairs. Enablement is resolved by a throwaway `node -e` one-liner — chosen over jq specifically because jq isn't installed in the image while node already is. That one-liner stacks three independent fail-open mechanisms: optional chaining (`snap.features?.[feature]`), a strict `value === false ? "false" : "true"` check that treats anything besides literal `false` (including `undefined`) as enabled, and a bash-level `|| echo "true"` wrapping the whole invocation so a corrupt snapshot degrades to "enabled" rather than crashing under `set -e`.

On the host side, `SERVICE_CONFIGS` entries in `start-services-robust.js` each declare a mandatory `feature` field, validated structurally by `tests/features/service-gating.test.mjs`'s "every service declares a feature" and "every declared feature is a real one" tests, which cross-check against `FEATURE_IDS` imported from `lib/features/catalogue.cjs`. The test suite's `featureSet()` helper constructs synthetic `loadFeatures()`-shaped output, stamping a `reason` string (`'on — test'`/`'off — test'`) into every entry to preserve the project-wide convention that every gating decision carries a human-readable reason for CLI/status-line/dashboard consumption. The suite also enforces the `disabled` vs. `degraded` status taxonomy (intent-off vs. wanted-but-broken) and ordering invariants like `SERVICE_ORDER[0:2]` for `transcriptMonitor`/`liveLoggingCoordinator`.

## Integration Points

FeatureGatingOverride sits directly beneath its parent APIServiceWrapper and alongside sibling ApiServiceChildWrapper, both of which describe entrypoint.sh's role as consumer of the host-resolved snapshot. It depends on an external, unspecified host process to write `/coding/.coding/runtime/features.json` before container start — a coupling the entrypoint's own comments acknowledge explicitly. On the host side it integrates with `lib/features/catalogue.cjs` (FEATURE_IDS) and the broader feature-resolution pipeline (`config/features.yaml` → `~/.coding/features.yaml` → `CODING_FEATURE_*` env vars) that ApiServiceChildWrapper attributes to `loadFeatures()`. Two independently-maintained catalogues — the bash `PROGRAM_FEATURES` string and the JS `SERVICE_CONFIGS` object — encode the same feature-to-process mapping for their respective runtimes, each validated by its own CI test (`tests/features/container-gating.test.mjs` and `tests/features/service-gating.test.mjs`) but with no shared schema linking them.

## Usage Guidelines

Developers adding a new gated program or service must update both catalogues independently: the `PROGRAM_FEATURES` string in `docker/entrypoint.sh` and `SERVICE_CONFIGS` in `start-services-robust.js`, each accompanied by its own coverage test. When adding a container program, remember the fail-open contract is intentional — do not "fix" the `node -e` fallback chain to fail closed, as it exists precisely so an unresolvable snapshot doesn't block supervisord from starting. Conversely, host-side services must preserve fail-loud behavior on unknown feature IDs; silently defaulting an unrecognized `feature` string to on or off would mask a real config typo. Any new gating decision surfaced to callers should include a `reason` string to honor the CLI/status-line/dashboard contract mirrored in `featureSet()`. Finally, resist reflexively deleting `start-services.sh`'s legacy branch or the stale Docker-down banner — while dead under default `ROBUST_MODE=true`, it's retained as a backward-compatibility fallback, though its messaging no longer reflects the current `disabled`/`degraded` status split and should not be treated as accurate documentation.

### Siblings
