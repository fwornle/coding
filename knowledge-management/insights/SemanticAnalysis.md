# SemanticAnalysis — Technical Insight Document

## What It Is

SemanticAnalysis is a component within the Coding root hierarchy responsible for classifying and analyzing code/knowledge artifacts through a multi-stage agent pipeline. Its concrete implementation is spread across `base-agent.ts` (the shared lifecycle framework), `semantic-analysis-agent.ts` (SemanticAnalysisAgent), and `ontology-classification-agent.ts` (OntologyClassificationAgent), with supporting ontology data files `upper.json`, `coding-ontology.json`, and `coding.lower.json`. As a child of Coding, it sits alongside siblings like LiveLoggingSystem, LLMAbstraction, and KnowledgeManagement, and it owns ten child components — Ontology, Pipeline, Insights, OntologyClassificationAgent, SemanticAnalysisAgent, BaseAgentFramework, L2RefinementClassifier, HealthCoordinator, AgentLauncherConfigs, and NoUnboundedFsScanGuard — that together implement classification, tracing, and taxonomy-derivation logic.

## Architecture and Design

The core architectural pattern is a rigid five-stage agent lifecycle enforced by `BaseAgent<TInput, TOutput>`: `process() → calculateConfidence() → detectIssues() → generateRouting() → applyCorrections() → buildMetadata()`, all wrapped in a try/catch that guarantees a standard `AgentResponse` envelope even on failure. This template-method pattern forces every concrete agent — SemanticAnalysisAgent, OntologyClassificationAgent — to implement discrete overrides rather than inlining logic, trading flexibility for structural predictability. A key consequence callers must internalize: confidence/issue/routing fields are always structurally present, but their presence does not imply meaningful analysis occurred, only that the lifecycle completed.

Within OntologyClassificationAgent, classification is a two-stage pipeline: an L1 pass (heuristic/LLM/hybrid) assigns generic classes (Component/SubComponent/Detail), followed by an optional L2 refinement narrowing to ten domain-specific classes from `coding.lower.json`, handled by L2RefinementClassifier's constituent functions (`loadL2Classes()`, `buildL2RefinementPrompt()`, `extractL2FromLLMResponse()`). A hard-root guard intercepts five closed-set hierarchy roots (CollectiveKnowledge, Coding, DynArch, Timeline, Normalisa) before any classifier runs, deliberately preventing LLM drift on foundational taxonomy anchors.

## Implementation Details

The registry resolution chain — `upper.json → coding-ontology.json → coding.lower.json` — is bridged from legacy abstractions (OntologyValidator, OntologyClassifier) to km-core's OntologyRegistry via a `LegacyOntologyAdapter` wrapper, an evolutionary-integration decision rather than a rewrite. Both the L2 extraction and the missing-data paths favor graceful degradation over hard failure: token-boundary regex matching against registered L2 names falls back silently to the L1 parent class on mismatch, and if `coding.lower.json` is missing or incomplete, L2 refinement is simply skipped.

SemanticAnalysisAgent separately implements a debugging mechanism: it writes a per-run "ULTRA DEBUG" trace file to `logs/semantic-analysis-trace-<timestamp>.json`, capturing full gitAnalysis/vibeAnalysis/codeGraphAnalysis input payloads pre-processing. The write is explicitly non-fatal, existing purely to support post-hoc debugging of multi-source correlation without becoming a functional dependency.

## Integration Points

![SemanticAnalysis — Relationship](images/semantic-analysis-relationship.png)

SemanticAnalysis's Insights child feeds an "intent spine" derivation pipeline that clusters insights into Intent entities via aggregate edges (consolidating five prior ad-hoc scripts). This spine depends on the categorical stability of OntologyClassificationAgent's and SemanticAnalysisAgent's L1/L2 output — validated through disjoint-sample re-derivation, where taxonomies are independently re-derived from separate data samples and measured for agreement before being "frozen" as a fixed foundation for downstream KB stages. Any instability here would propagate structural drift to every consumer depending on the spine.

The Pipeline and Ontology children are currently linked by an open defect: the pipeline emits a `CodingLowerOntologySource` reference despite documentation stating this source type should never be produced — a live contract violation near the lower-ontology consumption path in OntologyClassificationAgent or its upstream producers.

## Usage Guidelines

Developers extending agents must implement all five BaseAgent lifecycle stages explicitly and should not assume populated confidence/routing fields indicate real domain analysis. When touching L2 refinement, preserve the graceful-fallback behavior (L1 fallback on unmatched LLM output, skip refinement on missing `coding.lower.json`) rather than introducing hard failures. Do not bypass the hard-root guard for the five foundational roots — doing so risks destabilizing all downstream rooted-path classifications. Given the unresolved CodingLowerOntologySource emission bug, treat that emission path as known-bad rather than spec-compliant. Finally, any change to taxonomy-producing logic in SemanticAnalysisAgent or OntologyClassificationAgent should be validated via disjoint-sample re-derivation before being trusted as a stable spine for downstream KB consumers.
