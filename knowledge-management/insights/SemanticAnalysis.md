# SemanticAnalysis — Technical Insight Document

## What It Is

SemanticAnalysis is a component within the Coding project's development infrastructure, implemented primarily through TypeScript agent classes in the `integrations/semantic-analysis/src/agents/` area — specifically `semantic-analysis-agent.ts`, `ontology-classification-agent.ts`, and the shared `base-agent.ts`. It is responsible for two intertwined responsibilities: classifying code entities into an ontology hierarchy (via OntologyClassificationAgent, which houses the child concept L2SubsystemClassifier) and generating architectural insight by merging heuristic and LLM-derived pattern data (via SemanticAnalysisAgent). As a child of Coding, it draws on the same ontology infrastructure (`Ontology`) that defines sibling components like LiveLoggingSystem declaratively in JSON rather than code.

## Architecture and Design

The dominant architectural pattern is "deterministic-first, LLM-as-fallback," most visible in `classifySingleObservation()`, which checks incoming observation names against a hard-root-guard set (CollectiveKnowledge, Coding, DynArch, Timeline, Normalisa) imported from `@fwornle/km-core`'s `HIERARCHY_ROOTS` before ever invoking the LLM classifier. This defensive design protects structurally critical ontology nodes from probabilistic misclassification cascades.

![SemanticAnalysis — Architecture](images/semantic-analysis-architecture.png)

A second core pattern is the template-method structure enforced by BaseAgent's `execute()`, sequencing `process() → calculateConfidence() → detectIssues() → generateRouting() → applyCorrections() → buildMetadata()` and wrapping results in a standardized `AgentResponse` via `createAgentResponse()`. This lets the orchestrator treat SemanticAnalysisAgent, OntologyClassificationAgent, and the code-graph agent uniformly. Notably, this same philosophy recurs at the shell layer in sibling component CodingPatterns, where agent scripts implement common hooks (`agent_check_requirements`, `agent_pre_launch`, `agent_cleanup`) — evidence of a project-wide convention rather than an isolated choice.

The `Pipeline` child concept reflects this orchestration flow, while `Insights` represents the output of the merge-and-generate stage in SemanticAnalysisAgent.

## Implementation Details

The L2 refinement subsystem, `L2SubsystemClassifier`, is a closed-vocabulary classifier. `loadL2Classes()` filters `registry.classCatalog` down to classes whose `extends` field points to `REFINABLE_L1_PARENTS = ['Component','SubComponent','Detail']`, reading from `.data/ontologies/coding.lower.json` (currently 10 classes: LiveLoggingSystem, EtmDaemon, RapidLlmProxy, ConstraintMonitor, etc.). These are rendered into `buildL2RefinementPrompt()`, constraining the LLM to select from an enumerated set rather than freely generate labels.

Parsing LLM output is handled by `extractL2FromLLMResponse()`, which uses a token-boundary regex (`(^|[^A-Za-z0-9_])name([^A-Za-z0-9_]|$)`) to tolerate verbose responses while rejecting near-miss hallucinations like "EtmDaemonService." On failure to match, it gracefully degrades to the L1 parent class rather than failing outright.

SemanticAnalysisAgent merges heuristic pattern detectors (~10 regex/AST-based checks) with LLM-discovered patterns from `semanticInsights.keyPatterns`, deduplicating via a lowercased Set before appending to `codeAnalysis.architecturalPatterns`. Before analysis runs, it writes a full snapshot of `gitAnalysis`, `vibeAnalysis`, and `codeGraphAnalysis` to `logs/semantic-analysis-trace-<timestamp>.json`, a non-fatal operation supporting reproducibility and debugging.

## Integration Points

![SemanticAnalysis — Relationship](images/semantic-analysis-relationship.png)

SemanticAnalysis integrates tightly with the Ontology child component via `OntologyRegistry` and the JSON files `upper.json`, `coding-ontology.json`, and `coding.lower.json` — the same chain sibling LiveLoggingSystem relies on for its own L2 registration. It depends on `@fwornle/km-core` for `HIERARCHY_ROOTS`. BaseAgent provides the uniform contract consumed by the orchestrator, connecting SemanticAnalysisAgent, OntologyClassificationAgent, and the code-graph agent into one pipeline. The test suite (`ontology-classification-agent.test.ts`) integrates with real ontology files copied into tmpdir-isolated fixtures, exercising the full OntologyRegistry/OntologyClassifier chain end-to-end.

## Usage Guidelines

New L2 classes must be added to `.data/ontologies/coding.lower.json` before the classifier can assign them — the LLM cannot invent new SubComponent types. Any new agent joining the pipeline need only implement `process()` and confidence/issue-detection hooks to conform to BaseAgent's contract. Developers modifying ontology-driven classification should update the hard-root-guard set cautiously, given its role in preventing hierarchy corruption. When debugging unexpected pattern-detection or insight-generation results, consult the timestamped trace files in `logs/` before re-running expensive LLM-backed analysis. Fixture updates in the test suite must be manually synced whenever production ontology JSON structure changes, since fixtures are copies, not live references.

This design avoids needing separate health-monitoring logic for containerized vs local services, but it also means Docker-specific failures (e.g., supervisord misconfiguration killing a service inside the container) surface identically to host-side crashes, requiring log inspection to disambiguate.

This file, a NetworkX node-link JSON export, can be tens of megabytes, so GraphifyGraph implements mtime-based lazy caching — it stat()s the file and only re-parses when the mtime has changed since the last load. This pattern trades real-time graph mutation capability for drastically simpler deployment (no separate DB process) and fast repeated reads, at the cost of only picking up graph changes when the underlying analysis pipeline re-writes graph.json.
