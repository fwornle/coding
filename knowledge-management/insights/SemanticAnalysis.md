# SemanticAnalysis — Technical Insight Document

## What It Is

SemanticAnalysis is a batch-analysis component implemented as a multi-agent pipeline, with its core logic residing in `semantic-analysis-agent.ts` and `ontology-classification-agent.ts`. As a child component under the Coding project's knowledge hierarchy, it is responsible for extracting structured knowledge entities from raw inputs — specifically git history diffs/commits and LSL session logs — and then classifying those entities into a hierarchical ontology. The stated pipeline goal, "persist structured knowledge entities," positions this component not merely as a transformation stage but as a producer of data destined for a broader knowledge-graph persistence layer, likely the same graph-based storage described in the project's memory-systems architecture and fronted by the sibling KnowledgeManagement component's VKB server.

## Architecture and Design

The defining architectural pattern here is separation of concerns via a multi-agent workflow rather than a monolithic analyzer. Extraction and classification are deliberately split into two dedicated agent classes, each with a narrower, more testable prompt/response contract against the underlying LLM. This decomposition maps directly onto SemanticAnalysis's own child components: Pipeline (extraction) and Ontology (classification), each further broken into ordered sub-steps — Pipeline's `parse → extract → relate → enrich` and Ontology's `match → validate → extend`, as defined in `AGENT_SUBSTEPS` within `multi-agent-graph.tsx`. A third child, Insights, extends this chain with a `patterns` sub-step (tagged `llmUsage: 'premium'`) that consumes the Code entities and Relations produced upstream to generate Pattern instances — showing the pipeline's output feeding forward into higher-order analysis.

## Implementation Details

`semantic-analysis-agent.ts` must reconcile two structurally distinct input formats — structured commit/diff data and conversational/event-based LSL session logs — into a unified entity extraction schema, implying an internal normalization/adapter layer that developers should locate before assuming a single input shape. Its output feeds `ontology-classification-agent.ts`, which determines parent-child relationships and where each entity fits within the broader ontology.

Notably, hierarchy-root detection is treated as a distinct code path within the classification agent, evidenced by a dedicated test file, `ontology-classification-agent.hierarchy-roots.test.ts`, separate from the general `ontology-classification-agent.test.ts`. This suggests root-node classification (entities with no parent) requires different prompting or heuristic validation than mid-tree classification, and any change to root-detection logic must satisfy both suites since regressions could corrupt the top of the ontology tree and cascade incorrect groupings downward.

## Usage Guidelines

Developers extending the pipeline with a new stage should study `base-agent.ts` first to honor its interface contract before writing agent-specific logic, since deviating breaks polymorphic orchestration. Changes to root-detection conditionals in classification require updating both the general and hierarchy-roots test suites. The established testing convention — isolating edge-case behavior (root detection) into dedicated, descriptively-named test files rather than folding it into mainline suites — should be followed for new edge cases like orphaned entities, circular references, or duplicate hierarchy roots. Finally, any schema changes to extracted or classified entities must be coordinated with downstream persistence consumers to prevent silent data corruption across the knowledge graph.

It is built around a unified hook architecture that merges user-level (~/.coding-tools/hooks.json) and project-level (.coding/hooks.json) configurations, with project config taking precedence, and dispatches events (pre-tool, post-tool, pre-prompt, post-prompt, startup, shutdown, error) to registered handlers of type script, command, or module.

Core orchestration lives in UnifiedHookManager (lib/agent-api/hooks/hook-manager.js), which maintains a Map of event names to sorted handler arrays (by priority), supports duplicate-ID overwrite semantics, and exposes registerHandler/unregisterHandler APIs bridging agent-native hook systems to a common HookEvent enum. Configuration parsing and structural validation is handled separately by HookConfigLoader (lib/agent-api/hooks/hook-config.js), which loads, merges, and validates settings/hooks blocks, logging warnings (not throwing) on malformed entries.

Violation detection results are captured and persisted via ViolationCaptureService (scripts/violation-capture-service.js), which writes JSONL violation records to .mcp-sync/session-violations.jsonl and maintains an aggregated violation-history.json with session tracking and computed statistics (severity breakdowns, most common constraint, average violations per session) for dashboard consumption. Sensitive parameter values are redacted before being written to logs, and history is capped at 1000 entries to bound file growth.
