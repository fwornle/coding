# SemanticAnalysis

**Type:** Component

SemanticAnalysis is a multi-agent pipeline (integrations/semantic-analysis/src/agents/) that processes git history and LSL session data to extract, classify, and persist structured knowledge entities into the ontology-backed knowledge graph. It orchestrates specialized agents extending BaseAgent (base-agent.ts) which wrap agent-specific logic in a standardized AgentResponse envelope, computing confidence breakdowns, detecting issues, and generating routing suggestions for retry/escalation between workflow steps.

At its core, OntologyClassificationAgent (ontology-classification-agent.ts) assigns ontology metadata (class, confidence, method) to observations by combining heuristic classifiers, an LLM-backed OntologyClassifier, and hard-coded hierarchy-root guards for closed-set entities (CollectiveKnowledge, Coding, DynArch, Timeline, Normalisa) imported from @fwornle/km-core's HIERARCHY_ROOTS. A newer L2 refinement layer (Phase 57/60) further refines generic L1 classes (Component/SubComponent/Detail) into specific subsystem classes declared in coding.lower.json, using pure, independently-testable helper functions (loadL2Classes, buildL2RefinementPrompt, extractL2FromLLMResponse) alongside a deterministic keyword-based fallback classifier (l2-subsystem-classifier.ts).

The SemanticAnalysisAgent (semantic-analysis-agent.ts) performs the actual code/git/vibe cross-analysis, reading files from git history, computing complexity metrics and architectural pattern detection, and invoking an LLM (via @rapid/llm-proxy's LLMService) to generate deeper semantic insights that are merged with heuristically-detected patterns. The pipeline emphasizes testability (extensive node:test suites with tmpdir-isolated ontology fixtures) and graceful degradation (e.g., absent coding.lower.json yields empty L2 refinement rather than errors), reflecting an incremental, plan-driven development process (Phase 42/57/60 markers throughout the code).

# SemanticAnalysis — Technical Insight Document

## What It Is

SemanticAnalysis is a multi-agent pipeline implemented in `integrations/semantic-analysis/src/agents/`, responsible for processing git history and LSL (Live Session Logging) session data to extract, classify, and persist structured knowledge entities into the ontology-backed knowledge graph. As a child component of the Coding root, it sits alongside sibling subsystems (LiveLoggingSystem, LLMAbstraction, DockerizedServices, KnowledgeManagement, CodingPatterns, ConstraintSystem) as one of the seven major pillars of the development infrastructure, but is distinct in that its core purpose is turning raw development activity (commits, sessions, vibe/code cross-analysis) into ontology-classified entities rather than serving logs, LLM routing, or health checks.

The component is organized into six child components — Pipeline, Ontology, Insights, BaseAgent, L2SubsystemClassifier, and LegacyOntologyAdapter — each representing a distinct concern in the classification workflow, from standardized agent execution to ontology hierarchy enforcement.

## Architecture and Design

The architecture follows a layered agent pipeline pattern rooted in `BaseAgent` (`base-agent.ts`), which defines a uniform execution contract: `execute() -> process() -> calculateConfidence() -> detectIssues() -> generateRouting() -> applyCorrections() -> buildMetadata()`. Every specialized agent — notably `OntologyClassificationAgent` and `SemanticAnalysisAgent` — extends this base, ensuring that regardless of internal logic, outputs are wrapped in a standardized `AgentResponse` envelope carrying confidence breakdowns, detected issues, and routing suggestions for retry/escalation between workflow steps. This is a classic template-method pattern applied at the pipeline-orchestration level, and it's the mechanism by which the child component Pipeline and BaseAgent relate: Pipeline agents literally *are* BaseAgent subclasses.

A second key pattern is the combination of heuristics, LLM inference, and hard-coded guards for classification safety. `OntologyClassificationAgent` (`ontology-classification-agent.ts`) — the implementation behind the Ontology child component — blends heuristic classifiers with an LLM-backed `OntologyClassifier`, but short-circuits LLM involvement entirely for the five `HIERARCHY_ROOTS` entities (CollectiveKnowledge, Coding, DynArch, Timeline, Normalisa) imported from `@fwornle/km-core`. This "hard-root-guard" design decision (`classificationMethod='hard-root-guard'`) reflects a deliberate trade-off: sacrificing LLM flexibility at the topmost ontology tier to eliminate classification drift for structurally load-bearing entities.

Layered atop this is the L2 refinement subsystem (Phase 57/60), realized in the L2SubsystemClassifier child component. This adds a second classification pass that narrows generic L1 classes (Component/SubComponent/Detail — the `REFINABLE_L1_PARENTS`) into specific subsystem classes declared in `coding.lower.json`. The design favors pure, independently-testable functions over stateful classes, and includes a deterministic keyword-based fallback (`l2-subsystem-classifier.ts`) so LLM failures or missing config degrade gracefully rather than breaking the pipeline — consistent with the project's explicit "graceful degradation" philosophy.

## Implementation Details

`OntologyClassificationAgent.classifySingleObservation()` is the entry point for per-observation classification, checking observation names against `HIERARCHY_ROOTS` before falling through to heuristic/LLM classification. The L2 refinement layer decomposes cleanly into three pure functions: `loadL2Classes()` (reads and filters `coding.lower.json`), `buildL2RefinementPrompt()` (constructs the LLM prompt), and `extractL2FromLLMResponse()` (parses the model's output). Notably, `extractL2FromLLMResponse()` uses token-boundary regex matching (`escapeRegex` plus word-boundary lookalikes) specifically to avoid false-positive substring matches — e.g., preventing `'SuperEtmDaemonX'` from incorrectly resolving to `'EtmDaemon'`. This is a small but telling detail about the rigor applied to string-matching correctness in classification logic.

`OntologyClassificationAgent` also constructs an `OntologyRegistry` from `@fwornle/km-core` directly and wraps it with `LegacyOntologyAdapter` (`ontology/LegacyOntologyAdapter.ts`), a post-Phase-42-03 refactor decision that preserves compatibility with the pre-existing `OntologyValidator`/`OntologyClassifier` interfaces rather than requiring a disruptive rewrite of consumers — an adapter pattern shared conceptually with idioms cataloged under the sibling CodingPatterns component.

On the analysis side, `SemanticAnalysisAgent` (`semantic-analysis-agent.ts`) performs the actual code/git/vibe cross-analysis: reading files from git history, computing complexity metrics, detecting architectural patterns, and invoking an LLM via `@rapid/llm-proxy`'s `LLMService` (wrapped with `attachTokenLogger()` for token usage tracking and lazily initialized through `ensureLLMInitialized()`). Its `analyzeGitAndVibeData()` method supports tiered analysis depth — `'surface'` mode limits analysis to 5 files and skips cross-analysis entirely for speed, while `'deep'`/`'comprehensive'` modes perform fuller analysis — a scalability lever trading insight depth for latency/cost.

## Integration Points

SemanticAnalysis integrates with `@fwornle/km-core` for `HIERARCHY_ROOTS` and `OntologyRegistry`, forming the backbone of ontology-aware classification. It depends on `@rapid/llm-proxy`'s `LLMService` for all LLM-backed inference, both in `OntologyClassificationAgent`'s heuristic/LLM hybrid classifier and in `SemanticAnalysisAgent`'s deeper semantic insight generation — linking it to the broader LLMAbstraction sibling component's provider-agnostic LLM infrastructure, though SemanticAnalysis consumes this through the proxy layer rather than directly. The `coding.lower.json` configuration file is a critical external dependency for L2 subsystem refinement; its absence is explicitly handled as a non-error (empty refinement result), reinforcing the graceful-degradation contract. Internally, the pipeline's BaseAgent contract is the primary integration seam allowing new agents to be added to the pipeline without altering orchestration logic, since all agents produce a uniform `AgentResponse`.

## Usage Guidelines

Developers extending this component should route all new agent logic through `BaseAgent` to preserve the uniform `AgentResponse` envelope and confidence/routing semantics — bypassing this contract would break pipeline orchestration assumptions. When adding new ontology classes, respect the closed-set nature of `HIERARCHY_ROOTS`: these five entities are intentionally excluded from LLM-based classification and should not be extended casually, as the hard-root-guard exists specifically to prevent drift at the top of the hierarchy. For L2 subsystem work, new refinable classes should be added via `coding.lower.json` rather than hardcoded, and any new extraction logic should preserve token-boundary matching discipline (as in `extractL2FromLLMResponse()`) to avoid substring false positives. Given the extensive `node:test` suites using tmpdir-isolated ontology fixtures (e.g., `ontology-classification-agent.hierarchy-roots.test.ts`), new behavior should be accompanied by similarly isolated tests. Finally, be mindful of the analysis-depth trade-off in `SemanticAnalysisAgent`: choose `'surface'` depth for fast/cheap runs and reserve `'deep'`/`'comprehensive'` modes for cases where full cross-analysis fidelity is required, since surface mode intentionally truncates file coverage and skips cross-analysis.
