# LLMMockService — Technical Insight Document

## What It Is

LLMMockService is implemented in `llm-mock-service.ts` as part of the **LLMAbstraction** subsystem, providing a persisted, runtime-switchable mock/local/public mode toggle for LLM calls. Rather than relying on environment variables that require a process restart, it stores state in `.data/workflow-progress.json`, with an `LLMState` structure exposing `globalMode` and `perAgentOverrides` fields. This enables fine-grained testing scenarios — for example, forcing a single agent into mock mode while the rest of a multi-agent pipeline continues to hit real providers, avoiding API cost and non-determinism during targeted integration tests.

The centerpiece of the design is `getLLMMode()`, a three-tier precedence resolver: `perAgentOverrides` → `globalMode` → legacy `progress.mockLLM` boolean. This ordering is not incidental — it is the same architectural instinct repeated throughout the codebase whenever multiple signals could plausibly govern one decision.

## Architecture and Design

The defining pattern across LLMMockService and its children is **config-vs-runtime state separation**: a declared/enabled value is kept distinct from an observed/reachable value. This is most explicitly realized in child components **JudgeBackendEnabledReachableSplit** and **ClassifierJudgeDraftReconciliation**, both derived from `use-classifier-judge.ts`'s `JudgeBackend` interface, which hard-codes `enabled: boolean` separately from `reachable: boolean | null`. The header comment documents a real incident (2026-09-02) where a dead backend remained `enabled: true` for roughly a day, with every classified turn silently falling back to `gh-copilot/claude-sonnet-5` — the exact ambiguity that LLMMockService's precedence chain is structurally designed to prevent by never collapsing multiple signals into a single boolean.

This same instinct for multi-tier precedence recurs in sibling and related logic: `model-limits.cjs`'s `catalogueContextWindow()` resolves context window size via user config → `byPair` cache → `byModel` fallback → null, motivated by a production incident where a 188K-token session rendered as 94% red instead of 19% green. `cost-model.ts`'s `priceForModel()` similarly favors a deterministic `FAST_MODE_MULTIPLIER` rule over hand-maintained twin price rows, avoiding silent staleness. These are not independent inventions but a house convention: prefer explicit, documented precedence chains over flattened lookups or single-boolean collapses.

A second recurring pattern is **dual-write/overlay-rather-than-migrate** state evolution. LLMMockService's `setGlobalLLMMode()` retains the legacy `progress.mockLLM` flag as a compatibility shim rather than migrating history, mirrored by `cost-model.ts`'s `monthlyEurByMonth`, which overlays per-month budget overrides atop a standing `monthlyEur` value so historical months remain interpretable against the budget that existed at the time.

## Implementation Details

`getLLMMode()`'s read path is deliberately explicit about precedence rather than implicit: it inspects `perAgentOverrides` first (agent-specific forcing), falls back to `globalMode` (system-wide toggle), and only then consults the legacy `progress.mockLLM` boolean for backward compatibility. Any new developer must understand this chain before assuming a single toggle governs behavior — a caution reinforced by the analogous incident narrative in `use-classifier-judge.ts`, where collapsing `enabled` and `reachable` into one signal masked failure for an extended period.

The retirement of compatibility shims is itself a documented concern: `cost-model.ts`'s `freshInputTokens()` is a named identity function kept purely as documentation, warning that "a compensation for a defect must be removed when the defect is" — directly analogous to the risk that LLMMockService's legacy `progress.mockLLM` dual-write must eventually be retired rather than left to silently double up with `globalMode`/`perAgentOverrides`.

## Integration Points

LLMMockService sits within **LLMAbstraction** alongside siblings **DMRProvider**, **LLMProxyClient**, **LlmJsonParser**, **DashboardCostModel**, **OffloadRoutingDecision**, **ModelContextLimits**, and **AgentProviderSplicing**. While these siblings address different concerns (DMRProvider's OpenAI-shape protocol reuse, LLMProxyClient's control-plane/data-plane split, LlmJsonParser's two-stage malformed-JSON recovery, DashboardCostModel's pure-function cost math), they share LLMMockService's underlying design vocabulary: explicit precedence chains, config-vs-runtime separation, and caching-behind-identity-checks (as seen in `model-limits.cjs`'s mtime+size cache and DMR's `checkDMRAvailability()`).

The boundary discipline is also structural: `offload-decision.tsx` keeps `use-offload-policy-draft` and `use-classifier-judge.ts` writing to two separate files (`llm-routing.yaml` vs `config/prompt-classifier.yaml`) so an unrelated config error doesn't corrupt a different toggle — the same separation logic that keeps LLMMockService's runtime mock state (`globalMode`/`perAgentOverrides`) distinct from provider configuration files like `dmr-config.yaml`. Separately, `store/provider.tsx` establishes that dashboard-side consumers of this state live inside a centralized Redux store, not component-local state.

## Usage Guidelines

Developers modifying or consuming LLMMockService should never assume a single flag controls mock behavior — always trace through the `perAgentOverrides` → `globalMode` → legacy `progress.mockLLM` chain. When introducing new override tiers or config layers elsewhere in the system, follow the established convention of keeping declared state and observed/runtime state as distinct, independently-nullable fields (as `JudgeBackendEnabledReachableSplit` demonstrates) rather than collapsing them, since collapsing has caused real incidents. Any compatibility shim (like the legacy `progress.mockLLM` flag) should be tracked with the expectation of eventual retirement, and its removal should be coordinated carefully to avoid the double-compensation failure mode documented in `freshInputTokens()`. Finally, configuration that changes for different reasons should be persisted and saved through separate paths, even if presented together in a UI — mirroring the offload-policy/classifier-judge file split.
