# ConstraintSystem

**Type:** Component

The ConstraintSystem provides rule-based validation and enforcement for tool calls and file operations during Claude Code sessions, plus a hook infrastructure that lets agent-agnostic events (pre-tool, post-tool, startup, shutdown, etc.) trigger scripts, commands, or modules. It is composed of a hook configuration layer (lib/agent-api/hooks/hook-config.js) that loads and merges user-level (~/.coding-tools/hooks.json) and project-level (.coding/hooks.json) configs, and a central UnifiedHookManager (lib/agent-api/hooks/hook-manager.js) that registers, prioritizes, and dispatches handlers per event across all supported agents. Violations detected during live sessions are captured and persisted via the ViolationCaptureService (scripts/violation-capture-service.js), which writes JSONL logs and maintains rolling statistics for dashboard consumption.

Architecturally, the system favors a layered configuration-merge pattern (defaults → user → project) with validation warnings rather than hard failures, and a priority-sorted handler registry keyed by event name. Constraint violations flow from live session monitoring into a persistent JSON store capped at 1000 entries, with statistics (severity breakdown, most common violation, per-session averages) computed on write. The system also integrates with content/documentation validation (ContentValidationAgent in integrations/semantic-analysis) which, while primarily about entity staleness, shares the same validation-issue/severity taxonomy pattern used elsewhere in constraint reporting, and with the System Health Dashboard's workflow visualization hooks (React-side, distinct from the agent-api hook system) for rendering constraint/violation data.

# ConstraintSystem — Technical Insight Document

## What It Is

ConstraintSystem is a component within the Coding project that provides rule-based validation and enforcement for tool calls and file operations during Claude Code sessions, combined with an agent-agnostic hook infrastructure. It is implemented across four principal files/modules: `lib/agent-api/hooks/hook-config.js` (configuration loading and merging), `lib/agent-api/hooks/hook-manager.js` (the central `UnifiedHookManager`), `scripts/violation-capture-service.js` (the `ViolationCaptureService`), and `integrations/semantic-analysis`'s `ContentValidationAgent`. As a child of the Coding root, it sits alongside sibling components like LiveLoggingSystem, LLMAbstraction, DockerizedServices, KnowledgeManagement, CodingPatterns, and SemanticAnalysis, but is distinguished by its focus on live-session governance rather than logging, containerization, or knowledge storage.

## Architecture and Design

The system's defining architectural pattern is a layered configuration-merge model: defaults defined in `DEFAULT_CONFIG` (hook-config.js) are loaded first, then overridden by user-level config (`~/.coding-tools/hooks.json`), then by project-level config (`.coding/hooks.json`), via `mergeConfigs()`. This mirrors familiar cascading-config patterns but is applied specifically to hook event buckets — startup, shutdown, pre-tool, post-tool, pre-prompt, post-prompt, error — establishing a fixed, predictable set of lifecycle points.

![ConstraintSystem — Architecture](images/constraint-system-architecture.png)

Dispatch is handled by `UnifiedHookManager`, which maintains a `Map<event, HookHandler[]>` and re-sorts handlers by numeric priority after every `registerHandler()` call, guaranteeing deterministic execution order across all supported agents. A notable design trade-off is that `validateConfig()` in hook-config.js only logs warnings rather than throwing exceptions for malformed entries (e.g., missing `handler.type` or `handler.path`) — the system favors operational resilience over strict fail-fast enforcement, a contrast to the fail-fast philosophy seen in sibling LiveLoggingSystem's `validate-lsl-config.js`.

Violation persistence follows a capped, append-only log pattern: `ViolationCaptureService` writes JSONL records incrementally to `.mcp-sync/session-violations.jsonl` and maintains a rolling summary in `.mcp-sync/violation-history.json`, capped at 1000 entries via array slicing. Statistics (severity breakdown, most common violation, per-session averages) are computed synchronously on every write in `calculateStatistics()`, avoiding the need for a separate aggregation job at the cost of doing more work per write.

## Implementation Details

`HookConfigLoader` (hook-config.js) is responsible for locating and merging config from `CONFIG_PATHS.user` and `CONFIG_PATHS.project`, with project config always winning conflicts. `DEFAULT_CONFIG` acts as the schema anchor defining valid event buckets, so any new hook type must be added there to be recognized system-wide.

`UnifiedHookManager` (hook-manager.js) is the dispatch core: its handler registry is priority-sorted per event, ensuring that when multiple handlers are attached to, say, `pre-tool`, execution order is deterministic and reproducible across sessions and agents.

`ViolationCaptureService` (scripts/violation-capture-service.js) includes a security-conscious detail: `sanitizeParams()` redacts sensitive keys (password, token, key, secret, auth) from tool call parameters before persisting violation records, preventing credential leakage into logs — an important safeguard given that raw tool-call parameters could otherwise contain secrets. Its append-only JSONL write pattern avoids costly whole-file rewrites, while the paired `violation-history.json` summary supports fast dashboard reads without re-parsing the full log.

## Integration Points

![ConstraintSystem — Relationship](images/constraint-system-relationship.png)

ConstraintSystem's children — HookConfigLoader, UnifiedHookManager, ViolationCaptureService, and ContentValidationAgent — form a pipeline: configuration is loaded and merged (HookConfigLoader), handlers are registered and dispatched by event (UnifiedHookManager), and resulting violations are captured, sanitized, and persisted (ViolationCaptureService). ContentValidationAgent, while primarily concerned with entity staleness against live codebase state (per its description in integrations/semantic-analysis), shares the same validation-issue/severity taxonomy used elsewhere in constraint reporting, linking it conceptually to the rest of the system despite its different primary purpose.

Downstream, violation data feeds the System Health Dashboard's workflow visualization hooks (a distinct React-side hook system, not to be confused with the agent-api hook system), which renders constraint/violation data for operators. This dual use of the term "hooks" — lifecycle event hooks in agent-api versus React hooks in the dashboard — is a naming overlap worth noting explicitly to avoid confusion during cross-component work.

## Usage Guidelines

When extending hook behavior, developers should add new event types to `DEFAULT_CONFIG` first, since HookConfigLoader and UnifiedHookManager both key off this fixed set of lifecycle points. Because `validateConfig()` only warns on malformed handler entries, developers should not rely on the system to hard-fail on bad config — manual review or additional CI checks are needed to catch silent misconfigurations. When adding new violation types or handlers that touch tool call parameters, use or extend `sanitizeParams()`'s redaction key list to avoid leaking credentials into JSONL logs. Given the 1000-entry cap on stored violations, any long-term analytics needs should pull from `.mcp-sync/session-violations.jsonl` before entries are pruned, rather than relying solely on the rolling `violation-history.json` summary.
