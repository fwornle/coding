# ConstraintSystem: Technical Insight Document

## What It Is

ConstraintSystem is the governance and validation layer of the Coding project, implemented across `lib/agent-api/hooks/hook-config.js` (HookConfigLoader), `lib/agent-api/hooks/hook-manager.js` (UnifiedHookManager), `lib/agent-api/hooks-api.js` (the abstract HooksManager base class underlying KnowledgeInjectionHooks and HealthPromptHook), and `scripts/violation-capture-service.js` (ViolationCaptureService). Its purpose is twofold: enforcing runtime behavioral constraints on tool calls via a hook/handler pipeline, and capturing, sanitizing, and aggregating violations of those constraints for audit and dashboard consumption. As a child of the Coding root, it sits alongside sibling subsystems like SemanticAnalysis and KnowledgeManagement, and notably shares its "validate against ground truth" philosophy with SemanticAnalysis's ContentValidationAgent, which applies the same pattern to knowledge artifacts rather than live tool calls.

## Architecture and Design

![ConstraintSystem — Architecture](images/constraint-system-architecture.png)

The system is built on a layered configuration-and-dispatch architecture. At the configuration layer, HookConfigLoader implements a three-tier cascade — baked-in DEFAULT_CONFIG, user-level `~/.coding-tools/hooks.json`, and project-level `.coding/hooks.json` — merged via `mergeConfigs()`. This lets project-level constraints override user preferences but not the reverse, a deliberate governance-over-personalization design decision.

At the dispatch layer, both UnifiedHookManager and the older HooksManager abstraction in hooks-api.js (parent to KnowledgeInjectionHooks and HealthPromptHook) use a `Map<event, HookHandler[]>` registry pattern, consistently choosing to re-sort handler arrays by priority on every `registerHandler()`/`registerHook()` call rather than sorting lazily at dispatch time. This recurring pattern across both implementations reflects a deliberate trade-off: registration is infrequent (often startup-time), while `triggerHook()`/dispatch is invoked per tool call, so amortizing sort cost onto registration keeps the hot path a cheap linear scan. UnifiedHookManager extends this further with agent-specific scoping, meaning execution order is really "agent-filtered, then priority-sorted" rather than a single global order.

hooks-api.js's HooksManager is explicitly abstract (its constructor throws if instantiated directly), defining `getAgentType()`, `loadNativeHooks()`, and `saveNativeHooks()` as methods concrete subclasses must implement — pushing vendor-specific behavior (Claude's `~/.claude/settings.json` vs. Copilot's `.github/hooks/hooks.json`) out of the core registry and into subclasses.

## Implementation Details

HookConfigLoader's `mergeConfigs()` is not a uniform deep merge — array-type handler lists are concatenated or replaced depending on the key, so extending config schemas requires explicitly checking this logic to avoid silently dropping user-level handlers. UnifiedHookManager's dispatch loop combines agent-identity filtering with priority-based sorting maintained incrementally at registration time.

ViolationCaptureService centers on two functions with distinct responsibilities: `sanitizeParams()`, which redacts values for keys matching password/token/key/secret/auth via string matching before any record hits disk — a hard security boundary that must never be bypassed by writing raw parameters directly to the JSONL log — and `updateViolationHistory()`, which caps `.mcp-sync/violation-history.json` at 1000 entries via array slicing, an FIFO truncation trading historical completeness for bounded disk usage. `calculateStatistics()` layers on top, computing severity breakdowns, most-frequent constraint types, and per-session averages, likely invoked on-demand/scheduled rather than incrementally, so dashboards may reflect slightly stale aggregates.

## Integration Points

![ConstraintSystem — Relationship](images/constraint-system-relationship.png)

ConstraintSystem's four children — HookConfigLoader, UnifiedHookManager, KnowledgeInjectionHooks, HealthPromptHook — form an integrated pipeline: config loading feeds handler registration, which feeds prioritized, agent-scoped dispatch. The hooks-api.js abstraction is the shared foundation underneath KnowledgeInjectionHooks and HealthPromptHook, mirroring UnifiedHookManager's registry design but at a more generic, older layer. Architecturally, ConstraintSystem parallels sibling SemanticAnalysis's ContentValidationAgent, which cross-checks knowledge-base references against the filesystem using a GitStalenessDetector cache (`cachedGitCommits`, 60-second TTL) — the same "validate claims against ground truth" principle applied to documentation instead of runtime tool calls.

## Usage Guidelines

Developers adding new hook types must inspect `mergeConfigs()` to understand array-handling semantics before assuming deep-merge behavior. Anyone routing tool parameters through violation capture must go through `sanitizeParams()` — never write directly to the JSONL log. Given the 1000-entry FIFO cap on violation history, this file should not be treated as a long-term audit trail. Since `calculateStatistics()` may not update per-violation, real-time monitoring built atop it should account for potential staleness. Finally, because insertion order is irrelevant to both UnifiedHookManager and HooksManager dispatch — only priority (and agent scope) matters — new handlers must set priority values deliberately rather than relying on registration sequence.

This duality means developers must understand that 'starting a service' has two entirely separate code paths depending on deployment target, and that health-checking logic (service-probe.js) is written to be agnostic to which path is in effect — it only cares about HTTP/TCP reachability, not process ownership. This design avoids needing separate health-monitoring logic for containerized vs local services, but it also means Docker-specific failures (e.g., supervisord misconfiguration killing a service inside the container) surface identically to host-side crashes, requiring log inspection to disambiguate.

This file, a NetworkX node-link JSON export, can be tens of megabytes, so GraphifyGraph implements mtime-based lazy caching — it stat()s the file and only re-parses when the mtime has changed since the last load. This pattern trades real-time graph mutation capability for drastically simpler deployment (no separate DB process) and fast repeated reads, at the cost of only picking up graph changes when the underlying analysis pipeline re-writes graph.json.

This lets the rest of the system (e.g., wave-controller.ts or any dispatcher invoking these scripts) remain agnostic to which underlying agent CLI is actually installed—new agents can be onboarded by adding a new script that satisfies the same contract rather than modifying core dispatch logic, as described in docs/architecture/adding-new-agent.md.
