# ConstraintSystem

**Type:** Component

The ConstraintSystem provides rule-based validation and enforcement of code actions and file operations during Claude Code sessions, spanning hook configuration loading, hook dispatch orchestration, and violation capture/persistence. It is built around a unified hook architecture that merges user-level (~/.coding-tools/hooks.json) and project-level (.coding/hooks.json) configurations, with project config taking precedence, and dispatches events (pre-tool, post-tool, pre-prompt, post-prompt, startup, shutdown, error) to registered handlers of type script, command, or module.

Core orchestration lives in UnifiedHookManager (lib/agent-api/hooks/hook-manager.js), which maintains a Map of event names to sorted handler arrays (by priority), supports duplicate-ID overwrite semantics, and exposes registerHandler/unregisterHandler APIs bridging agent-native hook systems to a common HookEvent enum. Configuration parsing and structural validation is handled separately by HookConfigLoader (lib/agent-api/hooks/hook-config.js), which loads, merges, and validates settings/hooks blocks, logging warnings (not throwing) on malformed entries.

Violation detection results are captured and persisted via ViolationCaptureService (scripts/violation-capture-service.js), which writes JSONL violation records to .mcp-sync/session-violations.jsonl and maintains an aggregated violation-history.json with session tracking and computed statistics (severity breakdowns, most common constraint, average violations per session) for dashboard consumption. Sensitive parameter values are redacted before being written to logs, and history is capped at 1000 entries to bound file growth.

# ConstraintSystem: Technical Insight Document

## What It Is

The ConstraintSystem is a rule-based validation and enforcement subsystem for Claude Code sessions, implemented across three primary files: `lib/agent-api/hooks/hook-manager.js` (orchestration), `lib/agent-api/hooks/hook-config.js` (configuration loading), and `scripts/violation-capture-service.js` (violation persistence). As a child of the Coding project's root hierarchy, it sits alongside siblings like LiveLoggingSystem, LLMAbstraction, DockerizedServices, KnowledgeManagement, CodingPatterns, and SemanticAnalysis as one of the seven major infrastructure components. Its function is to intercept and validate code actions and file operations at defined lifecycle points, dispatching events (pre-tool, post-tool, pre-prompt, post-prompt, startup, shutdown, error) to registered handlers, and to durably record any detected violations for later analysis.

## Architecture and Design

The system's core architectural pattern is a **unified hook dispatch model** built around `UnifiedHookManager`, which bridges disparate "agent-native hook systems" into a common `HookEvent` enum and handler interface (script, command, or module type). This is a classic mediator/registry pattern: rather than tools directly coupling to validation logic, they emit events into a central Map<event, HookHandler[]>, decoupling producers of actionable events from consumers that enforce constraints.

![ConstraintSystem — Architecture](images/constraint-system-architecture.png)

Configuration follows a **two-tier override pattern** — user-level (`~/.coding-tools/hooks.json`) loaded first, then project-level (`.coding/hooks.json`) applied second via `mergeConfigs`/`applyConfig`, with project settings taking precedence. This mirrors common layered-config conventions (e.g., global vs. local git config) and is explicitly implemented in `HookManager`'s `initialize(projectPath)`, which calls `loadConfig(userConfigPath, 'user')` followed by `loadConfig(projectConfigPath, 'project')`.

Violation handling is architecturally separated from detection/dispatch: `ViolationCaptureService` is a distinct persistence layer, decoupled from the hook orchestration logic, following a **write-ahead log + aggregate view** split — an append-only JSONL stream paired with a computed rolling summary file for dashboards.

## Implementation Details

`UnifiedHookManager` initializes a `Map` entry for every `HookEvent` enum value up front, ensuring lookups never require existence checks. On `registerHandler()`, handlers are inserted and the array is re-sorted by numeric priority (lower = earlier), giving deterministic execution ordering. If no ID is supplied, a fallback ID is generated as `` `${event}-${handler.type}-${Date.now()}` ``; critically, handlers sharing an ID **overwrite** rather than duplicate, giving idempotent re-registration semantics — useful for hot-reload or repeated initialization scenarios.

`HookConfigLoader`'s `validateConfig()` deliberately only logs warnings instead of throwing on malformed hooks.json entries, favoring **graceful degradation** over hard failure — a partial, mostly-valid config is preferred to a crashed session. Related to this, `loadConfig()` applies `settings.enableLogging`, `stopOnError`, and `timeout` only when explicitly defined (`!== undefined` checks), preserving constructor defaults otherwise — a conservative merge strategy that avoids accidental overrides from sparse config files.

`ViolationCaptureService` writes JSONL records to `.mcp-sync/session-violations.jsonl` (append-only, one violation per line) while separately maintaining `violation-history.json`, capped at 1000 entries via `history.violations.slice(-1000)` to bound file growth. Before persistence, `sanitizeParams()` redacts values for keys matching password/token/key/secret/auth patterns, preventing credential leakage into logs — a security-conscious default applied uniformly regardless of tool. Aggregate statistics are computed by `calculateStatistics()`, which performs reduce-based aggregation for 24-hour rolling violation counts, severity breakdowns, and most-common-constraint identification, feeding dashboard consumption.

The ConstraintSystem's children — HookManager, HookConfigLoader, ViolationCaptureService, KnowledgeInjectionHooks, and HealthPromptHook — form its complete internal surface. KnowledgeInjectionHooks integrates via `isInjectionEnabled()`, reading `process.env.CODING_KNOWLEDGE_INJECTION` and defaulting to enabled unless explicitly disabled ('0'/'false'/'off'), showing the hook system's extensibility for environment-driven feature toggling. HealthPromptHook's `checkHealthStatus()` uses `existsSync(VERIFIER_SCRIPT)` as a heuristic to detect execution outside the coding repo, returning `servicesAvailable:false` rather than attempting network calls — an example of hook handlers making local, fast decisions rather than depending on external services.

Within the broader Coding hierarchy, the ConstraintSystem's reliance on environment variables and filesystem heuristics parallels patterns seen in sibling components like LLMAbstraction's layered mode-resolution and CodingPatterns' environment-variable-driven agent wrapper scripts — suggesting a project-wide convention of config precedence chains and env-var toggles.

## Usage Guidelines

Developers extending the ConstraintSystem should register handlers with explicit, stable IDs to control overwrite behavior deliberately rather than relying on the timestamp-based fallback ID, which changes on every call and thus never overwrites. When adding new configuration options, follow the `!== undefined` guard pattern in `loadConfig()` to avoid clobbering defaults with sparse configs. Given that `validateConfig()` only warns on malformed entries, developers should not assume config errors halt execution — malformed hooks.json files can silently partial-load, so validation warnings should be monitored. Any new violation-related parameters must pass through `sanitizeParams()`-equivalent redaction to avoid credential leakage, and consumers of `violation-history.json` should account for its 1000-entry cap when building long-term analytics.
