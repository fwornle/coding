# ConstraintSystem: Technical Insight Document

## What It Is

ConstraintSystem is the guardrail and validation subsystem of the Coding project, responsible for gating risky tool calls, enforcing configuration-driven policy, capturing violations for durable dashboard consumption, and extending validation semantics into the knowledge-base domain. Its implementation is anchored in six child components: HookConfigLoader (`lib/agent-api/hooks/hook-config.js`), UnifiedHookManager (`lib/agent-api/hooks/hook-manager.js`), ViolationCaptureService (`scripts/violation-capture-service.js`), ContentValidationAgent, KnowledgeInjectionHooks (`knowledge-injection-hook.js`), and HealthPromptHook. As a sibling to LiveLoggingSystem, LLMAbstraction, DockerizedServices, KnowledgeManagement, and CodingPatterns under the root Coding component, ConstraintSystem is the project's dedicated mechanism for real-time and asynchronous rule enforcement, distinguishing it from siblings focused on logging, LLM routing, or infrastructure health.

## Architecture and Design

The core architectural pattern is a two-tier layered configuration merge: HookConfigLoader distinguishes user-level global defaults (`~/.coding-tools/hooks.json`) from project-level overrides (`.coding/hooks.json`), combining them via `mergeConfigs()` where project config wins on key collisions but non-overlapping keys from both layers survive. This mirrors a policy-over-mechanism philosophy consistent with the broader project convention (echoed in CodingPatterns' externalized configuration approach).

Dispatch is centralized in UnifiedHookManager, which maintains a `Map<event, HookHandler[]>` keyed by event type (pre-tool, post-tool, pre-prompt, post-prompt) and re-sorts handlers by numeric priority on every `registerHandler()` call, favoring correctness over marginal registration-time efficiency. Notably, this design is architecturally duplicated: ContentValidationAgent's observations reveal a structurally near-identical abstract `HooksManager` class in `lib/agent-api/hooks-api.js` that independently implements the same Map-based registry, the same per-registration priority sort, and the same `Date.now()` fallback ID generation — a case of parallel evolution rather than inheritance, and a latent maintenance risk.

ViolationCaptureService and its bounded-history persistence layer (`.mcp-sync/violation-history.json`) implement a rolling-window design rather than an unbounded audit log, trading long-term completeness for bounded disk usage. ContentValidationAgent generalizes the same "validate claims against ground truth" philosophy from live tool-call gating into asynchronous documentation-integrity checking against repository state.

## Implementation Details

HookConfigLoader's `validateConfig()` checks required handler fields (`type`, `path`) and type constraints (e.g., positive `timeout`), but deliberately emits warnings rather than throwing — a fail-open, availability-over-strictness stance requiring developers to monitor logs actively.

UnifiedHookManager's `registerHandler()` contains duplicate-ID replacement logic: when a handler with an existing ID is re-registered (e.g., after a mid-session `.coding/hooks.json` reload), it is replaced in place rather than appended, preventing multiplied violation reports from redundant handlers accumulating over long-running sessions.

ViolationCaptureService's `sanitizeParams()` strips or masks parameters matching sensitive-key patterns (password, token, key, secret, auth) before writing JSONL violation records, a hard security boundary given that logs feed dashboards viewed by multiple team members. `updateViolationHistory()` caps history at 1000 entries, and `calculateStatistics()` recomputes severity breakdowns, 24-hour recency, and "most common violation" metrics from scratch each call rather than maintaining incremental counters — trading linear-but-bounded CPU cost for zero drift risk.

KnowledgeInjectionHooks gates its behavior via `isInjectionEnabled()`, reading `CODING_KNOWLEDGE_INJECTION` and treating only `'0'/'false'/'off'` as disabling, defaulting ON — a fail-open convention consistent with HookConfigLoader's lenient validation posture.

## Integration Points

ConstraintSystem's children interoperate tightly: HookConfigLoader's merged config feeds handler definitions into UnifiedHookManager (and the parallel `HooksManager`), which dispatches to registered handlers including those feeding ViolationCaptureService. ContentValidationAgent extends this enforcement model beyond runtime tool gating into KnowledgeManagement's domain, cross-checking entity observations, diagrams, and file/command references against actual repository state via git-based staleness detection — a direct conceptual bridge between ConstraintSystem and KnowledgeManagement's VKB-backed knowledge graph. HealthPromptHook likely ties into session/prompt lifecycle events dispatched through the same handler Map infrastructure.

## Usage Guidelines

Developers modifying constraint behavior must understand which config file takes effect at runtime — project-level `.coding/hooks.json` silently wins on collisions. Because `validateConfig()` only warns on malformed handlers, warning logs must be actively monitored; there is no hard failure to force attention. When registering handlers, be aware that duplicate IDs replace in place — reused IDs are the correct way to update a handler mid-session rather than accumulating duplicates. Anyone fixing the duplicate-ID or priority-sort logic must apply the same fix to both UnifiedHookManager and the parallel `HooksManager` in `hooks-api.js`, since they are not unified through inheritance. Finally, consumers relying on `.mcp-sync/violation-history.json` for long-term trend analysis must recognize its 1000-entry cap and build separate archival mechanisms if genuine historical auditing is required.
