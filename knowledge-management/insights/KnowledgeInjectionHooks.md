# KnowledgeInjectionHooks — Technical Insight Document

## What It Is

KnowledgeInjectionHooks is the agent-facing hook subsystem rooted in `lib/agent-api/hooks-api.js`, with its Claude Code integration living in `lib/agent-api/hooks/claude-bridge.js` and its feature-gating contract enforced by `tests/features/cli-and-rules-gating.test.mjs` and `lib/features/require-feature.sh`. As a child of ConstraintSystem, it sits alongside HookConfigLoader, UnifiedHookManager, and HealthPromptHook, and is composed of four child components that each implement a distinct facet of the same core `HooksManager` class: HooksManagerRegisterHook (registration/sort mechanics), UnifiedHookManagerHandlerRegistry (the priority-ordered dispatch registry), ClaudeBridgeEventTranslation (native-to-unified event mapping), and KnowledgeInjectionHookGating (the CLI-level feature-flag enforcement layer). Together these pieces form the mechanism by which "knowledge" — hook handlers registered against lifecycle events like PreToolUse/PostToolUse — gets injected into an agent's tool-call pipeline in a controlled, fail-safe way.

## Architecture and Design

The core of the design is a Template Method / Abstract Base Class pattern: `HooksManager` in `lib/agent-api/hooks-api.js` defines the registration/dispatch skeleton and a `Map<string, RegisteredHook[]>` registry seeded from `Object.values(HookEvent)` in its constructor, while deferring agent-specific behavior — `getAgentType()`, `loadNativeHooks()`, `saveNativeHooks()` — to subclasses. The constructor enforces this contract aggressively: `if (new.target === HooksManager) throw ...`, a JS-level emulation of abstract-class discipline more typical of typed languages.

![KnowledgeInjectionHooks — Architecture](images/knowledge-injection-hooks-architecture.png)

Layered on top of this abstraction is an Adapter/Bridge pattern in `claude-bridge.js`, which translates Claude Code's native stdin/stdout JSON hook protocol into the unified `HookContext`/`HookHandler` shape consumed by `hook-manager.js` (UnifiedHookManager, a sibling component). The bridge is tightly coupled by design to `hook-manager.js` — it dynamically imports `getHookManager()` at request time rather than through injection, a deliberate simplicity trade-off over dependency injection.

A defining architectural theme spanning nearly every layer is **fail-open by design**. `claude-bridge.js`'s `main()` wraps the entire execution path in try/catch and resolves any failure — JSON parse errors, initialization failures, handler exceptions — to `{decision: 'allow', ...}` plus `process.exit(0)`, backed by a 1000ms stdin-read timeout that resolves to `{}`. This mirrors, at the dispatch layer, `triggerHook()`'s per-handler try/catch in `HooksManager`, giving a dual-layer fail-open guarantee: no single bad hook or bridge bug can block an agent's tool call. The same philosophy reappears at the CLI layer in `require-feature.sh`, which fails open when `repo` can't be resolved or `node` isn't on PATH. This is architecturally distinct from the "fail loud at construction" boundary enforced by `HooksManager`'s constructor — a clear separation between programmer errors (never allowed to reach production) and runtime execution failures (always swallowed).

## Implementation Details

`HooksManagerRegisterHook` implements an eager-sort-on-insert strategy: `registerHook()` retrieves `this.hooks.get(event)`, pushes the new hook, and immediately re-sorts the full array by priority (`eventHooks.sort((a, b) => a.priority - b.priority)`) before re-setting the map entry. Because the map is pre-seeded with arrays for every `HookEvent` in the constructor, the `|| []` fallback and the trailing `this.hooks.set()` are effectively dead-code safety nets on an invariant that already holds — a minor inefficiency but not a correctness issue. This design is analyzed further by UnifiedHookManagerHandlerRegistry, which frames the trade-off explicitly: since `triggerHook()` runs on the hot path (once per tool call) while `registerHook()` runs only at startup/config-load time, paying O(n log n) on the cold write path is strictly preferable to a lazy-sort-on-read approach that would tax every dispatch.

ClaudeBridgeEventTranslation documents `transformContext()`'s lookup into `EVENT_MAP` for a fixed set of native events (PreToolUse, PostToolUse, Startup, Shutdown, PrePrompt/PostPrompt/Error), falling back to `nativeEvent.toLowerCase()` for anything unmapped. This fallback is a latent gap: the unified `HookEvent` enum uses hyphenated names (e.g., `pre-tool`), so an unrecognized native event silently produces a string that will never match any registered handler — a silent-drop failure mode consistent with, but riskier than, the system's general fail-open philosophy. Compounding this, the `EVENT_MAPPINGS` table in `hooks-api.js` encodes explicit per-agent asymmetry: claude maps `PRE_PROMPT`/`POST_PROMPT`/`ERROR` to `null` while copilot maps most of these to real native events except `POST_PROMPT` (explicitly commented "Not supported"). `translateEvent()` returns `null` silently for unmapped pairs, so downstream code must treat `null` as "not wired for this agent," not an error condition.

KnowledgeInjectionHookGating enforces the CLI-facing side of this system: `tests/features/cli-and-rules-gating.test.mjs` requires every hook-adjacent CLI (`bin/semantic`, `bin/graphify`, `bin/constraints`, `bin/log-session`) to source the shared `lib/features/require-feature.sh` and call `require_feature <name>` per its `GUARDED` map, with a strict exit-code contract — exit 2 for "feature disabled," distinct from a wrapped command's own failure (exit 1).

## Usage Guidelines

Developers extending KnowledgeInjectionHooks must respect several implicit contracts. First, never instantiate `HooksManager` directly — always subclass and implement `getAgentType()`, `loadNativeHooks()`, and `saveNativeHooks()`, or construction will throw immediately. Second, when adding new event types, check the `EVENT_MAPPINGS`/`EVENT_MAP` tables per-agent rather than assuming parity; a `null` or unmatched translation is a legitimate "not supported" state, not a bug to work around silently. Third, be aware that `transformContext()`'s lowercase fallback for unrecognized native events will never route to a correctly-named unified handler — any new Claude event type should be added explicitly to `EVENT_MAP` rather than relying on the fallback. Fourth, any new CLI that should be feature-gated must source `lib/features/require-feature.sh` and honor the exit-code-2-for-disabled convention to remain compatible with scripts that depend on this distinction. Finally, respect the system's pervasive fail-open convention: hook and guard failures should always resolve toward allowing the operation with a logged warning, never toward blocking or hanging the pipeline — a design principle that trades runtime safety guarantees for availability, deliberately, throughout this subsystem.
