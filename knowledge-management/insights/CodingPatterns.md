# CodingPatterns — Insight Document

## What It Is

CodingPatterns is not a single directory of runtime code but a cross-cutting set of enforced conventions distributed across the repository's tooling. There is no single "entry point" file to point to; instead, its implementation surfaces through guard scripts, style rules, and verification disciplines, each encoding a policy decision made in response to a specific observed failure. Concrete examples include the `docs/puml/` placement contract from the Documentation Style Guide, the `suiteOwnership()` guard for test exclusion, node:test-compatible test-inventory tooling, the manifest/graph synchronization safeguards for metadata merges, and the post-rewrite render-error triage discipline. A developer looking for "the CodingPatterns module" should instead look at these scattered enforcement points rather than expect a service boundary.

## Architecture and Design

The architectural pattern here is best described as **policy-as-tooling**: rather than documenting conventions in prose alone, CodingPatterns pushes them into machine-checked guards (e.g., `suiteOwnership()`) or structural contracts (e.g., mandatory file placement under `docs/puml/`). This reflects a recurring design principle — "explicit over implicit configuration" — where file location, guard checks, or exit codes serve as the actual configuration signal. Misplacing a `.puml` file, silently excluding a test, or chaining CI commands with `;` instead of `&&` all previously produced silent failures; the architectural response is to convert each into a visible, enforced failure mode.

## Implementation Details

Each child component carries its own concrete mechanism. TestingPractices addresses the "Test Inventory Discovery — node:test Compatibility" gap, where test files importing from `node:test` were previously invisible to test-inventory tooling and silently skipped rather than failing visibly; it works alongside the `suiteOwnership()` guard, which requires any test exclusion to be an explicit, verified declaration rather than an accidental, undocumented omission. DataIntegrityPatterns addresses the "Metadata Merge Bug — Destructive Overwrite Pattern," where manifest-level and graph-level parent entity descriptions could clobber one another during merges; the fix requires treating one representation as authoritative or reconciling explicitly rather than allowing last-write-wins semantics. PatternVerificationTooling encodes the "Post-Rewrite Render Error Triage" discipline, requiring render errors to be checked against a pre-rewrite baseline before being attributed to a rewrite as regressions. DocumentationStyleGuide fixes the placement contract for `.puml` source files, which must live under `docs/puml/` for the docs rendering pipeline to discover them correctly.

EntityTeamOwnershipHeuristics is the most concretely code-backed child: `src/ontology/heuristics/EntityPatternAnalyzer.ts` implements "Layer 1: File/Artifact Detection" via `analyzeEntityPatterns()`, which runs `checkLocalArtifact()` first (a hardcoded `teamDirectories` prefix-match Map, confidence 0.9) and falls back to `matchArtifactPattern()` (per-team naming-convention regexes like `/LSL(Session|Monitor|Classifier)/i`, confidence 0.75) only if the first check fails — a deliberate "known location beats plausible name" ordering.

## Usage Guidelines

Developers should treat file location and command wiring as load-bearing configuration, not incidental structure: `.puml` files must live in `docs/puml/` or the docs pipeline silently fails to render them; test exclusions must go through the `suiteOwnership()` guard rather than being dropped ad hoc; and CI scripts must chain with `&&` (not `;`) and propagate `tsc`/test exit codes so failures aren't swallowed. When adding new test runners or import styles, verify test-inventory tooling recognizes them, since silent skips are strictly worse than visible failures. When touching merge/consolidation logic that spans manifest and graph representations, explicitly designate an authoritative source or reconcile both sides rather than allowing whichever write lands last to win. After large rewrites, always triage render errors against a pre-rewrite baseline before assigning blame or prioritizing fixes — conflating pre-existing issues with regressions wastes debugging effort and undermines confidence in the rewrite.
