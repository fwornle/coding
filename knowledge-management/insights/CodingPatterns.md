## Architecture and Design

The architectural signature of CodingPatterns is externalization of policy from mechanism. Rather than hardcoding behavior, the project consistently pushes configuration into declarative artifacts: `config/features.yaml`, `config/feature-profiles.yaml`, `config/agent-profiles.json`, `config/task-taxonomy.yaml`, and `config/prompt-classifier.yaml`. This reflects the "Feature Modularity" philosophy documented in `docs/architecture/features.md`, and it recurs in classifiers like `OntologyClassifier`, which reads schema-driven config instead of embedding categorization logic directly.

A second architectural theme is decorator/wrapper-style resilience: `CircuitBreakerManager` and `CachingMechanism` wrap calls to `LLMServiceProvider`, implying a shared idiom applied uniformly to network-facing services rather than per-call error handling. This same wrapper posture appears conceptually in the child component ResilienceWrappers, though its actual source evidence (`scripts/knowledge-management/verify-patterns.sh`, `src/ontology/heuristics/EntityPatternAnalyzer.ts`) turns out to be guard-rail/compliance code rather than true circuit-breaker logic — a useful reminder that the CodingPatterns umbrella sometimes labels defensive coding practices loosely alongside classic resilience patterns.

Third, monitoring-as-code is a recurring convention: `ConstraintMonitoringService` and `config/health-verification-rules.json` codify best practices as declarative rule sets rather than embedded assertions, mirrored by the child component ConfigDrivenDesign's enforcement script.

## Implementation Details

The most concrete implementation artifact tied to this component family is `scripts/knowledge-management/verify-patterns.sh`, which anchors both the NamingConventions and ConfigDrivenDesign children. It performs compliance checking by grepping for `console.log` versus `Logger.*` calls to enforce the ConditionalLoggingPattern, and by evaluating other heuristics (ReduxStateManagementPattern, NetworkAwareInstallationPattern) via ripgrep. It resolves `CLAUDE_REPO` through `CODING_TOOLS_PATH`/`CODING_REPO` env vars, falling back to a path derived two directories above `SCRIPT_DIR` — a fragile coupling between script location and correctness that developers must respect if relocating the file.

Critically, the script reads a `TransferablePattern` list filtered by `significance >= 8` from a JSON knowledge base (`$SHARED_MEMORY`) via `jq`, and writes compliance scores back into that same file (`.metadata.last_pattern_verification`, `.metadata.pattern_compliance_score`). This makes the knowledge base simultaneously the source of truth and the telemetry sink — a self-referential monitoring-as-code loop consistent with `ConstraintMonitoringService`'s declarative style.

Naming itself is enforced through consistent suffixing: `*Manager` (GraphDatabaseManager, ProviderRegistryManager, ConnectionManager), `*Service` (LLMServiceProvider, SemanticAnalysisService, DashboardService), and `*Adapter` (TranscriptAdapter, SpecstoryAdapter) — a project-wide convention for signaling role clarity rather than a single class hierarchy.

## Usage Guidelines

Developers should treat CodingPatterns as a reference for idiom compliance rather than a component to modify directly. When adding new services or managers, follow the established `*Manager`/`*Service`/`*Adapter` suffix conventions for immediate role legibility. New configuration should be externalized into YAML/JSON files (following `config/features.yaml`-style patterns) rather than hardcoded, and network-facing service calls should be wrapped using the existing `CircuitBreakerManager`/`CachingMechanism` idiom rather than reimplementing per-call error handling. Anyone modifying `scripts/knowledge-management/verify-patterns.sh` must preserve its environment-variable-based repo-root resolution and its read/write contract against the `$SHARED_MEMORY` JSON knowledge base, since compliance scoring depends on that round-trip. Finally, note the looseness of the "ResilienceWrappers" label — not all files under that child component are actual network-resilience wrappers, so evaluate each artifact's grounding before assuming circuit-breaker semantics apply.

- [LiveLoggingSystem](./LiveLoggingSystem.md) -- [LLM] The LiveLoggingSystem's configuration validation is centralized in scripts/validate-lsl-config.js through the LSLConfigValidator class, which acts as a schema enforcement gatekeeper for two distinct config artifacts: .specstory/config/lsl-config.json (structural/behavioral settings) and .specstory/config/redaction-config.yaml (privacy/classification rules). Architecturally, the component favors thin wrappers over deep abstraction: llm-mock-service.ts persists mode state (mock/local/public) per-agent in a shared workflow-progress.json file with legacy fallback support; dmr-provider.ts implements a singleton client pattern with cached health checks and YAML-based config loading across multiple candidate paths; llm-with-process.ts is explicitly documented as a deliberate 'Option B' single-repo wrapper chosen over modifying the upstream @rapid/llm-proxy SDK, preserving SDK metrics tracking while injecting a missing 'process' telemetry field into requests.

A cross-cutting concern is defensive parsing of LLM output: parse-llm-json.ts implements a narrow, character-level state machine that repairs only raw control characters inside string literals (the specific failure mode observed in production on 2026-09-07), deliberately avoiding broader JSON-guessing to keep failures loud and diagnosable rather than silently misinterpreted.
- [DockerizedServices](./DockerizedServices.md) -- [LLM] The health-check subsystem enforces a strict invariant (documented as SPEC R6) that probing functions in service-probe.js—probeHttpHealth() and probeTcpPort()—must never report a 'healthy' status directly. Instead, these functions only distinguish between 'stopped' (connection refused, timeout, or non-2xx HTTP response) and 'unknown' (configuration errors, malformed URLs, or unresolvable hosts). This is a deliberate architectural choice: liveness probes are pessimistic by design, and the actual determination of 'healthy' is deferred to a higher-level coordinator that combines probe results with other signals (e.g., process registration state from ProcessStateManager). New developers extending probe logic must preserve this three-state contract rather than optimistically returning 'healthy' from a probe function, since downstream consumers (the health-coordinator) rely on the absence of false positives here.

Developers working on this component should understand that the VKB server is not just a passthrough to the database—it implements query logic, caching, and decay scheduling that must be preserved across any storage backend swap, as evidenced by the dedicated migration test suite.
- [ConstraintSystem](./ConstraintSystem.md) -- [LLM] The ConstraintSystem's configuration architecture follows a strict two-tier layered merge pattern implemented in HookConfigLoader (lib/agent-api/hooks/hook-config.js). User-level configuration lives at ~/.coding-tools/hooks.json and represents global defaults applicable across all projects, while project-level configuration at .coding/hooks.json can override specific handlers or add project-specific constraints. The mergeConfigs() function performs this layering, meaning a new developer modifying constraint behavior needs to understand which file actually takes effect at runtime — project config wins on key collisions, but non-overlapping keys from both sources are preserved. This design allows teams to ship organization-wide constraints via user config while individual projects retain the ability to loosen or tighten specific rules without forking the entire config file.
