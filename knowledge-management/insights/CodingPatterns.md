# CodingPatterns: Architectural Insight Document

## What It Is

CodingPatterns is not a single module but a cross-cutting catalog of recurring conventions observed throughout the Coding project — most concretely visible in `config/agents/*.sh` (claude.sh, copilot.sh, opencode.sh, pi.sh), `config/agent-profiles.json`, the `bin/` directory of single-purpose executables, and declarative config files such as `config/feature-profiles.yaml`, `config/features.yaml`, `config/task-taxonomy.yaml`, and `config/prompt-classifier.yaml`. As a component within the Coding ontology, its purpose is to codify *how* the codebase solves recurring problems — adapter normalization, CLI structure, configuration strategy, environment-variable discipline — rather than to implement a single runtime capability. Its four children, AgentAbstractionConventions, CLIScriptConventions, ConfigDrivenFeatureFlags, and EnvironmentVariableConfiguration, each drill into one facet of this pattern language.

## Architecture and Design

The dominant architectural idea is the **adapter/normalization boundary**: each script in `config/agents/*.sh` translates a vendor-specific CLI into a common invocation contract documented in `docs/architecture/agent-abstraction-api.md`, so orchestration code (e.g., `wave-controller.ts`) never needs to know which underlying agent binary is installed. This is reinforced by a **registry pattern**, `config/agent-profiles.json`, which centralizes agent metadata (flags, model defaults, timeouts) declaratively rather than through polymorphic class hierarchies — an approach explicitly compared to provider registries in the sibling KnowledgeManagement component.

A second major pattern is **configuration-over-code**: YAML/JSON catalogs (`feature-profiles.yaml`, `task-taxonomy.yaml`, `prompt-classifier.yaml`) drive behavior in classifiers like OntologyClassifier and SensitivityClassifier without code changes, making CodingPatterns best understood as an implicit schema contract rather than executable logic. Notably, this ideal is not universally honored: the child ConfigDrivenFeatureFlags documents a deviation in `EntityPatternAnalyzer` (src/ontology/heuristics/EntityPatternAnalyzer.ts), where `teamDirectories` and `artifactPatterns` are hardcoded TypeScript literals instead of external config, undermining the "ship via config PR" goal.

A third pattern, Unix-style composability, governs `bin/` — small, independently invocable executables (`bin/ckb`, `bin/graphify`, `bin/status`) rather than a monolithic CLI with subcommands, mirrored at the shell-script level by CLIScriptConventions' analysis of `scripts/knowledge-management/verify-patterns.sh`.

## Implementation Details

Each agent adapter script accepts identical positional arguments and environment variables (`LLM_PROXY_URL`, `CODING_OPENCODE_MODEL`), performs backend-specific argument translation, and emits a shared output format per `docs/architecture/adding-new-agent.md` — onboarding a new agent means writing a new script satisfying the contract, not modifying dispatch logic. `config/agent-profiles.json` decouples this invocation logic from capability metadata, so adding flag support is a JSON edit.

Environment-variable discipline follows a `PROVIDER_ROLE_PURPOSE` naming convention (`QWEN_LOCAL_API_KEY`, `QWEN_LAPTOP_API_BASE_URL`, `GSD_BROWSER_BROWSER_PATH`) enforced only informally — there is no central schema validator, so consistency depends on contributors following precedent, as documented in `docs/architecture/llm-routing.md`. This same fallback-chain idiom appears at the shell layer: `verify-patterns.sh` resolves its own root via `$(cd "$(dirname ...)" && pwd)` and computes `DEFAULT_REPO` relative to that, with `CODING_TOOLS_PATH`/`CODING_REPO` env vars overriding the default — directly paralleling `LLM_PROXY_URL`/`RAPID_LLM_PROXY_URL` fallback logic.

Initialization favors laziness: proxy clients keyed by `LLM_PROXY_URL` and other heavy resources (browser instances via `GSD_BROWSER_BROWSER_PATH`) are instantiated on first use, not in constructors, keeping `bin/` scripts cheap to start. Concurrency is handled via shared utility functions (promise-based queuing/throttling referenced near `wave-controller.ts`-style orchestration) rather than deep inheritance, keeping adapters thin.

## Integration Points

![CodingPatterns — Relationship](images/coding-patterns-relationship.png)

CodingPatterns sits as a sibling to LiveLoggingSystem, LLMAbstraction, DockerizedServices, KnowledgeManagement, ConstraintSystem, and SemanticAnalysis under the root Coding component, and its conventions recur in all of them: the agent-profiles.json registry mirrors provider registries in KnowledgeManagement; the three-tier precedence resolution used elsewhere (e.g., LLMAbstraction's `getLLMMode()`, ConstraintSystem's `HookConfigLoader` cascade) echoes the same layered-fallback philosophy seen in environment-variable resolution here. Its children make these cross-cutting ties explicit: AgentAbstractionConventions and CLIScriptConventions both point to `scripts/knowledge-management/verify-patterns.sh` as evidence that env-var-fallback and self-locating root resolution are project-wide, not LLM-specific. EnvironmentVariableConfiguration further generalizes the PROVIDER_ROLE_PURPOSE idiom to repo-root discovery (`CLAUDE_REPO="${CODING_TOOLS_PATH:-${CODING_REPO:-$DEFAULT_REPO}}"`).

## Usage Guidelines

New agent integrations should add a script to `config/agents/` satisfying the existing contract and register metadata in `config/agent-profiles.json`, rather than altering core dispatch logic. New discrete functionality belongs in its own `bin/<name>` script, not as a subcommand grafted onto an existing binary. New environment variables must follow `PROVIDER_ROLE_PURPOSE` naming to stay discoverable, since there is no schema enforcing this. Behavior changes should be pushed through YAML/JSON config files where a consuming classifier already exists — developers should be alert to exceptions like `EntityPatternAnalyzer`, where the convention is violated and hardcoded literals require a rebuild. Finally, any new script intended for CI/cron/submodule use should self-resolve its root directory and layer environment-variable overrides, following the `verify-patterns.sh` precedent, and defer heavyweight resource initialization until first use.

- [LLMAbstraction](./LLMAbstraction.md) -- [LLM] The mock/local/public mode toggle system in llm-mock-service.ts is designed around a persisted state file (.data/workflow-progress.json) rather than environment variables, which allows runtime mode switching without process restarts. The LLMState structure with globalMode and perAgentOverrides fields enables fine-grained control where a specific agent can be forced into mock mode for testing while the rest of the system runs against real providers. This is critical for integration testing scenarios where a developer wants to validate one agent's prompt-handling logic without incurring API costs or non-determinism from the LLM calls of other agents in a multi-agent pipeline. The getLLMMode() read path checks perAgentOverrides first, then falls back to globalMode, and finally to the legacy progress.mockLLM boolean, establishing a three-tier precedence resolution that any new developer must understand before assuming a single toggle controls behavior.
- [DockerizedServices](./DockerizedServices.md) -- [LLM] The DockerizedServices layer is architected around a dual-mode execution model: services can run either as supervisord-managed processes inside a single Docker container (per docker/docker-compose.yml, Dockerfile.coding-services, supervisord.conf) or as host-native Node subprocesses managed by lib/service-starter.js and PID-tracked via ProcessStateManager. This duality means developers must understand that 'starting a service' has two entirely separate code paths depending on deployment target, and that health-checking logic (service-probe.js) is written to be agnostic to which path is in effect — it only cares about HTTP/TCP reachability, not process ownership. This design avoids needing separate health-monitoring logic for containerized vs local services, but it also means Docker-specific failures (e.g., supervisord misconfiguration killing a service inside the container) surface identically to host-side crashes, requiring log inspection to disambiguate.
- [KnowledgeManagement](./KnowledgeManagement.md) -- [LLM] The GraphifyGraph reader (integrations/semantic-analysis/src/agents/graphify-graph.ts) represents a deliberate architectural simplification: rather than maintaining a live graph database connection (Memgraph via Cypher), the component now treats a static graph.json artifact produced by the graphify service as the source of truth for code-structure knowledge. This file, a NetworkX node-link JSON export, can be tens of megabytes, so GraphifyGraph implements mtime-based lazy caching — it stat()s the file and only re-parses when the mtime has changed since the last load. This pattern trades real-time graph mutation capability for drastically simpler deployment (no separate DB process) and fast repeated reads, at the cost of only picking up graph changes when the underlying analysis pipeline re-writes graph.json.
- [ConstraintSystem](./ConstraintSystem.md) -- [LLM] The configuration merging strategy in HookConfigLoader (lib/agent-api/hooks/hook-config.js) implements a three-tier cascade — DEFAULT_CONFIG baked into the code, user-level settings from ~/.coding-tools/hooks.json, and project-level settings from .coding/hooks.json — resolved through mergeConfigs(). This design lets individual developers set personal defaults (e.g., preferred logging verbosity or disabled hooks) while allowing a project to enforce mandatory constraints that override user preferences, but not vice versa. A new developer extending this system needs to understand that the merge is not a deep recursive merge in all cases; array-type handler lists are typically concatenated or replaced depending on the key, so adding a new hook type requires checking mergeConfigs() logic to avoid silently dropping user-level handlers.
- [SemanticAnalysis](./SemanticAnalysis.md) -- [LLM] The classification pipeline in OntologyClassificationAgent embodies a deliberate 'deterministic-first, LLM-as-fallback' philosophy that recurs throughout SemanticAnalysis. Before any LLM call is made, classifySingleObservation() checks the observation's name against the hard-root-guard set (CollectiveKnowledge, Coding, DynArch, Timeline, Normalisa) imported from @fwornle/km-core's HIERARCHY_ROOTS. If matched, the method immediately assigns classificationMethod='hard-root-guard' and returns without ever invoking classifier.classify() or touching the LLM. This is a defensive engineering decision: because these 5 names anchor the entire hierarchy, any LLM-driven misclassification of them would cascade corruption through the whole ontology tree, so the developers chose to hardcode an escape hatch rather than trust probabilistic classification for structurally critical nodes.
