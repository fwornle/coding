## Architecture and Design

The dominant architectural theme is **uniform interfaces over heterogeneous implementations**. The AgentWrapperScriptPattern exemplifies this: claude.sh, copilot.sh, opencode.sh, and pi.sh each normalize a different third-party CLI into a common invocation surface, reading agent-specific environment variables (e.g., CODING_OPENCODE_MODEL) and translating them into flags the underlying binary expects. This lets orchestration code (bin/coding, docs/architecture/agent-abstraction-api.md) remain agent-agnostic, at the cost of needing every wrapper kept in sync when a new capability is introduced — claude.sh serves as the canonical reference implementation per docs/architecture/adding-new-agent.md.

A second theme is **strict separation of entrypoint from logic**, embodied by CliEntrypointPattern. The bin/ directory (ckb, vkb, graphify, codegraph) enforces thin scripts that parse arguments and delegate immediately to library code, mirroring docker/entrypoint.sh's delegation to supervisord-managed subprocess scripts. Notably, scripts/knowledge-management/verify-patterns.sh diverges slightly — it's a standalone entrypoint invoked directly rather than through the bin/ dispatcher, computing paths relative to SCRIPT_DIR, showing that the convention has a canonical form (bin/) and an accepted variant (direct script invocation) for tooling that doesn't need central dispatch.

A third theme is **externalized, declarative behavior**, realized through ConfigAsCodeConvention and ExperimentDefinitionPattern. Behavior toggles live in config/features.yaml, task classification in config/task-taxonomy.yaml, and health rules in config/health-verification-rules.json, rather than being encoded imperatively. verify-patterns.sh itself demonstrates this recursively: it reads pattern definitions dynamically from a jq-queried JSON knowledge base ($SHARED_MEMORY), filtering entities by entityType == 'TransferablePattern' and significance >= 8 — meaning the pattern-verification tooling is itself configuration-driven. Benchmarks follow the same idiom: config/experiments/*.yaml (compare-fizzbuzz.yaml, wire-verify-82-06.yaml) and docs/benchmarks/coding-v1/README.md + RESULTS.md separate experiment definition from code and results documentation from configuration.

Finally, SupervisorManagedContainerPattern captures a deliberate departure from one-process-per-container norms: docker/entrypoint.sh and docker/supervisord.conf boot multiple long-running services (codegraph-index.sh, graphify-serve.sh) under a single supervised process table, shifting lifecycle and health responsibility away from Docker's native restart policies.

## Implementation Details

At the mechanical level, each pattern is implemented through small, focused artifacts rather than large frameworks. Agent wrappers are individual shell scripts, each owning its own environment-variable namespace and flag-translation logic — there is no shared abstraction layer script, only convention (docs/architecture/adding-new-agent.md as the spec, claude.sh as the template). Environment variable naming itself is patterned: a namespace/role prefix (QWEN, RAPID, LLM_CLI) followed by a purpose suffix (_PROXY_URL, _API_KEY, _API_BASE_URL), as seen in LLM_CLI_PROXY_URL, RAPID_LLM_PROXY_URL, QWEN_LOCAL_API_KEY, and QWEN_LAPTOP_API_BASE_URL — implying (though unverified without inspecting the routing code referenced in docs/architecture/llm-routing.md) that a central lookup mechanism matches by suffix/prefix rather than hardcoding each name.

EntityPatternAnalyzer, as a child of CodingPatterns, represents the tooling side of this component: the logic (surfaced through verify-patterns.sh) that queries the shared knowledge base for TransferablePattern entities above a significance threshold, effectively operationalizing "pattern" as a first-class, queryable knowledge-graph entity type rather than just a documentation convention.

Documentation itself is treated as an implementation artifact of the pattern system: docs/architecture/ follows one-file-per-subsystem (adding-new-agent.md, agent-abstraction-api.md, cross-project-knowledge.md, features.md, health-monitoring.md, llm-routing.md, memory-systems.md, system-overview.md, token-usage.md), mirroring code modularity so each concern has both a code module and a standalone doc.

## Integration Points

CodingPatterns' children are directly instantiated by the sibling components rather than being standalone: AgentWrapperScriptPattern underlies the agent orchestration used across the project's LLM tooling; SupervisorManagedContainerPattern is the operational backbone of DockerizedServices; ConfigAsCodeConvention governs how KnowledgeManagement's shared memory files and health rules are structured and consumed; and the health-check implications of SupervisorManagedContainerPattern connect to docs/architecture/health-monitoring.md and config/health-verification-rules.json, meaning health checks must poll supervisord/service endpoints rather than trusting container exit codes. EntityPatternAnalyzer bridges into KnowledgeManagement's graph storage by querying entities of type TransferablePattern via jq against $SHARED_MEMORY, showing CodingPatterns depends on the knowledge base infrastructure to self-document.

## Usage Guidelines

New agent support should be built by copying the structure of an existing wrapper (claude.sh) per docs/architecture/adding-new-agent.md, not by adding conditional branches in orchestration code. New bin/ tooling should stay thin — logic belongs in library modules, with the script limited to parsing, environment setup, and delegation, except where a standalone tool (like verify-patterns.sh) legitimately operates outside the central dispatcher. New feature flags or experiments should be added by extending YAML/JSON configuration (features.yaml, task-taxonomy.yaml, config/experiments/*.yaml) rather than writing new imperative code paths. When debugging containerized services, developers should inspect supervisord logs/status rather than assuming a single foreground process reflects overall health. And when a new subsystem is introduced, a corresponding doc should be created under docs/architecture/ rather than appended to an existing file, preserving the one-doc-per-module granularity that CodingPatterns itself models.

- [KnowledgeManagement](./KnowledgeManagement.md) -- [LLM] The KnowledgeManagement component centers around a VKB (Virtual Knowledge Base) server that exposes graph-based storage operations to the rest of the Coding infrastructure. This server acts as the primary access point for entity CRUD operations, query resolution, and relationship traversal across the knowledge graph, decoupling consumers (agents, CLI tools, other components) from the underlying storage engine. This abstraction layer is critical because it has allowed the project to migrate storage backends (LevelDB to KMCore) without requiring downstream consumers to change their integration code, as evidenced by the dedicated migration test suite.
- [ConstraintSystem](./ConstraintSystem.md) -- The ConstraintSystem provides rule-based validation and enforcement of code actions and file operations during Claude Code sessions, spanning hook configuration loading, hook dispatch orchestration, and violation capture/persistence. It is built around a unified hook architecture that merges user-level (~/.coding-tools/hooks.json) and project-level (.coding/hooks.json) configurations, with project config taking precedence, and dispatches events (pre-tool, post-tool, pre-prompt, post-prompt, startup, shutdown, error) to registered handlers of type script, command, or module.

Core orchestration lives in UnifiedHookManager (lib/agent-api/hooks/hook-manager.js), which maintains a Map of event names to sorted handler arrays (by priority), supports duplicate-ID overwrite semantics, and exposes registerHandler/unregisterHandler APIs bridging agent-native hook systems to a common HookEvent enum. Configuration parsing and structural validation is handled separately by HookConfigLoader (lib/agent-api/hooks/hook-config.js), which loads, merges, and validates settings/hooks blocks, logging warnings (not throwing) on malformed entries.

Violation detection results are captured and persisted via ViolationCaptureService (scripts/violation-capture-service.js), which writes JSONL violation records to .mcp-sync/session-violations.jsonl and maintains an aggregated violation-history.json with session tracking and computed statistics (severity breakdowns, most common constraint, average violations per session) for dashboard consumption. Sensitive parameter values are redacted before being written to logs, and history is capped at 1000 entries to bound file growth.
- [SemanticAnalysis](./SemanticAnalysis.md) -- [LLM] The batch-analysis pipeline is organized as a multi-agent workflow where distinct responsibilities are separated into dedicated agent classes rather than a single monolithic analyzer. semantic-analysis-agent.ts is responsible for extracting structured knowledge entities from raw inputs (git history diffs/commits and LSL session logs), while ontology-classification-agent.ts takes those extracted entities and classifies them into a hierarchy (determining parent-child relationships and where a given entity fits within the broader ontology). This separation of extraction from classification allows each agent to have a narrower, more testable prompt/response contract with the underlying LLM, and lets the pipeline swap or tune one stage without affecting the other's logic.
