# Pipeline — Technical Insight Document

## What It Is

Pipeline is the orchestration backbone of the SemanticAnalysis subsystem, implemented across the agent classes in `integrations/semantic-analysis/src/agents/` — most notably built atop `base-agent.ts` (BaseAgent). It represents the staged flow by which git history and LSL session data move from raw observations through classification, semantic enrichment, and persistence into the ontology-backed knowledge graph. Rather than a single monolithic function, Pipeline is best understood as a coordination pattern: a coordinator agent invokes discrete stage agents — OntologyClassificationAgent and SemanticAnalysisAgent — and threads their outputs forward through standardized envelopes, deduplication, and eventual knowledge-graph (KG) merge.

Test and orchestration evidence for pipeline-like flows also appears elsewhere in the codebase (e.g., `run_pipeline`, `full_pipeline` in `sample_calls.py`, and the extensive `test_pipeline.py` suite covering graph edges, community detection, god-node reporting, and incremental updates), suggesting the pipeline concept is a recurring architectural motif spanning both the TypeScript semantic-analysis agents and Python graph-analysis tooling (`graphify/analyze.py`, `graphify/build.py`, `graphify/cluster.py`).

## Architecture and Design

The core architectural pattern is a **chain-of-responsibility / staged pipeline**, where each stage extends BaseAgent and wraps its output in a standardized `AgentResponse` envelope containing confidence breakdowns. This envelope is the contract that lets stages communicate uniformly regardless of what specific analysis they perform. Chaining is not hardcoded sequencing but is driven by **routing suggestions** generated inside BaseAgent's `execute()` pipeline, enabling conditional retry and escalation paths between the coordinator, observation-generation, and persistence steps — a design that favors flexibility and error recovery over a rigid linear flow.

A second key decision is the **two-phase accumulate-then-merge design**: deduplication logic runs against the full accumulated observation set only after the pipeline has completed generating observations, rather than deduplicating incrementally. This trades some memory/latency overhead for simpler, more correct global dedup logic ahead of the final KG merge.

The coordinator agent itself embodies a **delegation-over-inlining** decision: rather than embedding classification and semantic-analysis logic directly, it invokes OntologyClassificationAgent and SemanticAnalysisAgent as discrete steps. This keeps each stage independently testable and replaceable, consistent with the parent SemanticAnalysis component's emphasis on modular, plan-driven development (Phase 42/57/60 markers).

## Implementation Details

Each pipeline stage inherits from **BaseAgent**, whose internal pipeline (as documented on the BaseAgent sibling entity) follows `execute() -> process() -> calculateConfidence() -> detectIssues() -> generateRouting() -> applyCorrections() -> buildMetadata()`. This gives every stage — classification, semantic analysis, persistence — identical guarantees around confidence scoring, issue detection, and routing metadata, regardless of the stage's domain logic.

The **coordinator** is the orchestration entry point, sequencing calls to OntologyClassificationAgent (which layers heuristics, an LLM-backed classifier, and hierarchy-root guards, with L2 refinement delegated to L2SubsystemClassifier's keyword-based fallback) and SemanticAnalysisAgent (which performs code/git/vibe cross-analysis and LLM-driven insight generation). Downstream, **persistence agents** consume the confidence and issue metadata computed upstream to make a binary decision: write entities directly to the KG or flag them for human review — a clean separation of concerns between "decide confidence" and "act on confidence."

Adjacent to this TypeScript pipeline, Python-side pipeline functions (`run_pipeline`, `full_pipeline` in `sample_calls.py`) and their test suite (`test_pipeline.py`) validate related pipeline concerns — end-to-end execution, graph edge construction, community assignment, god-node/report generation, and incremental updates — calling into `graphify` modules (`analyze.py`, `build.py`, `cluster.py`, `detect.py`) for scoring, clustering, and surprising-connection detection. The `pollKnowledgePipeline` function in `health-coordinator.js` indicates a monitoring/health-check touchpoint that polls pipeline state, likely to detect stalls or busy states (`obsApiBusyNow`, `evaluateObsApiAutoHeal`).

## Usage Guidelines

Developers extending the pipeline should implement new stages as BaseAgent subclasses to automatically inherit confidence computation, issue detection, and routing — bypassing this contract breaks the uniform envelope other stages depend on. When adding coordinator logic, prefer invoking new stages as discrete agents rather than inlining logic, matching the existing OntologyClassificationAgent/SemanticAnalysisAgent delegation pattern.

Because deduplication is deliberately deferred to a post-accumulation phase, new stages should not assume per-observation uniqueness mid-pipeline; dedup guarantees only hold after the full observation set is assembled and before KG merge. Persistence logic should continue to trust upstream confidence/issue metadata rather than recomputing it, preserving the separation between analysis and persistence decisions. Finally, given the parallel Python pipeline tests (`test_pipeline_runs_end_to_end`, `test_pipeline_incremental_update`, etc.), any pipeline changes affecting graph structure, community assignment, or incremental updates should be validated against this test suite to avoid regressions in graph-analytics consumers.

## Hierarchy Context

### Parent
- [SemanticAnalysis](./SemanticAnalysis.md) -- SemanticAnalysis is a multi-agent pipeline (integrations/semantic-analysis/src/agents/) that processes git history and LSL session data to extract, classify, and persist structured knowledge entities into the ontology-backed knowledge graph. It orchestrates specialized agents extending BaseAgent (base-agent.ts) which wrap agent-specific logic in a standardized AgentResponse envelope, computing confidence breakdowns, detecting issues, and generating routing suggestions for retry/escalation between workflow steps.

At its core, OntologyClassificationAgent (ontology-classification-agent.ts) assigns ontology metadata (class, confidence, method) to observations by combining heuristic classifiers, an LLM-backed OntologyClassifier, and hard-coded hierarchy-root guards for closed-set entities (CollectiveKnowledge, Coding, DynArch, Timeline, Normalisa) imported from @fwornle/km-core's HIERARCHY_ROOTS. A newer L2 refinement layer (Phase 57/60) further refines generic L1 classes (Component/SubComponent/Detail) into specific subsystem classes declared in coding.lower.json, using pure, independently-testable helper functions (loadL2Classes, buildL2RefinementPrompt, extractL2FromLLMResponse) alongside a deterministic keyword-based fallback classifier (l2-subsystem-classifier.ts).

The SemanticAnalysisAgent (semantic-analysis-agent.ts) performs the actual code/git/vibe cross-analysis, reading files from git history, computing complexity metrics and architectural pattern detection, and invoking an LLM (via @rapid/llm-proxy's LLMService) to generate deeper semantic insights that are merged with heuristically-detected patterns. The pipeline emphasizes testability (extensive node:test suites with tmpdir-isolated ontology fixtures) and graceful degradation (e.g., absent coding.lower.json yields empty L2 refinement rather than errors), reflecting an incremental, plan-driven development process (Phase 42/57/60 markers throughout the code).
