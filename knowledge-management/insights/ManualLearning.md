# ManualLearning — Technical Insight Document

## What It Is

ManualLearning, as a SubComponent under the parent KnowledgeManagement domain, is not a discrete service or module with its own directory — it is a *pattern* observed across the dashboard and viewer codebases whereby institutional knowledge about past bugs, tradeoffs, and design corrections is encoded directly into source artifacts rather than into external documentation, tickets, or a formal knowledge base. Its concrete manifestations live in `integrations/system-health-dashboard/src/components/ukb-workflow-modal.tsx`, `integrations/system-health-dashboard/src/components/workflow/multi-agent-graph.tsx`, and `integrations/unified-viewer/src/graph/D3GraphCanvas.tsx` and `color-fallback.ts`. In each case, a specific historical mistake — a performance regression, a rendering bug, a visual inconsistency, an API break — was fixed, and the fix was accompanied by a durable, human-authored comment or retained legacy artifact that prevents the mistake from being reintroduced.

Where its sibling GraphifyGraph encodes learning structurally (a static `graph.json` file replacing a live Memgraph connection), ManualLearning encodes learning *textually and behaviorally* — as prose embedded in TSX/TS source, as deprecated-but-retained functions, and as constants whose comments narrate the bug they prevent.

## Architecture and Design

Several recurring design patterns emerge. First, **decision-log-as-code-comment**: `D3GraphCanvas.tsx` is saturated with dated entries (e.g., "2026-06-13 (Phase 56-04)") recording retracted features, the operator feedback that triggered retraction, and the exact scope of any re-introduced code — such as `selectionSource` being reinstated only for Layer 0→Layer 1 transitions and deliberately excluded from the main render effect's dependency array. Second, **guardrail constants co-located with bug narratives**: `multi-agent-graph.tsx`'s `WAVE_AGENTS` and `KG_OPERATOR_CHILDREN` are pinned at module scope specifically because moving them elsewhere previously caused a historical bug (edges silently filtered out of history mode; a memoization defeated by per-render object identity).

Third, the **Strangler Fig / compatibility shim** pattern appears at the function level: `calculateStepAwareEta()` is explicitly docblocked as legacy, delegating to `calculateDynamicEta()` rather than being deleted, so existing call sites don't need atomic migration. This mirrors the same strangler-fig philosophy used structurally by sibling CodeGraphAgent, which now delegates to GraphifyGraph's static-file reader instead of speaking Cypher to Memgraph directly — though notably, `multi-agent-graph.tsx`'s own `AGENT_SUBSTEPS['code_graph']` still labels that step with the stale techNote "Cypher queries on Memgraph," a documentation-drift case that ManualLearning's own philosophy would flag as unfinished cleanup.

Fourth, a **tiered fallback / self-correcting estimation** pattern in `calculateDynamicEta()`, and fifth, a **canonical resolver consolidation** pattern in `color-fallback.ts`'s `nodeFillColor()`, which unifies three independently-drifting color implementations across D3GraphCanvas, Sigma's `buildGraph`, and LegendPanel.

## Implementation Details

`HISTORY_PAGE_SIZE` in `ukb-workflow-modal.tsx` carries a multi-paragraph comment explaining why raising it from 50 to 500 was "close to free": `/api/ukb/history` parses every report regardless of limit and only slices at the end, so the constant's value affects response size, not server work — a nuance a future performance-minded maintainer could easily get backwards without the comment.

`calculateDynamicEta()` implements genuine self-correcting estimation: it accumulates `learnedAvgBatchMs` from batches completed *within the current workflow run*, applies a conservative 1.2x multiplier when only one data point exists, and degrades through three confidence tiers — dynamic learning → historical `avgFinalizationDurationMs` → linear interpolation. It is bounded by sanity-check clamps (0.3x–2.0x of a naive linear estimate, 1s–30min absolute bounds), a defensive guard appropriate for a model whose "training set" is a single in-progress run.

In the unified-viewer, `deriveAncestryFromStorePath()` implements a "store wins, but degrade gracefully" merge between an inline BFS ancestry computation and the Redux-like store's authoritative `pathToSelected`. In `color-fallback.ts`, the deprecated FNV-1a `_classHue()` function is deliberately retained — not because it's used, but "for tests that pin the hierarchy contract," an unusual case where a superseded implementation survives purely to anchor a regression test's behavioral expectations. `nodeFillColor()`'s parent-walk logic (climbing `className` through `registry.parent`) is the synthesized replacement.

## Integration Points

ManualLearning artifacts sit atop Redux state managed in `ukbSlice.ts`, the single source of truth for workflow execution and preferences; components like D3GraphCanvas and MultiAgentGraph subscribe via selectors, with comments explicitly warning against expanding dependency lists on stability-critical render effects. The pattern also touches parent KnowledgeManagement's broader theme of file-as-API tradeoffs — GraphifyGraph's mtime-based lazy caching of `graph.json` and LevelDbMigrationScripts' unenforced two-phase migration ordering (`migrate-graph-db-entity-types.js` before `migrate-leveldb-to-kmcore.mjs`) are structurally analogous "manual learning" risks: knowledge that lives in a comment or a script's implicit contract rather than in enforced tooling. WaveInsightPersistence's three-wave persistence model (w1/w2/w3, with w3 uniquely performing "direct attribute merge") is a sibling example of behavior that depends on undocumented sequencing understood only by reading code.

## Usage Guidelines

Developers should read inline comments in these files as authoritative history before "optimizing" constants like `HISTORY_PAGE_SIZE`, WAVE_AGENTS, or KG_OPERATOR_CHILDREN — their placement and values are bug-fix artifacts, not arbitrary choices. Legacy delegates like `calculateStepAwareEta()` should not be deleted casually; they exist to avoid big-bang call-site migrations. When touching color or ancestry logic in the unified-viewer, prefer the canonical resolvers (`nodeFillColor`, `deriveAncestryFromStorePath`) over reintroducing per-component logic, since three independent implementations previously drifted. Critically, because this learning is captured as prose rather than structured metadata or tests, comprehension depends entirely on developers actually reading surrounding code — stale artifacts like the "Cypher queries on Memgraph" techNote in `multi-agent-graph.tsx` show this system can and does silently drift out of sync with the underlying architecture (e.g., GraphifyGraph's migration away from Memgraph) when nobody updates the narrative alongside the code.

- [KnowledgeManagement](./KnowledgeManagement.md) -- [LLM] The GraphifyGraph reader (integrations/semantic-analysis/src/agents/graphify-graph.ts) represents a deliberate architectural simplification: rather than maintaining a live graph database connection (Memgraph via Cypher), the component now treats a static graph.json artifact produced by the graphify service as the source of truth for code-structure knowledge. This file, a NetworkX node-link JSON export, can be tens of megabytes, so GraphifyGraph implements mtime-based lazy caching — it stat()s the file and only re-parses when the mtime has changed since the last load. This pattern trades real-time graph mutation capability for drastically simpler deployment (no separate DB process) and fast repeated reads, at the cost of only picking up graph changes when the underlying analysis pipeline re-writes graph.json.

The former is a static, hand-authored process diagram; the latter is a dynamic layout engine over live entity/relation data pulled through `useGraphData`. They happen to share the word 'graph' and the general shape of node/edge rendering, but there is no common rendering abstraction, color resolver, or type between them — any visual-consistency fix (e.g. dark-mode palette) has to be applied twice.
- [UkbWorkflowDashboard](./UkbWorkflowDashboard.md) -- [LLM] The HISTORY_PAGE_SIZE constant in ukb-workflow-modal.tsx (currently 500, previously 50) documents a concrete production incident in its own comment block: with the old cap, `/api/ukb/history` silently truncated the report list at 50 entries even though 119+ reports existed, making the single most important run — the batch-analysis run whose Pipeline Totals card shows commits/sessions/entity counts — permanently unreachable from the UI because it sat at position ~51. The fix works because the API route reads and parses every report on every call regardless of `limit`, slicing only at the very end, so raising the page size costs response payload size (roughly 13 header fields per report) rather than server-side work. This is a case where a UI paging constant silently created a data-loss illusion — the data was never lost, just permanently unreachable — and the comment functions as a postmortem note baked directly into source rather than a separate incident doc.
