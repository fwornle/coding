# ArtifactExtractionPipeline — Technical Insight Document

## What It Is

ArtifactExtractionPipeline is the extraction-and-classification front end of the OwnershipHeuristicPattern, implemented primarily in `src/ontology/heuristics/EntityPatternAnalyzer.ts`. Its job is to take raw content strings and, through `extractArtifacts()`, pull out candidate artifact identifiers — file paths, npm scopes, suffix-based class names, and bare directory prefixes — which are then handed to `analyzeEntityPatterns()` for ownership attribution via its two sibling mechanisms, TeamDirectoryPrefixMatch (`checkLocalArtifact()`) and ArtifactPatternRegexCascade (`matchArtifactPattern()`). A loosely coupled operational counterpart, `scripts/knowledge-management/verify-patterns.sh`, performs a structurally similar text-scanning heuristic (console.log vs Logger.* counting) against the codebase and writes its own compliance results back into the shared knowledge store consumed elsewhere in the pipeline.

## Architecture and Design

The core design pattern is regex-based static text scanning used as a lightweight substitute for AST analysis — applied both in `extractArtifacts()` and in `verify-patterns.sh`'s pattern counting. `extractArtifacts()` runs four independent `content.match()` passes and merges all results into a single `Set<string>`, which is architecturally significant: it collapses four different match sources of varying specificity — a precise extension-anchored `filePathPattern` versus a very loose `dirPattern` (`/[a-z-]+\/[a-z-]+\//g`) that matches any two lowercase-hyphen segments — into an undifferentiated pool of "artifacts." This is a deliberate simplicity-over-precision trade-off consistent with the parent OwnershipHeuristicPattern's documented goal of a two-step cascade (direct path match at 0.9 confidence, naming-convention match at 0.75), but it means the confidence hierarchy only operates at the team-matching stage, not at the extraction stage, so a low-precision directory guess and a high-precision file-path match can receive identical downstream scores.

Team ownership vocabulary is encoded as hardcoded in-memory structures — the `teamDirectories` Map and `artifactPatterns` array literals — rather than externalized YAML config, which is a deliberate contrast to other classifiers in the codebase and trades configurability for the analyzer's documented "<1ms response time" synchronous, dependency-free execution model. This duplication surfaces across three internal structures (`checkLocalArtifact`, `matchArtifactPattern`, `inferEntityClass`), with no single source of truth linking them.

## Implementation Details

`extractArtifacts()`'s four regex passes have no shared vocabulary discipline: the `classPattern` (`/[A-Z][a-zA-Z]+(Service|Agent|Manager|Engine|Handler|Analyzer|Classifier|Filter|Monitor)/g`) is intentionally broad, as detailed in sibling ArtifactPatternRegexCascade, while the per-team patterns tested by `matchArtifactPattern()` are narrow, enumerated alternations (`/VirtualTarget|EmbeddedFunction/i`, `/Lambda(Function)?|StepFunction/i`, `/EventMesh(Node|Producer|Consumer)/i`). This mismatch means many extracted class-name artifacts are silently dropped with no telemetry, and entries in `entityClassMap` (e.g. `Grafana: 'GrafanaDashboard'`) can imply broader coverage than the corresponding regex actually supports.

`checkLocalArtifact()`, the sibling TeamDirectoryPrefixMatch, performs an unguarded `Array.prototype.startsWith` scan over `teamDirectories` Map values in insertion order (Coding, RaaS, ReSi, UI). Because there is no trailing-slash or word-boundary guard, superficially similar but unrelated strings (e.g. `scripts-generator/foo.ts`) could falsely match a `'scripts'` prefix intended for the Coding team. Insertion order also creates a latent tie-breaking dependency: any future prefix collision across teams would silently resolve to whichever team was declared first in the constructor.

`inferEntityClass()` is noted as truncated and contains an orphaned `'Agentic'` team key that is unreachable given only four active teams recognized by `checkLocalArtifact()` — a sign of drift between the ownership vocabulary's declared surface and its actually wired logic.

## Integration Points

EntityPatternAnalyzer has no external dependencies beyond `LayerResult`/`ArtifactMatch` types, making it fully synchronous and I/O-free. Its only indirect integration with the broader system is through content strings it receives (presumably `knowledge.content`) and the shared JSON knowledge store. `verify-patterns.sh` connects to this same store non-programmatically: it mutates `$SHARED_MEMORY`'s `.metadata.last_pattern_verification` and `.metadata.pattern_compliance_score` via `jq`, without any direct import or interface link to the TypeScript pipeline. This creates a feedback-loop risk: if the script's own Markdown/JSON report is ever re-ingested as knowledge content, `extractArtifacts()` could scan it and generate spurious artifact entities extracted from a report *about* the codebase rather than the codebase itself.

The two XAML/C# fixtures (`integrations/graphify/tests/fixtures/xaml_viewmodel/...`) are bundled nearby but have no functional coupling — their `.cs`/`.xaml` extensions and `DesignViewModel` naming fall outside `extractArtifacts()`'s supported `filePathPattern` and `classPattern` vocabularies entirely, confirming they belong to graphify's separate indexer subsystem.

## Usage Guidelines

Developers extending `teamDirectories` or `artifactPatterns` should treat prefix strings as requiring implicit word-boundary discipline — a short or generic new prefix could silently reorder ownership resolution or cause cross-team false positives via `startsWith`. When adding new suffix vocabulary to `classPattern`, corresponding entries must also be added to the relevant team's `artifactPatterns` alternation, since the two are not automatically aligned and mismatches fail silently with no logging. Because extraction discards match-source provenance once merged into the `Set`, any future confidence-calibration work should be done at the extraction step, not assumed to propagate from it. Finally, `verify-patterns.sh`'s console.log detection shares the same textual-aliasing blind spot as the analyzer itself (e.g., renamed imports won't be caught), so it should be understood as a heuristic compliance signal, not a guarantee, and its compliance scoring has no allowlist for fixtures or generated files.

This ordering encodes an explicit confidence hierarchy: a direct path match returns confidence 0.9 while a naming-convention match returns 0.75, meaning the heuristic trusts 'where a file lives' strictly more than 'what a class is called' — a defensible choice given that directory placement is enforced by repo structure while naming conventions can drift.
