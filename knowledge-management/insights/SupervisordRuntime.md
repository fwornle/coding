# SupervisordRuntime — Technical Insight Document

## What It Is

SupervisordRuntime is the container-side execution boundary of DockerizedServices, implemented primarily in `docker/entrypoint.sh` and materialized in Supervisord's own `[program:...]` sections plus its `[include]`-directed override directory `/etc/supervisor/features.d/`. It is the runtime that turns a host-resolved feature snapshot into an actual set of running (or deliberately not-started) supervised processes inside the container. Its two children — FeatureGatingSnapshot and EnvFileImportFilter — represent the two distinct responsibilities entrypoint.sh fuses together at boot: deciding *which* programs supervisord should autostart, and sanitizing *what environment* those programs inherit.

![SupervisordRuntime — Architecture](images/supervisord-runtime-architecture.png)

Architecturally, SupervisordRuntime sits alongside ServiceStarter (the host-native equivalent) as one of the two "dual-mode" execution paths described in DockerizedServices — the same conceptual problem (feature-gated service startup) solved twice, once via shell/supervisord conf generation and once via JS's declarative SERVICE_CONFIGS.

## Architecture and Design

The dominant pattern is a **config-driven override/include layer rather than a rewrite**: entrypoint.sh never edits supervisord.conf's canonical `[program:...]` definitions. Instead, for each entry in the hardcoded `PROGRAM_FEATURES` mapping (`semantic-analysis:knowledge`, `graphify:codegraph`, `constraint-monitor:constraints`, `health-dashboard:health`), it shells out to `node -e` to consult the FeatureGatingSnapshot at `/coding/.coding/runtime/features.json` and, when a feature is off, writes only an `autostart=false` stanza into `disabled.conf`, which supervisord picks up via `[include]`. This keeps the "what programs exist" definition and the "what's currently enabled" decision in separate files — a clean separation that also means the override logic is trivially reversible (delete the include file, everything reappears).

A second, equally deliberate pattern is **fail-open startup behavior**: an absent snapshot, unreadable snapshot, or unrecognized feature key is treated as "enabled," on the explicit reasoning that a container silently running nothing is harder to diagnose than one running too much. This is the same philosophy documented for FeatureGatingSnapshot and is called out architecturally as an asymmetry — startup/display code fails open, whereas process-starting code elsewhere in the system tends to fail closed.

A third pattern, implemented by EnvFileImportFilter, is **env-driven credential boundary enforcement at process boot**: rather than an allowlist of approved variables, the `.env` import loop uses a suffix-based `case` match (`*_API_KEY|*_TOKEN|*_MANAGEMENT_KEY`) to `continue` past secret-shaped keys before exporting. This is explicitly narrower than but conceptually aligned with the "no direct secrets in-container" policy applied elsewhere (e.g., `scripts/prompt-classifier-service.mjs`'s `.env`-over-plist choice).

## Implementation Details

FeatureGatingSnapshot's mechanics are shell-native by necessity: because `jq` isn't installed in the image ("node is"), the PROGRAM_FEATURES list is a space-separated string parsed with `${pair%%:*}`/`${pair##*:}`, and each feature flag lookup is dispatched to a `node -e` one-liner reading the JSON snapshot. This is a deliberate trade of readability for zero added dependencies. The resulting `disabled.conf` stanzas are minimal — just enough to flip `autostart=false` — leaving supervisord.conf's program definitions as the single source of truth for command lines, directories, and other process configuration.

EnvFileImportFilter operates as a line-oriented `read -r key value` loop over `/coding/.env` (bind-mounted read-only), applying the suffix-match `case` guard *before* `export "$key=$value"`. Because the match is purely on variable-name patterns rather than content inspection, any secret whose name doesn't end in `_API_KEY`, `_TOKEN`, or `_MANAGEMENT_KEY` (e.g., a bare `SECRET`, `PASSWORD`, or `CREDENTIAL`) is not caught — a known, pattern-fragile boundary rather than a true secret scanner. The practical consequence is the T2 egress-lockdown invariant: in-container SDK clients cannot obtain raw provider credentials from the host `.env`, and must route outbound LLM/embedding calls through the host `llm-cli-proxy` at `:12435`.

## Integration Points

SupervisordRuntime is one of two independently-implemented enforcement points for feature gating in the system — the other being ServiceStarter's `SERVICE_CONFIGS[].feature` mechanism in `scripts/start-services-robust.js`. These two paths read from different sources (a mounted JSON snapshot vs. an in-process `loadFeatures()` call against `lib/features/catalogue.cjs`) and are coupled only by convention: `PROGRAM_FEATURES` names must line up with supervisord.conf's `[program:...]` sections and, separately, with the `FEATURE_IDS` catalogue used by SERVICE_CONFIGS. There is no shared code enforcing this correspondence — only test coverage, via `tests/features/container-gating.test.mjs` on the container side and `tests/features/service-gating.test.mjs` on the host side, the latter asserting SERVICE_ORDER/SERVICE_CONFIGS "cover each other exactly" and that disabled-vs-degraded semantics aren't conflated.

Within the parent DockerizedServices layer, SupervisordRuntime's outputs are consumed identically to host-native processes by ServiceProbe, which is deliberately blind to process ownership and only checks HTTP/TCP reachability — meaning a supervisord misconfiguration inside this runtime surfaces the same way as a host-side crash, requiring log inspection to disambiguate. Notably, entrypoint.sh's own `wait_for_service()` function implements its own ad-hoc `/dev/tcp` TCP probing for container-internal database readiness (Qdrant/Redis) rather than delegating to service-probe.js, so two independent health-probing implementations coexist in the codebase for different purposes.

## Usage Guidelines

Developers modifying PROGRAM_FEATURES must update three things in lockstep: the supervisord.conf `[program:...]` name, the entrypoint.sh mapping entry, and (if the feature also gates a host-side service) the corresponding SERVICE_CONFIGS `.feature` entry — none of these are structurally enforced except by tests, so drift is a real risk. When adding new secret-like environment variables, don't assume EnvFileImportFilter's suffix match protects them; if a variable doesn't end in `_API_KEY`, `_TOKEN`, or `_MANAGEMENT_KEY`, it will be exported into the container's environment unfiltered — new secret naming conventions should either conform to these suffixes or the filter's pattern list should be extended. Finally, when reasoning about "why is this container running fewer services than expected," remember the fail-open default: a missing or corrupt features.json is not a bug in this runtime, it's the documented, intentional fallback to "start everything."
