# BatchOnlinePaletteResolver — Technical Insight Document

## What It Is

BatchOnlinePaletteResolver is the SubComponent of **OnlineLearning** responsible for the concrete color/shape resolution mechanics implemented in `integrations/unified-viewer/src/graph/color-fallback.ts`. It sits alongside its siblings **LearningSourceClassifier** and **HierarchyParentDerivation** as one facet of a single file that answers the visual question "what color/shape should this node be?" through two structurally divergent code paths: `classColor()` (source-dependent, choosing between `BATCH_PALETTE` and `ONLINE_PALETTE`) and `nodeFillColor()`/`nodeShapeFor()` (source-independent, walking the ontology `parent` chain via `registry.get(cur)`). This entity's specific concern is the resolution logic that determines *which palette applies*, batch or online, given the ambiguity and historical fragility of the `metadata.source` signal described by its parent component.

## Architecture and Design

The defining architectural decision here is the deliberate **split between source-dependent and source-independent resolution**, a "Hybrid" redesign explicitly documented in code comments: online provenance was moved out of baked-in fill color and repositioned as a separate `ONLINE_RING_COLOR` overlay drawn in `D3GraphCanvas.tsx`. This means `classColor()` and `nodeFillColor()` are not alternate implementations of the same idea — they answer different questions (source classification vs. ontology inheritance) but risk being conflated in any naive refactor, since both ultimately produce colors from the same `BATCH_PALETTE`.

This resolver depends on the shared predicate `isOnlineLearned()` from `./learning-source` (owned conceptually by sibling **LearningSourceClassifier**) rather than any inline string comparison, reflecting the system-wide correction for the ETM/consolidator output stamping nodes `'online'` rather than `'auto'`. The deprecated `isOnlineSource(source)` function remains in place as a **deprecation-in-place** artifact — retained for legacy callers holding raw strings while `classColor()` itself has already migrated to invoking `isOnlineLearned({ metadata: { source } })` directly, illustrating non-atomic, in-progress migration within a single file.

## Implementation Details

`classColor()` takes a `className` and `source` string, delegates the batch/online boolean decision to `isOnlineLearned()`, and looks up the appropriate entry in `BATCH_PALETTE` or `ONLINE_PALETTE`. This is the resolver's core mechanism: a binary source-classification gate feeding a static palette table. It contrasts with the sibling **HierarchyParentDerivation**'s `nodeFillColor()`/`nodeShapeFor()` loops, which ignore `source` entirely and instead walk `registry.get(cur)?.parent` chains with cycle protection via a `seen` Set, falling back to `BATCH_PALETTE`/`DEFAULT_BATCH` or `SHAPE_PALETTE` when no ancestor override exists.

The ~138 entities lacking a `source` field entirely are handled not by this resolver's direct string comparison but by `isOnlineLearned()`'s broader subsystem/digest-shape fallback logic — a case the deprecated `isOnlineSource()` cannot see, since it only accepts bare strings. This asymmetry is a key implementation detail: the resolver's correctness depends on always going through the richer predicate rather than the legacy helper.

## Integration Points

BatchOnlinePaletteResolver's output feeds directly into `D3GraphCanvas.tsx`, where `nodeFillColor()` and the imported `ONLINE_RING_COLOR` are combined to render nodes — but explicitly kept out of the same dependency-list concerns as `deriveAncestryFromStorePath`, `selectedNodeIds`/`focalNodeId`, and `d3NodesRef` fit-to-bounds logic, per the documented "Locked Contract #3." This contract has been renegotiated across multiple phases, underscoring that the palette resolver's cheap, per-click nature must remain decoupled from expensive force-simulation rebuilds.

Upstream, this resolver depends on `isOnlineLearned` from `./learning-source` (LearningSourceClassifier's domain) and on the `ClassRegistryEntry` parent-chain data structure (HierarchyParentDerivation's domain). It has no coupling to unrelated online/batch-style patterns elsewhere in the system — notably `calculateDynamicEta()` in `ukb-workflow-modal.tsx` implements a parallel "live-learn, fallback-to-historical" shape for ETA math but shares zero code or abstraction with this resolver, and `ukbSlice.ts`'s `llmMode`/`mockLLM` duality and `multi-agent-graph.tsx`'s `llmUsage` tagging are similarly independent, unconsolidated instances of source/mode classification elsewhere in the codebase.

## Usage Guidelines

Developers extending or refactoring color-fallback.ts must preserve the intentional separation between `classColor()` and `nodeFillColor()`/`nodeShapeFor()` — they are not redundant despite structural similarity, and merging them would reintroduce the original online-classification bug the Hybrid redesign fixed. Any new caller needing online/batch classification should use `isOnlineLearned()` directly (as `classColor()` now does) rather than the deprecated `isOnlineSource()`, which cannot see subsystem or digest-shape fallbacks. Given that `nodeFillColor()` and `nodeShapeFor()` are copy-pasted parent-walking loops, adding a third visual property should prompt extraction of a shared `walkParentChain<T>()` helper rather than a third duplicate. Finally, any change to palette resolution logic must be checked against `D3GraphCanvas.tsx`'s Locked Contract #3 to avoid inadvertently pulling cheap color computation into expensive simulation-rebuild dependency lists.
