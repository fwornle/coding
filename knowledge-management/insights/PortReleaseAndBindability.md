# PortReleaseAndBindability

## What It Is

PortReleaseAndBindability is a pair of complementary port-lifecycle functions implemented in `scripts/start-services-robust.js`: `killProcessOnPortAndWait(port, options)` and `waitForPortBindable(port, options)`. Together they answer two distinct questions about the same resource — "did I successfully evict whatever was using this port?" and "can I actually bind to this port right now?" As a Detail component of its parent **ServiceStarter**, this logic sits underneath the feature-gated service catalogue: before `startOneService()` invokes a service's `startFn`, these functions are the tools available for ensuring a clean port before spawning a new process instance.

## Architecture and Design

The core architectural insight is that port release is verified through **two disjoint probes at different system layers**, rather than one. `killProcessOnPortAndWait()` implements a time-budget-driven escalation policy — SIGTERM first, then SIGKILL once half of `maxWaitMs` has elapsed — polling until the process appears gone. `waitForPortBindable()` then performs an entirely separate check: a throwaway `net.createServer().listen()` bound to `0.0.0.0`, which can detect kernel-level TIME_WAIT-style unavailability invisible to HTTP-level checks like `isPortListening()` in `lib/service-starter.js`. The explicit justification in code comments is that a crashed process leaves no HTTP listener to probe, yet the kernel may still hold the socket — so relying solely on process-kill success risks a caller hitting EADDRINUSE when spawning the replacement service.

This dual-probe design pairs with a third, structurally different function in the same file, `isProcessRunningByScript()`, which uses `pgrep` for **read-only reconciliation** (re-registering discovered processes via `psm.registerService()`) and never sends signals. The module thus encodes three risk postures side by side: destructive cleanup (kill), verification (bindability), and passive observation (pgrep-based reconciliation) — all fail-open on subprocess-command errors, treating `pgrep`/`lsof` failures as "not in use" rather than propagating.

## Implementation Details

`killProcessOnPortAndWait()` polls at `pollIntervalMs=200` against a `maxWaitMs=5000` default, escalating to SIGKILL at the midpoint regardless of how many poll ticks have occurred — an elapsed-time trigger, not an attempt-count trigger. It logs progress and failures via `console.log()` with a `[Cleanup]` prefix, including an explicit "Warning: Port {port} still in use after {maxWaitMs}ms timeout" message on failure.

`waitForPortBindable()` defaults to `maxWaitMs=5000`/`pollIntervalMs=250` and binds its probe server to `0.0.0.0` by default — deliberately calling `probe.unref()` on the throwaway server so an abandoned polling loop (e.g., from an unhandled rejection upstream) cannot pin the Node.js event loop. This mirrors other detached-handle patterns in the same file, such as the `transcriptMonitor` `startFn`'s `child.unref()` on the spawned `enhanced-transcript-monitor.js` process. Unlike its sibling function, however, `waitForPortBindable()` returns `false` on failure with **no logging at all** — no port number, no elapsed time — which is a notable observability gap precisely for the hardest-to-diagnose failure mode (kernel-held sockets after a crash) that the function exists to catch.

The `0.0.0.0` default bind host is calibrated for HTTP-serving members of `SERVICE_ORDER`, but not all `SERVICE_CONFIGS` entries actually need it — `transcriptMonitor`, for instance, doesn't bind a TCP port at all and is instead tracked via `createPidHealthCheck()`. A caller invoking the probe for a service that only binds `127.0.0.1` could get a false negative: the probe succeeds on all interfaces, but the real service later fails on loopback-only due to some other constraint.

## Integration Points

These two functions operate independently of the retry/backoff machinery that sibling component **RetryWithDeadlineStarter** provides via `startServiceWithRetry`, `isPortListening`, `isTcpPortListening`, `isProcessRunning`, and `sleep`, all imported from `lib/service-starter.js`. Critically, no observed caller chains `killProcessOnPortAndWait()` directly into `waitForPortBindable()` for the same port — despite the two being explicitly complementary — suggesting either implicit reliance on `startServiceWithRetry()`'s own retry loop to paper over the gap, or an unexercised integration seam.

The timeout systems are also uncoordinated: both port functions default to independent 5-second ceilings, entirely unrelated to the per-service `maxRetries`/`timeout` values declared in **FeatureGatedServiceCatalogue**'s `SERVICE_CONFIGS` (e.g., `transcriptMonitor`'s `maxRetries=3`/`timeout=20000`). A service's real startup budget is the sum of potentially several retry attempts, each of which may separately invoke port-release logic with its own 5-second window — a detail invisible from glancing at `SERVICE_CONFIGS' timeout` field, which only bounds the health-check wait inside `startServiceWithRetry()`, not any pre-flight cleanup a `startFn` chooses to perform.

## Usage Guidelines

Treat `killProcessOnPortAndWait()` and `waitForPortBindable()` as complementary, not redundant — a caller that only invokes the kill function and immediately spawns a new service risks an EADDRINUSE crash that silently consumes one of `startServiceWithRetry()`'s `maxRetries` slots. When adding new services to `SERVICE_CONFIGS`, consider whether the service actually binds a TCP port on all interfaces before relying on `waitForPortBindable()`'s default `0.0.0.0` host; PID-tracked services like `transcriptMonitor` should bypass this probe entirely. Because `waitForPortBindable()` is silent on failure, any new caller or debugging effort should assume the absence of logs does not mean absence of problems — add port number and elapsed-time diagnostics if extending this function. Finally, be aware that stacking retries (`SERVICE_CONFIGS`) on top of per-call port-release timeouts multiplies worst-case startup latency in ways not visible from either configuration surface alone; slow-dying old processes combined with slow-starting new ones can exceed expectations set by a single glance at the retry config.
