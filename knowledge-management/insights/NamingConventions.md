# NamingConventions

## What It Is

NamingConventions, as implemented in `src/ontology/heuristics/EntityPatternAnalyzer.ts` and enforced by `scripts/knowledge-management/verify-patterns.sh`, is the machine-readable operationalization of the suffix-based class-naming idiom described at the parent CodingPatterns level (Manager/Service/Adapter). Where CodingPatterns documents the human-facing convention — that `*Manager` classes signal stateful coordination points like `GraphDatabaseManager` or `CircuitBreakerManager` — NamingConventions is the subsystem that turns that convention into an automated classification and compliance-checking mechanism. It is not a passive documentation artifact: it is "Layer 1" of a larger classification pipeline (per `analyzeEntityPatterns()`, `EntityPatternAnalyzer.ts:79-95`), meaning naming conventions here are load-bearing infrastructure for team/entity attribution, not just readability sugar.

Its two children, TeamEntitySuffixMap and ArtifactPatternRegistry, describe complementary facets of the same underlying data: the team-scoped suffix vocabularies (`LSL(Session|Monitor|Classifier)`, `Kubernetes(Cluster|Pod|Service)`, `VirtualTarget`, `Lambda(Function)?`, etc.) and the pattern-matching registry that resolves them against extracted artifacts.

## Architecture and Design

![NamingConventions — Architecture](images/naming-conventions-architecture.png)

The core architectural pattern is a two-step artifact resolution strategy with tiered confidence scoring, sibling-documented in OntologyHeuristicsLayering: `checkLocalArtifact()` (`EntityPatternAnalyzer.ts:154-165`) attempts a cheap directory-prefix match against `teamDirectories` first, yielding 0.9 confidence, and only falls back to the more expensive `matchArtifactPattern()` (`:172-190`) regex pass, yielding 0.75 confidence, if no path match exists. This ordering is simultaneously a performance optimization (protecting a documented sub-millisecond budget by deferring `RegExp.test()` work) and an implicit trust hierarchy — verified location outranks inferred naming.

Underneath this, `extractArtifacts()` (`:128-146`) runs four independent regexes — `filePathPattern`, `npmPattern`, `classPattern` (the `*Service|*Agent|*Manager|*Engine|*Handler|*Analyzer|*Classifier|*Filter|*Monitor` suffix vocabulary), and `dirPattern` — merging all matches into a single untyped `Set<string>`, as detailed in TeamEntitySuffixMap. Because type information from the extraction phase is discarded, the two matchers implicitly re-partition the artifact space by shape (`startsWith()` for directory-like strings, `.test()` for name-like strings) rather than by explicit provenance. ArtifactPatternRegistry further notes that because `analyzeEntityPatterns()` returns on the first Set match, classification is order-dependent on V8 insertion order — a knowledge string containing both a real path and a coincidental class-name match will resolve nondeterministically relative to any explicit precedence rule.

Naming conventions here are also organized as per-team sub-dialects rather than one global scheme, composed under a shared classification mechanism — Coding-team conventions (`LSL*`, `Constraint*`, `MCP*`, `Knowledge*`) sit alongside RaaS (`Kubernetes*`, `Argo*`), ReSi (`VirtualTarget`, `MF4Container`), and UI (`Lambda*`, `React*`) idioms, all funneled through the same `artifactPatterns` array and `teamMappings` lookup.

## Implementation Details

![NamingConventions — Relationship](images/naming-conventions-relationship.png)

The duplication between `entityClassMap` (embedded per-pattern in `artifactPatterns`) and the private `teamMappings` record in `inferEntityClass()` (`:205-215`) is a concrete maintenance seam flagged across multiple observations: adding or changing a team's naming convention requires updating two separate data structures in the same file, since neither is the canonical source of truth. This sits alongside the sibling ConfigurationExternalization observation that `teamDirectories` and `artifactPatterns` are hardcoded class-field literals in the constructor rather than externalized to config files — a deliberate but partial externalization, where classification logic never branches on team name directly but the tables themselves aren't yet data-driven the way `verify-patterns.sh`'s pattern list is.

That script is the inverse operation: instead of inferring ownership from names, it audits compliance with named patterns like `ConditionalLoggingPattern` (counting `console.log` vs `Logger.(log|debug|info|warn|error)` via `rg`, `verify-patterns.sh:38-42`) and `ReduxStateManagementPattern` (`useState` vs `useSelector|useDispatch|createSlice`). Critically, its list of enforced patterns is pulled dynamically from `$SHARED_MEMORY` via a `jq` query selecting `TransferablePattern` entities with `significance >= 8` (`:100-108`), making pattern governance itself data-driven. It then computes a blunt `PASSED_CHECKS * 100 / TOTAL_CHECKS` compliance score and writes it back into `$SHARED_MEMORY.metadata.pattern_compliance_score` via a `jq`-then-`mv` atomic replace (`:175-181`) — meaning the same knowledge store both defines conventions and scores compliance against them, a tight coupling and single point of failure for the whole convention lifecycle.

A concrete gap in coverage: the XAML/C# fixtures under `integrations/graphify/tests/fixtures/xaml_viewmodel/` (`DesignViewModel.cs`, `DesignView.xaml`) follow the MVVM `*ViewModel`/`*View` suffix idiom, structurally analogous to but distinct from the TS-centric `*Manager`/`*Service` conventions this analyzer targets. Since `extractArtifacts()`'s `filePathPattern` is restricted to `.ts|.js|.cpp|.java|.tsx|.jsx|.py|.go|.rs`, `.xaml` and its C# view-model pair are invisible to Layer 1 entirely — no artifact is extracted, let alone classified.

## Usage Guidelines

New naming conventions for a team should be added carefully in both `entityClassMap` and `teamMappings` simultaneously, since no canonical single source exists yet — a change in one without the other silently desyncs classification. Developers introducing new artifact types should be aware that extraction is shape-based, not type-tagged, so a class name and a directory string are matched only by which regex succeeds, not by declared intent — precedence is effectively insertion-order-dependent and should not be relied upon for correctness-critical attribution. Anyone extending indexing to new languages (as graphify's XAML fixtures anticipate) must add both a file-extension pattern and a suffix vocabulary (e.g., `*ViewModel`/`*View`) or the analyzer will silently ignore those files. Finally, since `verify-patterns.sh` sources its enforced-pattern list from `$SHARED_MEMORY` entities marked `significance >= 8`, raising or lowering a pattern's significance score is the primary lever for turning compliance enforcement on or off for that convention.
