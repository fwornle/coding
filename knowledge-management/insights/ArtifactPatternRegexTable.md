# ArtifactPatternRegexTable: Technical Insight Document

## What It Is

The `ArtifactPatternRegexTable` is the `artifactPatterns` array literal defined in the constructor of `EntityPatternAnalyzer.ts` (lines 56-121). It is a hardcoded, four-team lookup table — covering Coding, RaaS, ReSi, and UI — where each entry pairs an array of case-insensitive `RegExp` objects with a parallel `entityClassMap`. This table is the data backbone consumed by `matchArtifactPattern()` (lines 187-206), which is the second-tier fallback heuristic in the team-attribution cascade implemented by its parent component, `AgentWrapperConvention`. As a child/detail of that parent, it embodies — but also undermines — the parent's stated philosophy that classification data should live outside code (as with `prompt-classifier.yaml`), since here the regexes and class maps are inline TypeScript literals rather than externalized configuration.

## Architecture and Design

Structurally, the table follows a rule-table / lookup-table pattern: an array of `{team, patterns, entityClassMap}` records that gets linearly scanned. It sits at the second step of the `TwoStepArtifactAttribution` cascade — invoked only when `checkLocalArtifact()` (using the sibling `HardcodedTeamDirectoryMap`, confidence 0.9) fails to find a directory-prefix match. Matches from this table yield a flat confidence of 0.75 regardless of pattern specificity.

A key architectural weakness is the total decoupling between this regex table and the `teamDirectories` Map checked in `checkLocalArtifact()`. Both structures independently encode "what identifies team X," yet share no vocabulary and no cross-validation — team identity has two structurally unrelated sources of truth. This mirrors the disconnection noted between `ArtifactPatternRegexTable` and the entirely separate `verify-patterns.sh` compliance script, whose case-statement pattern matcher recognizes only `Logging`/`Redux`/`State` substrings by name. Both mechanisms apply a "naming-convention-as-signal" philosophy, but as non-communicating hardcoded tables with no generation or validation link between them.

## Implementation Details

Each team entry contains regexes of varying structural rigor. Coding's four patterns are uniformly suffix-anchored compositions (e.g., `LSL(Session|Monitor|Classifier)`), which are precise and low-risk. In contrast, ReSi and UI mix suffix-anchored constructs (`MF4Container|MCAPContainer`, `ProtobufSPP|KaitaiBinaryBlob`, `Argo(Workflow|Template)`, `EventMesh(Node|Producer|Consumer)`) with bare, unanchored alternations like `/VirtualTarget|EmbeddedFunction/i`, `/Lambda(Function)?|StepFunction/i`, and UI's `/React(Component)?|Redux/i`. Because these regexes lack anchoring and rely on the `/i` flag, they can match arbitrary substrings inside artifacts produced upstream by `ArtifactExtractionRegexes` — e.g., a file path like `src/virtualtargetconfig.ts` or a class name `MyLambdaWrapper` — triggering confident (0.75) team attribution on weak evidence.

The `entityClassMap` per team (e.g., `Redux` → `ReduxState`, `Kubernetes`, `Argo`, `EventMesh`) is meant to be paired with the matched regex via `inferEntityClassFromPattern`, a method referenced but not fully shown. This inference is a fragile string-prefix operation: it must derive the map key (`Redux`) from an arbitrary matched substring (`ReduxState`, `useReduxHook`) without the benefit of a captured regex group, creating a silent-failure risk if the matched prefix and map key diverge (e.g., matching `PrometheusMetric` against a map key of `Prometheus` with no exact-match verification).

## Integration Points

This table is consumed exclusively by `matchArtifactPattern()`, which is called after `checkLocalArtifact()` returns no result in the `analyzeEntityPatterns()` flow. Upstream, it depends on artifacts produced by the sibling `ArtifactExtractionRegexes`, which runs four independent regex passes (file paths, npm scopes, class-suffix names, bare directory prefixes) into a single `Set<string>`. Because that extraction can produce near-duplicate or partial-overlap artifacts, the same underlying reference can hit this table's patterns multiple times with different outcomes depending on iteration order — compounding the ordering issue already identified in `TwoStepArtifactAttribution`, where the first matching artifact short-circuits the search rather than the highest-confidence one.

Downstream, the `entityClass` values from this table's maps flow directly into `analyzeEntityPatterns()`'s output field, always tagged with confidence 0.75 — an integration point where precision information is lost, since no distinction is made between a `LSLClassifier` match (Coding) and a bare `Redux` match (UI), despite very different specificity.

## Usage Guidelines

Any engineer modifying this table should recognize it as one of (at least) three independently maintained, uncoordinated team-identity sources in this codebase: the `HardcodedTeamDirectoryMap`, this regex table, and the unrelated `verify-patterns.sh` case statement. Adding a new module type (e.g., a hypothetical `XCPProtocol` class for ReSi) requires manually updating this array even if `teamDirectories` already implies coverage — there is no compiler or test-time check linking the two.

When adding new patterns, prefer suffix-anchored, multi-part compositions (as Coding does) over bare single-word alternations, since unanchored patterns risk false positives against arbitrary extracted substrings. Any new `entityClassMap` entry must have its key verified against what `inferEntityClassFromPattern` would actually extract from a real regex match — mismatches fail silently. Finally, treat the flat 0.75 confidence as a known limitation, not a guarantee of precision uniformity, and consider that externalizing this table to YAML/JSON (matching the `prompt-classifier.yaml` convention used elsewhere) would resolve much of the maintainability and validation risk described above.
