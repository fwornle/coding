# TeamDirectoryPrefixMatch — Technical Insight Document

## What It Is

TeamDirectoryPrefixMatch is implemented as the private `checkLocalArtifact()` method in `src/ontology/heuristics/EntityPatternAnalyzer.ts`, invoked as step (a) inside `analyzeEntityPatterns()`. It is the first-tier heuristic in a two-step ownership-attribution cascade defined by its parent component, `OwnershipHeuristicPattern`: given a candidate artifact string, it determines which team owns it by testing whether that string begins with any of a fixed set of directory prefixes. The implementation is deliberately minimal — a nested `O(teams × dirs-per-team)` scan using `dirs.some((dir) => artifact.startsWith(dir))` against a hardcoded `teamDirectories` Map covering four teams (`Coding`, `RaaS`, `ReSi`, `UI`). Its output, when a match is found, immediately short-circuits the rest of the cascade by calling `inferEntityClass(artifact, team)` and returning — it never consults the sibling suffix-based heuristic.

## Architecture and Design

The component embodies three related architectural patterns. First, a **cascading heuristic pattern**: cheap, deterministic prefix matching is attempted before falling back to the more expensive regex-based `matchArtifactPattern()` (the sibling logic described alongside `ArtifactPatternRegexCascade`). Second, a **closed-world lookup table pattern**: ownership resolution is driven entirely by a hardcoded `Map` literal rather than any dynamic or config-driven registry, meaning the four teams and their fifteen directory prefixes constitute the total universe of resolvable paths. Third, a **first-match-wins iteration** pattern: because `Map` iteration order follows insertion order (`Coding`, `RaaS`, `ReSi`, `UI`), any prefix collision between teams would silently favor whichever team was declared first — currently a latent rather than active risk, since none of the fifteen prefixes overlap.

This design encodes an explicit trust hierarchy, inherited from the parent `OwnershipHeuristicPattern`: physical file location is trusted strictly more than naming convention. A directory-prefix match yields confidence `0.9`, while the suffix-based fallback yields `0.75`. This is a defensible choice — directory structure is enforced by the repo, whereas naming conventions can drift — but it also means TeamDirectoryPrefixMatch has *unconditional* precedence, never allowing `matchArtifactPattern()` a chance to weigh in even when a class name strongly suggests a different team.

## Implementation Details

The core logic lives in `checkLocalArtifact()`: for each `[team, dirs]` entry in `teamDirectories`, it tests `artifact.startsWith(dir)` and returns an `ArtifactMatch` with `confidence: 0.9` on the first hit. The matching primitive is plain `String.prototype.startsWith`, not path-segment-aware comparison — there is no check for a trailing `/` or segment boundary, so a hypothetical future directory like `scripts-experimental` would falsely satisfy `artifact.startsWith('scripts')` and be misattributed to `Coding`. Today this doesn't manifest because the four teams' directory sets (`src/ontology`, `src/knowledge-management`, `src/live-logging`, `scripts`, `.specstory` for Coding; `raas-service`, `orchestration-engine`, `event-mesh` for RaaS; `virtual-target`, `embedded-functions`, `reprocessing-engine` for ReSi; `curriculum-alignment`, `aws-lambda`, `multi-agent-system` for UI) are structurally disjoint.

The `0.9` confidence figure is duplicated: once in the `ArtifactMatch` object inside `checkLocalArtifact()`, and again independently as an inline literal in the `LayerResult` constructed by `analyzeEntityPatterns()` when `localMatch` is truthy. The caller never reads `localMatch.confidence`, so these two literals have no enforced relationship — a classic duplication hazard also flagged at the `OwnershipHeuristicPattern` level.

Once a team is resolved via prefix match, `inferEntityClass(artifact, team)` is invoked with the team already fixed. This means the `teamMappings` object inside `inferEntityClass()` — including its `Agentic` branch — can never override a path-based decision; an artifact like `AgenticVectorStore` located under `src/ontology/` is bound to `Coding` at 0.9 confidence before any class-name-based mapping is considered, corroborating that the `Agentic` mapping is effectively dead code for path-derived artifacts.

## Integration Points

TeamDirectoryPrefixMatch depends entirely on candidate strings supplied by `extractArtifacts()`, specifically its directory-only regex pass (`/[a-z-]+\/[a-z-]+\//g`) and file-path regex pass (matching lowercase-hyphen segments ending in known extensions). This shared upstream pipeline is the same one feeding the sibling `ArtifactPatternRegexCascade` and is described in full by the sibling entity `ArtifactExtractionPipeline`, which unions four separate regex passes into a single `Set<string>` with no provenance tagging. As a consequence, TeamDirectoryPrefixMatch has no way to know whether a given string was extracted as a path or a class name — it simply applies `startsWith` to everything in the set uniformly. This also means the component inherits the extraction layer's case-sensitivity assumptions: any path segment with uppercase letters, leading underscores, or digits (e.g., `Src/Ontology/...`) is never extracted at all and silently bypasses the prefix heuristic, falling through to `matchArtifactPattern()` or to no match.

Downstream, its sole consumer is `analyzeEntityPatterns()`, which treats a non-null result from `checkLocalArtifact()` as authoritative and skips `matchArtifactPattern()` entirely for that artifact.

## Usage Guidelines

Developers extending `teamDirectories` should treat it as a closed, hand-maintained namespace: adding or renaming a team requires directly editing the Map literal in `EntityPatternAnalyzer.ts` and redeploying — there is no config-driven indirection. New prefixes must be checked against existing ones for accidental collisions, since `startsWith` performs no segment-boundary validation and insertion order silently determines tie-breaking. Any artifact whose path does not begin with one of the fifteen known prefixes (e.g., `integrations/graphify/`, `docker/`) returns `null` and falls through the cascade rather than defaulting to an "unknown" team — this closed-world behavior should be kept in mind when auditing coverage gaps. Finally, if the `0.9` confidence value is ever retuned, both duplicate literals — in `checkLocalArtifact()`'s `ArtifactMatch` and in `analyzeEntityPatterns()`'s `LayerResult` construction — must be updated together, since nothing in the `ArtifactMatch`/`LayerResult` types enforces synchronization.
