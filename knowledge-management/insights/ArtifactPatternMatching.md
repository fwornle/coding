# ArtifactPatternMatching — Technical Insight Document

## What It Is

ArtifactPatternMatching is the regex-driven fallback mechanism implemented in `src/ontology/heuristics/EntityPatternAnalyzer.ts`, responsible for inferring both team ownership and entity class of a code artifact when its file path does not match a known team directory prefix. It is the second layer in a two-step cascade defined in `analyzeEntityPatterns` (lines 120-165), operating on the results of `extractArtifacts` (lines 180-200), which scans free-form content with four independent regexes — file paths, npm packages, suffix-based class names (e.g., `/[A-Z][a-zA-Z]+(Service|Agent|Manager|Engine|Handler|Analyzer|Classifier|Filter|Monitor)/g`), and directory-only paths — merging all hits into a single `Set<string>` for downstream matching. The core data structure is the `ArtifactPattern` interface (lines 14-18), which couples a `team` identifier, an array of `RegExp` objects, and an `entityClassMap` keyed by keyword into one record per team.

## Architecture and Design

The dominant pattern here is rule-based/heuristic classification: rather than a trained classifier, teams are recognized via hand-authored regex arrays and keyword maps, functioning as a lightweight substitute for semantic understanding. This sits inside a chain-of-responsibility-style layered fallback shared with sibling component TeamDirectoryOwnership: `checkLocalArtifact` (directory-prefix match, confidence 0.9) runs first, and only on failure does `matchArtifactPattern` (regex suffix match, confidence 0.75) — the subject of this document — get invoked. This ordering is a deliberate design decision encoding the assumption that physical location in the repo tree is a stronger ownership signal than naming convention alone; a correctly-named class like `ConstraintRule` living inside `raas-service/` would be attributed to RaaS by the directory check before the Coding-team regex pattern ever has a chance to apply.

Architecturally, `EntityPatternAnalyzer` is a pure, synchronous, stateless-after-construction component with no external dependencies beyond its own `../types.js` module (`LayerResult`, `ArtifactMatch`), and no I/O — all state (`teamDirectories`, `artifactPatterns`) is built in-memory in the constructor, consistent with a documented sub-millisecond response budget. Convention-over-configuration is the guiding philosophy: both team ownership and entity class are derived purely from string suffixes/prefixes rather than explicit metadata, a design shared with parent component NamingConventions and its `verify-patterns.sh` script.

## Implementation Details

The suffix-based class-name regex in `extractArtifacts` is inherently permissive — it is case-insensitive-adjacent (capital-letter-led) and has no negative/exclusion list, meaning any capitalized word ending in one of the nine recognized suffixes (`Handler`, `Manager`, etc.) is treated as a candidate artifact, including incidental matches in prose or comments unrelated to team ownership. These candidates then flow into `matchArtifactPattern`, which checks them against each team's `patterns: RegExp[]` array and resolves an entity class via `inferEntityClassFromPattern`.

A concrete correctness gap exists in this resolution step: the Coding team's patterns array includes `/MCP(Agent|Service|Tool)/i`, but its `entityClassMap` only maps the bare keyword `MCP: 'MCPAgent'` (lines 64-83). This silently collapses `MCPService` and `MCPTool` matches into the same `MCPAgent` entity class — a latent classification-accuracy bug rather than a crash risk, since a class is still returned, just not necessarily the correct one.

Compounding this, the same team-to-convention knowledge is duplicated across three separate structures within the same file: the `teamDirectories` Map, the per-team `entityClassMap` nested in `artifactPatterns`, and a third `teamMappings` object inside `inferEntityClass` (~line 230+, truncated) used by the directory-match path. All three hard-code the same Coding-team keywords (`LSL`, `Constraint`, `Knowledge`, `MCP`) independently, meaning any new entity convention must be added in at least two, potentially three, places kept in sync by hand.

## Integration Points

ArtifactPatternMatching is tightly coupled to sibling components EntityClassMapping and TeamDirectoryOwnership within the same file and class — all three share the `ArtifactPattern` interface, the `teamDirectories` Map, and the entity-class lookup structures, forming an interlocking but non-centralized ownership-inference system. It has no dependency on other production modules beyond its types import, making it easy to unit test in isolation but also isolated from any shared canonical source of truth.

Notably, its parent NamingConventions component includes `verify-patterns.sh`, which independently encodes a structurally analogous "suffix/keyword implies compliance" heuristic (matching `Logger.(log|debug|info|warn|error)` via ripgrep versus raw `console.log` counts) in bash rather than TypeScript. These two systems are architecturally parallel but disconnected — neither shares logic nor a canonical pattern definition with the other, so keeping naming conventions consistent across the codebase currently requires manually synchronizing two independently maintained implementations.

Separately, the `integrations/graphify/tests/fixtures/xaml_viewmodel/` directory contains `DesignViewModel.cs` and `DesignView.xaml`, which exercise the same "suffix implies convention" idea (ViewModel-suffix, `d:DataContext` binding) but in C#/XAML for the graphify submodule's own pattern-detection logic. This fixture pair is test input data, not production convention-enforcement code, and is architecturally isolated from `EntityPatternAnalyzer.ts` — it validates a structurally analogous but independently implemented capability rather than reusing this component.

## Usage Guidelines

Developers extending team-ownership or entity-class inference should treat the directory-based check (TeamDirectoryOwnership) as authoritative and this pattern-matching fallback as a secondary signal only invoked when directory prefixes fail to match — do not assume regex-based matches override location-based ones. When adding a new keyword/suffix convention (e.g., a new `*Rule` or `*Session` type for the Coding team), all three duplicated structures — the team's `patterns` array, its `entityClassMap`, and the corresponding `teamMappings` entry in `inferEntityClass` — must be updated together; failing to do so reproduces the existing MCP suffix-collapse bug pattern. Because the suffix-based extraction regex has no exclusion list, developers should be cautious about feeding arbitrary prose or comments through `extractArtifacts`, as capitalized words ending in common suffixes will generate false-positive artifacts. Finally, given the disconnect between this TypeScript heuristic and the bash-based `verify-patterns.sh`, any change to canonical naming conventions should be manually mirrored in both places until a shared source of truth is established.
