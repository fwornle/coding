# ForceDirectedLayout — Technical Insight Document

## What It Is

ForceDirectedLayout is the dynamic layout engine underpinning `D3GraphCanvas.tsx` (`integrations/unified-viewer/src/graph/D3GraphCanvas.tsx`), the knowledge-graph rendering half of the parent `GraphVisualRendering` surface. Concretely, it is built on `d3.forceSimulation` combined with `d3.forceLink(150)` and `d3.forceManyBody(-500)` — parameters that are not independently derived from unified-viewer's own data, but are a deliberate, documented "port" of an earlier VKB component (`integrations/memory-visualizer/.../GraphVisualization.tsx`). The porting was a conscious response to failed attempts to replicate the same visual reference using `sigma` + `graphology-layout`, which drifted from the target look. As such, ForceDirectedLayout should be understood less as an organically tuned layout algorithm and more as a pinned visual contract with a prior codebase.

## Architecture and Design

The defining architectural decision is fidelity-over-independence: rather than tuning force parameters against unified-viewer's actual graph density/size, the team chose to preserve the VKB reference implementation's constants verbatim (`forceLink(150)`, `forceManyBody(-500)`) to guarantee visual parity. This trades adaptability for predictability.

Layered atop the simulation is a strict viewport-stability invariant, referred to internally as "Locked Contract #3." The main render `useEffect` in `D3GraphCanvas.tsx` treats its dependency array as load-bearing: an original centering effect (panning on `selectedNodeId` change) was removed after operator feedback, then selectively reintroduced under "Plan 06 gap-closure — Decision 2," but scoped narrowly to Layer-0→Layer-1 transitions via a `selectionSource` subscription that is deliberately excluded from the main effect's dependency list. This is a notable architectural pattern: using dependency-list exclusion as an intentional guard rail against scope creep, with the history of reversals preserved as inline comments — an audit trail documenting design correction directly in code rather than only in commit history.

Within this canvas, ancestry/highlight-path computation (`deriveAncestryFromStorePath`) implements a fast-path/slow-path reconciliation pattern: a fast path short-circuits when an inline BFS (`computeAncestryPath`) agrees exactly with the Zustand store's `pathToSelected` set, while a slow path prunes BFS results to store membership and assigns unreachable-but-store-tagged nodes the dimmest depth so they still render without dominating the gradient. This "writer's intent wins" strategy accommodates cases where filter changes cause the two sources of truth to diverge mid-session.

## Implementation Details

Node visual encoding is delegated to `color-fallback.ts`, where `nodeFillColor` and `nodeShapeFor` implement an identical parent-walk algorithm: registry `display.color`/`display.shape` lookup → static palette fallback → walk to `reg.parent`, guarded by a `seen` set against cycles. This walk logic is duplicated rather than abstracted into a shared helper, meaning any future resolver (e.g., a hypothetical `nodeBorderStyleFor`) would need to replicate the same traversal-with-cycle-guard by hand.

The file also carries three simultaneously-live generations of color resolution: the legacy `classColor` (FNV hue via `_classHue`, superseded but still exported), the `DEPRECATED isOnlineSource` (kept only for string-based callers, delegating to `isOnlineLearned`), and the current registry-based `nodeFillColor`/`nodeShapeFor`. Sibling entity **ClassColorFallback** documents the concrete motivation for this evolution: `classColor()`'s two-palette dispatch (`BATCH_PALETTE` vs `ONLINE_PALETTE`) previously misclassified nodes because it checked `source === 'auto'` literally, when online-learned data is usually stamped "online" by ETM/consolidator output. `isOnlineLearned` was extracted specifically to eliminate this string-literal drift, though the buggy predecessor remains present for backward compatibility.

## Integration Points

ForceDirectedLayout sits within `GraphVisualRendering` alongside a structurally unrelated sibling, **MultiAgentGraphSvg** (`multi-agent-graph.tsx`), which renders the UKB workflow pipeline as a static, fixed-topology SVG using hoisted constants `WAVE_AGENTS`, `KG_OPERATOR_CHILDREN`, and the large hand-authored `AGENT_SUBSTEPS` schema. Both are described as "graph" renderers but share no common node/edge type, color resolver, or rendering abstraction — dark-mode or other visual-consistency work must be solved independently via `useWorkflowColors()` on the multi-agent side and `nodeFillColor`/`nodeShapeFor` here. Sibling **HierarchyParentDerivation** frames this bifurcation as a legitimate consequence of differing problem domains (fixed pipeline topology vs. open-ended knowledge graph) rather than accidental duplication.

Data flows into the D3 simulation via `useGraphData`, contrasting with the multi-agent graph's static, hand-authored topology. `deriveAncestryFromStorePath` integrates with Zustand store state (`pathToSelected`) to reconcile derived and stored ancestry paths.

## Usage Guidelines

Developers modifying `D3GraphCanvas.tsx` must not casually add subscriptions to the main render `useEffect`'s dependency array — this is an explicit, comment-documented invariant ("Locked Contract #3") protecting viewport stability; new zoom/pan behavior tied to `selectionSource` should follow the established pattern of scoped, separate effects rather than expanding the primary dependency list. When tuning force-layout parameters, recognize that `forceLink(150)`/`forceManyBody(-500)` are pinned to a visual reference from another codebase (VKB's `GraphVisualization.tsx`), not to unified-viewer's actual data shape; this may become brittle as graphs grow larger or denser, and any retuning should be validated against real data rather than assumed safe. When resolving node color/shape, prefer `nodeFillColor`/`nodeShapeFor` over the deprecated `classColor`/`isOnlineSource`; if a new visual-encoding resolver is needed, replicate the existing parent-walk-with-cycle-guard pattern explicitly, since no shared helper currently exists to inherit from.
