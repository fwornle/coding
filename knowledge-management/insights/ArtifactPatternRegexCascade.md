# ArtifactPatternRegexCascade

## What It Is

ArtifactPatternRegexCascade refers to the pair of regex-driven detection mechanisms inside `src/ontology/heuristics/EntityPatternAnalyzer.ts` that together form the pattern-matching half of the ownership heuristic: `extractArtifacts()`, which harvests candidate artifact strings from raw content, and `matchArtifactPattern()`, which tests those candidates against per-team suffix vocabularies. As a child of the OwnershipHeuristicPattern, this cascade implements step (b) of the two-step confidence hierarchy — the lower-confidence (0.75) naming-convention fallback that only runs after the parent's path-based check (`checkLocalArtifact()`, embodied by sibling TeamDirectoryPrefixMatch) has failed to find a direct directory match. Its sibling ArtifactExtractionPipeline describes the extraction side of this same file; ArtifactPatternRegexCascade is best understood as the "regex vocabulary" layer that both the extraction and matching passes draw from, and where the vocabulary misalignment between them lives.

## Architecture and Design

The defining architectural trait here is "regex-as-executable-convention": informal engineering naming conventions (`*Service`, `*Manager`, `*Analyzer`) and directory conventions are re-encoded directly as regex literals and string arrays inside TypeScript, rather than through an external schema. This is explicitly called out as diverging from the YAML-driven configuration used elsewhere (e.g., <AWS_SECRET_REDACTED>), making EntityPatternAnalyzer's team taxonomy — `teamDirectories`, `artifactPatterns`, `teamMappings` — a set of hardcoded literals baked into the source file itself.

A second key design trait is the deliberate broad-then-narrow structure: `extractArtifacts()`'s `classPattern` regex (`/[A-Z][a-zA-Z]+(Service|Agent|Manager|Engine|Handler|Analyzer|Classifier|Filter|Monitor)/g`) is a strict superset of the vocabulary any single team's `artifactPatterns` entry actually tests for (e.g., `LSL(Session|Monitor|Classifier)`, `Kubernetes(Cluster|Pod|Service)`, `React(Component)?|Redux`). Extraction over-generates; matching narrowly enumerates. The two layers were evidently authored independently rather than derived from one shared vocabulary, and nothing in `matchArtifactPattern()`'s loop logs or surfaces the artifacts it silently discards.

## Implementation Details

`extractArtifacts()` runs four independent, unconditional regex passes — `filePathPattern`, `npmPattern`, `classPattern`, `dirPattern` — against the same content string on every call, unioning results into a `Set<string>` and losing provenance about which pattern produced each match (as detailed in ArtifactExtractionPipeline). Because `String.match()` with the `g` flag materializes a full match array before Set deduplication even starts, this is four full linear scans per `analyzeEntityPatterns()` invocation with no short-circuiting between sub-patterns.

`matchArtifactPattern()` then iterates roughly 19 compiled `RegExp` objects across per-team arrays using cheap `.test()` calls rather than `.match()`, which keeps the per-artifact cost genuinely sub-millisecond as the class's own doc comment claims. However, this cost is paid once per extracted artifact, not once per call: `analyzeEntityPatterns()` loops over every candidate in the extracted Set and re-runs `checkLocalArtifact()` then `matchArtifactPattern()` until a hit, so noisy content that yields many low-value candidates (npm-scope noise, generic-suffix false positives) linearly multiplies the cost.

Structural gaps compound the vocabulary misalignment. The `dirPattern` (`/[a-z-]+\/[a-z-]+\//g`) and `filePathPattern` regexes both assume lowercase-hyphenated path segments, which cannot match mixed-case or dotted `teamDirectories` entries, cannot match `.specstory` (leading dot, no preceding slash), and cannot match a bare `scripts` entry (no trailing slash, no extension) — meaning `checkLocalArtifact()` can never even receive that literal string as input, despite it being listed verbatim in `teamDirectories.get('Coding')`. Separately, `inferEntityClass()`'s `teamMappings` object contains an `'Agentic'` key that is structurally unreachable: `checkLocalArtifact()` is the sole caller and derives `team` only from the four active teams (Coding/RaaS/ReSi/UI), so this is dead configuration data left behind from an apparent team rename/absorption, never cleaned up.

The `.xaml`/`.cs` fixtures at `integrations/graphify/tests/fixtures/xaml_viewmodel/` demonstrate the vocabulary's blind spots concretely: `filePathPattern`'s extension alternation (`ts|js|cpp|java|tsx|jsx|py|go|rs`) omits `xaml` and `cs` entirely, and `DesignViewModel.cs`'s class name fails `classPattern`'s nine-suffix list since `ViewModel` isn't among them — making this fixture invisible on two independent axes simultaneously, confirming the heuristic was designed around the Coding/RaaS/ReSi/UI stack, not arbitrary polyglot code.

## Integration Points

ArtifactPatternRegexCascade is invoked exclusively from within `analyzeEntityPatterns()`'s outer for-loop, downstream of and subordinate to TeamDirectoryPrefixMatch's path-based check — it only fires per-artifact on a path-match miss, consistent with the parent OwnershipHeuristicPattern's explicit trust ordering (0.9 for path match vs. 0.75 for pattern match). It consumes the `Set<string>` produced by ArtifactExtractionPipeline's `extractArtifacts()`, inheriting that pipeline's loss of provenance — matching treats a bare directory prefix and a class-name string identically.

Outside this file, the same "regex-heuristic-as-compliance-check" philosophy reappears in `scripts/knowledge-management/verify-patterns.sh`, which shares the architectural DNA of converting informal conventions into countable matches but diverges sharply in failure mode: where EntityPatternAnalyzer degrades gracefully (a miss just returns no evidence), verify-patterns.sh's regex/ripgrep counts feed directly into a hardcoded `SCORE=$((PASSED_CHECKS * 100 / TOTAL_CHECKS))` and a `case` statement keyed on substrings like `*Logging*` or `*Redux*|*State*`, defaulting silently to `0` for unmatched pattern names — a much less forgiving integration of the same core idea.

## Usage Guidelines

Any change to a team's naming convention or directory structure requires updating three places in lockstep — `teamDirectories`, `artifactPatterns`, and the extraction regexes in `extractArtifacts()` — since nothing enforces consistency between them; the `scripts`/`.specstory` gap and the orphaned `Agentic` key are proof that this synchronization has already lapsed at least twice. Developers extending team coverage should treat `classPattern`'s suffix list as a ceiling, not a guarantee: adding a suffix there does nothing unless the corresponding team's `artifactPatterns` entry is also updated, and conversely a narrow per-team pattern addition doesn't need a matching `classPattern` change only if the target strings are already being extracted by one of the four passes. Given the demonstrated blind spots (`.xaml`, `.cs`, `ViewModel` suffix, dotted/bare directory names), anyone onboarding a new language stack or team into this heuristic should audit all four extraction regexes and the suffix vocabulary together rather than assuming coverage. Finally, because discards are silent, any debugging of "why wasn't this artifact attributed" should start by manually replaying content through all four extraction regexes before assuming the fault lies in `matchArtifactPattern()`.

This ordering encodes an explicit confidence hierarchy: a direct path match returns confidence 0.9 while a naming-convention match returns 0.75, meaning the heuristic trusts 'where a file lives' strictly more than 'what a class is called' — a defensible choice given that directory placement is enforced by repo structure while naming conventions can drift.

### Siblings
- [TeamDirectoryPrefixMatch](./TeamDirectoryPrefixMatch.md) -- [LLM] TeamDirectoryPrefixMatch corresponds to the private `checkLocalArtifact()` method in `src/ontology/heuristics/EntityPatternAnalyzer.ts`, which is invoked as step (a) inside `analyzeEntityPatterns()`. Its implementation is a simple O(teams × dirs-per-team) nested scan: for each `[team, dirs]` entry in the `teamDirectories` Map, it calls `dirs.some((dir) => artifact.startsWith(dir))`. Because JavaScript `Map` iteration order is insertion order, and the Map is constructed with `Coding` first, `RaaS` second, `ReSi` third, `UI` fourth, any artifact string whose prefix could theoretically satisfy more than one team's directory list would always resolve to whichever team was inserted first — in practice a non-issue today since the four directory lists (`src/ontology`/`src/knowledge-management`/... vs `raas-service`/... vs `virtual-target`/... vs `curriculum-alignment`/...) do not share prefixes, but it is a latent ordering dependency that a naive future edit (e.g. adding a short/generic prefix like `src/` to a second team) could silently break.
- [ArtifactExtractionPipeline](./ArtifactExtractionPipeline.md) -- [LLM] The `extractArtifacts()` method in `src/ontology/heuristics/EntityPatternAnalyzer.ts` runs four separate `content.match()` regex passes (file paths, npm scopes, suffix-based class names, bare directory prefixes) and unions the results into a single `Set<string>`, discarding any information about *which* regex produced a given match. This means `analyzeEntityPatterns()` cannot distinguish 'this looked like a file path' from 'this looked like a class name' once it starts iterating `artifacts` — both `checkLocalArtifact()` (a `startsWith` prefix test) and `matchArtifactPattern()` (a full `RegExp.test`) are applied uniformly to every string in the set regardless of its origin, so a bare directory-prefix match like `src/ontology/` and a class-name match like `KnowledgeExtractor` are treated as interchangeable candidates in the same loop.
