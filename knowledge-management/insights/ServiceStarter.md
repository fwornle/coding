# ServiceStarter — Technical Insight Document

## What It Is

ServiceStarter is the reusable orchestration layer implemented in `lib/service-starter.js`, providing resilient process-startup primitives for the DockerizedServices ecosystem. Its core exports are three child components covered here: `StartServiceWithRetry` (the retry-with-backoff orchestrator at `lib/service-starter.js:139-236`), `WithDeadline` (the timeout/race guard at `lib/service-starter.js:100-118`), and `PortListeningChecks` (two composable readiness helpers, `isPortListening()` and `isTcpPortListening()`). Together these form a toolkit for turning an arbitrary async `startFn()`/`healthCheckFn()` pair into a supervised, retried, deadline-bounded service startup — the kind of scaffolding needed anywhere a Node process must spawn and verify another process (an API server, dashboard, or backing datastore wrapper) without hanging or leaking resources.

## Architecture and Design

The central architectural insight is `withDeadline()`'s handling of `Promise.race()`. A naive race between a work promise and a `setTimeout`-based rejection leaves the losing timer armed on the event loop; `withDeadline()` closes this gap with a `try/finally` that unconditionally calls `clearTimeout()`. This single primitive underlies everything else: `startServiceWithRetry()` calls it twice per attempt — once around `startFn()` with the caller-supplied `timeout`, once around `healthCheckFn()` hardcoded to 10000ms — so across `maxRetries` exponential-backoff attempts, the leak-avoidance compounds in importance rather than being a cosmetic detail.

`startServiceWithRetry()` itself follows a three-phase attempt cycle: start (deadline-guarded `startFn()`), settle (a fixed 2000ms sleep to let a freshly spawned process bind its port), and verify (deadline-guarded `healthCheckFn()`). Only a failed verify phase triggers active cleanup — SIGTERM followed by SIGKILL escalation after another 1000ms if `isProcessRunning()` still reports the process alive. Notably, a `startFn()` that throws leaves no `serviceInfo.pid` to clean up, implying the retry loop assumes `startFn()` either returns a valid `{pid, port}` or throws before any real process spawns — there is no defensive cleanup for a throw that happens *after* spawning.

The `required`/`optional` classification (via `options.required`, default `true`) is a clean example of pushing a graceful-degradation decision into the options object rather than branching function signatures: exhausted retries either throw (blocking) or return `{status: 'degraded', ...}`, letting `startServicesParallel()` uniformly `Promise.allSettled()` a heterogeneous list of services and bucket outcomes by inspecting `status`.

## Implementation Details

`WithDeadline` is the atomic building block — race a work promise against a timeout rejection, guarantee timer cleanup regardless of winner. `StartServiceWithRetry` layers exponential backoff (`retryDelay * 2^(attempt-1)`) atop this, encoding the start/settle/verify cycle and the required-vs-optional exit semantics at `lib/service-starter.js:216-234`. `PortListeningChecks` supplies `isPortListening()` (HTTP GET to `/health`, 2xx = healthy) and `isTcpPortListening()` (raw `net.Socket` connect, resolving on the `connect` event) — but critically, neither is invoked inside `startServiceWithRetry()` itself. The retry loop only knows about an arbitrary `healthCheckFn(serviceInfo)` parameter, so these two helpers are building blocks a caller composes into its own health check rather than logic wired into the retry machinery. This decouples "how do I know this service is up" (HTTP endpoint vs. bare TCP handshake vs. something else) from "how many times do I retry and how do I back off," letting the same scaffolding serve services with heterogeneous health semantics — an HTTP health check for something like VKB Server versus a TCP handshake for Qdrant/Redis-style dependencies.

## Integration Points

![ServiceStarter — Relationship](images/service-starter-relationship.png)

Despite being the designated shared abstraction under DockerizedServices, ServiceStarter is notably *not* directly invoked by the sibling `ServiceWrapperScripts` — `scripts/api-service.js` and `scripts/dashboard-service.js` implement their own inline spawn/register/unregister logic instead of calling `startServiceWithRetry()`. Both scripts share an identical template: resolve `CODING_REPO`, verify existence via `fs.existsSync()`, spawn with `stdio: 'inherit'`, and register/unregister the child PID with `ProcessStateManager` via repeated dynamic `import()` calls — duplicated boilerplate suggesting copy-paste origin rather than a common wrapper factory, and confirming inconsistent adoption of ServiceStarter's retry abstraction across the codebase.

At the sibling/parent level, ServiceStarter's health-check consumers must respect the SPEC R6 invariant enforced by `ServiceProbe` (parent context): probe functions never assert "healthy" directly, only "stopped" or "unknown," deferring the actual healthy determination to a higher-level coordinator combining probe results with `ProcessStateManager` registration state. `DockerEntrypoint`'s `wait_for_service()` independently implements the same "don't block startup on a slow dependency" philosophy in bash — TCP-probing Qdrant/Redis via `/dev/tcp` redirection and unconditionally returning success on exhaustion — but this is a parallel, unshared implementation rather than reuse of the JS retry/backoff logic, meaning two independent readiness-polling systems coexist in the same deployment (see also sibling `StartServicesRobust`).

Configuration wiring is loosely coupled by convention rather than a shared source of truth: `dashboard-service.js` hardcodes `NEXT_PUBLIC_API_BASE_URL: 'http://localhost:3031'` rather than deriving it from `CONSTRAINT_API_PORT`, the same env var `api-service.js` reads for its own port — a latent drift risk if the port is ever overridden.

## Usage Guidelines

Developers extending ServiceStarter should preserve the `finally`-clearTimeout pattern in any new deadline/timeout wrapper — this is the load-bearing detail preventing hung test runners and CLIs. When adding new services, prefer composing `isPortListening()`/`isTcpPortListening()` into a custom `healthCheckFn` rather than duplicating polling logic, and use the `required` option rather than inventing new control-flow branches for optional services, keeping `startServicesParallel()` uniform. Given that `startFn()` failures after spawning aren't defensively cleaned up, callers should ensure `startFn()` either fully succeeds (returning `{pid, port}`) or throws before any process launches. Finally, given the demonstrated divergence between ServiceStarter and the hand-rolled `ServiceWrapperScripts`, any refactor effort should prioritize migrating `api-service.js`/`dashboard-service.js` onto `startServiceWithRetry()` to eliminate duplicated PID-registration boilerplate and close the configuration-drift gap around `CONSTRAINT_API_PORT`.
