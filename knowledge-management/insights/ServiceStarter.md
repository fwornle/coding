# ServiceStarter — Technical Insight Document

## What It Is

ServiceStarter is the host-side orchestration layer for starting, gating, and monitoring service processes, implemented principally in `scripts/start-services-robust.js` and invoked from the legacy `start-services.sh` when `ROBUST_MODE=true` (the default). It sits within the broader `DockerizedServices` component, acting as the Node/host-native counterpart to the container-based supervisord path (`docker/entrypoint.sh`, `Dockerfile.coding-services`). ServiceStarter is composed of three child subsystems — `FeatureGatedServiceCatalogue`, `RetryWithDeadlineStarter`, and `PortReleaseAndBindability` — each responsible for one axis of the startup problem: what to start, how to retry it, and how to ensure the port it needs is actually free.

## Architecture and Design

The dominant pattern is feature-gated orchestration: `SERVICE_CONFIGS` and `SERVICE_ORDER` in `start-services-robust.js` form a declarative catalogue where each service declares a `feature` string checked via `loadFeatures` (`lib/features/index.mjs`) before `startOneService()` decides to skip, start, or block it. This is the `FeatureGatedServiceCatalogue` child component made concrete, and it is structurally guarded by `tests/features/service-gating.test.mjs`'s assertion that `SERVICE_ORDER` and `SERVICE_CONFIGS` "cover each other exactly" — a JS-level substitute for compile-time exhaustiveness checking.

Crucially, this same feature-gating concept is duplicated at the container layer in `docker/entrypoint.sh`'s `PROGRAM_FEATURES` mapping, which the sibling components `APIServiceWrapper` and `SupervisordRuntime` also document. The two mechanisms — a JS object graph versus shell-generated supervisord `.conf` overrides — are conceptually identical but implementationally independent, meaning any new feature must be wired into both to avoid drift between deployment modes. This mirrors the parent `DockerizedServices`'s dual-mode execution model, where "starting a service" has genuinely separate code paths depending on target.

Retry and deadline logic is cleanly separated out: ServiceStarter's per-service `startFn`/`healthCheckFn` closures delegate the actual spawn/health-check/backoff loop to `startServiceWithRetry` from `lib/service-starter.js` (the `RetryWithDeadlineStarter` child), so backoff timing and deadline semantics live in one place reused across `transcriptMonitor`, `liveLoggingCoordinator`, and the rest of `SERVICE_ORDER`.

## Implementation Details

`startOneService()` produces a result object with a deliberate `disabled` vs `degraded` status split: a feature turned off intentionally must never be reported as degraded, whereas a `required: true` service (e.g., `transcriptMonitor`) whose `startFn` throws sets `blocked=true` and halts downstream startup — enforced by `tests/features/service-gating.test.mjs` using `maxRetries=1` to avoid real exponential backoff costs during tests. The required/optional classification has real blast-radius consequences, as `DashboardServiceWrapper`'s observations note: `SERVICE_ORDER.slice(0,2)` must be `['transcriptMonitor', 'liveLoggingCoordinator']` because later services register against them.

Idempotency is handled via `isProcessRunningByScript()`, used inside `SERVICE_CONFIGS.transcriptMonitor.startFn`, implementing a three-tier check: global `ProcessStateManager` (psm.isServiceRunning), per-project PSM state, then an OS-level `pgrep` fallback that re-registers orphaned processes via `psm.registerService()`. This compensates for PSM's JSON-backed state drifting from actual OS reality after crashes.

The `PortReleaseAndBindability` child component encodes two distinct port-lifecycle failure modes: `killProcessOnPortAndWait()` handles SIGTERM→SIGKILL escalation with polling for actively-listening processes, while `waitForPortBindable()` performs a throwaway `net.createServer().listen()` probe to detect kernel-level TIME_WAIT-style unavailability invisible to HTTP-based `isPortListening()` checks. These are explicitly non-redundant — skipping the bind probe risks an EADDRINUSE crash silently consuming one of `startServiceWithRetry()`'s `maxRetries` slots.

## Integration Points

ServiceStarter sits under `DockerizedServices` and is one of several siblings alongside `ServiceProbe`, `APIServiceWrapper`, `DashboardServiceWrapper`, `SupervisordRuntime`, and `ProcessStateManager`. It depends on `lib/features/index.mjs` (feature loading) and `lib/features/catalogue.cjs` (`FEATURE_IDS` validation), and on `lib/service-starter.js` for `startServiceWithRetry`, `createHttpHealthCheck`, `createPidHealthCheck`, `isPortListening`, `isTcpPortListening`, `isProcessRunning`, and `sleep`. It consumes `ProcessStateManager` as an imperfect authoritative store, supplementing it with OS-level `pgrep` verification. Health checking itself is delegated conceptually to the same philosophy as `ServiceProbe`, though `docker/entrypoint.sh`'s `wait_for_service()` implements its own ad-hoc `/dev/tcp` probing rather than reusing `service-probe.js`, leaving two independent probing implementations in the codebase. The legacy `start-services.sh` remains a coexisting entrypoint with hardcoded ports (3030 dashboard, 3031 API) that must stay numerically in sync with `PORTS` defaults in `start-services-robust.js`.

## Usage Guidelines

Any new service added to `SERVICE_CONFIGS` must also be added to `SERVICE_ORDER` (and vice versa), and must declare a valid `feature` string present in `FEATURE_IDS` — the test suite will fail the build otherwise. When adding a feature gate, update both `start-services-robust.js`'s `SERVICE_CONFIGS` and `docker/entrypoint.sh`'s `PROGRAM_FEATURES` to prevent host/container drift. Never mark a genuinely required service (like `transcriptMonitor`) as optional, since downstream services register against it and a silent misclassification breaks observability rather than failing loudly. When killing a service on a port, always follow `killProcessOnPortAndWait()` with `waitForPortBindable()` before respawning — treating them as redundant risks wasting retry budget on EADDRINUSE. Finally, prefer PSM-registered state but don't trust it exclusively; the orphan-detection fallback pattern in `isProcessRunningByScript()` should be replicated wherever new services manage long-lived subprocesses.


## Hierarchy Context

### Parent
- [DockerizedServices](./DockerizedServices.md) -- [LLM] The DockerizedServices layer is architected around a dual-mode execution model: services can run either as supervisord-managed processes inside a single Docker container (per docker/docker-compose.yml, Dockerfile.coding-services, supervisord.conf) or as host-native Node subprocesses managed by lib/service-starter.js and PID-tracked via ProcessStateManager. This duality means developers must understand that 'starting a service' has two entirely separate code paths depending on deployment target, and that health-checking logic (service-probe.js) is written to be agnostic to which path is in effect — it only cares about HTTP/TCP reachability, not process ownership. This design avoids needing separate health-monitoring logic for containerized vs local services, but it also means Docker-specific failures (e.g., supervisord misconfiguration killing a service inside the container) surface identically to host-side crashes, requiring log inspection to disambiguate.

This means a caller that only uses killProcessOnPortAndWait() and then immediately spawns a new service risks an EADDRINUSE crash that silently consumes one of startServiceWithRetry()'s maxRetries slots — the two functions are not redundant, they cover disjoint failure windows in the same port-release lifecycle.

This means a bug in `startServiceWithRetry()` (imported from `../lib/service-starter.js`) that mis-marks a service's required flag has very different blast radii depending on which service it touches — misclassifying `transcriptMonitor` as optional would silently break the observability pipeline that most other services register against, since `tests/features/service-gating.test.mjs` explicitly asserts `SERVICE_ORDER.slice(0, 2)` must be `['transcriptMonitor', 'liveLoggingCoordinator']` because 'later services register against' them.
- [SupervisordRuntime](./SupervisordRuntime.md) -- [LLM] docker/entrypoint.sh implements a fail-open feature-gating layer that sits in front of supervisord rather than inside it: it reads a host-written snapshot at /coding/.coding/runtime/features.json (mounted read-only) and, for each entry in the PROGRAM_FEATURES mapping (e.g. `semantic-analysis:knowledge`, `graphify:codegraph`, `constraint-monitor:constraints`, `health-dashboard:health`), shells out to `node -e` to read the flag and writes a `[program:<name]\nautostart=false` stanza into /etc/supervisor/features.d/disabled.conf when a feature is off. Because supervisord.conf's `[include]` directive pulls in that directory, the override never touches the canonical program definitions — it only flips autostart. The script deliberately treats an absent snapshot, an unreadable snapshot, or an unknown feature key as 'enabled' (comment: 'starts everything — the historical behaviour'), which is a conscious fail-open decision to avoid a container that silently runs nothing because a JSON file arrived late.

- [StartServicesRobust](./StartServicesRobust.md) -- [LLM] scripts/start-services-robust.js implements a two-class service model — REQUIRED (transcriptMonitor, liveLoggingCoordinator) vs OPTIONAL (everything else) — that is enforced not by a flag on the service itself but by how startOneService() (referenced in tests/features/service-gating.test.mjs) interprets the `required: true` field on SERVICE_CONFIGS entries. The test 'a required failure blocks, so downstream services do not start' confirms that a required-service failure sets `out.blocked = true` and halts SERVICE_ORDER iteration, while an optional failure is recorded in `results.failed` or `results.degraded` without stopping subsequent services. This is the concrete mechanism behind the parent-context claim that the toolkit 'should remain usable in a degraded state' — degradation is implemented as a loop-continuation decision, not a separate code path.
