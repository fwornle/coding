# ServiceStarter — Technical Insight Document

## What It Is

ServiceStarter is implemented primarily in `scripts/start-services-robust.js`, a Node.js orchestrator that wraps primitives from `lib/service-starter.js` (`startServiceWithRetry`, `createHttpHealthCheck`, `createPidHealthCheck`) into a declarative service registry called `SERVICE_CONFIGS`. Each entry in this registry is a tuple of `{name, feature, psmPath, required, maxRetries, timeout, startFn, healthCheckFn}`. The entry point users actually invoke, `start-services.sh`, is a thin bash shim (lines 14-18) that execs this Node script whenever `ROBUST_MODE=true` — the default — and only falls back to a legacy inline bash startup path (manual docker-compose/lsof/kill logic) when `ROBUST_MODE=false`. That legacy path is effectively dead code in normal operation, retained purely for backward compatibility.

As a SubComponent, ServiceStarter sits beneath DockerizedServices and is one of several service-wrapper siblings (APIServiceWrapper, DashboardServiceWrapper, MockLLMService, SupervisordRuntime, StartServicesOrchestrator) — though unlike those, its own implementation is well-attested directly in the retrieved source rather than inferred from parent context.

## Architecture and Design

The architecture is config-driven: `SERVICE_CONFIGS` and its companion ordering array `SERVICE_ORDER` describe the entire service catalogue, and structural correctness is enforced by `tests/features/service-gating.test.mjs`, which asserts that every service declares a `feature` matching a real `FEATURE_IDS` entry, that `SERVICE_ORDER` and `SERVICE_CONFIGS` keys cover each other exactly, and that `transcriptMonitor` and `liveLoggingCoordinator` remain the first two entries because later services register against them. This is the responsibility now delegated to the child component ServiceCatalogueGating, which also owns the catalogue's dual role: the same process that decides which services to start locally (via `loadFeatures` from `lib/features/index.mjs`) also writes the flat feature snapshot (via `writeSnapshot` from `lib/features/snapshot.cjs`) that `docker/entrypoint.sh` later reads to gate supervisord programs in the container. This means one Node process is upstream of two independent, parallel gating mechanisms — host-side Node looping and container-side supervisord — each implementing its own "fail open if the gating signal is missing" safety default.

A second major design theme is idempotent, defensive startup, embodied in children PortHealthChecks and PortReleaseWaiting. `killProcessOnPortAndWait()` and `waitForPortBindable()` form a graceful-then-forceful pair: the former issues SIGTERM, polls occupancy via `lsof -ti:${port}` at a configurable interval (default 200ms) up to a max wait (default 5000ms), escalating to SIGKILL only after half the timeout elapses. The latter distrusts HTTP-level health checks and instead probes raw TCP bindability with a throwaway `net.createServer().listen()`, because the kernel can hold a socket in a post-crash window where HTTP probes go unanswered yet `EADDRINUSE` still fires on bind — a deliberate two-tier check to avoid burning a `maxRetries` slot on a spurious conflict. The child entity WithDeadlineRacing appears to be an analytical label for this same race-avoidance behavior rather than a separately named function in code.

## Implementation Details

The `transcriptMonitor` service configuration illustrates the depth of duplicate-detection logic layered into `startFn`: before spawning `enhanced-transcript-monitor.js`, it runs three independent checks — `psm.isServiceRunning('transcript-monitor', 'global')`, `psm.isServiceRunning('enhanced-transcript-monitor', 'per-project', {projectPath})`, and an OS-level `isProcessRunningByScript('enhanced-transcript-monitor.js')` pgrep fallback. That fallback re-registers any orphaned process it finds with ProcessStateManager (PSM), explicitly "to catch orphaned processes PSM doesn't know about" — an implicit admission that PSM's JSON/registry state has previously drifted from actual OS reality.

The disabled/degraded/failed distinction is treated as a load-bearing contract, not cosmetic logging: a service skipped because its feature flag is off must land in `results.disabled`, never `results.degraded`, since "degraded means we wanted this and could not have it." Conflating the two would make a deliberately pared-down install look broken, and this invariant is directly enforced by `tests/features/service-gating.test.mjs`.

Container-side, `docker/entrypoint.sh` implements a parallel gating mechanism: it reads a read-only mounted `/coding/.coding/runtime/features.json` snapshot (since the host's `~/.coding/features.yaml` resolver cannot run inside the container) and generates `/etc/supervisor/features.d/disabled.conf` entries via a `PROGRAM_FEATURES` mapping string, flipping `autostart=false` for gated supervisord programs.

## Integration Points

ServiceStarter depends on `lib/service-starter.js` for retry/health-check primitives, on ProcessStateManager for cross-session process bookkeeping, and on `lib/features/index.mjs` / `lib/features/snapshot.cjs` for feature resolution and snapshot persistence — the latter being the bridge to `docker/entrypoint.sh` and supervisord in the container runtime (SupervisordRuntime). Its parent, DockerizedServices, layers manual verification procedures on top (the "Docker Container Restart Verification Baseline" and "Health Verification Workflow" session records), implying that supervisord-managed services have previously appeared to restart successfully while actually degraded — an outage class SupervisordRuntime's own "Runtime Config Drift Investigation" is separately tracking. ServiceStarter's structural tests give some assurance against a related class of failure (silently missing feature/service registrations) but do not by themselves resolve container-side drift.

## Usage Guidelines

Developers modifying the service catalogue must keep `SERVICE_ORDER` and `SERVICE_CONFIGS` in exact correspondence and preserve `transcriptMonitor`/`liveLoggingCoordinator` as the first two entries, since later services depend on that registration order — the test suite will fail otherwise. New services must declare a real `feature` id, and any startup-skip logic must route through `results.disabled` rather than `results.degraded` when the cause is a disabled feature flag, preserving the semantic distinction the tests enforce. When adding duplicate-detection logic for new long-running services, follow the `transcriptMonitor` pattern of layering PSM checks with an OS-level pgrep fallback rather than trusting PSM state alone. Finally, because both host (`start-services-robust.js`) and container (`docker/entrypoint.sh`) implement independent fail-open gating, changes to one side's feature-flag semantics should be mirrored in the other to avoid divergence between what runs on the host versus inside the container.
