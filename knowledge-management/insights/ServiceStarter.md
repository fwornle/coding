# ServiceStarter — Technical Insight Document

## What It Is

ServiceStarter is the orchestration layer for bringing up the coding-services stack, concretely implemented in `scripts/start-services-robust.js` and reachable via the dual-mode dispatcher `start-services.sh`. It is not a single class but a cluster of module-level functions and data structures — `SERVICE_CONFIGS`, `SERVICE_ORDER`, `startServiceWithRetry`, `waitForPortBindable`, `killProcessOnPortAndWait`, and `isProcessRunningByScript` — that together decide which services start, in what order, with what retry/health-check behavior, and how failures are classified. It sits beneath the parent DockerizedServices component, which governs the broader container lifecycle (rebuild via docker-compose, health verification before trusting downstream pipelines like wave-analysis), and it shares the runtime environment with siblings ProcessStateManager, DockerEntrypoint, StartServicesScripts, and ServiceWrapperScripts.

## Architecture and Design

The dominant pattern is retry-with-backoff startup, embodied by `startServiceWithRetry`, which every service-specific `startFn` in `SERVICE_CONFIGS` is driven through. Layered on top of this generic primitive are orchestration-specific helpers that compensate for known failure modes: `waitForPortBindable` distinguishes a kernel-held socket left by a crashed process from a normal "not yet listening" state, explicitly avoiding burning a `maxRetries` slot on a spawn attempt doomed to `EADDRINUSE`; `killProcessOnPortAndWait` performs SIGTERM-then-SIGKILL escalation with polling; and `isProcessRunningByScript` provides an OS-level `pgrep` fallback so orphaned processes unknown to ProcessStateManager (PSM) don't get double-started.

A second major pattern is feature-flag gating, applied redundantly at two layers. On the host side, `SERVICE_CONFIGS` entries carry a `feature` id validated against `lib/features/catalogue.cjs`; on the container side, `docker/entrypoint.sh` reads the same feature catalogue via `PROGRAM_FEATURES` and writes supervisord `autostart=false` includes under `/etc/supervisor/features.d/`. This is the concrete mechanism behind the child component FeatureGatedSupervisorStartup — a deliberately independent, parallel gating path rather than a shared library, meaning the host orchestrator and the container supervisor must be kept in sync by convention and by the cross-cutting test `tests/features/container-gating.test.mjs`.

A third pattern, required-vs-optional classification with graceful degradation, governs startup ordering: `transcriptMonitor` and `liveLoggingCoordinator` are REQUIRED and must start first, since later services register against them via PSM, as enforced structurally in `tests/features/service-gating.test.mjs`.

## Implementation Details

`scripts/start-services-robust.js` is the concrete realization of the child component RobustServiceRetryOrchestrator. It imports generic primitives — `startServiceWithRetry`, `createHttpHealthCheck`, `createPidHealthCheck`, `isPortListening`, `isTcpPortListening`, `isProcessRunning`, `sleep` — from `lib/service-starter.js`, rather than embedding retry logic directly, keeping orchestration policy separate from low-level mechanics. Each entry in `SERVICE_CONFIGS` (the child ServiceWrapperScripts detail) declares `feature`, `startFn`, `healthCheckFn`, `required`, and `maxRetries`/`timeout`. The `transcriptMonitor.startFn` is the clearest example of the "thin wrapper" idiom: it checks `psm.isServiceRunning('transcript-monitor', 'global')` and the `isProcessRunningByScript` pgrep fallback before spawning `enhanced-transcript-monitor.js` detached, redirecting stdio to `.data/etm.log`, injecting `OBS_API_URL`, and calling `child.unref()` so the wrapper can exit without keeping the child alive as a dependent.

Outcome semantics are deliberately three-valued rather than binary: `startOneService` results distinguish 'disabled' (feature off, never attempted — not a failure), 'degraded' (wanted but unavailable), and 'blocked' (a required service's failure preventing downstream startup). This prevents a pared-down install from being misreported as broken, and is directly asserted by `tests/features/service-gating.test.mjs`, which also enforces that `SERVICE_ORDER` and `SERVICE_CONFIGS` keys match exactly and that every feature id resolves against the catalogue.

The child component HealthCheckFunctions is only partially visible from this vantage point: the concrete implementations of `createHttpHealthCheck`, `createPidHealthCheck`, `isPortListening`, etc., live in `lib/service-starter.js`, outside the supplied files. Only the call site is visible — `transcriptMonitor.healthCheckFn` short-circuits to `true` when `result.skipRegistration` is set, otherwise delegates to `createPidHealthCheck()(result)`. Similarly, no literal "DeadlineRacer" abstraction exists in the codebase; the closest analogues are `waitForPortBindable` and `killProcessOnPortAndWait`, which race deadlines against kernel/process state without a shared named class.

## Integration Points

![ServiceStarter — Relationship](images/service-starter-relationship.png)

ServiceStarter is invoked through `start-services.sh`, which is a dual-mode dispatcher: by default (`ROBUST_MODE=true`) it execs `node scripts/start-services-robust.js` and exits immediately, deferring all real orchestration; when `ROBUST_MODE=false`, it falls back to roughly 200+ lines of legacy bash logic (sibling StartServicesScripts) — port-killing, docker-compose invocation, manual `docker run` fallback for constraint-monitor — retained explicitly for backward compatibility rather than deleted.

Downstream, ServiceStarter depends on ProcessStateManager (sibling) for in-process service registration, falling back to OS-level `pgrep` detection when PSM state is stale or missing. It coexists with, but does not share code with, DockerEntrypoint's `wait_for_service()`, a fail-open TCP readiness gate for Qdrant/Redis that warns but does not block on exhaustion, leaving ultimate liveness to whatever happens once supervisord starts each process. The feature-gating logic in `docker/entrypoint.sh` (child FeatureGatedSupervisorStartup) is a structurally parallel but independently maintained mechanism to the host-side `SERVICE_CONFIGS.feature` gating, joined only by the shared feature catalogue and cross-validating tests.

## Usage Guidelines

Operators must treat `SERVICE_ORDER` as authoritative for startup sequencing — `transcriptMonitor`/`liveLoggingCoordinator` must remain first, since other services register against them via PSM. Any new service added to `SERVICE_CONFIGS` must declare a valid `feature` id from `lib/features/catalogue.cjs`, and both `SERVICE_ORDER` and `SERVICE_CONFIGS` keys must stay exactly in sync, or `tests/features/service-gating.test.mjs` will fail. Per the parent DockerizedServices' Health Verification Workflow, after any docker-compose rebuild, all supervised processes and health endpoints must be explicitly confirmed live before trusting downstream pipelines such as wave-analysis — this applies equally to the container-side entrypoint.sh/supervisord path and the host-side ServiceStarter. Because ROBUST_MODE toggles between two materially different orchestration paths, when debugging startup issues, confirm which mode is active before assuming which logic path (Node retry orchestrator vs. legacy bash) is actually running; and because feature gating exists redundantly in two places (`SERVICE_CONFIGS.feature` and `PROGRAM_FEATURES` in entrypoint.sh), any change to the feature catalogue must be mirrored in both locations to avoid divergence between host and container behavior.
