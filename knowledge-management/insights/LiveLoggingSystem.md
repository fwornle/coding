# LiveLoggingSystem — Technical Insight Document

## What It Is

LiveLoggingSystem (LSL) is the Coding project's infrastructure for capturing, validating, and privacy-guarding session transcripts, centered on `scripts/validate-lsl-config.js` and its `LSLConfigValidator` class. It governs two distinct configuration artifacts — `.specstory/config/lsl-config.json` for structural/behavioral settings and `.specstory/config/redaction-config.yaml` for privacy/classification rules — and enforces their correctness before the system is allowed to record anything. Within the project's ontology (`.data/ontologies/coding.lower.json`), LiveLoggingSystem is formally registered as one of exactly ten L2 classes extending the L1 'Component' carrier, a fact asserted directly in `ontology-classification-agent.test.ts` (Test 1). As a child of the root **Coding** hierarchy, it sits alongside sibling components like **LLMAbstraction**, **DockerizedServices**, **KnowledgeManagement**, **ConstraintSystem**, **SemanticAnalysis**, and **CodingPatterns**, but occupies a distinct niche: durable, privacy-aware logging of live agent/user sessions.

## Architecture and Design

The defining architectural decision in LSL is the separation of "how the logger behaves" from "what the logger is allowed to record." Behavioral concerns (multi-user session windowing, file rotation, batching) live in `lsl-config.json`, while privacy/classification concerns live in `redaction-config.yaml`. This decoupling allows redaction policy to evolve independently of file-management logic, a design mirrored in the child components: **RedactionConfigManager** owns privacy enforcement, **MultiUserSessionRouter** owns per-user routing, **OperationalLogger** owns batched write mechanics, and **TranscriptAdapterFramework** (with its concrete **SpecstoryAdapter** implementation) owns ingestion of external transcript formats.

Validation itself follows a strict fail-closed model: `initializeSchemas()` in `LSLConfigValidator` requires five top-level sections — `version`, `multiUser`, `fileManager`, `operationalLogger`, and `classification` — and rejects configs missing any one of them outright. Critically, `classification` is treated as a mandatory, first-class schema section rather than an optional add-on, placing redaction on equal architectural footing with file-rotation and session-windowing settings. This signals that privacy protections were designed into LSL from inception rather than bolted on, a constraint that any new adapter (such as **SpecstoryAdapter** or future transcript formats built on **TranscriptAdapterFramework**) must respect by flowing through classification validation rather than bypassing it during development.

## Implementation Details

`LSLConfigValidator` enforces specific numeric invariants that encode operational experience rather than arbitrary defaults: `multiUser.userHashLength` must be 6–12 characters (balancing collision resistance against filesystem path practicality), `fileManager.maxFileSize` must be 1MB–100MB, and `operationalLogger.batchSize` must be 10–1000 (balancing write amplification against memory-buffering risk and durability delay). Developers extending file-rotation or multi-user routing logic — likely touching **OperationalLogger** (`OperationalLogger.js`) or **MultiUserSessionRouter** — should treat these bounds as documented invariants, not casual defaults.

User isolation is implemented via SHA-256 hashing rather than raw usernames: `validateUserEnvironment()` in `validate-lsl-config.js` hashes `process.env.USER` and truncates it to 6 characters for deterministic, pseudonymized file routing, tying into the project-wide `FOREGROUND_USER_HASHES` convention used elsewhere in Coding infrastructure. Notably, this invariant is *not* uniformly honored downstream: **RedactionConfigManager**'s associated observation flags that `lib/agent-api/transcripts/claude-parser.js:parseFile()` sets `userHash: process.env.USER || 'unknown'` — the raw, unhashed OS username — directly contradicting LSL's pseudonymization pattern. This is a concrete plaintext-username leak risk in exactly the transcript metadata the classification schema is meant to guard, and should be reconciled against whatever rules **RedactionConfigManager** applies downstream of the Claude adapter.

At the ontology-tooling layer, `buildL2RefinementPrompt()` and `extractL2FromLLMResponse()` in `ontology-classification-agent.ts` use token-boundary regex matching (not substring search) to avoid misclassifying names like a hypothetical "SuperLiveLoggingSystemX" as LiveLoggingSystem — a defensive parsing pattern worth replicating in any future L2 extraction logic.

## Usage Guidelines

Any config touching LSL must supply all five required schema sections or fail validation — there is no permissive fallback. When extending file-rotation, batching, or multi-user hashing logic, respect the documented numeric bounds rather than override them casually, since they encode production safety margins. New transcript adapters must route their output through the classification/redaction schema validation path before being considered pipeline-compliant — bypassing it, as `claude-parser.js` currently appears to do with raw `process.env.USER`, reintroduces the exact plaintext-leak risk the classification schema exists to prevent, and should be audited/fixed to hash-and-truncate consistently with `validateUserEnvironment()`. Finally, anyone extending ontology classification logic for LSL-adjacent names should follow the token-boundary matching precedent in `ontology-classification-agent.ts` to avoid naming collisions.
