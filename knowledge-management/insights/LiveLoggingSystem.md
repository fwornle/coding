# LiveLoggingSystem: Technical Insight Document

## What It Is

LiveLoggingSystem is a pipeline component for capturing, structuring, and persisting live Claude Code session transcripts. Its implementation is distributed across a small set of purpose-specific files: `scripts/validate-lsl-config.js` for pre-flight configuration checks, `logging.ts` for the terminal transcript-capture pipeline, and `ontology-classification-agent.ts` for hierarchical content classification, backed by `ontology-classification-agent.hierarchy-roots.test.ts` for correctness enforcement. As the parent of two documented sub-components — ConfigValidation and LoggingPipeline — LiveLoggingSystem represents the umbrella architecture under which configuration integrity and the actual logging execution are deliberately separated.

## Architecture and Design

The defining architectural pattern here is a staged, ordered pipeline with hard separation of concerns: configuration validation → session windowing/file routing → classification → transcript capture. Each stage is loosely coupled enough to be independently invoked or tested, yet the runtime flow enforces strict sequencing. This is most visible in the relationship between ConfigValidation (`scripts/validate-lsl-config.js`) and LoggingPipeline (`logging.ts`): the validation script is a standalone pre-flight tool, runnable without triggering `logging.ts`, embodying a fail-fast philosophy where misconfiguration (bad session window durations, routing rules) is caught before any live data capture begins, rather than discovered mid-capture where data loss is possible.

This ordering dependency also implies a deliberate design trade-off: `logging.ts`, as the terminal stage, likely performs minimal defensive validation of its own, trusting that upstream stages (the validation script and the classification agent) have already guaranteed well-formed input. This keeps the capture logic lean but creates an implicit contract — any refactor that bypasses the standard invocation order risks feeding unvalidated or unclassified data directly into persistence.

The classification layer's naming convention (`ontology-classification-agent.ts`) signals an agent-based design rather than static pattern matching, consistent with the project's broader agent-abstraction conventions seen in sibling components like LLMAbstraction. This suggests classification decisions may be LLM-driven or rule-driven rather than hardcoded, tying live logging into the project's larger ontology-integration and cross-project-knowledge systems.

## Implementation Details

Session windowing is a core structural concept: live conversations are not logged as a continuous unbounded stream but chunked into discrete windows before routing to files. Window boundary logic is tightly coupled to file routing, and both are governed by the same configuration schema that `scripts/validate-lsl-config.js` checks — meaning window overlaps, gaps, or bad thresholds can cause dropped, duplicated, or misrouted transcript data if not caught by that script. This makes `validate-lsl-config.js` the authoritative pre-check contract for any change to the windowing/routing config schema.

The classification stage applies hierarchical categorization to session content as it flows through the pipeline. Correctness here is enforced structurally: `ontology-classification-agent.hierarchy-roots.test.ts` validates that classification output maps to a fixed, stable set of top-level hierarchy roots. This implies the underlying ontology has a defined root-category schema that must not silently drift — any change to the classification agent's logic needs validation against this fixed root set to avoid corrupting downstream knowledge-graph queries with orphaned or invalid branches.

Because the classification agent likely integrates with the project's shared LLM proxy infrastructure (`LLM_PROXY_URL`, `RAPID_LLM_PROXY_URL`, per the agent-abstraction and LLM-routing conventions), classification per session window may involve network calls to an LLM backend. This introduces a distinct latency/failure surface — proxy downtime, rate limiting — compared to the purely local, file-based windowing and routing logic.

## Integration Points

LiveLoggingSystem sits as a peer component alongside LLMAbstraction, DockerizedServices, KnowledgeManagement, CodingPatterns, ConstraintSystem, and SemanticAnalysis under the root Coding hierarchy. Its most direct dependency is on LLMAbstraction-style infrastructure for the classification agent's potential LLM calls, echoing the mode-resolution and proxy-routing patterns documented for that sibling. It also feeds enriched, hierarchically-tagged session data toward cross-project-knowledge systems and the ontology-integration system described elsewhere in the project, aligning it conceptually with KnowledgeManagement's graph-based storage model, though no direct VKB server interaction is confirmed in these observations.

Internally, its two children — ConfigValidation and LoggingPipeline — form the enforced ordering backbone: ConfigValidation's `validate-lsl-config.js` gatekeeps before LoggingPipeline's `logging.ts` executes the main capture pipeline.

## Usage Guidelines

Developers modifying session window or file routing configuration schemas must treat `scripts/validate-lsl-config.js` as the authoritative contract — run it as a standalone check before touching `logging.ts`. Changes to `ontology-classification-agent.ts` must be validated against `ontology-classification-agent.hierarchy-roots.test.ts` to guarantee the fixed hierarchy-root schema remains intact; silent drift here would corrupt downstream knowledge-graph consumers. Because `logging.ts` likely assumes well-formed, pre-validated, pre-classified input, any bypass of the standard validation → windowing/routing → classification → capture order is risky and should be avoided. Finally, since classification may depend on live LLM proxy calls, developers should verify whether classification failures degrade gracefully (e.g., falling back to an "unclassified" root) rather than blocking the entire capture pipeline — this is noted as an open design consideration rather than a confirmed behavior.
