# LiveLoggingSystem — Technical Insight Document

## What It Is

The LiveLoggingSystem is centered on `logging.ts`, which owns the core responsibilities of session windowing, file routing, and transcript capture for live Claude Code conversations. This module functions as the single ingestion point for raw conversation events, making it the authoritative source of truth for how conversation data is structured before persistence to disk. As a major component within the broader **Coding** project (its parent in the knowledge hierarchy), LiveLoggingSystem sits alongside siblings like LLMAbstraction, DockerizedServices, KnowledgeManagement, CodingPatterns, ConstraintSystem, and SemanticAnalysis as one of seven pillars of development infrastructure.

Beyond raw capture, the system encompasses semantic classification (`ontology-classification-agent.ts`) and standalone configuration validation (`scripts/validate-lsl-config.js`), forming a layered pipeline that transforms live transcripts into validated, categorized data suitable for downstream consumption.

## Architecture and Design

The architecture follows a clear layered pipeline: raw capture (`logging.ts`) → semantic classification (`ontology-classification-agent.ts`) → validated configuration gatekeeping (`validate-lsl-config.js`). This mirrors the broader Coding project's emphasis on modular, testable components as documented in `docs/architecture/features.md`, where each concern is independently swappable and testable.

A key design decision is the architectural decoupling of classification from capture. `ontology-classification-agent.ts` implements a producer/consumer pattern: `logging.ts` produces raw transcript data, while the classification agent consumes and annotates it after the fact rather than during ingestion. This allows classification logic (e.g., adding new hierarchy roots) to evolve independently without touching file routing code — a deliberate trade-off favoring separation of concerns over inline enrichment, at the cost of an extra processing pass over captured data.

Similarly, configuration validation is intentionally isolated into a standalone script rather than embedded in `logging.ts`. This lets LSL (Live Session Logging) configuration correctness — output paths, rotation thresholds, routing rules — be checked independently, e.g., in CI or as a pre-flight check, failing fast before session windowing logic ever executes.

This layered design is reinforced by how the system's child components implement distinct concerns: **TranscriptAdapterAPI** defines `TranscriptAdapter`, an abstract base class enforcing subclass implementation of `getAgentType`, `readTranscripts`, `convertToLSL`, and `getCurrentSession` via a `new.target` guard — pushing agent-specific capture logic into pluggable subclasses rather than `logging.ts` itself.

## Implementation Details

`logging.ts` handles session windowing and file routing, and must safely manage concurrent sessions — likely using session identifiers and possibly hashed user identifiers (comparable to `FOREGROUND_USER_HASHES` referenced elsewhere in the project) to prevent transcript content from different active sessions interleaving into the same file, which would corrupt downstream ontology assignments.

The classification layer's correctness is enforced through two distinct test suites: `ontology-classification-agent.hierarchy-roots.test.ts`, which validates that top-level ontology categories are correctly seeded without orphaned or cyclic assignments, and `ontology-classification-agent.test.ts`, covering general classification edge cases. This split reflects a deliberate testing strategy treating hierarchy-root correctness as foundational to the semantic categorization scheme used across the wider Coding project's ontology integration (see `docs/RELEASE-2.0.md`).

Within the child components, `lsl-sessions.mjs` (LslSessionDashboard) defines a "chain" as an hourly tranche encompassing rotation parts rather than a single file — accounting for legacy headerless markdown fragments split mid-token and pi-format parts linked via `parentSession`. `BackendLoggerCore`'s `Logger.js` loads `config/logging-config.json` once via `loadConfig()`, caching it in a module-level `sharedConfig` and exposing `reloadConfig()` for forced refresh. `SpecstoryAdapter.initialize()` attempts three connection methods in fallback order — `connectViaHTTP()`, `connectViaIPC()`, `connectViaFileWatch()` — while `ProgressFireTrigger`'s `progressFireDecision()` fires on either a token-delta trigger or a wall-clock trigger, whichever condition is met first.

These children map cleanly onto the pipeline's stages — adapters read agent-native transcripts and convert them to LSL format, the logger core persists configuration-driven output, and the dashboard reconstructs session chains for display.

Downstream, the classification agent and config validation tooling both depend on the session lifecycle semantics defined in `logging.ts`; any change to how a session window is defined or rolled over cascades into these consumers. Within the sibling landscape, this component parallels ConstraintSystem's own violation-capture pipeline (`ViolationCaptureService`, JSONL persistence) in its emphasis on structured, append-only logging with capped growth and dashboard-ready aggregation, though LiveLoggingSystem's specific artifacts (transcripts, ontology classes) differ from ConstraintSystem's rule violations.

## Usage Guidelines

Developers should treat `logging.ts` as the authoritative source of truth for raw conversation event structure — changes to session windowing or file routing semantics have cascading effects and must be evaluated against classification and config-validation consumers. When modifying the classification agent, both `ontology-classification-agent.hierarchy-roots.test.ts` and `ontology-classification-agent.test.ts` should be run, since hierarchy-root correctness underpins the ontology scheme used project-wide.

New developers extending this system should avoid introducing cross-cutting concerns (classification, validation) directly into `logging.ts`; the established pattern favors pushing such logic into separate, independently-tested modules. Configuration issues should be caught via `scripts/validate-lsl-config.js` before the logging daemon starts, reducing the risk of silent corruption of live transcript capture. When implementing new agent adapters, subclass `TranscriptAdapter` and implement its required methods rather than instantiating it directly, consistent with the abstract base class's enforcement mechanism.

This separation of extraction from classification allows each agent to have a narrower, more testable prompt/response contract with the underlying LLM, and lets the pipeline swap or tune one stage without affecting the other's logic.
