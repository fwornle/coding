# LiveLoggingSystem

**Type:** Component

[LLM] LiveLoggingSystem's logging behavior should be understood in contrast with the simpler, general-purpose logging utility in integrations/semantic-analysis/src/logging.ts, which uses an asynchronous buffered write pattern (FLUSH_INTERVAL_MS=100, MAX_BUFFER_SIZE=50) to append entries to dated files like `${CODING_REPO}/.data/logs/semantic-analysis-<date>.log`. While both systems share the broader convention of writing logs relative to CODING_REPO/.data/logs, LiveLoggingSystem's responsibilities are considerably more complex: it must handle session windowing (grouping related conversation turns), file routing (directing output to per-user or per-session files), and content classification/redaction — none of which the semantic-analysis logger needs to do. Developers should not conflate the two; reusing the simple buffered-flush logger pattern for LSL's transcript capture would miss essential session-boundary and redaction handling that LSLConfigValidator is specifically designed to verify is correctly configured.

# LiveLoggingSystem — Technical Insight Document

## What It Is

LiveLoggingSystem is a L2 subsystem within the Coding project's ontology, declaratively registered in `.data/ontologies/coding.lower.json` as an extension of the shared 'Component' L1 carrier (one of three L1 carriers — Component/SubComponent/Detail — used across all L2 subsystems). Critically, there is no single `LiveLoggingSystem` class in the traditional OOP sense; its identity is materialized through the ontology registry chain (`upper.json → coding-ontology.json → coding.lower.json`), loaded at runtime by `OntologyRegistry` from the `@fwornle/km-core` package. Functionally, LiveLoggingSystem is the subsystem responsible for capturing, routing, redacting, and persisting live coding-session transcripts and token-usage data across multiple foreground coding agents (Claude Code, Copilot CLI, OpenCode). As a child of the Coding root component, it sits alongside sibling L2 subsystems like LLMAbstraction, DockerizedServices, KnowledgeManagement, CodingPatterns, ConstraintSystem, and SemanticAnalysis, sharing the ontology-driven classification approach but addressing a distinct operational concern: real-time, multi-user, multi-agent session logging.

## Architecture and Design

The system's architecture reflects a "compensation and reconciliation" philosophy rather than clean instrumentation. Its children — LSLConfigValidator, RedactionConfigManager, MultiUserHashManager, LiveTranscriptWatchers, TokenUsageAdapters, and ObservationWriter — each address a discrete concern: configuration correctness, content redaction, user anonymization, transcript capture, token accounting, and observation persistence, respectively. This category separation mirrors the LSLConfigValidator's own validation architecture, which checks environment variables, directory structure, redaction config, user hash setup, system health, performance, and security as independent categories rather than a monolithic pass — enabling targeted diagnostics when a live-logging setup fails.

Classification of content into the LiveLoggingSystem L2 class follows a dual-path model consistent with the broader SemanticAnalysis subsystem's "deterministic-first, LLM-as-fallback" pattern: a deterministic path via `classifyL2()` in `l2-subsystem-classifier.ts`, and an LLM-driven path via `OntologyClassificationAgent` in `ontology-classification-agent.ts`, which loads exactly 10 valid L2 classes via `loadL2Classes()` and constrains output through `buildL2RefinementPrompt()`. Notably, this prompt text explicitly references 'ETM', creating a documented conceptual linkage to the sibling EtmDaemon L2 class — a reminder that LiveLoggingSystem's description text must stay precise to avoid classification drift.

TokenUsageAdapters embodies a deliberate "second writer" architecture: rather than intercepting network calls to the rapid-llm-proxy (the authoritative source for `token_usage.db`), it reconstructs token rows after the fact from each agent's own persistence artifacts. This is explicitly a lossy, best-effort compensation strategy, not a clean instrumentation point.

## Implementation Details

Configuration is file-based and schema-validated, centered on `.specstory/config/lsl-config.json` and `redaction-config.yaml`. `LSLConfigValidator` (in `scripts/validate-lsl-config.js`) computes `configDir = path.join(projectPath, '.specstory', 'config')` and enforces concrete numeric bounds — `userHashLength` between 6–12 characters, `fileManager.maxFileSize` between 1MB–100MB — via `this.schemas.lslConfig.constraints`, failing validation rather than silently degrading.

Multi-user isolation appears at two layers. At the OS level, `validateUserEnvironment()` hashes the `USER` env var with SHA-256 and truncates to 6 hex characters (24 bits) for session/file routing — a design acknowledged to carry nontrivial collision risk at scale, suited only to small teams. At the token subsystem level (MultiUserHashManager), `lib/lsl/token/token-db.mjs` instead uses fixed per-adapter hash constants (`ADAPTER_USER_HASH_CLAUDE`='cladpt', `ADAPTER_USER_HASH_COPILOT`='copadt', `ADAPTER_USER_HASH_OPENCODE`='opnadt'), each matching a `/^[a-z][a-z0-9]{5}$/` charset — a manual sharding scheme (decision D-06) preventing id-collision across the SQLite composite primary key `(user_hash, id)` shared by the proxy and adapters.

RedactionConfigManager has no standalone class; its behavior is wired directly into `src/live-logging/ObservationWriter.js`, which imports `ConfigurableRedactor`, `getLSLWindow` (from `lib/lsl/window.mjs`), and `routeFromArtifacts` (from `lib/attribution/repo-router.mjs`). ObservationWriter retains `this.dbPath` purely as a config path (not a handle) to derive `projectRoot` for the redactor, coupling redaction resolution to constructor-time setup.

LiveTranscriptWatchers is realized via two structurally unrelated implementations: `lib/lsl/live/copilot-events-tail.mjs` polls `~/.copilot/session-state/<uuid>/events.jsonl` every 200ms (`TAIL_POLL_INTERVAL_MS`), while `lib/lsl/token/opencode-token-rows.mjs` performs on-demand SQLite reads against `~/.local/share/opencode/opencode.db` at measurement-stop — push-polling versus pull-snapshot models with no shared abstraction.

## Integration Points

LiveLoggingSystem's classification integration relies on `extractL2FromLLMResponse()` in `ontology-classification-agent.ts`, which performs token-boundary regex matching against registered L2 class names to prevent hallucinated compound terms from falsely matching "LiveLoggingSystem." Any renaming of the class must preserve this regex compatibility.

Operationally, it depends on `.specstory/config/` per-project directory conventions, shares the `CODING_REPO/.data/logs` logging convention with the simpler logger in `integrations/semantic-analysis/src/logging.ts` (though LSL's session-windowing, routing, and redaction needs are substantially more complex), and interfaces with the rapid-llm-proxy at `:12435` as the authoritative token-usage source that TokenUsageAdapters compensates around.

## Usage Guidelines

Developers must edit ontology JSON files, not TypeScript, to change LiveLoggingSystem's semantic definition. Manual edits to `lsl-config.json` must respect validator-enforced numeric bounds. Do not reuse the simple buffered-flush logging pattern for transcript capture — it lacks session-boundary and redaction handling. When adding a new agent to LiveTranscriptWatchers, evaluate its on-disk artifact shape rather than assuming a reusable watcher exists. Any extension of the 24-bit user-hash scheme to larger deployments should reconsider collision probability, and new token-usage adapters must never let failures propagate, consistent with the existing best-effort compensation design.
