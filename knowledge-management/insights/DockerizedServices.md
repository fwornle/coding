# DockerizedServices

**Type:** Component

[LLM] The health-check subsystem enforces a strict invariant (documented as SPEC R6) that probing functions in service-probe.js—probeHttpHealth() and probeTcpPort()—must never report a 'healthy' status directly. Instead, these functions only distinguish between 'stopped' (connection refused, timeout, or non-2xx HTTP response) and 'unknown' (configuration errors, malformed URLs, or unresolvable hosts). This is a deliberate architectural choice: liveness probes are pessimistic by design, and the actual determination of 'healthy' is deferred to a higher-level coordinator that combines probe results with other signals (e.g., process registration state from ProcessStateManager). New developers extending probe logic must preserve this three-state contract rather than optimistically returning 'healthy' from a probe function, since downstream consumers (the health-coordinator) rely on the absence of false positives here.

# DockerizedServices: Technical Insight Document

## What It Is

DockerizedServices is the infrastructure component within the Coding project responsible for orchestrating, health-checking, and containerizing the system's runtime services. It spans a set of concrete implementation files: `lib/service-starter.js` (retry/backoff orchestration), `service-probe.js` (liveness probing), `process-state-manager.js` (global process tracking), `llm-mock-service.ts` (cross-boundary LLM mode state), and the Docker packaging layer itself — `docker/docker-compose.yml`, `Dockerfile.coding-services`, `entrypoint.sh`, and `supervisord.conf`. Wrapper scripts under `scripts/` (`api-service.js`, `dashboard-service.js`) tie these pieces together by spawning and registering real backend processes (Express's `dashboard-server.js` on port 3031, Next.js's dev server on port 3030).

As the parent of ServiceStarter, ServiceProbe, ProcessStateManager, LLMMockService, DockerEntrypoint, StartServicesRobust, and ServiceWrapperScripts, DockerizedServices functions as the umbrella for "how services get started, watched, and packaged" across both native host execution and containerized Docker execution — a duality that recurs throughout its design.

## Architecture and Design

The component's defining architectural trait is a strict separation between *pessimistic detection* and *optimistic determination*. SPEC R6, enforced in `service-probe.js`, mandates that `probeHttpHealth()` and `probeTcpPort()` never report "healthy" — only "stopped" or "unknown" — deferring true health determination to a higher-level health-coordinator that combines probe results with ProcessStateManager's registration state. This same pessimism-by-design philosophy echoes down into DockerEntrypoint, whose `wait_for_service()` TCP-probes Qdrant and Redis but explicitly returns success regardless of outcome ("Don't fail — let supervisord handle it"), pushing real health determination further downstream still.

![DockerizedServices — Architecture](images/dockerized-services-architecture.png)

A second major architectural decision is bundling multiple independent Node/Next.js services plus datastores (Redis, Memgraph) into a single Docker image using supervisord as an in-container process manager, rather than the conventional one-process-per-container model. This trades Docker/Kubernetes-native process supervision for deployment simplicity, shifting the burden of restart policy and log multiplexing onto `entrypoint.sh` and `supervisord.conf`.

A third recurring pattern is externalized, file-based state sharing across the host/container boundary — seen both in `llm-mock-service.ts` (LLM mode persisted in `.data/workflow-progress.json`, path-resolved via `CODING_ROOT`) and in DockerEntrypoint's consumption of a host-written `/coding/.coding/runtime/features.json` snapshot, translated into supervisord include files. Both avoid independent state derivation on each side of the boundary, preventing drift.

## Implementation Details

ServiceStarter's `startServiceWithRetry()` implements a three-layer resilience wrapper: an outer retry loop (default `maxRetries=3`) with exponential backoff (`retryDelay * 2^(attempt-1)`), an inner `withDeadline()` timeout guard applied separately to the start call (30000ms default) and health check call (10000ms hardcoded), and post-failure cleanup that SIGTERMs then SIGKILLs unhealthy children before retrying. Critically, `withDeadline()` wraps `Promise.race()` and clears its timer in a `finally` block regardless of which promise wins — avoiding the classic Node.js dangling-timer leak that would otherwise accumulate across retry attempts and hang test runners or CLIs. ServiceStarter also distinguishes "required" from "optional" services, letting the system boot even if a service like graphify fails.

ServiceWrapperScripts (`api-service.js`, `dashboard-service.js`) follow a consistent spawn-register-unregister pattern: each spawns a real backend child process, registers it with ProcessStateManager's `ProcessStateManager` class for global visibility, and unregisters on exit — giving a Global Service Coordinator system-wide process visibility without bespoke IPC. `dashboard-service.js` additionally injects `NEXT_PUBLIC_API_BASE_URL` into the child environment, illustrating environment-variable-based cross-service wiring rather than service discovery.

DockerEntrypoint's feature-gating logic embeds a `node -e` snippet that treats any value other than `false` as enabled — a deliberate fail-open default ensuring older host snapshots never accidentally disable new features.

## Usage Guidelines

Developers extending probe logic must preserve ServiceProbe's three-state contract (SPEC R6) — never optimistically return "healthy" from a probe function, since the health-coordinator relies on the absence of false positives. Anyone adding retry/timeout logic should model new code on ServiceStarter's `withDeadline()` pattern, always clearing timers in a `finally` block to avoid event-loop leaks. New service wrappers should follow ServiceWrapperScripts' spawn/register/unregister convention against ProcessStateManager rather than inventing bespoke tracking. Because ports and paths are environment-driven, new services should avoid hardcoding host/port values and instead support override via environment variables, consistent with the CODING_ROOT/container-path duality baked into LLMMockService and DockerEntrypoint. Finally, remember that supervisord-based bundling in the Docker layer means restart/log-multiplexing behavior lives in `entrypoint.sh`/`supervisord.conf`, not in Docker/Kubernetes primitives — changes to service supervision must be made there.
