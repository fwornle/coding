# DockerizedServices

**Type:** Component

[LLM] The DockerizedServices layer is architected around a dual-mode execution model: services can run either as supervisord-managed processes inside a single Docker container (per docker/docker-compose.yml, Dockerfile.coding-services, supervisord.conf) or as host-native Node subprocesses managed by lib/service-starter.js and PID-tracked via ProcessStateManager. This duality means developers must understand that 'starting a service' has two entirely separate code paths depending on deployment target, and that health-checking logic (service-probe.js) is written to be agnostic to which path is in effect — it only cares about HTTP/TCP reachability, not process ownership. This design avoids needing separate health-monitoring logic for containerized vs local services, but it also means Docker-specific failures (e.g., supervisord misconfiguration killing a service inside the container) surface identically to host-side crashes, requiring log inspection to disambiguate.

# DockerizedServices — Technical Insight Document

## What It Is

DockerizedServices is the component responsible for running, supervising, and health-checking the coding toolkit's service processes across two fundamentally different deployment targets: a single Docker container using supervisord (defined in `docker/docker-compose.yml`, `Dockerfile.coding-services`, `supervisord.conf`), or host-native Node subprocesses orchestrated by `lib/service-starter.js` and tracked via `ProcessStateManager`. As the parent of `ServiceStarter`, `ServiceProbe`, `APIServiceWrapper`, `DashboardServiceWrapper`, `SupervisordRuntime`, `ProcessStateManager`, and `StartServicesRobust`, this component embodies the "dual-mode execution model" that sits alongside its siblings LiveLoggingSystem, LLMAbstraction, KnowledgeManagement, CodingPatterns, ConstraintSystem, and SemanticAnalysis under the root Coding hierarchy.

## Architecture and Design

The defining architectural decision is that "starting a service" is not a single code path but two parallel ones, unified only at the health-checking layer. `service-probe.js` (child component ServiceProbe) is deliberately blind to process ownership — it only cares about HTTP/TCP reachability — which lets the same polling logic serve both supervisord-managed processes and host subprocesses. This is a classic adapter/normalization pattern, echoed by `APIServiceWrapper` and `DashboardServiceWrapper` (`scripts/api-service.js`, `scripts/dashboard-service.js`), which wrap heterogeneous underlying processes (a plain Express API vs. a Next.js dev server) behind one lifecycle contract: spawn, `registerService()` against the global `ProcessStateManager`, and SIGTERM/SIGINT handling with cleanup. The Global Service Coordinator never needs to know a service is actually `npm run dev` under the hood.

A notable structural risk is duplication rather than unification: `docker/entrypoint.sh`'s `wait_for_service()` implements its own ad-hoc `/dev/tcp` probing for container-internal database readiness (Qdrant/Redis), entirely separate from `service-probe.js`'s ongoing post-startup polling. Similarly, feature-gating exists in two independently maintained mechanisms — `ServiceStarter`'s `SERVICE_CONFIGS`/`SERVICE_ORDER` JS object config (checked via `loadFeatures`) for the host path, and `SupervisordRuntime`'s `docker/entrypoint.sh` shell-based generation of `/etc/supervisor/features.d/disabled.conf` for the container path. Both implement the same feature-string concept (e.g., `semantic-analysis:knowledge`, `graphify:codegraph`) but any new feature must be wired into both, a drift risk explicitly guarded by `tests/features/service-gating.test.mjs`.

## Implementation Details

`service-starter.js`'s `startServiceWithRetry()` encodes the resilience policy: exponential backoff, a configurable `maxRetries` ceiling, and a `withDeadline()` helper racing startup against a hard timer with guaranteed `clearTimeout()` cleanup. This is paired with a required/optional split — `DashboardServiceWrapper` documents that `transcriptMonitor` and `liveLoggingCoordinator` are `required: true` with hard-fail semantics (since later services register against them, enforced by `SERVICE_ORDER.slice(0,2)` assertions), while dashboard/graphify are optional and allowed to fail without aborting the system.

`service-probe.js` implements SPEC R6's strict three-state model — running/stopped/unknown — never synthesizing a "healthy" status. `probeHttpHealth()` and `probeTcpPort()` map connection-refused errors to "stopped" but configuration errors (malformed URL, missing port) to "unknown," a distinction the health-coordinator's 5-second poll uses to differentiate safe-to-restart crashes from ambiguous situations requiring alerting instead.

`SupervisordRuntime`'s entrypoint script reads `/coding/.coding/runtime/features.json`, and for each `PROGRAM_FEATURES` entry shells out to `node -e` (jq is unavailable in the image) to decide whether to emit `autostart=false` stanzas — never touching canonical `supervisord.conf` program definitions, only flipping autostart via the `[include]` directive. This is explicitly fail-open: missing snapshots or unknown features default to "enabled," reasoning that a silently-empty container is harder to diagnose than one running too much.

## Integration Points

DockerizedServices integrates tightly with LLMAbstraction: `llm-mock-service.ts`'s `isMockLLMEnabled()`, `getLLMMode()`, `getLLMState()`, and `setGlobalLLMMode()` use `process.env.CODING_ROOT || repositoryPath` specifically to bridge host vs. container filesystem paths when constraint-monitor or semantic-analysis services run inside the Docker container. The LLMState structure with globalMode and perAgentOverrides fields enables fine-grained control where a specific agent can be forced into mock mode for testing while the rest of the system runs against real providers. This is critical for integration testing scenarios where a developer wants to validate one agent's prompt-handling logic without incurring API costs or non-determinism from the LLM calls of other agents in a multi-agent pipeline. The getLLMMode() read path checks perAgentOverrides first, then falls back to globalMode, and finally to the legacy progress.mockLLM boolean, establishing a three-tier precedence resolution that any new developer must understand before assuming a single toggle controls behavior.
- [KnowledgeManagement](./KnowledgeManagement.md) -- [LLM] The GraphifyGraph reader (integrations/semantic-analysis/src/agents/graphify-graph.ts) represents a deliberate architectural simplification: rather than maintaining a live graph database connection (Memgraph via Cypher), the component now treats a static graph.json artifact produced by the graphify service as the source of truth for code-structure knowledge. This file, a NetworkX node-link JSON export, can be tens of megabytes, so GraphifyGraph implements mtime-based lazy caching — it stat()s the file and only re-parses when the mtime has changed since the last load. This pattern trades real-time graph mutation capability for drastically simpler deployment (no separate DB process) and fast repeated reads, at the cost of only picking up graph changes when the underlying analysis pipeline re-writes graph.json.
- [CodingPatterns](./CodingPatterns.md) -- [LLM] The config/agents/*.sh scripts (claude.sh, copilot.sh, opencode.sh, pi.sh) implement a uniform adapter pattern where each script normalizes a different vendor CLI into a common invocation contract described in docs/architecture/agent-abstraction-api.md. Concretely, each script accepts the same positional arguments and environment variables (e.g., LLM_PROXY_URL, CODING_OPENCODE_MODEL), performs argument translation specific to its backend binary, and emits output in a shared format consumable by the orchestrator layer. This lets the rest of the system (e.g., wave-controller.ts or any dispatcher invoking these scripts) remain agnostic to which underlying agent CLI is actually installed—new agents can be onboarded by adding a new script that satisfies the same contract rather than modifying core dispatch logic, as described in docs/architecture/adding-new-agent.md.
- [ConstraintSystem](./ConstraintSystem.md) -- [LLM] The configuration merging strategy in HookConfigLoader (lib/agent-api/hooks/hook-config.js) implements a three-tier cascade — DEFAULT_CONFIG baked into the code, user-level settings from ~/.coding-tools/hooks.json, and project-level settings from .coding/hooks.json — resolved through mergeConfigs(). This design lets individual developers set personal defaults (e.g., preferred logging verbosity or disabled hooks) while allowing a project to enforce mandatory constraints that override user preferences, but not vice versa. A new developer extending this system needs to understand that the merge is not a deep recursive merge in all cases; array-type handler lists are typically concatenated or replaced depending on the key, so adding a new hook type requires checking mergeConfigs() logic to avoid silently dropping user-level handlers.
- [SemanticAnalysis](./SemanticAnalysis.md) -- [LLM] The classification pipeline in OntologyClassificationAgent embodies a deliberate 'deterministic-first, LLM-as-fallback' philosophy that recurs throughout SemanticAnalysis. Before any LLM call is made, classifySingleObservation() checks the observation's name against the hard-root-guard set (CollectiveKnowledge, Coding, DynArch, Timeline, Normalisa) imported from @fwornle/km-core's HIERARCHY_ROOTS. If matched, the method immediately assigns classificationMethod='hard-root-guard' and returns without ever invoking classifier.classify() or touching the LLM. This is a defensive engineering decision: because these 5 names anchor the entire hierarchy, any LLM-driven misclassification of them would cascade corruption through the whole ontology tree, so the developers chose to hardcode an escape hatch rather than trust probabilistic classification for structurally critical nodes.
