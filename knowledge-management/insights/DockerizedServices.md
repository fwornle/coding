# DockerizedServices — Technical Insight Document

## What It Is

DockerizedServices is the supervised-process and health-verification layer for the Coding project's containerized backend, implemented centrally in `lib/service-probe.js` (health-check polling) and `lib/service-starter.js` (process lifecycle management). Rather than mapping one Docker Compose entry to one process, this component manages multiple logical services — including `scripts/api-service.js`, `scripts/dashboard-service.js`, semantic analysis MCP, and the constraint monitor — as supervised child processes within a shared container context. Its children realize this architecture concretely: `ContainerEntrypoint` (`docker/entrypoint.sh`) gates process startup on database availability, `RobustServiceStarter` (`scripts/start-services-robust.js`) drives feature-gated, retry-aware startup, `ConstraintMonitorServices` provisions and launches the constraint-monitor stack, `PromptClassifierService` handles classifier backend routing, and `DockerMcpConfigGenerator` is listed as a child but has no corroborating implementation in the supplied sources.

## Architecture and Design

The defining architectural decision is centralized in-container orchestration rather than per-service container isolation. `lib/service-starter.js` acts as a single Node-based supervisor for multiple logical services, trading Docker-level isolation for simpler inter-process communication via shared filesystem and in-process ports. This is a deliberate trade-off: it sacrifices fault isolation (a starter crash takes down all supervised services) in exchange for operational simplicity.

Layered on top is a tiered readiness model. At the lowest level, `ContainerEntrypoint`'s `docker/entrypoint.sh` blocks on raw TCP `wait_for_service()` checks for Qdrant and Redis before `exec`-ing into supervisord — a weaker guarantee than true readiness, since a TCP-open port doesn't mean the service has finished cold-starting. Above that, `lib/service-probe.js` implements HTTP-level health polling with a "consecutive failures within a window" heuristic to distinguish genuine failure from transient slowness — critical given highly variable container cold-start times (model loading, DB connections). `RobustServiceStarter`'s `SERVICE_CONFIGS` (in `scripts/start-services-robust.js`) formalizes this further with per-service required/optional classification, `maxRetries`, `timeout`, `startFn`, and `healthCheckFn`, giving graceful degradation for optional services while blocking on required ones — confirmed by `tests/features/service-gating.test.mjs`.

Health verification is explicitly *not* automatic: the standard operating procedure (documented in the Coding-Services Docker Container workflow) is rebuild via docker-compose, then explicitly confirm supervised processes and health endpoints before downstream pipelines like wave-analysis proceed. A container reporting "up" in Docker does not imply its internal processes are healthy.

## Implementation Details

`lib/service-probe.js`'s polling logic is reused across multiple entry points rather than being bespoke per command — the same ServiceProbe machinery backs both direct container verification and the `coding --copilot` launcher's health check, meaning probe-timing changes have cross-cutting effects system-wide. `ConstraintMonitorServices`'s legacy path in `start-services.sh` (used when `ROBUST_MODE=false`) is illustrative of the less-robust alternative: it conditionally `git clone`s `constraint-monitor`, runs `npm install --production`, and prefers `docker-compose up -d` (checking for `qdrant`/`redis` reporting `Up.*healthy`), falling back to raw `docker run` for `constraint-monitor-qdrant` (6333/6334) and `constraint-monitor-redis` (6379), then backgrounds the dashboard (`PORT=3030`) and API (`3031`) as shell jobs — with status captured only in shell-local variables and no structured health object returned to callers. This contrasts sharply with the HTTP-polling model elsewhere and represents a maintainability gap.

`PromptClassifierService` addresses a related resilience issue: the classifier previously held one fixed backend URL from boot, causing HTTP 502s when network topology changed. `config/prompt-classifier.yaml` now declares an ordered backend list with first-enabled-network-match semantics, mirroring `llm-routing.yaml`'s offload pattern.

## Usage Guidelines

Always treat a Docker "up" state as necessary but not sufficient — run the explicit rebuild-and-verify workflow after any code or data change (e.g., KB Stage 1 fixes) before relying on downstream consumers. Because `lib/service-probe.js` is shared across the container verification flow and the `coding --copilot` launcher, any change to health endpoint behavior or probe timing must be validated against both usage paths. Prefer the `RobustServiceStarter` path (`ROBUST_MODE=true`) over the legacy `start-services.sh` path for constraint-monitor provisioning, since the legacy path lacks structured health reporting and only prints status to console. When modifying classifier backend behavior, follow the `config/prompt-classifier.yaml` ordered-backend-list pattern rather than reintroducing a single fixed URL.
