# DMRProvider — Technical Insight Document

## What It Is

DMRProvider is implemented in `dmr-provider.ts` as a client for Docker Model Runner (DMR), a locally-hosted model backend reachable at `http://${DMR_HOST}:${DMR_PORT}/engines/v1`. Rather than being a bespoke client with its own request/response formats, error mappers, and streaming logic, DMRProvider is built as a thin adapter that reuses the OpenAI SDK integration's request/response contract — DMR happens to expose an OpenAI-compatible wire format, and the provider exploits that compatibility instead of writing DMR-specific plumbing. Configuration is externalized to `dmr-config.yaml` and resolved through `loadDMRConfig()`, and the provider's liveness is tracked via a cached health check, `checkDMRAvailability()`, gated by a configurable `healthCheckInterval`. As a SubComponent, DMRProvider lives beneath its parent, LLMAbstraction, and functions as one interchangeable backend within that abstraction's pluggable provider system.

## Architecture and Design

The dominant architectural choice is **protocol reuse**: DMRProvider deliberately mimics the OpenAI wire shape so it can piggyback on existing request builders, response parsers, and error handling rather than duplicating that logic. This is a calculated trade-off — it minimizes DMR-specific surface area and code duplication, but it also means any true DMR quirks (divergent error codes, different streaming semantics, unusual rate-limit headers) would have to be shimmed awkwardly into the OpenAI shape rather than handled on their own terms, creating a latent leaky-abstraction risk if DMR's compatibility layer ever drifts from the OpenAI spec it imitates.

![DMRProvider — Architecture](images/dmrprovider-architecture.png)

Configuration resolution follows a **layered resolution pattern** that recurs across the LLM subsystem: `loadDMRConfig()` searches multiple candidate file paths and applies `expandEnvVars()` for shell-style `${VAR:-default}` expansion, closely mirroring `llm-with-process.ts`'s `resolveProxyCompleteUrl()`, which resolves an ordered precedence of environment variables (`RAPID_LLM_PROXY_URL` → `LLM_CLI_PROXY_URL` → `LLM_PROXY_URL` → localhost fallback). This repetition across independently-authored modules indicates a house convention: new provider implementations are expected to replicate this "search paths, then expand env vars with defaulting" pattern rather than invent their own.

Availability tracking uses a **cached health-check pattern**: `checkDMRAvailability()` amortizes liveness probing over a configurable interval instead of checking synchronously on every call. Given that DMR is a local, potentially slow-starting or restarting backend, this avoids injecting probe latency into every request in workflows that may issue dozens of LLM calls per run — trading a small window of staleness for consistent low-latency behavior on the hot path.

## Implementation Details

`dmr-provider.ts` centers on a small set of responsibilities: constructing OpenAI-shaped requests against the DMR engines endpoint, parsing OpenAI-shaped responses, and exposing `checkDMRAvailability()` as a gated liveness check. Configuration loading via `loadDMRConfig()` decouples runtime behavior from hardcoded values, searching multiple candidate paths for `dmr-config.yaml` and expanding environment variable placeholders with shell-parameter-expansion semantics (`${VAR:-default}`).

Because DMRProvider emits OpenAI-shaped JSON-mode output, it is exposed to the same malformed-output failure modes as any SDK-driven provider — embedded control characters corrupting string literals, and token-ceiling truncation mid-object/mid-array. Rather than reimplementing repair logic, DMRProvider is expected to flow its output through the shared repair pipeline in `parse-llm-json.ts`, specifically `escapeControlCharsInStrings()` and `truncateToLastCompleteElement()`. This reflects the codebase's general preference for shared utility layers over per-provider duplication — a sibling entity, LlmJsonParser, treats these as two independent, orthogonal failure modes handled by a fixed two-stage pipeline rather than a single catch-all heuristic.

## Integration Points

![DMRProvider — Relationship](images/dmrprovider-relationship.png)

DMRProvider is not invoked directly as a standalone client; it is one backend orchestrated by its parent, LLMAbstraction, whose sibling component LLMMockService governs backend selection through `getLLMMode()`. This function resolves state in three tiers — `perAgentOverrides`, then `globalMode`, then the legacy `progress.mockLLM` boolean — persisted in `.data/workflow-progress.json` rather than environment variables, enabling hot-swapping between DMR, a real cloud provider, or a mock without process restarts. This runtime pluggability is precisely why the OpenAI-shape-compatibility decision matters: it's what allows call sites to remain agnostic about whether DMR, a cloud SDK, or a mock actually serves a given request.

`setGlobalLLMMode()` dual-writes both the new `llmState` and the legacy `progress.mockLLM` flag on every mode change rather than performing a one-time migration, implying unknown or undocumented external consumers of the legacy flag exist outside the LLM abstraction's own boundary. Any code toggling DMR into or out of active use must go through `getLLMMode()` rather than reading mode state directly, or it risks observing a stale/inconsistent signal — exactly the failure mode the dual-write exists to prevent. This same config-vs-runtime distinction shows up in a sibling subsystem, the offload judge behind `use-classifier-judge.ts`, where a documented incident (`enabled: true` masking a dead backend for roughly a day) underscores why collapsing "configured" and "actually working" into one boolean is dangerous — the same class of ambiguity `getLLMMode()`'s explicit three-tier precedence is designed to avoid.

Beyond mode selection, DMRProvider's JSON-mode outputs are expected to pass through the shared repair pipeline (`parse-llm-json.ts`), and its metrics likely interoperate with the duck-typed `MetricsTrackerLike` interface seen in `llm-with-process.ts`, keeping observability consistent across all OpenAI-shaped backends regardless of which one actually serves a call.

## Usage Guidelines

Developers extending or maintaining DMRProvider should treat it as a backend implementation behind a shared interface, not a standalone client — new logic should conform to the existing OpenAI-shaped request/response contract rather than special-casing DMR behavior deeper in the stack. When adding configuration, follow the established multi-path-search-plus-shell-expansion convention (`loadDMRConfig()` / `expandEnvVars()`) rather than introducing a new config resolution mechanism. Avoid adding synchronous availability checks to the request hot path; extend the existing cached `checkDMRAvailability()` interval mechanism instead. Callers or tooling that need to know which backend is currently active must read state through `getLLMMode()`'s three-tier precedence rather than inspecting `progress.mockLLM` or `globalMode` directly, since the dual-write compatibility shim only guarantees consistency through that accessor. Finally, any new JSON-mode handling should be routed through the shared `parse-llm-json.ts` repair utilities rather than duplicated locally, preserving the codebase's convention of centralizing cross-cutting concerns (JSON repair, metrics, config resolution) rather than re-solving them per provider.
