# StartServicesRobust — Technical Insight Document

## What It Is

StartServicesRobust is implemented primarily in `scripts/start-services-robust.js`, and serves as the host-native orchestration layer within the `DockerizedServices` domain — the counterpart to supervisord-managed containerized process startup. Its core artifact is a configuration table, `SERVICE_CONFIGS`, keyed by service name and iterated in a fixed sequence via `SERVICE_ORDER`, with each entry declaring a `startFn`, `healthCheckFn`, an optional `feature` gate, and a `required` boolean. This table-driven design is exposed structurally to its children: `ServiceOrderRegistry` embodies the SERVICE_CONFIGS/SERVICE_ORDER pairing as a self-consistent registry, and `PortCleanupUtilities` implements the low-level process/port termination logic (`killProcessOnPortAndWait`, `waitForPortBindable`) that startFn implementations depend on before spawning.

## Architecture and Design

The dominant pattern is configuration-table dispatch: rather than ten hand-written, bespoke start blocks, one loop (`startOneService()`) walks `SERVICE_ORDER` and interprets each `SERVICE_CONFIGS` entry uniformly. Two classification axes are layered orthogonally on this same table rather than conflated: required/optional (does a failure block startup) and feature-enabled/disabled (did the operator want this service at all). `tests/features/service-gating.test.mjs` encodes this distinction precisely — a disabled service is never reported as "degraded" (disabling and degrading are opposite operator intents), and a required service whose feature is off does not block startup, since `required` only applies once a feature is actually active.

This produces the module's headline design tension: it must fail closed for the two REQUIRED services (`transcriptMonitor`, `liveLoggingCoordinator`) — a required failure sets `out.blocked = true` and halts SERVICE_ORDER iteration — while remaining fail-open enough elsewhere to keep the toolkit "usable in a degraded state." Notably, this is the inverse fail-direction from its sibling `docker/entrypoint.sh` gating logic, which treats missing/unreadable snapshots and unknown feature keys as "enabled" because silently running nothing is harder to diagnose than running too much. StartServicesRobust and the container-side gating are two independent implementations of the same concept (JS object config vs. shell/supervisord-conf generation), kept in sync only by test-enforced structural assertions, not shared code — the same "enumerate both sides and diff" idiom appears in `tests/features/container-gating.test.mjs` for the PROGRAM_FEATURES mapping.

## Implementation Details

The `transcriptMonitor` startFn is the most heavily defended path in the module, reflecting deep distrust of its own bookkeeping. It runs a three-tier duplicate-detection cascade — ProcessStateManager global check, PSM per-project check, then an OS-level `pgrep`-based check (`isProcessRunningByScript()`) with automatic re-registration of orphans found only at the OS level — before ever spawning. This cascade is historical residue from a retired per-project LSL coordinator (per a "Phase 33 plan 07" comment); spawning responsibility now lives in `bin/coding` calling `enhanced-transcript-monitor.js` directly, meaning a future refactor risks removing the wrong defensive layer.

Port/process lifecycle management, delegated conceptually to `PortCleanupUtilities`, is similarly layered: `killProcessOnPortAndWait()` implements SIGTERM-then-poll-then-SIGKILL escalation with a hard deadline (default 5000ms, escalating at the halfway point), and `waitForPortBindable()` probes actual TCP bindability via a throwaway `net.createServer()` rather than trusting HTTP-based `isPortListening()` checks, because a just-crashed process can leave a kernel-held socket that isn't answering HTTP but will still `EADDRINUSE` a fresh listener. Together with the PSM registry and `pgrep`, this gives three independent verification layers before trusting a "not running" determination.

`ServiceOrderRegistry`'s structural guarantees are enforced by `tests/features/service-gating.test.mjs`: every SERVICE_CONFIGS entry must declare a `feature`, and SERVICE_ORDER/SERVICE_CONFIGS keys must be exactly set-equal — sorted and diffed rather than trusted to hand-maintenance, because "ten hand-written start blocks were ten chances to forget a gate." The test also pins `SERVICE_ORDER.slice(0, 2)` to `['transcriptMonitor', 'liveLoggingCoordinator']`, since later services register against this pair.

## Integration Points

StartServicesRobust sits under `DockerizedServices` alongside sibling components `ServiceStarter` (whose `startServiceWithRetry()` supplies the retry/timeout mechanics that StartServicesRobust's SERVICE_CONFIGS entries invoke), `ServiceProbe` (protocol-level health <COMPANY_NAME_REDACTED> reused for health-check functions), `ProcessStateManager` (the registry this module deliberately re-verifies rather than trusts), `APIServiceWrapper`, `DashboardServiceWrapper`, and `SupervisordRuntime` (the containerized analog implementing the parallel but independent PROGRAM_FEATURES gating in `docker/entrypoint.sh`). Feature resolution is sourced from `lib/features/index.mjs`'s `loadFeatures()`, consumed via each SERVICE_CONFIGS entry's `feature` field — the same resolver whose logic cannot run inside the container, forcing `docker/entrypoint.sh` to consume a flat JSON snapshot instead. `start-services.sh:9`'s `ROBUST_MODE` flag is the toggle between this script and legacy shell-based startup, making StartServicesRobust an opt-in replacement path rather than the sole entry point.

## Usage Guidelines

Developers adding a new service must register it in both SERVICE_CONFIGS and SERVICE_ORDER — omitting either triggers the coverage test failure by design. The `required` flag should be reserved for services whose failure should legitimately halt all downstream startup (currently only `transcriptMonitor` and `liveLoggingCoordinator`); misclassifying a service as required risks unnecessarily blocking start-up, while misclassifying `transcriptMonitor` as optional would silently break the observability pipeline other services depend on. When introducing a new feature flag, it must be wired into both this host-side table and the container-side `PROGRAM_FEATURES` mapping in `docker/entrypoint.sh`, or the two deployment modes will drift undetected outside of test coverage. Anyone modifying the transcriptMonitor duplicate-detection cascade should be aware it partially defends against a spawn path (the retired per-project LSL coordinator) that no longer exists, and should verify against current spawn topology before removing any layer.

This duality means developers must understand that 'starting a service' has two entirely separate code paths depending on deployment target, and that health-checking logic (service-probe.js) is written to be agnostic to which path is in effect — it only cares about HTTP/TCP reachability, not process ownership. - [PortCleanupUtilities](./PortCleanupUtilities.md) -- [LLM] `killProcessOnPortAndWait()` in scripts/start-services-robust.js implements a SIGTERM-then-poll-then-SIGKILL escalation rather than a blind `kill -9`: it first checks `checkPortInUse()` via `lsof -ti:${port}`, sends SIGTERM to all owning PIDs, then polls every `pollIntervalMs` (default 200ms) up to `maxWaitMs` (default 5000ms), only escalating to SIGKILL once half the wait budget has elapsed. This two-phase design gives a well-behaved process a real chance to release its socket and flush state before being forcibly killed, while still guaranteeing termination within a hard deadline — a deliberate trade-off between graceful shutdown and startup-blocking latency.
