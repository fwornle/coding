# Coding — Project Insight Document

## What It Is

Coding is the root project encompassing the entire development infrastructure knowledge hierarchy, organized into seven L1 components: LiveLoggingSystem, LLMAbstraction, DockerizedServices, KnowledgeManagement, CodingPatterns, ConstraintSystem, and SemanticAnalysis. These components are not arbitrary groupings — each represents a cohesive functional subsystem with its own implementation surface (e.g., `scripts/validate-lsl-config.js`, `integrations/semantic-analysis/src/agents/`, `lib/agent-api` for HookConfigLoader), while CodingPatterns exists as a cross-cutting conceptual layer rather than a discrete directory. Together they form the operational backbone for session logging, multi-provider LLM access, service health monitoring, knowledge persistence, constraint enforcement, and semantic extraction from development history.

## Architecture and Design

The project exhibits a strong preference for **layered, fail-closed, and pessimistic-by-default** design across its components. LiveLoggingSystem's `LSLConfigValidator` enforces strict schema validation across two decoupled config artifacts (behavioral vs. redaction policy), rejecting any config missing required sections rather than degrading gracefully. DockerizedServices mirrors this caution in its health-check subsystem: probe functions in `service-probe.js` are architecturally forbidden from asserting "healthy" status (SPEC R6), instead reporting only "stopped" or "unknown" and deferring the healthy determination to a higher-level coordinator that fuses probe results with process registration state. This is the same pessimistic-probe pattern echoed conceptually across the project's approach to uncertainty.

LLMAbstraction favors **thin wrappers over deep abstraction** — a deliberate architectural stance documented explicitly as "Option B" in `llm-with-process.ts`, where a single-repo wrapper was chosen over modifying the upstream `@rapid/llm-proxy` SDK. This preserves existing SDK metrics while patching gaps, illustrating a broader project convention of minimal-invasion extension rather than forking dependencies.

CodingPatterns formalizes these idioms as project-wide conventions: adapter patterns for storage backends, lazy initialization for agent classes, circuit-breaker/caching decorators around external calls, and dependency-injected registries (`ProviderRegistryManager`). Configuration-driven behavior (`config/features.yaml`, `config/agent-profiles.json`) is favored over hardcoded logic — externalizing policy from mechanism is a recurring theme also visible in ConstraintSystem's two-tier layered merge pattern in `HookConfigLoader`.

## Implementation Details

Within LLMAbstraction, `llm-mock-service.ts` persists per-agent mode state (mock/local/public) in a shared `workflow-progress.json` with legacy fallback support; `dmr-provider.ts` implements a singleton client with cached health checks and YAML config loading across multiple candidate paths; `parse-llm-json.ts` implements a narrow character-level state machine that repairs only raw control characters in string literals — a deliberately narrow fix scoped to an observed production failure mode, avoiding broad JSON-guessing so failures remain loud and diagnosable.

In DockerizedServices, `probeHttpHealth()` and `probeTcpPort()` implement the three-state contract (stopped/unknown, never healthy) that downstream consumers depend on for false-positive avoidance. In KnowledgeManagement, the VKB server sits atop KMCore (a graph database backend that replaced an earlier LevelDB engine), implementing query logic, caching, and decay scheduling as first-class responsibilities beyond simple passthrough — validated by a dedicated migration test suite ensuring behavior survives storage-backend swaps.

Cross-component integration is evident through shared conventions rather than direct coupling: CodingPatterns' idioms (Manager/Adapter/Service suffixes, `CircuitBreakerManager`, `ConstraintMonitoringService`, `egress-lint-allowlist.json`) are implemented consistently across otherwise independent SubComponents like GraphDatabaseManager and LLMServiceProvider. SemanticAnalysis, as a multi-agent pipeline, consumes both git history and LSL session data — directly depending on LiveLoggingSystem's output as an input source.

## Usage Guidelines

Developers extending probe logic in DockerizedServices must preserve the three-state contract and never optimistically return "healthy." Config changes in LiveLoggingSystem must satisfy all five required top-level schema sections or fail validation entirely — no partial/permissive configs. When integrating new LLM providers, follow the established thin-wrapper convention (as in `llm-with-process.ts`) rather than modifying upstream SDKs directly. Any storage backend changes in KnowledgeManagement must preserve VKB's query/caching/decay semantics, verified via the migration test suite. Broadly, new code should adopt CodingPatterns' naming and structural idioms (`*Manager`, `*Adapter`, `*Service`) and externalize policy into configuration files rather than hardcoding behavior.
