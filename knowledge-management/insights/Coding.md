# Coding — Project-Level Insight Document

## What It Is

Coding is the root project encompassing the full development infrastructure knowledge hierarchy, organized into seven L1 components: LiveLoggingSystem, LLMAbstraction, DockerizedServices, KnowledgeManagement, CodingPatterns, ConstraintSystem, and SemanticAnalysis. Rather than being a single monolithic codebase, Coding is best understood as an ontology-driven knowledge system — its own child component, LiveLoggingSystem, is not even a traditional class but an L2 entry in `.data/ontologies/coding.lower.json`, extending a shared `Component` carrier used across all L2 subsystems. This signals that Coding as a whole is self-descriptive: the project models its own architecture as data (ontology JSON files loaded via OntologyRegistry from `@fwornle/km-core`) as much as it models external code.

## Architecture and Design

Several recurring architectural philosophies cut across Coding's children. First, a **declarative-over-imperative** pattern: semantic identity (as with LiveLoggingSystem) lives in ontology registry chains (`upper.json` → `coding-ontology.json` → `coding.lower.json`) rather than in TypeScript class hierarchies. Second, a **dual-mode execution** pattern recurs in both LLMAbstraction (mock/local/public toggle backed by `.data/workflow-progress.json`) and DockerizedServices (supervisord-managed containerized processes vs. host-native subprocesses via `lib/service-starter.js`), where a single abstraction layer hides two divergent runtime paths behind a common interface (e.g., `service-probe.js` health checks agnostic to process ownership). Third, a **simplification-for-deployability** trade-off appears in KnowledgeManagement, where GraphifyGraph reads a static `graph.json` snapshot instead of maintaining a live Memgraph connection — trading real-time mutation for operational simplicity. Fourth, a **uniform adapter pattern** in CodingPatterns (`config/agents/*.sh` scripts) normalizes heterogeneous vendor CLIs into one invocation contract, keeping orchestration logic (e.g., `wave-controller.ts`) agnostic to backend specifics. These patterns collectively suggest a project-wide design ethos: isolate volatility (vendor differences, deployment targets, LLM non-determinism) behind stable, cascade-resolved interfaces.

## Implementation Details

Precedence-cascade resolution is a recurring implementation mechanic: LLMAbstraction's `getLLMMode()` checks `perAgentOverrides`, then `globalMode`, then the legacy `progress.mockLLM` boolean — a three-tier fallback mirrored conceptually in ConstraintSystem's `HookConfigLoader`, which merges `DEFAULT_CONFIG` with cascading overrides. KnowledgeManagement's GraphifyGraph uses mtime-based lazy caching (`stat()` comparison) to avoid re-parsing potentially tens-of-megabytes-large NetworkX node-link JSON files. DockerizedServices tracks process state via `ProcessStateManager` with PID tracking for host-native services, paralleling supervisord's process ownership inside containers per `docker/docker-compose.yml` and `Dockerfile.coding-services`. CodingPatterns' shell adapters (`claude.sh`, `copilot.sh`, `opencode.sh`, `pi.sh`) all accept identical positional arguments and environment variables (`LLM_PROXY_URL`, `CODING_OPENCODE_MODEL`), translating them into backend-specific invocations while emitting a shared output format.

## Integration Points

The seven L1 components integrate as siblings under Coding via parent-child relationships, but also interoperate directly: LiveLoggingSystem's ontology registration depends on the shared `Component` L1 carrier used across all L2 subsystems, implying SemanticAnalysis's classification pipeline and KnowledgeManagement's graph representation likely reference the same ontology carriers. LLMAbstraction's mode toggling is a cross-cutting concern that other agent-driven components (CodingPatterns' adapter scripts, SemanticAnalysis's OntologyClassificationAgent) would consume when invoking LLM calls. DockerizedServices' health-check abstraction is a dependency for any component requiring service availability regardless of deployment target. CodingPatterns' agent scripts are documented via `docs/architecture/agent-abstraction-api.md` and `docs/architecture/adding-new-agent.md`, serving as the integration contract for orchestrators like `wave-controller.ts`.

## Usage Guidelines

Developers should not search for conventional class definitions when working with ontology-backed components like LiveLoggingSystem — semantic changes belong in the JSON ontology files, not TypeScript source. When debugging LLM behavior, understand the three-tier precedence in LLMAbstraction before assuming a single global toggle applies. When diagnosing service failures, remember DockerizedServices' dual-mode model means identical symptoms can stem from either supervisord misconfiguration or host-process crashes — log inspection is required to disambiguate. KnowledgeManagement consumers should be aware that graph data is only as fresh as the last `graph.json` write by the graphify pipeline, not live. Finally, onboarding a new coding agent should follow CodingPatterns' established contract (new script in `config/agents/`) rather than modifying core dispatch logic, preserving the adapter pattern's extensibility.

- [LLMAbstraction](./LLMAbstraction.md) -- [LLM] The mock/local/public mode toggle system in llm-mock-service.ts is designed around a persisted state file (.data/workflow-progress.json) rather than environment variables, which allows runtime mode switching without process restarts. The LLMState structure with globalMode and perAgentOverrides fields enables fine-grained control where a specific agent can be forced into mock mode for testing while the rest of the system runs against real providers. This is critical for integration testing scenarios where a developer wants to validate one agent's prompt-handling logic without incurring API costs or non-determinism from the LLM calls of other agents in a multi-agent pipeline. The getLLMMode() read path checks perAgentOverrides first, then falls back to globalMode, and finally to the legacy progress.mockLLM boolean, establishing a three-tier precedence resolution that any new developer must understand before assuming a single toggle controls behavior.
- [DockerizedServices](./DockerizedServices.md) -- [LLM] The DockerizedServices layer is architected around a dual-mode execution model: services can run either as supervisord-managed processes inside a single Docker container (per docker/docker-compose.yml, Dockerfile.coding-services, supervisord.conf) or as host-native Node subprocesses managed by lib/service-starter.js and PID-tracked via ProcessStateManager. This duality means developers must understand that 'starting a service' has two entirely separate code paths depending on deployment target, and that health-checking logic (service-probe.js) is written to be agnostic to which path is in effect — it only cares about HTTP/TCP reachability, not process ownership. This design avoids needing separate health-monitoring logic for containerized vs local services, but it also means Docker-specific failures (e.g., supervisord misconfiguration killing a service inside the container) surface identically to host-side crashes, requiring log inspection to disambiguate.
- [KnowledgeManagement](./KnowledgeManagement.md) -- [LLM] The GraphifyGraph reader (integrations/semantic-analysis/src/agents/graphify-graph.ts) represents a deliberate architectural simplification: rather than maintaining a live graph database connection (Memgraph via Cypher), the component now treats a static graph.json artifact produced by the graphify service as the source of truth for code-structure knowledge. This file, a NetworkX node-link JSON export, can be tens of megabytes, so GraphifyGraph implements mtime-based lazy caching — it stat()s the file and only re-parses when the mtime has changed since the last load. This pattern trades real-time graph mutation capability for drastically simpler deployment (no separate DB process) and fast repeated reads, at the cost of only picking up graph changes when the underlying analysis pipeline re-writes graph.json.
- [CodingPatterns](./CodingPatterns.md) -- [LLM] The config/agents/*.sh scripts (claude.sh, copilot.sh, opencode.sh, pi.sh) implement a uniform adapter pattern where each script normalizes a different vendor CLI into a common invocation contract described in docs/architecture/agent-abstraction-api.md. Concretely, each script accepts the same positional arguments and environment variables (e.g., LLM_PROXY_URL, CODING_OPENCODE_MODEL), performs argument translation specific to its backend binary, and emits output in a shared format consumable by the orchestrator layer. This lets the rest of the system (e.g., wave-controller.ts or any dispatcher invoking these scripts) remain agnostic to which underlying agent CLI is actually installed—new agents can be onboarded by adding a new script that satisfies the same contract rather than modifying core dispatch logic, as described in docs/architecture/adding-new-agent.md.
- [ConstraintSystem](./ConstraintSystem.md) -- [LLM] The configuration merging strategy in HookConfigLoader (lib/agent-api/hooks/hook-config.js) implements a three-tier cascade — DEFAULT_CONFIG baked into the code, user-level settings from ~/.coding-tools/hooks.json, and project-level settings from .coding/hooks.json — resolved through mergeConfigs(). This design lets individual developers set personal defaults (e.g., preferred logging verbosity or disabled hooks) while allowing a project to enforce mandatory constraints that override user preferences, but not vice versa. A new developer extending this system needs to understand that the merge is not a deep recursive merge in all cases; array-type handler lists are typically concatenated or replaced depending on the key, so adding a new hook type requires checking mergeConfigs() logic to avoid silently dropping user-level handlers.
- [SemanticAnalysis](./SemanticAnalysis.md) -- [LLM] The classification pipeline in OntologyClassificationAgent embodies a deliberate 'deterministic-first, LLM-as-fallback' philosophy that recurs throughout SemanticAnalysis. Before any LLM call is made, classifySingleObservation() checks the observation's name against the hard-root-guard set (CollectiveKnowledge, Coding, DynArch, Timeline, Normalisa) imported from @fwornle/km-core's HIERARCHY_ROOTS. If matched, the method immediately assigns classificationMethod='hard-root-guard' and returns without ever invoking classifier.classify() or touching the LLM. This is a defensive engineering decision: because these 5 names anchor the entire hierarchy, any LLM-driven misclassification of them would cascade corruption through the whole ontology tree, so the developers chose to hardcode an escape hatch rather than trust probabilistic classification for structurally critical nodes.
