# TwoStepArtifactAttribution — Technical Insight Document

## What It Is

TwoStepArtifactAttribution is the core control-flow logic implemented in `src/ontology/heuristics/EntityPatternAnalyzer.ts`, specifically within `analyzeEntityPatterns()`. It formalizes a two-tier confidence cascade for attributing a free-text artifact reference (a file path, npm scope, class name, or directory prefix) to an owning team. The first tier, `checkLocalArtifact()`, performs a directory-prefix match against the hardcoded `teamDirectories` Map (documented separately as HardcodedTeamDirectoryMap) and assigns confidence 0.9. If no match is found, the second tier, `matchArtifactPattern()`, falls back to regex matching against the `artifactPatterns` array (ArtifactPatternRegexTable) at confidence 0.75. This mirrors the Classifier-suffix convention documented in the parent entity, AgentWrapperConvention, but critically diverges from that parent's "data not code" philosophy by encoding all matching logic as hardcoded TypeScript literals rather than YAML configuration.

## Architecture and Design

The dominant pattern is a confidence-scored cascade / chain-of-responsibility: try the higher-confidence, cheaper check first (prefix match), only falling through to the looser regex-based check if the first fails. Layered on top of this is a first-match-wins short-circuit: `analyzeEntityPatterns()` returns on the *first* artifact (from the Set produced by ArtifactExtractionRegexes' `extractArtifacts()`) that matches *anything*, rather than scanning all extracted artifacts and selecting the globally highest-confidence result. Because `extractArtifacts()` populates a `Set<string>` in JavaScript insertion order (file paths, then npm packages, then class names, then bare directories), the resulting evidence priority is an accidental byproduct of regex-pass ordering rather than an intentional design decision — a stronger signal appearing later in the source text can be starved by a weaker one matched earlier.

A second structural pattern is the team-to-pattern registry: parallel data structures (`teamDirectories` Map and `artifactPatterns` array) both keyed by team name, each independently maintained. This duplication is compounded by `inferEntityClass()`'s `teamMappings`, which contains a fully-populated but entirely unreachable `'Agentic'` branch — complete code with no producing directory or pattern definitions, suggesting either an incomplete removal or an expectation that some external caller supplies `team: 'Agentic'` directly, bypassing this class's detection logic altogether.

## Implementation Details

`extractArtifacts()` runs four independent regex passes (file-path, npm-scope, class-suffix, bare-directory — detailed in sibling ArtifactExtractionRegexes) into a single untyped Set, meaning a single reference like `src/ontology/heuristics/EntityPatternAnalyzer.ts` can yield multiple overlapping artifacts (full path, bare directory prefix, and class name `EntityPatternAnalyzer` itself, since it ends in the allow-listed suffix "Analyzer"). Each of these independently flows through the two-step cascade in `analyzeEntityPatterns()`.

`checkLocalArtifact()` uses a plain `dirs.some((dir) => artifact.startsWith(dir))` test with no path-boundary normalization — as HardcodedTeamDirectoryMap notes, this makes prefix collisions (e.g., `scripts-legacy/` vs. registered `scripts`) a latent risk, relying on convention rather than enforcement.

`matchArtifactPattern()` calls `inferEntityClassFromPattern(artifact, entityClassMap)` using the raw artifact string rather than the specific RegExp that matched, decoupling entity-class inference from match provenance (also noted in ArtifactPatternRegexTable, e.g. the fragile Redux/ReduxState substring inference). Both success paths shape their output into the shared `LayerResult` type (imported from `../types.js`), hardcoding `layer: 1` and `layerName: 'EntityPatternAnalyzer'` as literals repeated across both return statements rather than derived from a single constant.

## Integration Points

TwoStepArtifactAttribution depends on `ArtifactMatch`/`LayerResult` types from `../types.js`, and structurally sits beneath AgentWrapperConvention, sharing its Classifier-suffix naming heuristic with siblings SensitivityClassifier and OntologyClassifier mentioned in that parent. It directly consumes the outputs of HardcodedTeamDirectoryMap and ArtifactPatternRegexTable, and operates on the Set produced by ArtifactExtractionRegexes. Downstream, any code inspecting `result.layerName === 'EntityPatternAnalyzer'` implicitly depends on the hardcoded string literal, and `scripts/knowledge-management/verify-patterns.sh` separately touches related pattern-usage verification via a case-statement stub, though that script is architecturally distinct and monolithic in its own right.

## Usage Guidelines

Developers extending this heuristic should be aware that match ordering is accidental, not designed — adding new extraction regexes or reordering `extractArtifacts()`'s passes will silently change attribution outcomes. New teams must be added consistently to both `teamDirectories` and `artifactPatterns` (and ideally `teamMappings`) to avoid dead branches like `'Agentic'`. Directory prefixes should use trailing slashes or equivalent normalization to avoid `startsWith` collisions. Because `layerName` is a hand-repeated literal, any rename of `EntityPatternAnalyzer` requires manually updating both return sites and all downstream string comparisons — a compiler-invisible risk worth converting into a shared constant.
