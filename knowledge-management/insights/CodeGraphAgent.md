# CodeGraphAgent

**Type:** SubComponent

## What It Is

CodeGraphAgent is implemented at `integrations/semantic-analysis/src/agents/code-graph-agent.ts`, within the KnowledgeManagement component. It is described by the parent entity's context as a compatibility shim: a class that preserves the full historical public interface — the `CodeEntity` and `CodeRelationship` types (surfaced further via its child, CodeEntityRelationshipTypes) and the `checkMemgraphConnection` method — from an era when it queried a live Memgraph/Cypher graph backend. Internally, it now delegates entirely to GraphifyGraph, a sibling-adjacent module at `integrations/semantic-analysis/src/agents/graphify-graph.ts` that reads a static, file-based graph export rather than a live database. No code files for CodeGraphAgent itself were retrieved in this pass; the description here is grounded entirely in parent-entity context and should be read accordingly.

## Architecture and Design

The dominant pattern is a Facade/Adapter applied across a backend migration: consumer code written against the old Memgraph-era contract — including guard clauses like `if (!connectionCheck.connected)` — continues to run unmodified even though "connection" is now a meaningless concept under a static-file backend. This is a deliberate trade-off: it decouples caller code from the storage migration at the cost of a permanently misleading method name (`checkMemgraphConnection`) sitting in the API surface, where its name no longer describes its behavior.

![CodeGraphAgent — Architecture](images/code-graph-agent-architecture.png)

Underneath, GraphifyGraph treats a static NetworkX node-link `graph.json` export as sole source of truth. Its nodes carry no explicit `type` or `name` fields; instead, `kindOf()` and `nameOf()` helpers derive these at read time by parsing each node's `label` string. This turns an implicit string-formatting convention into a de facto schema, with no validation layer to catch drift — meaning the entity taxonomy CodeGraphAgent exposes is only as reliable as whatever the upstream graphify export process happened to produce.

## Implementation Details

Two independent points of type-drift risk compound within CodeGraphAgent's delegation chain. First, GraphifyGraph's label-parsing derivation (`kindOf`/`nameOf`) can produce a type inconsistent with the entity's original semantic category. Second, `scripts/migrate-graph-db-entity-types.js` performs a separate, lossy consolidation via a hardcoded `ENTITY_TYPE_MAPPING` table, folding six historically distinct types into a single canonical `Pattern` type — and defaulting any unmapped type to `Pattern` rather than rejecting or flagging it. A CodeEntity's `.type` field reaching a CodeGraphAgent consumer may therefore have silently diverged from its true category through either mechanism before the consumer ever sees it.

Entity-resolution correctness is another concern directly relevant to any lookup logic this shim exposes. The Wave Insight Persistence work documents that an anchor pass originally resolved entities via `findEntityByName` alone, causing a new Detail-type node to silently inherit 24 incoming edges from an unrelated, same-named SubComponent node. The fix threaded `entityType` through `queryIncomingRelations` and `storeRelationship` so lookups disambiguate by (name, type) pairs, plus a fallback `projectAnchorName = 'Coding'` anchor so unresolvable nodes don't become orphans — a correctness constraint any shim-style entity-resolution surface, including CodeGraphAgent's, must respect.

## Usage Guidelines

Developers consuming CodeGraphAgent should treat `checkMemgraphConnection` as a legacy-named no-op-equivalent check rather than literal evidence of a database connection — it reflects file-read availability under GraphifyGraph, not Cypher connectivity. Any code relying on `CodeEntity.type` should be aware that the value may have passed through two lossy, unvalidated transformations (label-string parsing and entity-type-mapping consolidation) and should not assume it precisely reflects original semantic intent. Any new entity-resolution code built on this shim should disambiguate by (name, type) rather than name alone, per the fix applied to `findEntityByName`, and should provide an anchor fallback rather than allowing orphaned nodes. Finally, if this shim's read-only delegation is ever extended to writes, it must adopt GraphDatabaseService's explicit dirty-flag/flush discipline — otherwise mutations risk silent loss, and reads elsewhere in the system (as the Wave Insight Persistence incident shows) will have no way to detect that a write never landed.
