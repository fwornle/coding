## Architecture and Design

The dominant pattern is **gate-before-persist**: the `init()` docstring in `ObservationWriter.js` states it "opens the km-core GraphKMStore ... and the PII/secret redactor," positioning ConfigurableRedactor in the mandatory hot path for every Observation, Digest, and Insight persisted via `writeObservation`. Since the Phase 44 Plan 12/13 SQLite→km-core cutover eliminated the dual-write window (per the file's CONTEXT R-4 reference), km-core is now the single canonical write target — meaning there is no secondary filter downstream of ObservationWriter. Any bypass or failure at this single gate leaks directly into the dashboard-visible knowledge store.

This design is reinforced by adjacent defense-in-depth conventions rather than a single centralized enforcement point. `token-db.mjs`'s `insertTokenRow`/`baseValues` coerce fields through `text()`/`num()` coalescers and bind exclusively via `?` placeholders (explicitly tagged "V5 / SQL-injection (T-69-sql)"), and `ObservationWriter`'s constructor enforces `if (retentionDays < 1) throw new Error(...)`. These "fail loud at construction" idioms are structurally analogous to what a redaction gate should enforce, suggesting the codebase treats sanitization — SQL, retention math, and PII — as a cross-cutting concern rather than one centralized subsystem, echoed by sibling MultiUserFileManager's convention-based (not class-based) ownership checks (`isOwnedByMe()`, `ownedDbPath()`).

RedactionEngine's scope is asymmetric across sibling components. These stubs, stamped `lsl_incomplete: true`, structurally cannot leak conversational PII since there's no inner content — sidestepping rather than solving the redaction problem for that agent, in contrast to full-fidelity opencode/claude-derived observations that carry raw transcript content requiring redaction.

## Usage Guidelines

Developers should treat the ObservationWriter → RedactionEngine linkage as the single point of enforcement for the full-fidelity write path — any new write path into km-core must route through the same `init()`-established redactor rather than assuming a downstream filter exists, since none does post-cutover. When modifying `_observationEmitter` subscribers or test helpers (`_emitObservationWrittenForTests`), preserve ordering guarantees so redaction always precedes emission. When extending token-usage capture (`summarizeParts`/`snip`), evaluate whether `prompt_preview` content should route through the same redactor rather than relying on truncation alone. Finally, because `projectRoot` (derived from `dbPath`) parameterizes redactor configuration, any change to how ObservationWriter is constructed across projects should be checked against redaction config assumptions — particularly since LSLConfigValidator's `redaction-config.yaml` validation is a decoupled preflight check, not a runtime guarantee, per the parent LiveLoggingSystem's validator/runtime separation.
