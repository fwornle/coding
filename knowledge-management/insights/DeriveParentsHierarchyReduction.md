# DeriveParentsHierarchyReduction — Technical Insight Document

## What It Is

`DeriveParentsHierarchyReduction` is best understood not as a single function but as a named pattern that surfaces twice in the `integrations/unified-viewer/src/graph` codebase, in two structurally similar but semantically distinct forms. The first, and most literal, realization is the ontology parent-walk implemented redundantly in `color-fallback.ts`'s `nodeFillColor()` and `nodeShapeFor()`: both take a `className` and a `ReadonlyMap<string, ClassRegistryEntry>` registry and ascend `cur = reg?.parent ?? undefined` until they find an entry in `BATCH_PALETTE`/`SHAPE_PALETTE` or a registry override. The second is `deriveAncestryFromStorePath()` in `D3GraphCanvas.tsx`, which reduces two independently-computed ancestry sets — the store's `pathToSelected` and a local BFS from `computeAncestryPath()` — into a single `AncestryPathResult`. Both are documented in detail by sibling entities `HierarchyCycleBreaking` and `ComputeAncestryPathExtraction`/`DeriveAncestryFromStorePath`, and this document treats them as the two concrete faces of the same named abstraction under its parent, `GraphViewerHierarchy`.

## Architecture and Design

The dominant pattern across both implementations is "reduce-to-nearest-authoritative-ancestor": rather than requiring every entity or node to carry its own explicit styling or path membership, the system walks upward (through class inheritance in one case, through graph/store ancestry in the other) until it finds a value with recognized authority. In `color-fallback.ts` this authority is a static palette table; in `D3GraphCanvas.tsx` it is the Zustand store's `pathToSelected`, which is explicitly privileged over a fresher, locally recomputed BFS — a deliberate inversion of the more typical "recomputed value trumps cached value" convention. The `GraphViewerHierarchy` parent context explains why: `D3GraphCanvas.tsx` is a Zustand-ported descendant of a Redux-based `GraphVisualization.tsx`, maintained in parallel with a second Sigma/WebGL rendering path (`graph-builder.ts`), so ancestry logic must be re-derived and reconciled at the render layer rather than trusted from a single shared traversal implementation.

A recurring optimization pattern is the fast-path/slow-path split in `deriveAncestryFromStorePath`: a cheap structural-equality check (`inline.nodeDepths.size === storePath.size` plus membership) short-circuits the expensive pruning fold when the two ancestry sources already agree — the expected steady state once a selection has settled. Cycle-guarded traversal is the other cross-cutting pattern, implemented via `Set`-based `seen` guards in both `nodeFillColor`/`nodeShapeFor` (explicit) and implicitly bounded in the ancestry reconciliation — a defensive measure against malformed registry or graph data, elaborated by the sibling `HierarchyCycleBreaking` entity, which notes that an unguarded cycle here would hang the entire canvas render, not just one node.

## Implementation Details

In `color-fallback.ts`, both `nodeFillColor()` and `nodeShapeFor()` implement nearly identical `while (cur && !seen.has(cur))` loops: at each step they check a registry override, then a static table (`BATCH_PALETTE` or `SHAPE_PALETTE`), before reassigning `cur` to `reg?.parent`. The `seen` set prevents infinite loops on cyclic registries. This duplication — two loops differing only in which table they consult — is flagged as a structural echo of the same duplication pattern seen in `deriveAncestryFromStorePath()`, i.e., a codebase-wide tendency to write a fresh ancestor-walk per consumer instead of a shared generic reducer.

In `D3GraphCanvas.tsx`, `deriveAncestryFromStorePath()` builds a `prunedNodeDepths` map when the fast path fails: store-only nodes (present in `pathToSelected` but unreachable by the local `computeAncestryPath()` BFS) are retained with a synthetic `maxDepth` slot so they still render, albeit at the dim end of the color gradient; BFS-only nodes are dropped entirely; and `prunedEdges` is filtered to edges whose endpoints both survive pruning. This "writer's intent wins, but degrade gracefully" policy — detailed further by sibling `ComputeAncestryPathExtraction` — accounts for the case where a filter removes an intermediate ancestor between the moment a writer (graph click, history click, timeline tick, per `selectionSource`) recorded the path and the current render.

## Integration Points

`nodeFillColor`/`nodeShapeFor` are consumed across three previously-diverging render paths — the D3-based `D3GraphCanvas`, the Sigma-based `graph-builder.ts`, and `LegendPanel` — per the color-fallback.ts file header's own note that "three implementations disagree, so build the one true function." Their purity (no store writes, no mutation of inputs) is what makes this sharing safe. `deriveAncestryFromStorePath` integrates directly with the Zustand store's `pathToSelected` and imports `computeAncestryPath` from `./ancestry`, and its purity is likewise load-bearing: it must be callable synchronously inside a render-triggering `useMemo`/`useEffect` without violating `D3GraphCanvas.tsx`'s documented viewport-stability contract (Locked Contract #3), which forbids state writes from within the main render effect. The related `LearningSourceClassifier` sibling (`isOnlineLearned()`) is imported into both `D3GraphCanvas.tsx` and `color-fallback.ts`, showing that classification logic and hierarchy-reduction logic co-exist in the same render-path files and must both respect the same purity constraints.

## Usage Guidelines

Anyone extending or consolidating this component should heed the explicit naming/domain warning: the ontology parent-chain walk (color-fallback.ts) and the ancestry-path reconciliation (D3GraphCanvas.tsx) share vocabulary — "ancestry," "parent," "depth," "hierarchy" — but operate on fundamentally different data: a static class-inheritance registry versus live per-render BFS graph connectivity. Future consolidation attempts, echoing the "build the one true function" precedent already undertaken for `nodeFillColor`/`nodeShapeFor`, should not merge these two reducers. Any new reduction function invoked inside D3GraphCanvas's render path must remain pure and synchronous to avoid violating Locked Contract #3. Given evidence of past incidents (the defensive `seen`-guard cycle protection), registry/ontology data reaching these leaf consumers should not be assumed pre-validated — cycle guards should be preserved in any refactor. Finally, the duplicated-loop pattern here (and in `deriveAncestryFromStorePath` vs. `computeAncestryPath`) is a known maintainability debt; a shared generic ancestor-walk utility, parameterized by lookup table, is the natural refactor target but must respect the domain-separation warning above.
