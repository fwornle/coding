# IsOwnedByMeGuard — Technical Insight Document

## What It Is

`IsOwnedByMeGuard` is not a class or a single module — it is a recurring idiom implemented independently in two places: `isOwnedByMe(sessionDir, myUid)` in `lib/lsl/live/copilot-events-tail.mjs`, and `ownedDbPath(dbPath)` in `lib/lsl/token/opencode-token-rows.mjs`. Both functions perform the same core check: call `fs.statSync` on a target path, compare `st.uid` against the current process's uid (`process.getuid()`), and return a falsy sentinel (`false` or `''`) whenever the stat fails or the uid does not match. Functionally, this is a uid-ownership gate that decides whether the current process is allowed to read a file or directory that potentially belongs to another OS user.

As the parent entity, `MultiUserFileManager` has no literal implementation in the codebase — it's a conceptual grouping for a cross-cutting concern (safe multi-user file access) that is distributed across independently-written guards rather than centralized in one class. `IsOwnedByMeGuard` is one of the concrete realizations of that concern, alongside its siblings `OwnedDbPathGuard` (which documents the same `ownedDbPath`/`isOwnedByMe` pair from a divergence-analysis angle) and `LiveLockStalenessCheck` (`findLiveLockFile`), which addresses a different multi-user hazard: detecting whether a session lock is stale.

## Architecture and Design

The dominant architectural pattern here is **duplication-by-convention** rather than shared abstraction: there is no import relationship between `copilot-events-tail.mjs` and `opencode-token-rows.mjs`, so the "same" security check exists as two hand-written copies. This is explicitly corroborated by the observation that the two functions spell platform detection differently — `isOwnedByMe` returns `true` early when `myUid == null`, while `ownedDbPath` checks `typeof process.getuid === 'function'` only after the `fs.statSync` call succeeds. The idiom is therefore only as strong as its weakest copy, since a regression in either could silently reopen a cross-user read.

The guard also embodies a **fail-closed authorization pattern** paired with the codebase's D-08 "never-throw" philosophy: instead of throwing on failure, both functions return sentinel values (`false`, `''`, or an empty array further up the stack) that callers interpret as "skip this." This composes with a **cost-avoidance / short-circuit optimization**: both guards are placed immediately before expensive or stateful operations — `ownedDbPath` runs before `new Database(...)` is opened in `buildOpencodeTokenRows`, and `isOwnedByMe` runs before `findLiveLockFile(sessionDir)` and its underlying `fs.readdirSync`/`fs.statSync` loop in `scanForLiveSessions`. Authorization and performance concerns are thus coupled at the same call site.

Critically, the blast radius of a guard failure depends entirely on what it's nested inside, not on the guard itself. `isOwnedByMe` gates one iteration of a directory scan — failure skips a single session directory and the loop continues. `ownedDbPath` gates a single, all-or-nothing file open — failure discards the entire `opencode.db` token result set for that call. The identical idiom therefore produces a **partial-skip** failure mode in one caller and a **total-abstention** failure mode in the other.

## Implementation Details

`isOwnedByMe(sessionDir, myUid)` wraps `fs.statSync` in a single `try/catch`, collapsing both stat failure and uid mismatch into one `return false`, with no differentiated logging emitted from the guard itself — differentiation only happens one layer up in `scanForLiveSessions`, which logs `[live-copilot] skipping non-owned session ${sessionId}` on a traversal skip, but has no visibility into a raw stat exception, which is silently swallowed.

`ownedDbPath(dbPath)` is the stricter, more observable implementation. It distinguishes a stat *failure* from a stat *success with uid mismatch*, emitting two distinct `[token-adapter-opencode]`-prefixed stderr messages: `stat failed: ${dbPath}: ${err.message}` versus `skipping non-owned ${dbPath} (file uid=${st.uid} != ${me})`. This finer-grained diagnostics is a meaningful implementation delta despite the shared intent, as also detailed by sibling entity `OwnedDbPathGuard`, which notes the platform-check ordering also differs subtly between the two (pre-stat short-circuit in `isOwnedByMe` vs. post-stat check in `ownedDbPath`), meaning a POSIX-specific `statSync` throw would be handled differently by each.

Neither implementation defends against TOCTOU (time-of-check-to-time-of-use) races: nothing prevents a symlink swap between the `fs.statSync` call and the subsequent `fs.readFileSync`/`db.open`. The codebase's own docstring frames this as acceptable, labeling the check `T-51-09-FI uid-check on session dirs + events.jsonl files (defense-in-depth)` — i.e., a hardening measure against a largely theoretical threat in a single-user, home-directory deployment model, not a hard security boundary.

## Integration Points

`IsOwnedByMeGuard`'s two instances integrate with distinct call sites: `isOwnedByMe` is invoked inside `scanForLiveSessions(sessionStateDir, myUid)`, gating traversal of `~/.copilot/session-state/`; `ownedDbPath` is invoked inside `buildOpencodeTokenRows(dbPath, ctx)`, gating the opening of `opencode.db` via `new Database(resolved, { readonly: true, timeout: 5000 })` and subsequent prepared statements (`partStmt`, the `message` query). Neither guard depends on the other, and neither is a dependency of `LiveLockStalenessCheck`'s `findLiveLockFile()`, which addresses a separate hazard (stale lock detection via mtime heuristics) using the same file (`copilot-events-tail.mjs`) but an entirely different mechanism, with no shared code path. There is currently no automated test coverage for either guard — `tests/agents/copilot-session-command.test.mjs` exercises only the unrelated `/sl` plugin command — leaving the idiom's correctness unverified by CI.

## Usage Guidelines

Developers extending multi-user file access in this codebase should recognize that "the multi-user file manager" is not a locatable module but a convention: anyone adding a new file/directory access path that could cross user boundaries should replicate the `isOwnedByMe`/`ownedDbPath` uid-check idiom, ideally converging on one implementation rather than adding a third divergent copy. Given the acknowledged weakest-link risk, any change to either guard should be mirrored in the other, and adding shared test coverage asserting uid-mismatch behavior should be treated as a priority given the current absence of one. Because the TOCTOU gap is real, this guard should continue to be understood as defense-in-depth rather than a hard security boundary, and its placement should remain immediately upstream of the expensive operation it protects, preserving its dual role as both authorization gate and cost-avoidance short-circuit.
