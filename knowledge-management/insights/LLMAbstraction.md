# LLMAbstraction: Technical Insight Document

## What It Is

LLMAbstraction is the component within the Coding project that mediates all LLM request routing, provider selection, mock/live mode resolution, and response normalization. Its concrete implementation surfaces across several files evident in observations: `llm-mock-service.ts` (mock mode resolution), `dmr-provider.ts` (Docker Model Runner integration), `llm-with-process.ts` (proxy-attached telemetry client), and `parse-llm-json.ts` (JSON repair). It sits as a peer to LiveLoggingSystem, DockerizedServices, KnowledgeManagement, CodingPatterns, ConstraintSystem, and SemanticAnalysis under the Coding root, and it decomposes into eight children — LLMMockService, DMRProvider, LLMWithProcessClient, LlmJsonParser, CopilotModelIdAlignment, CostModel, OffloadRoutingDashboard, and ModelContextLimits — each owning a narrow slice of the routing/provider problem.

## Architecture and Design

The dominant architectural theme is tiered fallback with strict ordering, applied at multiple layers. At the routing level, the 'LLM Routing Tier Priority' session record establishes that requests must exhaust max-subscription models, then work/GH Copilot-tier models, before ever reaching Groq Llama-70B — a cost/capability-driven policy, not something derivable from provider-selection code alone, and one that had previously regressed into treating low-tier providers as primary. The same fallback-chain pattern recurs structurally: `getLLMMode()` in LLMMockService cascades through perAgentOverrides → globalMode → legacy `progress.mockLLM` boolean → a `'public'` default, preserving backward compatibility with older workflow-progress.json formats without forcing migration. DMRProvider's `loadDMRConfig()` similarly probes three filesystem locations in sequence before falling back to an in-code DEFAULT_CONFIG, accommodating invocation as both a top-level script and an imported dependency from within the semantic-analysis integration subtree.

Where the SDK's request contract is insufficient, the design choice is a parallel implementation rather than a wrapper: LLMWithProcessClient (`llm-with-process.ts`) bypasses the SDK's LLMService entirely with a direct `fetch()` to rapid-llm-proxy's `/api/complete`, because the SDK shape can't carry the `process` telemetry field the proxy requires. This is a deliberate trade-off — duck-typing the response back into the SDK's contract keeps callers of `getMetricsTracker()` unaffected, at the cost of two code paths that must be manually kept in sync when the proxy's schema changes.

## Implementation Details

`getLLMMode()` in LLMMockService is a four-branch resolver; every branch must be preserved when modified, since the legacy `mockLLM` boolean field predates richer state structures and removing a branch silently breaks callers still emitting the old format. `checkDMRAvailability()` in DMRProvider implements a time-windowed cache, comparing `Date.now()` against `lastHealthCheck + dmrConfig.connection.healthCheckInterval` to avoid redundant network probes on tight-loop batch calls — accepting a stale-availability window as the cost of avoiding excessive HTTP round-trips.

LLMWithProcessClient's `resolveProxyCompleteUrl()` performs a 4-tier environment variable fallback (`RAPID_LLM_PROXY_URL` → `LLM_CLI_PROXY_URL` → `LLM_PROXY_URL` → hardcoded port 12435), then normalizes flat vs. nested token-count response shapes so downstream metrics consumers see a consistent contract regardless of which code path served the request.

LlmJsonParser's `parseLlmJson()` is intentionally narrow: an explicit `inString` state-machine flag tracks whether the parser is inside a string literal, and only control characters within strings are escaped — structural whitespace in pretty-printed JSON is untouched, and non-control-character malformations are left to fail loudly rather than be guessed at. This scope was set directly in response to a production incident where an unescaped newline inside a string silently discarded an entire component analysis, establishing the project's stance that JSON repair must remain tightly bounded.

## Usage Guidelines

Developers modifying `getLLMMode()` must preserve all four resolution branches to avoid silently breaking legacy `mockLLM`-based callers. Anyone extending DMRProvider's config loading should respect the triple-path search order, since it exists specifically to support both script and imported-dependency invocation contexts. When diagnosing CLI/UKB timeout issues, investigation should focus on individual provider backends rather than re-auditing rapid-llm-proxy, per the established diagnostic finding. Any change to rapid-llm-proxy's response schema requires updating both the SDK-based and direct-fetch (LLMWithProcessClient) paths in tandem, since they are deliberately unlinked implementations. Finally, JSON-repair logic in LlmJsonParser should remain narrowly scoped to control-character escaping within strings — resist the temptation to broaden it to catch other malformation classes, as that expansion caused past silent data loss.
