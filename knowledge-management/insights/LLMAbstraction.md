# LLMAbstraction

**Type:** Component

## What It Is

LLMAbstraction is the layer that sits between coding agents (claude, copilot, opencode) and the actual LLM inference paths, providing mode resolution, JSON repair, local-inference fallback, and proxy client access. Its implementation is spread across concrete files named directly in observations: `llm-mock-service.ts` (mode resolution), `dmr-provider.ts` (Docker Model Runner wrapper), `parse-llm-json.ts` (defensive JSON repair), and `llm-with-process.ts` (a parallel proxy client implementation). These call outward into `proxy-bridge/server.mjs`, an external persistent service, rather than embedding provider logic themselves.

## Architecture and Design

The dominant pattern is centralization of cross-cutting decisions with delegation of transport. `getLLMMode()` in `llm-mock-service.ts` is the single authority for "what mode am I in" — checking per-agent override, then global mode, then a legacy `mockLLM` boolean, then defaulting to `'public'` — with all state persisted in one shared JSON file (`.data/workflow-progress.json`), using `CODING_ROOT` to reconcile Docker/host path differences. This avoids scattering mode checks or relying on environment variables that could diverge between processes.

A second pattern is tiered fallback with gating, seen both in `dmr-provider.ts`'s singleton `dmrClient` (checked via `checkDMRAvailability()` with a `healthCheckInterval` to avoid re-hitting the network on every call) and in the 4-tier proxy URL resolution in `llm-with-process.ts` (`RAPID_LLM_PROXY_URL` > `LLM_CLI_PROXY_URL` > `LLM_PROXY_URL` > localhost fallback). The actual provider fallback and network-mode-aware routing chain, however, lives upstream in `proxy-bridge/server.mjs`, which LLMAbstraction's HTTP clients call into but do not implement themselves — a boundary worth keeping in mind when diagnosing failures.

## Implementation Details

`parse-llm-json.ts` implements a two-stage repair pipeline addressing distinct failure modes independently: `escapeControlCharsInStrings()` walks output character-by-character, tracking string-literal state, to escape raw newlines/tabs LLMs sometimes emit unescaped; `truncateToLastCompleteElement()` is a separate, optional stage for salvaging truncated output, but only accepts a nested bracket close as a valid cutoff point so it never fabricates values.

`llm-with-process.ts` is explicitly a conscious duplication of the `@rapid/llm-proxy` SDK's `LLMService`, not a replacement — it re-implements URL resolution and appends `/api/complete` exactly once via `resolveProxyCompleteUrl()`, adding a `process` attribution field the SDK omits, to preserve existing metrics-tracker instrumentation rather than migrate callers. This is a deliberate two-codepath tradeoff that must be kept in sync manually with proxy contract changes.

The model catalogue logic (surfaced in observations as endpoint-gated access rules) must track which models are valid via Responses API versus `/chat/completions`, rejecting invalid combinations rather than silently allowing or pruning them — a distinction not visible from a static supported-models list.

## Integration Points

LLMAbstraction depends on `proxy-bridge/server.mjs` running as the persistent launchd service `com.coding.llm-cli-proxy`; this is an external dependency, not owned by this component, so failures in HTTP calls to localhost:12435 may originate from that service being down or restarted rather than from LLMAbstraction's own code. Downstream, all three agent integrations (claude, copilot, opencode) depend on this chain being alive.

Among children, LLMMockService owns mode-state logic; DMRProvider wraps local inference; LLMJsonRepairUtility implements the repair pipeline; ProxyClientWrapper and CopilotModelIdAlignment address proxy access and endpoint-gating concerns respectively. ## Usage Guidelines

Mode should always be queried through `getLLMMode()` rather than reading environment variables or local flags directly, since the shared JSON file is the sole source of truth agents rely on for consistency. When touching `llm-with-process.ts`, remember it is a parallel path to the SDK's `LLMService`, not a bug to consolidate away — any proxy contract change must be applied to both. JSON repair logic should not be extended to guess past incomplete nested structures; the existing refusal to fabricate cutoffs is intentional. Finally, when debugging call failures, check the health of `com.coding.llm-cli-proxy` before assuming a defect in LLMAbstraction's own client code, and treat model/endpoint mismatches (per CopilotModelIdAlignment and the catalogue rules) as hard rejections rather than silent pruning.
