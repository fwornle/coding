# LLMAbstraction

**Type:** Component

[LLM] The DMRProvider (dmr-provider.ts) integrates Docker Model Runner as a local inference backend by loading YAML configuration from multiple candidate paths via loadDMRConfig()—a resilience pattern that tolerates differences in working directory or deployment layout without requiring a single hardcoded config location. Once loaded, expandEnvVars() performs ${VAR}-style placeholder substitution on the config values (e.g., for API base URLs or keys like QWEN_LAPTOP_API_BASE_URL), enabling the same YAML file to work across different environments without hardcoding secrets or hostnames. The resulting configuration is used to construct an OpenAI-compatible client, meaning DMR is treated as just another OpenAI-shaped provider from the abstraction's point of view—this design choice significantly simplifies the provider interface but also means any DMR-specific quirks must be handled either in the YAML config or via shims rather than through provider-specific code paths.

# LLMAbstraction — Technical Insight Document

## What It Is

LLMAbstraction is the component responsible for mediating all LLM calls made across the Coding project, providing a unified surface over multiple backends (mock, local Docker Model Runner, public API) and multiple invocation paths (SDK-based and direct-fetch). Its core logic is distributed across a small number of files: `llm-mock-service.ts` (mode resolution and mock dispatch), `dmr-provider.ts` (Docker Model Runner integration), `llm-with-process.ts` (a parallel non-SDK invocation path), and `cost-model.ts` (token-to-cost accounting). As a sibling to DockerizedServices, LiveLoggingSystem, KnowledgeManagement, ConstraintSystem, and SemanticAnalysis under the Coding root, LLMAbstraction specifically owns the question of "how and where does an LLM call actually execute," making it foundational infrastructure that other subsystems depend on implicitly whenever they invoke an agent.

## Architecture and Design

The defining architectural pattern here is a **layered precedence/fallback chain**, applied consistently across multiple concerns. For mode resolution, `getLLMMode()` in `llm-mock-service.ts` (child: LLMMockService) checks a per-agent override, then a global mode, then a legacy `mockLLM` boolean, and finally defaults to `'public'`. The same fallback philosophy appears in `ProxyURLResolver`, which resolves the proxy endpoint through a 4-tier environment variable chain (`RAPID_LLM_PROXY_URL` → `LLM_CLI_PROXY_URL` → `LLM_PROXY_URL` → localhost:12435 default), and in `DMRProvider`'s `loadDMRConfig()`, which tries multiple candidate YAML paths rather than assuming a single fixed location. This repeated pattern reflects a design philosophy favoring graceful degradation and backward compatibility over strict configuration enforcement.

A second key decision is the **deliberate bypass of the SDK** in `LLMWithProcessClient` (`llm-with-process.ts`). Rather than extending the standard `LLMService` SDK to support `process`-tagged telemetry, the team built a parallel `llmWithProcessComplete()` path using direct `fetch()` calls. This avoided risking existing metrics-tracker instrumentation but introduced a maintenance burden: response-shape normalization logic now exists in two places instead of one.

Cost accounting is architecturally decoupled as a downstream consumer: `CostModel` (`cost-model.ts`) doesn't invoke LLMs itself but consumes token-usage data emitted by both the SDK path and the process-tagged path, closing the loop from invocation to budget bucketing.

## Implementation Details

`LLMMockService`'s `getLLMMode()` is the entry point for dispatch decisions, and it's paired with `isMockLLMEnabled()`/`getLLMState()`, which persist mode/config state to `.data/workflow-progress.json`. Both honor a `CODING_ROOT` environment override to remap file paths for Docker contexts — a detail shared conceptually with DockerizedServices' handling of container-vs-host path differences.

`DMRProvider` loads YAML config via `loadDMRConfig()` and performs `${VAR}`-style substitution via `expandEnvVars()` (e.g., for `QWEN_LAPTOP_API_BASE_URL`), then constructs an OpenAI-compatible client — treating DMR as just another OpenAI-shaped provider. Availability is tracked via `checkDMRAvailability()`, which caches results in an `isAvailable` boolean gated by a `healthCheckInterval` timer, trading real-time accuracy for reduced polling overhead against `models.list()`.

`LLMWithProcessClient`'s `llmWithProcessComplete()` manually normalizes the proxy's flat `{tokens: number}` response into the SDK's richer `{total, input, output}` shape expected by `CostModel` and the metrics-tracker — inline, duplicated logic that must be kept in sync with the SDK path.

`CostModel`'s `priceForModel()` resolves pricing by exact model-name match first, falling back to `modelFamily()`-based resolution for unlisted variants, and `isOpenAIWireProvider()` distinguishes Anthropic's vs. OpenAI's differing cache-token semantics to keep copilot/claude-max budget buckets accurate.

## Integration Points

LLMAbstraction sits beneath every agent call in the Coding system, making its children — LLMMockService, DMRProvider, LLMWithProcessClient, CostModel, and ProxyURLResolver — critical dependencies for any component invoking LLMs. It shares infrastructure concerns with DockerizedServices, particularly around `CODING_ROOT` path remapping and mock-mode support for containerized testing (DockerizedServices explicitly references `llm-mock-service.ts` as enabling deterministic mock behavior via the shared `workflow-progress.json` state file). `CostModel` integrates downstream with metrics-tracker instrumentation, and both LLM invocation paths (SDK and process-tagged) must produce token-usage data in a shape `CostModel` can consume, creating an implicit contract between LLMWithProcessClient and the SDK's expected data shape.

## Usage Guidelines

Developers debugging unexpected LLM behavior for a specific agent must check all four levels of the mode-resolution hierarchy — per-agent overrides silently win over global settings, a common source of confusion during multi-agent experiments. When working in Docker/containerized contexts, `CODING_ROOT` must be set correctly, since misconfiguration silently redirects state file reads/writes rather than throwing errors. Anyone relying on DMR health status for failover logic must account for the caching window in `checkDMRAvailability()` — availability can be stale for up to one `healthCheckInterval`. Any change to the proxy's response format or the SDK's expected token-usage shape requires updating normalization logic in both the SDK path and `llm-with-process.ts` independently, since they don't share transformation code — a known drift risk. Finally, pricing-table maintainers should rely on `modelFamily()` fallback behavior in `CostModel` for new model variants but should still verify that `isOpenAIWireProvider()` correctly classifies new providers to avoid miscounting cache-token costs.

This design supports fail-fast behavior: catching misconfiguration before any live session data is captured, rather than discovering issues mid-capture when data loss or malformed logs could occur.
- [DockerizedServices](./DockerizedServices.md) -- DockerizedServices provides the containerization and process-management layer that wraps Coding's various services (semantic analysis MCP, constraint monitor API/dashboard, graphify, LLM services) so they can run reliably both inside Docker containers and as standalone Node processes managed by a Global Service Coordinator. The layer combines Docker artifacts (docker-compose.yml, Dockerfile.coding-services, supervisord.conf, entrypoint.sh) with a set of Node.js wrapper scripts (api-service.js, dashboard-service.js) that spawn actual backend processes, forward signals, and register/unregister with a ProcessStateManager (PSM) for lifecycle tracking.

A core architectural pattern is robust startup with retry/backoff and health verification, implemented in lib/service-starter.js's startServiceWithRetry(), which wraps a start function and a health-check function with timeouts (via withDeadline) and exponential backoff, distinguishing required vs optional services for graceful degradation. Complementing this, lib/utils/service-probe.js implements liveness probes (probeHttpHealth, probeTcpPort) used by scripts/health-coordinator.js to poll services every 5 seconds per config/health-verification-rules.json, strictly avoiding false-positive 'healthy' states per its SPEC R6 invariant.

Service wrappers such as api-service.js and dashboard-service.js follow a consistent pattern: resolve CODING_REPO-relative paths, verify target files/directories exist, spawn the real process with stdio inherited, forward SIGTERM/SIGINT, and asynchronously register/unregister with ProcessStateManager for centralized process tracking across the dockerized/global service fleet. Mock-mode support (llm-mock-service.ts) allows service behavior (LLM calls) to be swapped for deterministic mocks driven by a shared workflow-progress.json state file, aiding testing inside containers where CODING_ROOT may differ from host paths.

This separation of concerns means the VKB server is the single choke point for consistency guarantees, caching, and decay tracking logic, so any schema change to entities must be coordinated through it rather than through ad-hoc script access.

- [ConstraintSystem](./ConstraintSystem.md) -- The ConstraintSystem provides rule-based validation and enforcement for tool calls and file operations during Claude Code sessions, plus a hook infrastructure that lets agent-agnostic events (pre-tool, post-tool, startup, shutdown, etc.) trigger scripts, commands, or modules. It is composed of a hook configuration layer (lib/agent-api/hooks/hook-config.js) that loads and merges user-level (~/.coding-tools/hooks.json) and project-level (.coding/hooks.json) configs, and a central UnifiedHookManager (lib/agent-api/hooks/hook-manager.js) that registers, prioritizes, and dispatches handlers per event across all supported agents. Violations detected during live sessions are captured and persisted via the ViolationCaptureService (scripts/violation-capture-service.js), which writes JSONL logs and maintains rolling statistics for dashboard consumption.

Architecturally, the system favors a layered configuration-merge pattern (defaults → user → project) with validation warnings rather than hard failures, and a priority-sorted handler registry keyed by event name. Constraint violations flow from live session monitoring into a persistent JSON store capped at 1000 entries, with statistics (severity breakdown, most common violation, per-session averages) computed on write. The system also integrates with content/documentation validation (ContentValidationAgent in integrations/semantic-analysis) which, while primarily about entity staleness, shares the same validation-issue/severity taxonomy pattern used elsewhere in constraint reporting, and with the System Health Dashboard's workflow visualization hooks (React-side, distinct from the agent-api hook system) for rendering constraint/violation data.
- [SemanticAnalysis](./SemanticAnalysis.md) -- [LLM] The batch-analysis workflow is structured as a multi-stage pipeline where semantic-analysis-agent.ts is responsible for extracting raw entities and relationships from git history and LSL (likely 'Language/Session Log') session data, while ontology-classification-agent.ts takes those extracted entities and maps them into a hierarchical ontology structure. This separation of concerns means the extraction logic (identifying what something is—a function, a decision, a bug fix) is decoupled from the classification logic (determining where that entity fits in a broader knowledge hierarchy), allowing each agent to be independently tuned, tested, and potentially swapped out without affecting the other stage's implementation.
