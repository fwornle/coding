# LLMAbstraction — Technical Insight Document

## What It Is

LLMAbstraction is the component within the Coding project responsible for mediating all access to large language model backends—whether local (via Docker Model Runner) or remote (via the rapid-llm-proxy daemon)—while normalizing configuration, cost accounting, and mock/production mode switching into a consistent interface. Its implementation spans several key files: `llm-mock-service.ts` (mode resolution and mock/production switching), `dmr-provider.ts` (local Docker Model Runner client), `llm-with-process.ts` (proxy completion client and token normalization), and `cost-model.ts` (pricing and cost computation). As the parent to DMRProvider, ProxyCompletionClient, CostModelEngine, ModelNormalization, and OffloadDecisionEngine, LLMAbstraction acts as the umbrella boundary separating "how the rest of Coding calls an LLM" from "which specific provider/runtime actually services that call."

## Architecture and Design

The component is built around several recurring architectural patterns rather than a single monolithic design. First, a **layered precedence-chain resolution pattern** appears repeatedly: `getLLMMode()` in `llm-mock-service.ts` resolves mode via a four-tier chain (per-agent override in `workflow-progress.json` → global mode → legacy `mockLLM` boolean → 'public' fallback), and `resolveProxyCompleteUrl()` in `llm-with-process.ts` similarly resolves the proxy endpoint via a four-tier environment variable chain (`RAPID_LLM_PROXY_URL` > `LLM_CLI_PROXY_URL` > `LLM_PROXY_URL` > localhost default). This is a deliberate strategy for backward compatibility across an evolving system where naming conventions and config schemas changed over time but old callers must not break.

Second, a **defensive multi-path configuration discovery pattern** is embodied in `loadDMRConfig()`, which tries three candidate file locations for `dmr-config.yaml` before failing, reflecting the reality that the same code runs on bare-metal dev machines, inside Docker containers, and in CI. This pattern recurs elsewhere in the codebase, signaling a broader architectural theme: configuration loading never assumes a single canonical location.

Third, the **singleton/caching pattern** in `dmr-provider.ts` (a reused `dmrClient` instance, plus a time-windowed `checkDMRAvailability()` health check) trades real-time accuracy for reduced load on the local DMR endpoint—an explicit reliability/performance tradeoff that yields eventually-consistent availability state.

Finally, a **response normalization/shim pattern** appears in `llmWithProcessComplete()`, which reconciles heterogeneous token-usage shapes (flat number vs. `{total, input, output}`) into a single canonical `LLMWithProcessResponse.tokens` structure, and in `priceForModel()` (CostModelEngine), which falls back through exact-match → family-representative → generic family match before defaulting to a zero-priced 'none' source (per the three-tier resolution documented on CostModelEngine itself).

## Implementation Details

`llm-mock-service.ts` contains the mode-resolution engine: `getLLMMode()`, `isMockLLMEnabled()`, and `getLLMState()` all consult both the new `llmState` shape and the legacy `mockLLM` boolean, deliberately dual-checking both to support state files or tooling written before the schema evolved. These functions are also CODING_ROOT-aware, normalizing filesystem path resolution for `workflow-progress.json` so that state is read correctly whether running natively on a host or inside a Docker container (a hybrid deployment concern also documented in `docker/README.md` under sibling component DockerizedServices).

`dmr-provider.ts` implements DMRProvider as an OpenAI-compatible client, allowing it to be substituted for remote providers without changing call sites. It centralizes access behind a singleton `dmrClient`, and its `loadDMRConfig()` function chains three file-path attempts before invoking `expandEnvVars()`, which performs `${VAR}`-style substitution specifically on the `baseUrl` field—enabling environment-specific endpoints like `QWEN_LAPTOP_API_BASE_URL` without hardcoding hostnames.

`llm-with-process.ts` implements ProxyCompletionClient, tagging each completion request with a process identifier that flows downstream into `CostRow.process` in `cost-model.ts`. Its `resolveProxyCompleteUrl()` handles the multi-variable proxy URL resolution described above, and `llmWithProcessComplete()` performs the token-shape normalization critical to downstream cost accuracy.

`cost-model.ts` implements CostModelEngine's `priceForModel()`, using `modelFamily()` classification (haiku/sonnet/opus/fable/gpt-4o/gpt-5) and `FAMILY_REPRESENTATIVE` fallback lookups to approximate pricing for model identifiers not present in the exact `modelPrices` table—a pragmatic response to the rapid cadence of dated model releases (e.g., `claude-3-5-sonnet-20241022`).

## Integration Points

LLMAbstraction's children each implement a distinct facet of the abstraction: DMRProvider handles local inference via an OpenAI-compatible interface; ProxyCompletionClient handles remote inference via the rapid-llm-proxy daemon and tags requests for cost tracking; CostModelEngine consumes normalized model identifiers (produced by ModelNormalization) as keys into `CostConfig.modelPrices`; and OffloadDecisionEngine's `evaluateOffload()` in `offload-gates.ts` reproduces the proxy's exact short-circuit gate order (considered→route-allows→band→target→target-band→scope→transport→offloaded) so that reason-string attribution stays consistent with the proxy's own decision logic.

Cross-component dependencies extend beyond LLMAbstraction's boundary: mode resolution reads `workflow-progress.json`, a state file shared with broader agent orchestration, and its CODING_ROOT-awareness mirrors deployment concerns documented under DockerizedServices. Token normalization output feeds both `cost-model.ts`'s `priceForModel()` and the dashboard's `models.ts`, meaning any change to the canonical tokens shape has direct billing-accuracy implications for downstream consumers.

## Usage Guidelines

Developers debugging unexpected LLM behavior should check the full four-tier precedence chain in `getLLMMode()` before assuming a global mode setting took effect—a stale per-agent override in `workflow-progress.json` silently wins. Similarly, when tracing why a proxy call hits an unexpected host, check all three legacy env vars (`LLM_CLI_PROXY_URL`, `LLM_PROXY_URL`) in addition to the preferred `RAPID_LLM_PROXY_URL`, since new code should adopt the latter but must not assume it's exclusive.

Because DMR availability checks are cached on a `healthCheckInterval` timer, treat availability as eventually-consistent, not real-time—a crashed DMR container may appear available for up to one interval window. Any new code reading `.data/workflow-progress.json` should replicate the CODING_ROOT-aware path resolution rather than hardcoding relative paths, to avoid reading stale state inside containers. Finally, when adding support for a new model's pricing, verify whether `priceForModel()`'s family-based fallback produces acceptable estimates before relying on it, or add an explicit `modelPrices` entry if precision matters.
