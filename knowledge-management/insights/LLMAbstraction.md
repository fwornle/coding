## What It Is

## Architecture and Design

The component deliberately favors thin wrappers over deep abstraction rather than building a unified LLM SDK from scratch. This is most explicit in `llm-with-process.ts`, which is documented as an intentional "Option B" decision: rather than modifying the upstream `@rapid/llm-proxy` SDK, the team built a single-repo wrapper that preserves SDK metrics tracking while injecting a missing `process` telemetry field into requests. This trade-off avoids fork-maintenance burden on third-party code at the cost of an extra request-shaping layer.

`dmr-provider.ts` implements a singleton client pattern (module-level `dmrClient`, `isAvailable`, `lastHealthCheck` state) with cached health checks gated by `dmrConfig.connection.healthCheckInterval`, avoiding redundant network calls—a pragmatic performance/simplicity trade-off over a more elaborate connection-pool design. `llm-mock-service.ts` uses a priority-cascade resolution model (per-agent override > global mode > legacy `mockLLM` flag > `public` default) persisted in the shared `.data/workflow-progress.json`, reflecting a design that tolerates legacy fallback rather than forcing a breaking migration.

A cross-cutting design principle in `parse-llm-json.ts` is *narrow, targeted repair over broad guessing*: the parser only fixes the specific failure mode observed in production (raw control characters inside string literals), deliberately declining to implement generalized JSON-guessing so that failures remain loud and diagnosable rather than silently misinterpreted—an explicit maintainability-over-resilience trade-off.

## Implementation Details

`llm-mock-service.ts` defines the `LLMMode` type (`'mock'|'local'|'public'`) resolved via `getLLMMode()`, reading state from `.data/workflow-progress.json` on a per-agent basis with legacy fallback support baked into the resolution order.

`dmr-provider.ts`'s `loadDMRConfig()` searches three candidate paths (`cwd/config`, `integrations/semantic-analysis/config`, and a path relative to `__dirname`) for `dmr-config.yaml`, then expands `${VAR}` environment variables in `baseUrl` via `expandEnvVars()`—a defensive-loading strategy accommodating varying invocation contexts (CLI vs. integration-embedded execution). `checkDMRAvailability()` caches health results to prevent redundant probing.

`llm-with-process.ts`'s `resolveProxyCompleteUrl()` implements a 4-tier environment variable resolution order (`RAPID_LLM_PROXY_URL` > `LLM_CLI_PROXY_URL` > `LLM_PROXY_URL` > localhost default), explicitly matching the SDK's own `cli-provider-base.ts` convention, and ensures `/api/complete` is appended exactly once to avoid path duplication bugs. `llmWithProcessComplete()` accepts an optional duck-typed `MetricsTrackerLike` interface, letting callers pass an existing SDK metrics tracker (`llmService.getMetricsTracker()`) to avoid standing up a duplicate instrumentation system.

`parse-llm-json.ts`'s `escapeControlCharsInStrings()` is a hand-rolled character-level state machine tracking `inString`/`escaped` flags, escaping control characters only within JSON string literals while leaving pretty-printed whitespace between tokens untouched. Critically, `parseLlmJson()` always surfaces the *first* parse error—from the original unrepaired content—rather than any secondary error introduced by the repair attempt, preserving fidelity to what the model actually produced.

## Integration Points

LLMAbstraction interfaces with the upstream `@rapid/llm-proxy` SDK without modifying it, instead wrapping and extending it (`llm-with-process.ts`), and integrates with `llmService.getMetricsTracker()` for shared telemetry. It reads/writes shared state via `.data/workflow-progress.json`, coupling it to whatever workflow-orchestration mechanism also touches that file. Configuration loading in `dmr-provider.ts` searches paths including `integrations/semantic-analysis/config`, indicating a direct dependency relationship with the **SemanticAnalysis** component's config space. Its resilient JSON parsing utilities serve as a foundational cross-cutting concern likely consumed by any component parsing LLM output, aligning with the **CodingPatterns** component's cataloged idiom of caching/circuit-breaker-style wrappers around external service calls.

## Usage Guidelines

Developers extending this component should preserve its narrow-repair philosophy in `parse-llm-json.ts`—resist the temptation to add speculative JSON-guessing logic, since the design intentionally keeps failures loud and traceable to actual model output rather than repair artifacts. When modifying proxy URL resolution, maintain consistency with the SDK's `cli-provider-base.ts` env var convention to avoid divergent behavior between the wrapper and upstream SDK. Any new provider integration should follow the singleton-with-cached-health-check pattern established in `dmr-provider.ts` rather than introducing per-call network probes. Finally, changes to mode resolution in `llm-mock-service.ts` must respect the existing priority order and legacy fallback to avoid breaking agents relying on older `mockLLM` flag behavior.
