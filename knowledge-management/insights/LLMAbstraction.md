# LLMAbstraction — Technical Insight Document

## What It Is

LLMAbstraction is the component responsible for mediating access to LLM providers, mock/live mode selection, and request-level bookkeeping across the coding project. Its implementation is spread across several concrete files: `llm-mock-service.ts` (mock/live routing logic), `dmr-provider.ts` (local Docker Model Runner client), `llm-with-process.ts` (direct-fetch wrapper for process-tagged completions), and `parse-llm-json.ts` (JSON repair for LLM output). As the parent of LLMMockService, DMRProvider, ParseLlmJson, LLMWithProcessClient, CostModel, OffloadRoutingUI, AgentModelConfigSplice, and ModelContextLimits, it forms the abstraction layer sitting between agent/workflow code and actual model providers, sibling to components like LiveLoggingSystem, DockerizedServices, and SemanticAnalysis under the root Coding hierarchy.

## Architecture and Design

The dominant pattern is layered fallback resolution, appearing repeatedly at different levels of the stack. `getLLMMode()` in `llm-mock-service.ts` resolves mock-vs-live status through a three-tier precedence: per-agent override → global mode → legacy `progress.mockLLM` boolean → default `'public'`, preserving backward compatibility with older `workflow-progress.json` files. Similarly, `resolveProxyCompleteUrl()` in `llm-with-process.ts` applies a 4-tier environment variable precedence (`RAPID_LLM_PROXY_URL` > `LLM_CLI_PROXY_URL` > `LLM_PROXY_URL` > localhost fallback) so the same code runs correctly whether on host or inside a container. `loadDMRConfig()` in `dmr-provider.ts` follows the same philosophy with a three-location filesystem search for `dmr-config.yaml`. A distinct but related architectural concern — the intended provider **tier priority** (max-subscription → work/Copilot → Groq Llama-70B as absolute last resort) — is a routing-order policy documented at the session level, separate from these mode/config fallbacks; a known defect here was providers being demoted to primary rather than preserving that order.

## Implementation Details

`dmr-provider.ts` wraps an OpenAI-compatible client against a local Docker Model Runner endpoint and caches availability via module-level `isAvailable`/`lastHealthCheck` globals, re-probing only after `dmrConfig.connection.healthCheckInterval` (default 30000ms) elapses — a deliberate staleness-for-latency trade-off benefiting hot-loop callers like wave analysis. Its config loader applies `expandEnvVars()` to interpolate `${VAR}` and `${VAR:-default}` syntax, letting one YAML file resolve differently on host versus containerized deployments.

`llm-with-process.ts` exists specifically because the `@rapid/llm-proxy` SDK's `LLMCompletionRequest` type lacks a `process` field; without this bypass, wave-analysis calls would be attributed to `process='unknown'` in token-usage telemetry, breaking per-stage cost dashboards.

`parse-llm-json.ts` is a narrowly-scoped repair pipeline rather than a general lenient parser: `escapeControlCharsInStrings()` escapes stray control characters only inside string literals, and `truncateToLastCompleteElement()` only treats nested bracket closes as safe truncation points — both targeting specific production failure modes rather than arbitrary malformed JSON.

## Integration Points

## Usage Guidelines

Developers should respect the tiered fallback conventions rather than bypassing them: mode resolution must check per-agent overrides before global state before the legacy flag, and provider selection must preserve the max-subscription → Copilot → Groq last-resort order rather than treating lower tiers as primary. DMR health checks should not be forced on every call in hot paths — rely on the existing cache interval. When diagnosing timeout or provider errors, investigate provider-specific client code before suspecting the shared proxy layer, per prior diagnostic findings. Extensions to `parse-llm-json.ts` should remain targeted at observed failure patterns rather than growing into a general-purpose lenient JSON parser.
