# DynamicEtaLearning — Technical Insight Document

## What It Is

DynamicEtaLearning is the adaptive ETA-estimation logic implemented entirely within `integrations/system-health-dashboard/src/components/ukb-workflow-modal.tsx`, centered on the function `calculateDynamicEta()`. Its purpose is to produce a live, self-correcting estimate of remaining workflow time by learning `learnedAvgBatchMs` from a running UKB workflow's own `batchIterations`, rather than depending solely on static historical statistics. A secondary function, `calculateStepAwareEta()`, exists as a legacy delegate that forwards to `calculateDynamicEta()`. As the child concept under the ManualLearning SubComponent, DynamicEtaLearning represents the interactive/online side of workflow observability — surfacing progress feedback for runs happening outside (or during) the scheduled batch wave-analysis pipeline, conceptually parallel to how the sibling OnlineBatchPaletteSplit visually distinguishes online-learned from batch-learned knowledge via `isOnlineLearned()`.

## Architecture and Design

The core design is a **layered fallback chain** with three confidence tiers: (1) an average over `batchIterations` whose steps are all `completed`/`skipped`, once 2+ such batches exist — the genuinely "learned" tier; (2) a single completed batch scaled by a 1.2x conservatism factor; (3) `workflowStats?.avgBatchDurationMs` or a crude `totalElapsedMs / currentBatch` division when nothing has finished yet. This is a deliberate **self-correcting/adaptive estimator pattern**, but it means estimate reliability silently changes over a run's lifetime with no UI indicator of which tier is active.

Surrounding this estimator is a **sanity-clamp/trust-boundary pattern**: `etaMs = Math.max(linearEtaMs * 0.3, Math.min(linearEtaMs * 2.0, etaMs))`, bounding the learned value to 30–200% of a naive linear-interpolation baseline (`linearEtaMs = totalElapsedMs * ((100 - progressPercent) / progressPercent)`). A stale code comment claims the floor is `0.5x`, while the implementation actually enforces `0.3x` — a documented doc/implementation drift. Outside this clamp, absolute guard rails `MIN_ETA_MS` (1000ms) and `MAX_ETA_MS` (30 minutes) form a defense-in-depth structure against three distinct failure modes: pathologically small learned averages, outlier-inflated averages, and degenerate `linearEtaMs` values when `progressPercent` is 0 or 100.

During finalization, the design shifts to a **median-over-mean outlier-resistance pattern**: `getStepMedianDuration()` and `calculateMedian()` sum expected durations of `pending`/`running` steps rather than averaging, specifically to resist skew from `step.recentDurations` outliers.

## Implementation Details

`calculateDynamicEta()`'s only external inputs are `process.batchProgress`, `process.batchIterations`, and `workflowStats` (a `WorkflowTimingStats | null` sourced from Redux state in `ukbSlice.ts`). The three-tier fallback logic performs reduce/every scans over `batchIterations` to determine which batches are fully complete. The finalization branch (`isInFinalization`) contains a secondary fallback, triggered when `etaMs === 0 && workflowStats?.avgFinalizationDurationMs` is truthy, which reconstructs a finalization-progress fraction from `process.completedSteps` and `process.totalSteps`, subtracting `totalBatches * 8` — a magic constant assuming 8 steps per batch that isn't derived from any schema field, creating a silent-drift risk if the real per-batch step count changes.

`calculateStepAwareEta()` is explicitly documented as a "Legacy function — now delegates to calculateDynamicEta," preserved for compatibility with existing call sites — a live adapter/facade instance that notably contradicts the project's own CLAUDE.md convention against parallel/legacy-named functions.

## Integration Points

DynamicEtaLearning reads from `UKBProcess.batchIterations` and `WorkflowTimingStats`, both defined in `integrations/system-health-dashboard/src/store/slices/ukbSlice.ts`. Critically, it has zero awareness of `WorkflowPreferencesState.mockLLM` and `singleStepMode`, also defined in `ukbSlice.ts` — meaning debug modes (near-instant mock durations, or operator-paused single-stepping) can feed artificially skewed data into `learnedAvgBatchMs` with no compensating signal. This mirrors the blind-spot pattern seen in the sibling LearningSourceClassifier, where correctness depends entirely on a single shared predicate (`isOnlineLearned()` in `./learning-source`) staying in lockstep with upstream data — here, correctness depends on the estimator staying in lockstep with preference-state toggles it doesn't consult.

Architecturally, the logic lives inside a React presentational component rather than a hook, selector, or backend service — consistent with the parent ManualLearning context's characterization of this area as dashboard/visualization-dominated rather than a distinct pipeline module.

## Usage Guidelines

Developers extending this logic should treat the three clamps (tier fallback, 0.3x/2.0x sanity clamp, MIN/MAX absolute bounds) as a unit — loosening one without the others reintroduces the exact failure modes they were layered to prevent. The stale `0.5x` comment should be corrected to `0.3x` to prevent future misreading. Any change to per-batch step count must also update the hardcoded `8` in the finalization fallback. Because `calculateDynamicEta()` has no `useMemo`/`useCallback` wrapping, it recomputes its full O(batches × steps) scan on every render while a workflow is active; call sites should consider memoization before this scales further. Finally, if debug-mode ETAs are surfaced to users, `mockLLM`/`singleStepMode` should be threaded into the estimator or its output flagged as unreliable in those modes. New call sites should target `calculateDynamicEta()` directly rather than `calculateStepAwareEta()`, whose retention exists only to avoid migration work.
