# HookConfigMigrationTool — Technical Insight Document

## What It Is

HookConfigMigrationTool is a child entity of **HookConfigLoader**, the module (implemented in `hook-config.js`) responsible for the hooks subsystem's three-tier configuration cascade: `DEFAULT_CONFIG → ~/.coding-tools/hooks.json → .coding/hooks.json`, merged through `mergeConfigs()`. As a migration-focused tool under this loader, its purpose is inherently tied to evolving or transforming the shape of hook configuration data across these tiers — user-level and project-level JSON files whose structure must remain compatible with what downstream consumers expect.

Critically, no direct implementation of HookConfigMigrationTool (or even HookConfigLoader itself) appears in the observed code files; its existence and responsibilities must be inferred from the contract it presumably serves. The strongest evidence of that contract comes from `lib/agent-api/hooks-api.js`, where the `HookConfig` JSDoc typedef documents `userConfigPath` (`~/.coding-tools/hooks.json`) and `projectConfigPath` (`.coding/hooks.json`) — an exact match to HookConfigLoader's cascade despite zero visible imports or coupling between the files. Any migration tool operating on these config files must preserve this cross-file contract even though it is nowhere enforced in code.

## Architecture and Design

The hooks subsystem mixes several coexisting design idioms, and HookConfigMigrationTool sits at the boundary of one of the more fragile ones: **flat config-file cascading** for policy data (HookConfigLoader's domain) versus **OOP inheritance** for agent adapters (`HooksManager` in hooks-api.js, using a `new.target` guard and throw-based abstract methods `getAgentType()`, `loadNativeHooks()`, `saveNativeHooks()` as a runtime-checked Template Method pattern). Nothing in the visible code enforces synchronization between these two extension points — a lesson directly relevant to migration tooling, since a config migration could change data that HooksManager subclasses (or the sibling `hook-manager.js` runtime) silently assume is still shaped a certain way.

The sibling entity **UnifiedHookConfigLoader** shares the same evidentiary gap: its merge semantics (array concatenation vs. override, deep vs. shallow merge) are unverified from any implementation file, meaning HookConfigMigrationTool's transformations must be validated against downstream consumers (`hooks-api.js`, `claude-bridge.js`) rather than against the loader's own source, since only the loader's *effects* are observable.

Two other siblings bear on migration risk: **EventTranslationMaps** documents that `EVENT_MAPPINGS` (hooks-api.js) and `EVENT_MAP` (claude-bridge.js) are independently maintained, structurally opposite translations of the same event vocabulary with no shared source of truth. **HandlerPriorityRegistry** likely refers to the in-memory `eventHooks` array inside `HooksManager.registerHook()`, sorted via `eventHooks.sort((a,b) => a.priority - b.priority)` on every registration call. Any migration that changes priority values or event names in config files has direct, non-obvious blast radius across these two duplicated maps and the re-sorted registry.

## Implementation Details

Although HookConfigMigrationTool's own code is not present in the observations, its operating environment is well characterized. Config data flows into a runtime consumer through one of two possible paths — `HooksManager` (class-based, hooks-api.js) or the function-based `getHookManager()`/`executeHooks()` singleton in `hook-manager.js`. Evidence from `claude-bridge.js`'s `main()` shows it dynamically imports `getHookManager` from `./hook-manager.js` and calls `manager.initialize(projectPath)` — meaning the **actual runtime entry point** for consuming migrated config is `hook-manager.js`, not `HooksManager.triggerHook()` in hooks-api.js. Any migration validation work must therefore be checked against `hook-manager.js`'s `initialize()`, not assumed to flow through the hooks-api.js class hierarchy.

Registration-time cost is also relevant: `registerHook()` resorts the entire `eventHooks` array on every call (O(n log n) per registration), so if a migrated config introduces many more hooks (project + user + default combined), initialization cost grows superlinearly purely from repeated resorting.

Runtime evaluation order matters too: `triggerHook()` iterates all hooks per event and sets `allow = false` when a hook returns `result.allow === false`, with no early exit. Analysis of this loop shows the accumulation is **monotonic-toward-false** — a later hook can add another `false` but never reset an existing `false` back to `true` — but message ordering remains decoupled from which hook actually caused a block. Migration tooling that reorders or reprioritizes hooks should account for this asymmetry: priority changes affect message ordering and *which* hook's message is attributed to a block, even though they cannot flip a block decision back to allow.

## Integration Points

HookConfigMigrationTool's most consequential integration point is the **fail-open error handling** in `claude-bridge.js`'s `main()`: the catch block wraps the entire pipeline, including the dynamic import of `hook-manager.js` and `manager.initialize(projectPath)`. If a migration produces malformed JSON or an incompatible schema in `.coding/hooks.json`, `mergeConfigs()` (or its consumer) throwing an exception during `initialize()` degrades silently to `{ decision: 'allow', message: 'Hook bridge error: ...' }` with `process.exit(0)` — meaning a migration bug could invisibly bypass a project's security constraints rather than producing a visible failure. This makes migration correctness a security-relevant concern, not merely a data-hygiene one.

Additionally, `transformContext()` in claude-bridge.js spreads all of Claude Code's raw stdin context into `metadata` without an allowlist, meaning any config-driven hook logic that inspects `metadata` fields has an undocumented dependency on Claude Code's JSON shape — a further consideration if migration tooling also touches metadata-related configuration.

## Usage Guidelines

Developers extending or invoking HookConfigMigrationTool should verify any schema change against both event-translation tables (`EVENT_MAPPINGS` in hooks-api.js and `EVENT_MAP` in claude-bridge.js) to avoid desynchronization, confirm the runtime consumption path via `hook-manager.js` rather than assuming `HooksManager` handles it, and treat priority-value changes as affecting message attribution order in `triggerHook()`, not just numeric ordering. Because config-loading failures fail open, migrations should be tested to ensure they never throw inside `initialize()` in production, and any new policy tier introduced by a migration should be paired with corresponding updates to `hook-config.js`'s merge logic rather than assumed to be handled automatically by HooksManager subclassing.

Combined with claude-bridge.js's transformResponse(), which does `decision: unifiedResult.allow ?
