# UidOwnershipGuard — Technical Insight Document

## What It Is

UidOwnershipGuard is not a single class or shared utility but a recurring **security convention** implemented independently in at least two locations: `isOwnedByMe()` in `lib/lsl/live/copilot-events-tail.mjs`, and `ownedDbPath()` in `lib/lsl/token/opencode-token-rows.mjs`. Both functions answer the same question — "does the current process uid own this filesystem resource?" — but they are separate implementations rather than calls into a common helper. As a child concept of CopilotLiveTail, this guard sits alongside sibling mechanisms LockStaleDetection, ProjectFiltering, and DegradedParityStub as one of several composed, single-purpose gates that `scanForLiveSessions()` applies to candidate session directories before tailing them.

## Architecture and Design

The dominant pattern is **fail-closed-on-error, fail-open-on-unsupported-platform**: when a uid concept doesn't exist (Windows, detected via `myUid == null` or the absence of `process.getuid`), the check is skipped and access is permitted; when a uid concept exists but `fs.statSync` fails, access is denied. This asymmetry only makes sense under a threat model — documented in the copilot-events-tail.mjs header as `T-51-09-FI` — that treats uid checks purely as *defense-in-depth against traversal into another user's Copilot state on a shared host*, not as a universal access-control layer. Windows deployments get zero protection from this code path and rely entirely on OS-level ACLs instead.

A second pattern, visible across both implementations and their sibling LockStaleDetection, is **skip-and-continue error isolation**: a rejected resource never throws or aborts the broader scan. In `scanForLiveSessions()`, a non-owned directory triggers a `process.stderr.write('[live-copilot] skipping non-owned session ...')` and a `continue`, mirroring the try/catch isolation `findLiveLockFile()` uses around individual lock-file stats. Notably, this produces an **observability asymmetry** with LockStaleDetection: ownership rejections are logged loudly to stderr, while stale-lock skips are silent, meaning operators debugging "why isn't my session tailed" get a signal only for the security case, not the freshness case.

The guard is strictly **read-only and advisory** — it decides whether to proceed with reading a resource, never attempts `chown`, deletion, or remediation. This narrow scope is consistent with the broader CopilotLiveTail philosophy of accepting structural limitations (as seen in DegradedParityStub's permanent data-loss contract) rather than trying to fix them at this layer.

## Implementation Details

`isOwnedByMe(sessionDir, myUid)` receives the caller's uid as an explicit parameter (presumably resolved once at watcher startup, though the call site isn't shown), compares it against `fs.statSync(sessionDir).uid`, and is invoked per-entry inside `scanForLiveSessions()`'s loop over `fs.readdirSync(sessionStateDir, { withFileTypes: true })`. Because it gates *one entry among many*, its granularity is a single skipped directory, not a whole-scan failure.

`ownedDbPath()` in `lib/lsl/token/opencode-token-rows.mjs` implements the same conceptual check with materially different mechanics: it detects POSIX support via `typeof process.getuid === 'function'` rather than a passed-in parameter, calls `process.getuid()` fresh on every invocation, and on mismatch returns `''` with a `[token-adapter-opencode]`-prefixed stderr line. Because `ownedDbPath()` gates a single SQLite file rather than one of many loop entries, a rejection propagates further: `buildOpencodeTokenRows()` checks `if (!resolved) return [];`, short-circuiting the *entire* call to an empty array — an all-or-nothing variant appropriate to a binary owned/not-owned resource.

Notably, `token-db.mjs`'s `openTokenDb()` shows no inline uid-check at all in its excerpt, relying instead on `{ fileMustExist: true }` and SQLite's `busy_timeout`. This implies the ownership guard for `token-usage.db` is enforced upstream by whatever caller resolves the db path, reinforcing that UidOwnershipGuard is a convention applied at inconsistent call depths rather than a uniformly enforced layer.

## Integration Points

Within CopilotLiveTail, UidOwnershipGuard composes with LockStaleDetection inside `scanForLiveSessions()`: ownership is checked as a harder, earlier gate — an owned-but-crashed session (stale lock) is silently dropped, while a foreign session is loudly rejected before staleness is even evaluated. It also operates independently of ProjectFiltering's `projectMatches()`, which applies a separate fail-closed policy (rejecting sessions with unreadable or `'unknown'` `workspace.yaml` project resolution) — both are opt-in, defense-oriented filters layered onto the same directory-scan loop but addressing different concerns (identity vs. project scope).

Across module boundaries, the pattern reappears in the token subsystem (`opencode-token-rows.mjs`, `token-db.mjs`), showing that the convention transcends CopilotLiveTail specifically and reflects a broader system-wide discipline around multi-tenant/shared-host safety for local state files.

## Usage Guidelines

Developers extending either call site should preserve the existing fail-closed-on-stat-error / fail-open-on-non-POSIX asymmetry rather than "fixing" it into a symmetric model, since it is a deliberate reflection of the stated threat model rather than an oversight. Any new ownership check should decide up front whether it protects *one resource* (favoring the `ownedDbPath()` short-circuit-to-empty style) or *one of many scanned entries* (favoring the `isOwnedByMe()` skip-and-continue style), and should emit a stderr diagnostic consistent with the existing `[live-copilot]` / `[token-adapter-opencode]` prefixes rather than throwing.

A latent risk worth flagging: `isOwnedByMe()`'s caller-supplied `myUid` could go stale if resolved once at process startup and the process later changes uid (e.g., in containerized/sandboxed agent environments), whereas `ownedDbPath()`'s inline `process.getuid()` call avoids this at a small per-call cost. Future work should not attempt to consolidate these into one shared utility without first confirming that the granularity difference (single-resource vs. per-entry) is preserved, since collapsing them risks either over-broad short-circuiting or silent under-protection. As with DegradedParityStub, this guard is a permanent, intentional constraint, not a bug — its scope is defense-in-depth for shared hosts, not comprehensive access control.
