# ServiceProbe

**Type:** SubComponent

[LLM] docker/entrypoint.sh reveals a second, feature-gating layer that sits upstream of any health probing: PROGRAM_FEATURES maps supervisord program names (semantic-analysis, embedding-listener, graphify, constraint-monitor, constraint-dashboard, constraint-dashboard-api, health-dashboard, health-dashboard-frontend) to feature IDs, and generates a supervisord include file (/etc/supervisor/features.d/disabled.conf) that sets autostart=false for disabled programs. This means ServiceProbe/service-probe.js's 'stopped' vs 'unknown' distinction must be interpreted differently depending on whether a program was never started (feature disabled — expected, not a fault) versus started and then crashed (feature enabled but failing — a real fault). The entrypoint script does not communicate feature-disabled state to the probing layer directly; it only prevents supervisord from launching the process, so any probe-based health system must independently know which features are enabled to avoid alerting on intentionally-off services. This is corroborated by tests/features/service-gating.test.mjs's explicit distinction between results.disabled and results.degraded on the host side — the same disabled-vs-degraded semantic split exists in both the container gating (entrypoint.sh) and host-side gating (start-services-robust.js), suggesting a deliberate, mirrored architecture rather than coincidence.

# ServiceProbe — Technical Insight Document

## What It Is

ServiceProbe is the protocol-level health-checking module implemented primarily in `service-probe.js`, which exposes `probeHttpHealth()` and `probeTcpPort()` as the canonical implementation of SPEC R6's strict three-state health model (running/stopped/unknown). It is deliberately architected as a "pure" <COMPANY_NAME_REDACTED>: it is blind to process ownership, deployment topology, or service identity beyond a URL or port. This positions it as a shared primitive within its parent, DockerizedServices, which relies on ServiceProbe's ambivalence toward deployment target to avoid maintaining separate health-monitoring logic for supervisord-managed containerized processes versus host-native Node subprocesses.

Critically, ServiceProbe is not the only health-checking logic in the codebase — it coexists with, but is architecturally distinct from, at least two other ad-hoc implementations, represented here as its children: EntrypointTcpWaitForService (the `wait_for_service()` bash function in `docker/entrypoint.sh`) and ServiceStarterHealthPrimitives / WaitForPortBindable (bespoke primitives in `scripts/start-services-robust.js`). Understanding ServiceProbe therefore requires understanding what it deliberately does *not* cover, as much as what it does.

## Architecture and Design

The dominant pattern is a Strategy/dual-mode execution model: the same HTTP/TCP probing contract in `service-probe.js` is applied uniformly across two different process-ownership substrates — supervisord/container-managed processes (`docker/entrypoint.sh`, `Dockerfile.coding-services`) and host-native subprocesses (`scripts/start-services-robust.js` via `lib/service-starter.js`). This is a conscious trade-off: uniformity of health semantics is bought at the cost of losing any awareness of *why* a service is down.

That trade-off is compounded by a second architectural layer sitting upstream of any probing: feature gating. `docker/entrypoint.sh`'s `PROGRAM_FEATURES` table maps supervisord program names (semantic-analysis, embedding-listener, graphify, constraint-monitor, constraint-dashboard, constraint-dashboard-api, health-dashboard, health-dashboard-frontend) to feature IDs and generates `/etc/supervisor/features.d/disabled.conf` to set `autostart=false` for disabled features. Because this gating happens entirely outside the probing layer, ServiceProbe's "stopped" vs "unknown" verdicts are semantically ambiguous unless the caller separately knows whether a service was disabled by feature flag (expected) or crashed after starting (a fault). This same disabled-vs-degraded split is mirrored on the host side in `startOneService()`, as tested by `tests/features/service-gating.test.mjs` — a deliberate, structurally-enforced symmetry between container and host gating rather than a coincidence.

![ServiceProbe — Relationship](images/service-probe-relationship.png)

A further asymmetry is the fail-open/fail-closed split: entrypoint.sh's feature-snapshot handling fails open (missing/unreadable `features.json`, or an unknown feature key, defaults to "enabled" — "starting everything"), even though it participates in a starting pathway, as an explicit documented carve-out against the general CLAUDE.md rule that starting logic fails closed. By contrast, `start-services-robust.js`'s `startOneService()` can set `blocked=true` for required services that fail, halting downstream startup entirely — a fail-closed posture for host-side required services.

## Implementation Details

Three independent health/readiness mechanisms exist side by side, each with different failure semantics:

1. **service-probe.js** implements the strict three-state model (running/stopped/unknown) via `probeHttpHealth()` and `probeTcpPort()`, intended for post-startup, ongoing health polling.
2. **EntrypointTcpWaitForService** (`docker/entrypoint.sh:14-33`) implements `wait_for_service()` using `timeout 2 bash -c "echo >/dev/tcp/$host/$port"` in a bounded retry loop (max_attempts=30, 2s sleep), used for Qdrant (6333) and Redis (6379) readiness at container-entry time. Its final branch, on exhausting retries, still `return 0`s with the comment "Don't fail - let supervisord handle it" — this probe can never block `exec "$@"` from launching supervisord; it can only emit a warning.
3. **ServiceStarterHealthPrimitives / WaitForPortBindable** (`scripts/start-services-robust.js:157-215`) implement `isProcessRunningByScript()` (pgrep-based orphan detection outside ProcessStateManager's knowledge), `killProcessOnPortAndWait()` (SIGTERM-then-SIGKILL escalation with port-release polling), and `waitForPortBindable()`, which performs a throwaway `net.createServer().listen()` bind attempt specifically because a listening-socket check can false-negative during a kernel TIME_WAIT-like hold after a crash — layering a bind probe atop connection probes to avoid burning a `maxRetries` slot on a spurious EADDRINUSE.

A fourth, legacy implementation also exists: `start-services.sh` duplicates health semantics yet again via `check_port()` (lsof), `docker-compose ps | grep 'Up.*healthy'` polling, and `lsof -ti:PORT | wc -l` checks, gated behind the `ROBUST_MODE` environment variable (default `true`) and retained for backward compatibility.

`startOneService()` in `start-services-robust.js` (exercised by `tests/features/service-gating.test.mjs:66-140`) formalizes the required/optional distinction into four outcome buckets: disabled (feature off, never attempted), degraded (attempted, failed, optional), failed (required and failed, sets `blocked=true`), and successful. `SERVICE_ORDER` hardcodes `transcriptMonitor` and `liveLoggingCoordinator` as the first two entries because "later services register against them" — an ordering dependency enforced only by array position and a dedicated test, not a declared dependency graph.

## Integration Points

ServiceProbe's parent, DockerizedServices, depends on it as the deployment-agnostic health-check substrate, but sibling components implement their own parallel gating and readiness logic that ServiceProbe does not participate in: ServiceStarter's `SERVICE_CONFIGS`/`SERVICE_ORDER` catalogue gates via `loadFeatures()` from `lib/features/index.mjs`; APIServiceWrapper and SupervisordRuntime both describe the same `PROGRAM_FEATURES`-to-`features.json` fail-open override mechanism in entrypoint.sh; DashboardServiceWrapper documents the required-vs-optional asymmetry enacted through `startServiceWithRetry()` in `lib/service-starter.js`; and ProcessStateManager tracks PIDs that `isProcessRunningByScript()` cross-checks against orphaned processes.

Two independent drift-prevention tests bind these layers together: `tests/features/service-gating.test.mjs` asserts `SERVICE_CONFIGS`/`SERVICE_ORDER` cover each other and every service declares a real feature, while `tests/features/container-gating.test.mjs` asserts `PROGRAM_FEATURES` covers exactly the `[program:...]` sections of `supervisord.conf`. Together these enforce the "four mappings must agree" invariant referenced in CLAUDE.md, even though there is no single generated source of truth — the container reads a JSON snapshot written by the host rather than querying a live feature service.

## Usage Guidelines

Developers extending or debugging health checks must recognize that a fix made in `service-probe.js` will **not** automatically propagate to `EntrypointTcpWaitForService`'s `/dev/tcp` checks, to `WaitForPortBindable`/`ServiceStarterHealthPrimitives`, or to the legacy `start-services.sh` polling logic — these are three (arguably four, counting the legacy path) independently maintained implementations of "is this service healthy," and a behavioral change intended to be universal must be manually mirrored across all of them.

When a service under DockerizedServices reports "stopped" or is simply absent, the responsible layer is not ServiceProbe's judgment alone but the interaction with feature gating: check whether the feature was disabled (expected, no fault) via the host-written `features.json` snapshot before assuming a crash. If a feature toggle "didn't take" inside the container, the correct diagnostic path is verifying that `features.json` was mounted and readable — not inspecting `supervisord.conf` directly, since entrypoint.sh's override only writes to `/etc/supervisor/features.d/disabled.conf` via `[include]`, never touching canonical program definitions.

New services, whether container-managed (supervisord program) or host-managed (`SERVICE_CONFIGS` entry), must be registered against a real feature ID in both mapping tables; failing to do so will be caught by `service-gating.test.mjs` or `container-gating.test.mjs`, but only if those tests are run. Finally, `transcriptMonitor` and `liveLoggingCoordinator` must remain the first two entries in `SERVICE_ORDER` — reordering or misclassifying either as optional risks silently breaking the observability pipeline that other services register against, a risk mitigated only by test coverage, not by structural enforcement in the code itself.

This duality means developers must understand that 'starting a service' has two entirely separate code paths depending on deployment target, and that health-checking logic (service-probe.js) is written to be agnostic to which path is in effect — it only cares about HTTP/TCP reachability, not process ownership. This design avoids needing separate health-monitoring logic for containerized vs local services, but it also means Docker-specific failures (e.g., supervisord misconfiguration killing a service inside the container) surface identically to host-side crashes, requiring log inspection to disambiguate.
