# ServiceProbe: Technical Insight Document

## What It Is

ServiceProbe is the health-verification and resilient-startup subsystem living primarily in `lib/service-starter.js`, with its container-level analog expressed through `docker/entrypoint.sh`'s `wait_for_service()` function. As a child of DockerizedServices, ServiceProbe is bound by a strict architectural invariant (SPEC R6, documented at the parent level): probing functions must never assert "healthy" directly. Instead, probes distinguish only between "stopped" (connection refused, timeout, non-2xx) and "unknown" (config errors, malformed URLs, unresolvable hosts), deferring the actual healthy determination to a higher-level coordinator that combines probe results with signals like ProcessStateManager's registration state. This pessimism-by-design philosophy is the organizing principle behind all three of ServiceProbe's children: WithDeadlineHelper, StartServiceWithRetry, and PortListeningProbes.

## Architecture and Design

The subsystem layers three concerns cleanly. At the innermost layer, WithDeadlineHelper (`withDeadline()`) wraps `Promise.race()` to enforce timeouts without leaking Node.js event-loop handles — a `let timer` declared outside the race array is assigned inside the timeout promise's executor and unconditionally cleared in a `finally` block, regardless of which side of the race wins. This detail matters specifically because it's invoked twice per attempt inside StartServiceWithRetry (`startServiceWithRetry()`): once wrapping the caller's `startFn()` (default 30000ms) and once wrapping `healthCheckFn()` (hardcoded 10000ms). Under exponential backoff across `maxRetries` attempts, a naive implementation would compound dangling timers, causing hung test runners or one-shot CLIs — even though in the long-lived service-starter context itself, the leak would be invisible.

StartServiceWithRetry itself implements a three-layer resilience wrapper: an outer retry loop with exponential backoff (`retryDelay * 2^(attempt-1)`), the withDeadline timeout guard applied independently to start and health-check calls, and post-failure cleanup that SIGTERMs then SIGKILLs an unhealthy child process before retrying. Crucially, the function branches on a `required` vs `optional` classification after retries exhaust: required services throw (a fatal "BLOCKING startup" error), while optional services return a `{ status: 'degraded', healthy: false, error, attempts }` object with "continuing in DEGRADED mode" logging. This is a graceful-degradation pattern, but it's an implicit contract — the file is plain JS/JSDoc, not TypeScript — so callers must know in advance whether to catch exceptions or inspect a status field.

PortListeningProbes rounds out the layer with two opt-in primitives, `isPortListening()` (HTTP GET to `/health`, treating 2xx as listening) and `isTcpPortListening()` (raw `net.Socket` connect event, intended for non-HTTP services like Memgraph Bolt or PostgreSQL). Neither is wired automatically into StartServiceWithRetry — `healthCheckFn` is caller-supplied — so these remain building blocks rather than an enforced contract, meaning a careless caller could bypass both with an always-true check function.

## Implementation Details

The core mechanic across all three children is disciplined timer/process lifecycle management. WithDeadlineHelper's try/finally pattern is the load-bearing detail: without it, `Promise.race()`'s losing timer stays armed on the event loop for the full `ms` duration even after the work resolves. StartServiceWithRetry compounds this risk by calling `withDeadline()` twice per attempt, so the fix is doubly important under retry loops where dozens of timers could otherwise accumulate. Sibling component ServiceStarter and StartServicesRobust both describe this exact same mechanism from complementary angles, confirming it as the subsystem's central engineering concern rather than an isolated one-off fix.

At the container boundary, `docker/entrypoint.sh`'s `wait_for_service()` mirrors ServiceProbe's pessimism but takes it one step further: it doesn't even distinguish stopped/unknown, it simply polls a TCP port via `timeout 2 bash -c 'echo >/dev/tcp/$host/$port'` (default 30 attempts, 2s sleep) and, on exhaustion, logs a WARNING but still `return 0`. Combined with `set -e` at the top of the script, this means a slow or unreachable Qdrant/Redis never aborts the entrypoint — only a genuinely unhandled command failure elsewhere does. The explicit intent, per sibling DockerEntrypoint's documentation, is that supervisord — not the entrypoint script — is the ultimate arbiter of whether a dependent service being unreachable is fatal, pushing real health determination further downstream toward the health-coordinator.

## Integration Points

ServiceProbe's outputs feed a higher-level health-coordinator that is not itself part of this subsystem but consumes its three-state (stopped/unknown/degraded) signals alongside ProcessStateManager's process registration state. Sibling ProcessStateManager is used directly by ServiceWrapperScripts (`scripts/api-service.js`, `scripts/dashboard-service.js`) for cross-process registration/unregistration, giving the coordinator a second, independent signal to combine with probe results — reinforcing why probes themselves must stay pessimistic and never self-declare health.

At the container level, DockerEntrypoint and LLMMockService both illustrate the same "trust a flattened artifact rather than re-derive policy" pattern: entrypoint.sh reads `/coding/.coding/runtime/features.json` to gate which programs supervisord starts, defaulting unknown/missing feature keys to enabled (fail-open) so that older host snapshots can never accidentally disable a new container program. This fail-open philosophy stands in instructive contrast to the pessimistic-by-default philosophy of the probe functions themselves — the codebase deliberately fails open at the container-startup layer (better to over-start than silently run nothing) while failing closed/uncertain at the health-assertion layer (never claim health you can't verify).

## Usage Guidelines

Developers extending ServiceProbe's probe functions must preserve the three-state contract (stopped/unknown, never healthy) — this is an enforced architectural invariant (SPEC R6) at the parent DockerizedServices level, not a suggestion. When using StartServiceWithRetry, callers must explicitly branch on `options.required`: a thrown exception signals a required-service failure, while a returned `{ status: 'degraded' }` object signals an optional-service failure — since this isn't type-enforced, misreading the contract silently swallows failures. When composing custom health-check functions, prefer wiring in PortListeningProbes' `isPortListening()` or `isTcpPortListening()` rather than ad hoc checks, and choose the HTTP vs raw-TCP variant based on whether the target service exposes an HTTP `/health` endpoint or is a raw protocol service like a database. Any new timeout-guarded async operation added to this subsystem should follow WithDeadlineHelper's try/finally clearTimeout pattern exactly — omitting it reintroduces the exact hung-process bug class the existing code was written to eliminate, particularly dangerous for short-lived callers like test runners or one-shot CLIs even though long-lived service contexts mask the leak.
