# DashboardServiceWrapper — Technical Insight Document

## What It Is

DashboardServiceWrapper is the orchestration layer implemented primarily across `scripts/start-services-robust.js`, `docker/entrypoint.sh`, `start-services.sh`, and `tests/features/service-gating.test.mjs`, that governs how heterogeneous services (Express APIs, Next.js dev servers, Python subprocesses) are started, gated by feature flags, and verified as healthy — both on the host and inside a Docker container. As a child of DockerizedServices, it embodies the same dual-mode execution reality: services either run as supervisord-managed processes inside a single container, or as host-native Node subprocesses tracked through ProcessStateManager. DashboardServiceWrapper is the concrete machinery that makes that duality operable, containing four sub-components — ServiceRequiredFlagAsymmetry, SERVICE_ORDER_Contract, FeatureGatedStartOneService, and DockerEntrypointFeatureSnapshot — each addressing a distinct facet of the same underlying problem: keeping configuration, ordering, and feature-gating consistent across two independently editable execution paths.

## Architecture and Design

The core architectural pattern is a wrapper/adapter normalizing disparate service types behind one PSM lifecycle contract, layered with declarative feature-gating checked against a shared catalogue (`FEATURE_IDS` from `lib/features/catalogue.cjs`). Crucially, this catalogue is enforced at two physically separate boundaries — the host (`SERVICE_CONFIGS[...].feature` in `start-services-robust.js`) and the container (`PROGRAM_FEATURES` in `docker/entrypoint.sh`) — with no shared runtime code crossing that boundary. Instead, consistency between the two is enforced entirely by tests: `tests/features/service-gating.test.mjs` on the host side, and `tests/features/container-gating.test.mjs` on the container side, mirroring each other's role as drift detectors.

A second defining pattern is the snapshot-file bridge: `docker/entrypoint.sh` reads a host-written, read-only snapshot at `/coding/.coding/runtime/features.json` rather than attempting to run the host's feature resolver inside the container. This is architecturally identical to the `CODING_ROOT` override bridge noted in the parent DockerizedServices observations and in `llm-mock-service.ts` — both cross the host/container boundary via a mounted file instead of environment variables passed at container-create time.

The most consequential design decision is the deliberate asymmetry in failure posture. FeatureGatedStartOneService (host side) fails **closed**: an unknown feature name throws rather than silently skipping. DockerEntrypointFeatureSnapshot (container side) fails **open**: an unknown feature key, or an entirely missing snapshot, defaults to "enabled," per the explicit rationale in the entrypoint script that a container silently running nothing is harder to diagnose than one running too much. This is not an oversight but a considered per-blast-radius choice, tested explicitly by both service-gating and container-gating suites.

## Implementation Details

At the host level, `scripts/start-services-robust.js` defines `SERVICE_CONFIGS` and `SERVICE_ORDER` as plain data structures — there's no schema or type system enforcing shape. ServiceRequiredFlagAsymmetry lives here: `transcriptMonitor` and `liveLoggingCoordinator` are marked `required: true, maxRetries: 3`, forming the base that "later services register against" (per the test's own comment), while services like dashboard/graphify are optional, consistent with the module's stated goal of "retry-with-timeout and graceful degradation for all services." Nothing in the language prevents someone from flipping `required: true` to `false` — the only guard is `SERVICE_ORDER_Contract`'s assertion in `tests/features/service-gating.test.mjs` that `SERVICE_ORDER.slice(0, 2)` equals `['transcriptMonitor', 'liveLoggingCoordinator']`.

The wrapper also implements dual "is this running" verification: PSM-based checks (`psm.isServiceRunning(...)`) plus `isProcessRunningByScript()`, a `pgrep`-based scan for orphaned processes. When an orphan is found, it is explicitly re-registered with PSM — a self-healing reconciliation-on-read, not a passive check. This same "guard against drift between source of truth and observed reality" concern reappears architecturally in DockerEntrypointFeatureSnapshot's handling of `PROGRAM_FEATURES` versus `supervisord.conf`.

Port lifecycle management is similarly two-phased: `killProcessOnPortAndWait()` (SIGTERM→poll→SIGKILL escalation) followed by `waitForPortBindable()`, which distinguishes "HTTP-responsive" from "actually bindable" using a throwaway `net.createServer()` probe — a fix for a concrete observed kernel race (post-crash TIME_WAIT-like states) that would otherwise burn a `maxRetries` slot on a doomed `EADDRINUSE` spawn.

On the container side, `FeatureGatedStartOneService`'s sibling `DockerEntrypointFeatureSnapshot` mechanism is implemented via fragile-but-intentional shell idioms: `PROGRAM_FEATURES` is a whitespace-delimited string parsed with `${pair%%:*}`/`${pair##*:}`, and a `node -e` one-liner must emit exactly `"true"`/`"false"` on stdout for the surrounding `if [ "$enabled" = "false" ]` string comparison to behave correctly. The `2>/dev/null || echo "true"` fallback only catches nonzero exit codes, not malformed-but-successful output — an undocumented edge case that still fails open, consistent with policy but not explicitly guarded.

Finally, `start-services.sh` retains a legacy bash path (`ROBUST_MODE=false`) using raw `lsof`/`kill -9`/`docker-compose` calls and string-based status tracking (`CONSTRAINT_MONITOR_STATUS="✅ FULLY OPERATIONAL"`), which the Node.js rewrite replaced with PSM registration and structured retry. This is a live migration seam, not dead code — `ROBUST_MODE` defaults `true` but the fallback remains reachable.

## Integration Points

DashboardServiceWrapper sits directly beneath DockerizedServices and interacts closely with its siblings. ServiceStarter formalizes the same SERVICE_CONFIGS/SERVICE_ORDER feature-gating logic that DockerEntrypointFeatureSnapshot mirrors on the container side — both must be updated together or the two deployment modes drift, a risk `tests/features/service-gating.test.mjs`'s coverage assertion is designed to catch. ServiceProbe supplies the protocol-level health <COMPANY_NAME_REDACTED> (`probeHttpHealth`/`probeTcpPort`) that DashboardServiceWrapper's health checks build upon, though `entrypoint.sh`'s `wait_for_service()` implements its own ad-hoc `/dev/tcp` probing rather than delegating to it — an acknowledged duplication. ProcessStateManager is the registry that both PSM-based checks and orphan re-registration in `isProcessRunningByScript()` depend on. APIServiceWrapper and SupervisordRuntime share the same `PROGRAM_FEATURES`/entrypoint.sh mechanism described here, confirming that DockerEntrypointFeatureSnapshot is a cross-cutting concern rather than isolated to this component alone.

## Usage Guidelines

Developers modifying `SERVICE_CONFIGS` or `SERVICE_ORDER` must keep both in sync — the coverage test will fail CI otherwise, which is the intended enforcement mechanism, not a suggestion. Never assume flipping `required` on `transcriptMonitor` or `liveLoggingCoordinator` is safe: doing so risks silently breaking the observability pipeline other services register against, guarded only by one `assert.deepEqual`. When adding a new feature flag, it must be wired into both the host catalogue (`FEATURE_IDS`) and the container's `PROGRAM_FEATURES` map — these are independently maintained and only kept consistent by tests, not shared code. On the container side, remember the fail-open default: an absent or malformed snapshot, or unknown feature key, means "run it," so container gating should never be relied upon as a security boundary. Conversely, host-side gating fails loudly on typos, so `startOneService()` errors should be treated as configuration bugs to fix immediately, not degraded-mode conditions. Finally, treat `start-services.sh`'s legacy bash branch as still-live migration code, not deletable cruft, until `ROBUST_MODE` is fully retired.
