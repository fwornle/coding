# ClassColorFallback: Technical Insight Document

## What It Is

`ClassColorFallback` is implemented in `integrations/unified-viewer/src/graph/color-fallback.ts` and provides the visual attribute resolution layer (color, shape, border, pulse) for nodes rendered by the knowledge-graph viewer. As a child concern of the `GraphVisualRendering` parent, it specifically serves the D3-based path — `D3GraphCanvas.tsx` — rather than the sibling static SVG rendering found in `multi-agent-graph.tsx`. The module exposes multiple overlapping resolvers (`classColor()`, `nodeFillColor()`, `nodeShapeFor()`, `borderStyleFallback()`, `pulseRuleFallback()`) that together answer the question "how should this ontology-classed entity look on screen," while explicitly separating fill color (source-independent) from online-learned provenance (rendered as an overlay ring, `ONLINE_RING_COLOR` #f472b6).

## Architecture and Design

The module encodes several coexisting design patterns rather than a single unified one, and the observations make clear this is a snapshot of partial migration rather than a finished design. `nodeFillColor()` (color-fallback.ts:~230-250) and `nodeShapeFor()` (~255-270) both implement a chain-of-responsibility fallback: registry-provided `display.color`/`display.shape` first, then a static palette lookup (`BATCH_PALETTE` or `SHAPE_PALETTE`), then recursive ancestor walk via `ClassRegistryEntry.parent` guarded by a `seen` Set against cycles, and finally a hard default (`DEFAULT_BATCH` slate or `'circle'`). This tiered contract is documented against an external "UI-SPEC §14" rule set (rules 1-5), but those rules live only as inline numbered comments in this file rather than in a shared spec module — a drift risk explicitly called out in the architecture notes.

Separately, `classColor()` (~60-75) implements a strategy-dispatch pattern: a boolean from `isOnlineLearned()` selects between `BATCH_PALETTE` and `ONLINE_PALETTE`, two structurally parallel teal/blue vs. red/pink hierarchy tables. This function is explicitly the *legacy* resolver — the 2026-06-28 comment block declares `nodeFillColor()` the canonical, operator-mandated "Hybrid" scheme (fill is source-independent; provenance is a ring overlay), leaving `classColor()` in place seemingly for unmigrated callers, though no such caller is visible in the provided files. This is a clear architectural inflection point: the operator rejected mixing source and class into a single color axis, and the module now carries both the old and new philosophies simultaneously.

## Implementation Details

`isOnlineLearned({ metadata: { source } })` (imported from `./learning-source`) replaced a prior literal check `source === 'auto'`, which under-matched because ETM/consolidator output is stamped "online" far more often than "auto" — a concrete historical bug this classifier extraction was built to eliminate. Its deprecated sibling, `isOnlineSource(source?: string | null)` (~195-205), is kept alive as a string-compatible shim for callers that hold only a bare string rather than a full node object; the doc comment quantifies why it's dangerous to rely on alone — it cannot see the subsystem/digest-shape fallbacks needed to correctly classify roughly 138 entities that carry no `source` field at all.

`borderStyleFallback()` deliberately ignores its own `_className` parameter (underscore-prefixed per convention) because border state is "purely a function of" whether the entity has relations in the current filtered view — a value the caller (graph-builder) must compute from a live graphology `Graph` *before* stamping the display attribute. This is an implicit, type-unenforced ordering contract: stamp-after-filter is required for correctness, and violating it fails silently.

`_classHue()` (~90-100) is legacy FNV-1a hash-based hue derivation from an earlier randomized-color scheme the operator rejected for looking like a "children's drawing book." It has no production caller but is retained solely because `color-fallback.test.ts` pins its output to discriminate distinct class names — a test-driven maintenance liability that couples the test suite to dead code indefinitely, or requires a deliberate test rewrite to shed it.

## Integration Points

The clearest confirmed consumer is `D3GraphCanvas.tsx`, which imports `nodeFillColor`, `ONLINE_RING_COLOR`, and `ClassRegistryEntry` directly, building a `registryMap: Map<string, ClassRegistryEntry>` from `ontology` data and threading it through the render path. This mirrors the sibling `ForceDirectedLayout`'s status as a deliberate port of VKB's `GraphVisualization.tsx`, preserving `d3.forceSimulation`/`forceLink(150)`/`forceManyBody(-500)` verbatim — meaning the visual resolvers here operate downstream of layout parameters tuned for a different codebase's data shape. Sigma's `buildGraph` and `LegendPanel` are referenced only in comments as sibling consumers of the "ONE canonical resolver," but this claim is unverified from the code given here — a gap worth closing before relying on it.

At the parent level, `GraphVisualRendering` is architecturally split: `multi-agent-graph.tsx` (sibling `MultiAgentGraphSvg`) resolves its own colors via `useWorkflowColors()` entirely independently, with zero shared type, abstraction, or resolver with `color-fallback.ts`. Any cross-cutting visual change (dark mode, palette refresh) must be solved twice, a structural consequence noted at the `HierarchyParentDerivation` level as well.

## Usage Guidelines

Developers should treat `nodeFillColor()`/`nodeShapeFor()` as canonical and avoid introducing new callers of `classColor()`, which conflates source and class in a way the operator has explicitly moved away from. When adding new source-classification logic, prefer `isOnlineLearned(node)` over `isOnlineSource(string)` — the latter cannot see the 138 sourceless entities' fallback signals and should only be used where only a bare string is available. Any change to the fallback tiers in `nodeFillColor`/`nodeShapeFor` must be mirrored in both functions and cross-checked against UI-SPEC §14, since the rules exist only as comments, not as a shared, checkable spec artifact. Callers building the relation-count input to `borderStyleFallback()` must compute it from a pre-filter graph state — stamping attributes before filtering will silently corrupt border rendering with no error signal. Finally, do not delete `_classHue()` without first updating or removing its pinning test in `color-fallback.test.ts`, and be aware that any future consolidation with the Sigma/`LegendPanel` consumers should first verify their actual usage of this module rather than assuming parity with `D3GraphCanvas.tsx`.
