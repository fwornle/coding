# ClaudeBridgeAdapter — Technical Insight Document

## What It Is

ClaudeBridgeAdapter is implemented in `lib/agent-api/hooks/claude-bridge.js`, principally through its `main()` function (lines 123-159), a paired `readStdin()` routine (lines 45-70), and a `transformContext()`/`transformResponse()` pair (lines 76-104) that translate between Claude Code's native hook protocol (stdin/stdout JSON) and its parent component, UnifiedHookManager. Structurally, it is a child of UnifiedHookManager (per the hierarchy context "UnifiedHookManager contains ClaudeBridgeAdapter"), and it is spawned as a fresh Node process per Claude tool-call event (PreToolUse/PostToolUse), delegating actual hook execution to the manager it dynamically imports from `./hook-manager.js`. It sits alongside sibling components UnifiedHookConfigLoader, HandlerRegistry, and HookMigrationTool as one of several subsystems orbiting UnifiedHookManager, each addressing a distinct facet: config loading, handler storage, migration, and — in this case — protocol translation at the process boundary.

## Architecture and Design

The dominant pattern is Adapter/Bridge: claude-bridge.js exists solely to translate Claude Code's native stdin/stdout hook contract into UnifiedHookManager's internal event vocabulary and back, via `transformContext()`/`transformResponse()` and the `EVENT_MAP` translation table (`PreToolUse→pre-tool`, etc., lines 33-41). Layered onto this is a strict linear pipeline: `readStdin() → transformContext() → dynamic import('./hook-manager.js') → manager.initialize()/executeHooks() → transformResponse()`, all wrapped in a single outer try/catch.

This produces a deliberate fail-open contract, shared conceptually with sibling descriptions (UnifiedHookConfigLoader, HookMigrationTool): every failure mode — JSON parse errors, import failures, `initialize()` or `executeHooks()` throwing — collapses into the same `{decision: 'allow', message: 'Hook bridge error: ...'}` response with `process.exit(0)`. This is an explicit availability-over-enforcement trade-off: Claude Code's tool-call gate can never be blocked by a bridge-level bug, only by a legitimate `allow: false` from a properly executing handler. The corollary, noted as a real operational risk, is that a bug in `transformContext()` and a genuinely missing `hook-manager.js` module are observationally indistinguishable from Claude Code's perspective — operators must tail `logger.error('Bridge execution failed', ...)` logs rather than trust exit codes.

The module also embodies a dual-mode design: an `if (process.argv[1] === fileURLToPath(import.<COMPANY_NAME_REDACTED>.url)) { main(); }` guard alongside named exports (`main`, `transformContext`, `transformResponse`, `EVENT_MAP`) lets it function both as a CLI entrypoint and as a unit-testable library, deliberately separating pure transformation logic from the stateful manager dependency (the dynamic `import()` is deferred until after stdin is read/parsed).

## Implementation Details

`readStdin()` (lines 45-70) races the `process.stdin.on('end', ...)` event against a hardcoded 1000ms `setTimeout` that only resolves to `{}` if `data` is still empty. This means partial/slow JSON writes from a slow parent process are not rescued by the timeout — they fall through to the `'end'` handler and either parse or throw, conflating "slow stdin" with "malformed stdin" under the same generic bridge-failure message.

`transformContext()` builds `unifiedContext.metadata` via `{ workingDirectory, projectPath, ...claudeContext }`, spreading the entire raw stdin payload into metadata even after already extracting `tool_name`/`tool_input`/`tool_output`/`session_id` into typed fields — producing redundant duplication (e.g., `metadata.tool_input` alongside `unifiedContext.tool.input`). No sanitize/redact call precedes this spread, so the bridge assumes UnifiedHookManager.executeHooks() or a downstream consumer performs redaction.

`main()`'s lazy `manager.initialized` guard (lines 145-149) checks initialization state before calling `manager.initialize(projectPath)`, avoiding redundant config reloads despite the module being re-spawned as a fresh process per tool-call event — a lazy singleton pattern relying on UnifiedHookManager's internal state rather than any cross-process cache.

## Integration Points

ClaudeBridgeAdapter's primary integration is with UnifiedHookManager via `getHookManager()` in `hook-manager.js`, imported dynamically rather than statically. Its `EVENT_MAP` is structurally near-identical but inverse-keyed to the `claude` sub-object of `EVENT_MAPPINGS` in `lib/agent-api/hooks-api.js`'s `HooksManager.translateEvent()` — claude-bridge.js maps agent-native→unified while hooks-api.js maps unified→agent-native, using different vocabularies (string literals vs. `HookEvent` enum constants) with no shared import, creating a synchronization hazard for new lifecycle events.

Notably, despite structural similarity — sibling HandlerRegistry's abstract `HooksManager` base class (constructor throwing on `new.target === HooksManager`, abstract `getAgentType()`/`loadNativeHooks()`/`saveNativeHooks()`) — nothing confirms UnifiedHookManager extends `HooksManager`; claude-bridge.js imports only from `hook-manager.js`, never `hooks-api.js`. This confirms two independent, non-inheriting hook systems, meaning `registerHook()`'s priority-sort-on-push behavior in hooks-api.js must be independently reimplemented in hook-manager.js.

Unrelated bundled files (workflow/hooks.ts, usePolledFetch.ts, cli-and-rules-gating.test.mjs) share only the word "hook" and no runtime dependency — a naming collision between agent lifecycle hooks and React hooks that future search/indexing must disambiguate.

## Usage Guidelines

Developers must not treat the bridge as a place for mandatory, non-bypassable policy enforcement — its fail-open contract guarantees that infrastructure failures behave identically to explicit allows. Any monitoring must tail `logger.error` output rather than rely on exit codes or stdout. When adding new lifecycle events, both EVENT_MAP (claude-bridge.js) and EVENT_MAPPINGS (hooks-api.js) must be updated consistently in their opposite directions, since nothing enforces this at build time. Given the unsanitized metadata spread in `transformContext()`, any sensitive data handling must occur downstream in UnifiedHookManager.executeHooks() or consuming services — the bridge itself provides no redaction boundary. Finally, because the two hook-manager implementations (HooksManager vs UnifiedHookManager) do not share inheritance, changes to registration/priority logic in one must be manually mirrored in the other.
