# HookMigrationTool: Technical Insight Document

## Architecture and Design

The surrounding system exhibits several classic patterns. **Adapter/Bridge**: `claude-bridge.js`'s `main()` executes a strict linear pipeline — `readStdin() → transformContext() → dynamic import('./hook-manager.js') → manager.executeHooks() → transformResponse()` — translating Claude's native protocol into the unified context shape. **Template Method**: `hooks-api.js`'s `HooksManager` class throws `'HooksManager is abstract and cannot be instantiated directly'` when `new.target === HooksManager`, leaving `getAgentType()`, `loadNativeHooks()`, and `saveNativeHooks()` as abstract stubs for subclasses (mirroring HandlerRegistry's characterization of this as a "classic Gang-of-Four abstract base class"). **Fail-soft/fail-open layering**: `HooksManager.triggerHook()` catches exceptions per-handler into a messages array (fail-soft), while `claude-bridge.js`'s outer try/catch guarantees `process.exit(0)` with `decision: 'allow'` regardless of failure mode (fail-open) — a philosophy ClaudeBridgeAdapter's sibling notes explicitly makes "the bridge a poor place to add mandatory, non-bypassable policy checks." **Lazy initialization** appears at two stacked layers: the deferred `await import('./hook-manager.js')` inside `main()`, and `manager.initialized` gating a call to `manager.initialize(projectPath)` — both optimizations meaningful specifically because the bridge spawns as a fresh Node process on every single tool call.

A significant unresolved structural question, raised consistently across observations and by sibling HandlerRegistry, is whether **UnifiedHookManager** (HookMigrationTool's parent) literally extends `HooksManager` from `hooks-api.js`, or independently reimplements the same `Map<event, Handler[]>` + priority-sort pattern in parallel. No `extends` clause is visible in the code graph bundle to confirm inheritance either way.

## Implementation Details

Two duplicated event-mapping tables encode the same domain knowledge in inverted directions. `EVENT_MAP` in `claude-bridge.js` is flat and claude-only, mapping native names (e.g., `'PreToolUse'`) to unified names. `EVENT_MAPPINGS` in `hooks-api.js` is nested per `agentType` (`claude`, `copilot`), mapping `HookEvent` enum values to native names — the opposite direction, with `null` entries for unsupported translations like `copilot.POST_PROMPT`. This inversion means a mapping bug could pass validation in one direction while silently failing in the other.

`HooksManager.registerHook()` sorts handlers by ascending priority immediately at registration time (`eventHooks.sort((a, b) => a.priority - b.priority)`), a pattern also attributed to `UnifiedHookManager.registerHandler()`. `HooksManager.triggerHook()` constructs a `fullContext` object (`event`, `agentEvent`, `agentType`, `sessionId`, `timestamp`, spread `context`) that is structurally near-identical to `transformContext()`'s output in `claude-bridge.js` — yet no shared builder or type is visible connecting them, suggesting either genuine code reuse not captured in this bundle or coincidental convergent design.

A specific implementation risk: `transformContext()` builds `metadata` as `{ workingDirectory, projectPath, ...claudeContext }`, with the unsanitized spread occurring *after* the two named fields — meaning any key collision from Claude's own payload (e.g., a `workingDirectory` key) silently overwrites the bridge's derived values, compounding the broader lack of a sanitization boundary at this layer.

## Integration Points

HookMigrationTool's placement as a child of **UnifiedHookManager** implies it consumes or transforms artifacts produced by the manager — plausibly bridging the legacy native-hook formats (loaded/saved via `HooksManager.loadNativeHooks()`/`saveNativeHooks()`) toward the unified representation. Its siblings clarify the division of labor: **ClaudeBridgeAdapter** owns the per-process stdin/stdout translation and fail-open exit contract; **HandlerRegistry** owns the abstract registration template inherited (or paralleled) from `hooks-api.js`; **UnifiedHookConfigLoader** owns lazy config loading gated by `manager.initialized`. HookMigrationTool likely operates at the seam where native per-agent hook definitions (EVENT_MAPPINGS' `claude`/`copilot` structures) must be reconciled into UnifiedHookManager's internal model — a migration concern distinct from, but dependent on, the dual event-mapping tables described above.

Notably, `integrations/system-health-dashboard`'s `hooks.ts` and `usePolledFetch.ts`, along with `tests/features/cli-and-rules-gating.test.mjs`, are confirmed structurally disconnected from this subsystem despite surface-level naming similarity ("hooks") — an artifact of code-graph search rather than real coupling, and should not be treated as integration points.

## Usage Guidelines

Given the fail-open architecture inherited from the surrounding bridge and manager layers, any migration logic in HookMigrationTool must not assume that a non-error return means a hook genuinely executed — `claude-bridge.js` cannot distinguish "no one objected" from "the hook infrastructure was broken," and this ambiguity likely propagates into any tooling built atop UnifiedHookManager. Before extending or modifying migration logic, developers should verify — rather than assume — the inheritance relationship between `HooksManager` and `UnifiedHookManager`, since the two event-mapping tables (`EVENT_MAP` vs. `EVENT_MAPPINGS`) must stay synchronized in both content and direction; migration code touching either table should include tests validating round-trip correctness in both directions. Finally, because metadata sanitization does not occur at the bridge layer, any migration tool consuming raw context should treat incoming `metadata` as untrusted and apply its own validation rather than assuming upstream sanitization occurred.
