# WaitForPortBindable — Technical Insight Document

## What It Is

`waitForPortBindable(port, options)` is a function implemented in `scripts/start-services-robust.js` that answers a narrow but important question: is a given port actually bindable right now, as opposed to merely "not being listened on"? It works by repeatedly instantiating a throwaway `net.createServer()` and calling `.listen(port, host)`, treating the `listening` event as success and an `error` event (or synchronous throw) as failure, polling every `pollIntervalMs` (default 250ms) up to `maxWaitMs` (default 5000ms). It is logically a child of the broader **ServiceProbe** concept in this codebase — sitting conceptually alongside `probeHttpHealth()`/`probeTcpPort()` in `service-probe.js` — but it is implemented independently, directly against Node's `net` module, rather than by delegating to that shared probing logic.

## Architecture and Design

The defining architectural decision here is treating "kill" and "rebind" as two separate, independently-verified facts rather than assuming one implies the other. This is made explicit in the function's own inline comment noting that the kernel may hold a socket in a TIME_WAIT-like state even after the owning process is confirmed dead. This directly complements its sibling in the same file, `killProcessOnPortAndWait(port, options)`, which polls `lsof -ti:${port}` to confirm process death via SIGTERM/SIGKILL escalation — together the two form a two-phase kill-then-rebind sequence in the service-restart lifecycle.

Structurally, the file contains three independent, unrelated health primitives: `waitForPortBindable`, `isPortListening`/`isTcpPortListening` (imported from `lib/service-starter.js`), and `isProcessRunningByScript()` (pgrep-based). None share a common abstraction — this is the same "multiple independent probing implementations" pattern noted for the parent ServiceProbe's relationship to `docker/entrypoint.sh`'s `wait_for_service()` (sibling **EntrypointTcpWaitForService**). The codebase as a whole thus favors defense-in-depth via layered, purpose-built probes over a single unified health-check abstraction — a recurring architectural tension across both the host-native (`start-services-robust.js`) and containerized (`docker/entrypoint.sh`, supervisord) startup paths.

The pattern is a bounded polling/spin-wait against a computed deadline, using a throwaway probe object purely to interrogate kernel state before discarding it — architecturally simple by design, deliberately eschewing exponential backoff or jitter in favor of a fixed-interval loop (up to 20 attempts at defaults).

## Implementation Details

The core mechanics are defensive-by-construction: `probe.unref()` ensures the throwaway server never keeps the Node event loop alive if the process exits mid-probe. The `try/catch` wrapped around `probe.listen(port, host)` normalizes both synchronous throws (e.g., invalid host) and asynchronous `error` events (e.g., EADDRINUSE) into the same `false` outcome, feeding back into the poll loop. This collapsing of failure modes is a notable trade-off: a genuinely permanent failure (e.g., attempting to bind a privileged port without capability) is indistinguishable from a transient "still held by dying process" state — both simply exhaust `maxWaitMs` and return `false`, in contrast to `probeTcpPort()`'s documented three-state (running/stopped/unknown) model in service-probe.js.

The return contract is a plain boolean with no error surfaced and no timing/diagnostic information returned to the caller — a much thinner contract than the disabled/degraded/failed trichotomy used by `startOneService()` elsewhere in the same file, or the three-state model in ServiceProbe. This is consistent with its role as an internal timing gate, not a health signal consumed by any dashboard or aggregation layer.

## Integration Points

`waitForPortBindable` has no entry in `SERVICE_ORDER`/`SERVICE_CONFIGS`, and consequently falls outside the structural coverage enforced by `tests/features/service-gating.test.mjs` ("SERVICE_ORDER and SERVICE_CONFIGS cover each other exactly"). It is invoked as a low-level utility from within one or more `startFn` closures rather than being itself subject to the feature-gating contract that `startOneService()` enforces. Its timing constants are overridable per-call via the `options` object, giving callers control without altering default behavior — deliberately leaving retry-on-failure and escalation decisions (retry whole service start, mark degraded, etc.) to the caller rather than implementing that logic itself, unlike the exponential-retry semantics implied by `startServiceWithRetry()` in `lib/service-starter.js`.

Within the parent ServiceProbe grouping, this function coexists with — but does not share code with — `EntrypointTcpWaitForService`'s bash-based `wait_for_service()` in `docker/entrypoint.sh`, and with `ServiceStarterHealthPrimitives`. Notably, entrypoint.sh's probe is purely advisory (always returns 0, "Don't fail - let supervisord handle it"), whereas `waitForPortBindable`'s boolean result is meant to gate actual retry logic in its caller — the same underlying question ("is this ready?") is answered with very different failure semantics depending on which startup path is asking.

## Usage Guidelines

Callers should treat `waitForPortBindable` strictly as a bounded, composable pre-flight check — not a substitute for process-death confirmation (`killProcessOnPortAndWait`) nor a full retry/backoff mechanism. Because it silently unifies all bind failure causes into `false`, callers attempting to bind privileged ports or otherwise permanently-unbindable addresses should not expect a distinct error; they will simply see `maxWaitMs` exhausted and `false` returned. Since it is untested by the service-gating structural tests, any change to its retry/timeout behavior requires manual verification rather than relying on `service-gating.test.mjs` to catch regressions. Developers extending startup logic should compose this function inside a `startFn`'s own retry loop rather than expecting it to retry the broader service start itself, and should be aware that its result is not logged or exposed through any status API by default.
