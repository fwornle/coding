# DockerEntrypointFeatureSnapshot: Technical Insight Document

## What It Is

`DockerEntrypointFeatureSnapshot` is the container-side feature-gating mechanism implemented in `docker/entrypoint.sh` (roughly lines 95–140), which reads a host-produced snapshot file at `/coding/.coding/runtime/features.json` and uses it to selectively disable `supervisord`-managed programs at container boot. It is the runtime counterpart to the host-side gating logic embodied in its sibling `FeatureGatedStartOneService` and the broader `scripts/start-services-robust.js` startup pipeline (parent: `DashboardServiceWrapper`). Where the host decides which Node-level services to start, the entrypoint decides which supervisord `[program:...]` sections are allowed to autostart inside the container — the same conceptual problem solved twice, once per side of the host/container boundary, with deliberately different safety postures.

## Architecture and Design

The core architectural pattern is an **additive override layer over static configuration**: `supervisord.conf` remains, by explicit inline comment, "the single place every program's command and logging are defined," and the entrypoint is "an override rather than a rewrite." Gating is bolted on entirely through a separate `/etc/supervisor/features.d/disabled.conf` directory that is fully regenerated (`rm -f "$FEATURES_DIR"/*.conf`) on every boot rather than diffed — a full rewrite of the thin override layer, never the base layer. This keeps the gating mechanism minimally coupled to program definitions.

The second defining pattern is a **two-tier fail-open policy**. If the feature snapshot file is missing entirely, the script takes the `else` branch and starts everything, logging "No feature snapshot ... starting everything." If the snapshot is present but a queried key is absent from `PROGRAM_FEATURES`, the per-pair `node -e` lookup's ternary (`value === false ? "false" : "true"`) again defaults to enabled. Both failures point the same direction — run more, not less — justified inline by the reasoning that a container silently running nothing due to a late JSON file is harder to diagnose than one running too much.

This is architecturally significant because it **inverts** the posture taken by the host-side sibling `FeatureGatedStartOneService` and `ServiceRequiredFlagAsymmetry`: `tests/features/service-gating.test.mjs` requires an unknown feature name on a `SERVICE_CONFIGS` entry to throw loudly (`/unknown feature 'nope'/`), since that configuration is fully repo-controlled and validated against `FEATURE_IDS` in `lib/features/catalogue.cjs`. The container, by contrast, must tolerate a host snapshot that may be stale by days or versions, so it is architected to degrade toward permissiveness rather than refusal. This boundary-dependent fail posture — same mechanism, opposite safety direction depending on which side controls config freshness — is the single most important design decision documented across this cluster of entities.

## Implementation Details

`PROGRAM_FEATURES` is a flat, hand-maintained, whitespace-delimited string: `"semantic-analysis:knowledge embedding-listener:knowledge graphify:codegraph constraint-monitor:constraints constraint-dashboard:constraints constraint-dashboard-api:constraints health-dashboard:health health-dashboard-frontend:health"`. It is parsed with bash parameter expansion (`${pair%%:*}` for the program name, `${pair##*:}` for the feature key) rather than an array or JSON structure — a deliberately lightweight, brittle-by-design substitute for a map, bound entirely by convention rather than language guarantees.

For each pair, the script shells out to `node -e` individually inside a bash `for` loop, meaning N feature entries spawn N separate Node processes just to repeatedly read the same `features.json` file. Each invocation has its own independent fallback (`2>/dev/null || echo "true"`), so a Node crash on one feature lookup fails open in isolation rather than aborting the whole gating pass — trading a small, count-proportional startup cost for per-feature failure isolation. This is a real (if minor) scalability consideration: gating cost grows linearly with the number of gated programs, unlike a hypothetical single batch resolution via something like the host's `lib/features/index.mjs` loader.

The correctness of this mechanism, as detailed by sibling `FeatureGatedStartOneService`, hinges on a narrow contract: the `node -e` one-liner must emit *exactly* the literal strings `"true"` or `"false"` on stdout, because the surrounding `if [ "$enabled" = "false" ]` is a plain string comparison. Any stray stderr leak or malformed-but-successful output (e.g., valid JSON that isn't an object) would produce a value that is neither literal, and since the `2>/dev/null || echo "true"` fallback only catches nonzero exit codes — not malformed successful output — that failure class fails open silently, an undocumented gap consistent with, but not explicitly called out by, the script's stated philosophy.

Additionally, the program-to-feature mapping is **many-to-one**: `knowledge` gates both `semantic-analysis` and `embedding-listener`; `constraints` gates three programs (`constraint-monitor`, `constraint-dashboard`, `constraint-dashboard-api`). A single host-side flag flip therefore fans out to disabling multiple supervisord programs at once — coarser granularity than the host's strict 1:1 `SERVICE_CONFIGS` mapping enforced by `service-gating.test.mjs`'s "every service declares a feature" test.

## Integration Points

The entrypoint's correctness depends entirely on `tests/features/container-gating.test.mjs`, referenced directly in the entrypoint's own comments, which asserts that `PROGRAM_FEATURES` covers exactly the `[program:...]` sections in `supervisord.conf` and names only real features. Since bash provides no compile-time safety over the flat string format, this test is the sole guard against drift — a clear instance of the **test-as-contract** pattern that also appears at the sibling level via `SERVICE_ORDER_Contract`'s cross-check between `SERVICE_ORDER` and `SERVICE_CONFIGS` in `scripts/start-services-robust.js`.

Conceptually, the entrypoint is the container-side half of a host/container boundary crossed via a **snapshot/mount pattern** rather than environment variables passed at container-create time — the host writes `/coding/.coding/runtime/features.json`, and the container reads it fresh at boot. This is architecturally distinct from, but directly parallel to, the host's `startOneService` feature checks (sibling `FeatureGatedStartOneService`) and `SERVICE_CONFIGS` in `scripts/start-services-robust.js`, which is itself the parent `DashboardServiceWrapper`'s core data structure.

## Usage Guidelines

Anyone modifying `PROGRAM_FEATURES` must keep it synchronized with both `supervisord.conf`'s `[program:...]` sections and real feature IDs, and should rely on `tests/features/container-gating.test.mjs` to catch drift rather than manual review, since the bash string format offers no structural safety. Developers should not "fix" the fail-open behavior to match the host's fail-closed posture without recognizing that the asymmetry is intentional and boundary-justified — the container legitimately cannot assume its snapshot is fresh, whereas host-side `SERVICE_CONFIGS` legitimately can assume its own repo-tracked correctness. Anyone touching the `node -e` lookup should preserve its strict `"true"`/`"false"` stdout contract, being aware that malformed-but-successful output is an unguarded gap. Finally, changes to the many-to-one feature-to-program mapping should be made with awareness that disabling one feature can silently take down multiple supervisord programs at once, unlike the tightly 1:1-enforced host-side service configs.
