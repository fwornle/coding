# CLAUDE.md - Coding Project Guidelines

## Mandatory Rules

- **PlantUML**: Use `plantuml` CLI command. NEVER `java -jar plantuml.jar`
- **TypeScript**: Mandatory with strict type checking
- **API design**: Never modify working APIs for TypeScript compliance; fix types instead
- **Visual UI verification — use `gsd-browser`**: For visual smoke/screenshot/click-through against `localhost:3002`/`3032`/`8080` or any local web UI, use the `gsd-browser` CLI (`navigate`, `screenshot`, `click`, `eval`, `select-frame`, `snapshot`) — wraps Playwright with the correct chromium resolution, avoids `ERR_MODULE_NOT_FOUND` from inline `chromium.launch()` scripts. `/playwright-cli` is an allowed entry point but a hand-rolled `node /tmp/foo.mjs` Playwright script still violates `prefer-gsd-browser`. Structured E2E tests go under `tests/e2e/<area>/<spec>.spec.ts`, run via `npx playwright test`.
- **Constraint dodging is forbidden**: fix the underlying issue, don't swap APIs to pattern-match around a regex (e.g. `process.stderr.write` to dodge `no-console-log`). For legitimate exceptions, include `OVERRIDE_CONSTRAINT: <id>` with rationale.
- **km-core LLM proxy endpoint**: rapid-llm-proxy serves `POST /api/complete` (NOT OpenAI `/v1/chat/completions`) on port **12435** (host) / `host.docker.internal:12435` (container, pre-set as `LLM_CLI_PROXY_URL`). Don't confuse with port **3033** (Health API — silently 404s `Cannot POST /api/complete`). Body: `{ process, messages, complexity? }`; response: `{ content, provider, model, tokens, latencyMs }` (not OpenAI-wrapped; `provider` is the ACCOUNT id). URL precedence: `RAPID_LLM_PROXY_URL` → `LLM_CLI_PROXY_URL` → `LLM_PROXY_URL` → `http://localhost:${LLM_CLI_PROXY_PORT ?? '12435'}`, append `/api/complete` once. Canonical clients: `scripts/backfill-raw-observations.mjs:40,95` (host), `integrations/semantic-analysis/src/agents/llm-with-process.ts` (container). **`taskType` does nothing** — only the `complexity` band (via `bg-<process>` route in `llm-routing.yaml`, or per-request on a `from-caller` route) controls cost.
- **km-core reads MUST NOT write — pass `readOnly` on request-scoped opens**: `close()` persists by default; `persistGraph` writes the WHOLE graph under one LevelDB key, so a read-only open still rewrites it on close. Fine for a one-shot CLI, fatal for a polled HTTP route (caused a 550× disk-amplification OOM-kill loop on vkb-server via `/api/experiments/runs`). Use `openExperimentStore({ readOnly: true })` for any read-path handler. Diagnostic: one GET adding one ~1MB `.ldb` file, or an order-of-magnitude gap between `du -sh` of the LevelDB and its JSON export. Recovery: stop vkb-server, `launchctl bootout` the writers, move the leveldb dir aside, open+close once to let `hydrate()` rebuild from `.data/experiments/exports/*.json`.

- **VKB**: `vkb` command opens http://localhost:8080
- **rapid-llm-proxy routing**: read from two version-controlled YAMLs — `_work/rapid-llm-proxy/config/llm-routing.yaml` (provider+model) and `config/llm-fallback.yaml` (fallback chains+guards). Nothing to run at startup; both hot-reload on mtime change. `scripts/configure-wave-analysis-routing.sh` is **DELETED** (used to PUT runtime overrides at boot, racing the proxy's own startup) — a config that won't parse now aborts proxy boot instead of silently skipping. Edit via dashboard (**Token Usage → Settings**, Routing/Fallback tabs) or by hand. **Flow** tab draws the config as a graph with edge thickness from real traffic — a thick edge to a provider with no route naming it means work is arriving by fallback. Each provider declares `available_models`; a band naming a model outside it fails validation at boot. Diagnose: `curl -s 'localhost:12435/api/llm/routing/resolve?job=bg-<service>' | jq -r .summary` (`&tools=true` for capability gate, `&network=corporate` to evaluate the other network). Full ref: `docs/architecture/llm-routing.md`.
- **Semantic offload — two targets, gated by network AND fg/bg `scope`**: `semantic_routing.targets` (ordered list, first `require_network` match wins — the old single `local_provider`+`require_network` keys are refused at boot). Targets: `qwen-local` (on-prem V100 cluster, corporate only, `scope:[fg,bg]`, ON) and `qwen-laptop` (llama.cpp on this laptop, `127.0.0.1:8081`, public only, `scope:[fg]`, OFF — **`llama-server` isn't installed/running here**, so it's declared-but-unreachable off-VPN). `offloadSkipped` distinguishes "no target here" / "target off" / "target doesn't serve this work".
- **The prompt-complexity JUDGE is network-aware and its own service**: config in `config/prompt-classifier.yaml`, served by `scripts/prompt-classifier-service.mjs` (`com.coding.prompt-classifier`, `127.0.0.1:12437`, hot-reloaded). `backends:` is an ordered, network-guarded list mirroring `semantic_routing.targets` (`qwen-local` corporate, `qwen-laptop` public). The judge is **never a metered model** — no reachable backend means no verdict and the caller's own band stands (fails open). Network comes from the proxy's cached `/health .networkMode`. Edit in dashboard **Token Usage → Routing → "The judge"** (shows `enabled` vs `reachable` as separate fields, and the rubric). `GET /api/llm/routing/behaviour` → `classifierNotes` surfaces a dead judge in aggregate.
- **`offload_bands` is `[small, medium]`; a TARGET may only narrow it, never widen** (a widening target would opt itself into work excluded everywhere; `qwen-laptop` declares `[small]`). Gate ladder: `considered · route-allows · band · target · target-band · scope · transport · offloaded` — `RUNG_OFFLOADED` is 7; always derive rung numbers from `GATES`/`RUNG_OFFLOADED`, never hardcode. `scripts/eval-prompt-classifier.mjs` gates on the WORST per-band precision (32-case corpus, 10/11/11) — re-run against a real model before trusting any further widening.
  - `scope` (who may be waiting) is independent of `offload_bands` (how hard the work may be) and independent of `enabled` (reachability ≠ usability) — all three default safe (`[fg,bg]`, subset check, `false`). A dashboard reorder now carries `scope` forward explicitly (used to silently reset it).
  - `QWEN_LOCAL_API_KEY` MUST live in `_work/rapid-llm-proxy/.env` (only file `bin/start-llm-proxy.sh` sources) — it silently does nothing from `coding/.env`. Verify with `/bin/ps -Eww -p <proxy pid> | tr ' ' '\n' | grep QWEN_LOCAL`, not by reading a `.env`.
  - A target is never probed on a network it doesn't serve (avoids leaking the corporate bearer off-network). `fg-chat/claude` can never be offloaded on any network — it's a verbatim Anthropic-wire passthrough.
  - A fg route pinned to a fixed band can never offload — all fg routes (`claude`/`copilot`/`opencode`/`pi`) are `from-caller` now. Residual gap: **Copilot CLI has no per-turn effort seam** (verified on the wire — no `reasoning_effort`, no caller-controlled header), so it still resolves to `defaults.fg-chat` (high) in practice; `effortLevel` in `~/.copilot/settings.json` is a decoy, not forwarded on the BYOK path.
- **`qwen-laptop` is the ONE name for the laptop-local Qwen, in every agent**: llama.cpp on this Mac, `127.0.0.1:8081`, model id `qwen3.8-27b-local` (same spelling in `llm-routing.yaml`, opencode config, pi's `models.json`). It used to collide with `qwen-local` (the proxy's name for the on-prem cluster) inside opencode's config — never reintroduce that name there. The on-prem `hga` direct-dial provider is **DELETED** from opencode (bypassed the proxy — no fallback/accounting/capability gate); reach the cluster through `rapid-proxy`.
  - Only opencode and pi can name it — claude speaks the Anthropic wire only, copilot's provider slot is held by the proxy's BYOK seam; for those two it's reachable only via semantic offload (never for claude off-VPN).
  - A direct picker selection (`qwen-laptop/qwen3.8-27b-local` in Ctrl+P) is **deliberately unmeasured** — bypasses the proxy's tap, writes no `token_usage` row. Acceptable: loopback, unmetered, credential-free. Not the default in either agent.
  - Base URL: `QWEN_LAPTOP_API_BASE_URL` (default `http://127.0.0.1:8081/v1`), same env var in both the proxy and `config/agents/pi.sh`.
- **Model ids are validated in TWO places**: (a) at boot, a provider's `models:` band table must draw from its `available_models`; (b) `node scripts/audit-agent-model-catalogue.mjs` (in `npm test`) checks every AGENT-declared id against the same catalogue, matching opencode providers **by base URL**. Needed because `/api/complete` silently discards and replaces whatever model an agent asked for with the routed one — a wrong id never 400s, never warns (this is how `claude-opus-4.6` survived in three configs at once).
  - Out of scope: providers that don't front the proxy (opencode's `github-copilot`, `qwen-laptop`) and foreground claude (`/v1/messages` is a verbatim passthrough — Claude Code's own model selection goes on the wire unconstrained).
  - `config/agents/opencode.sh` no longer has a network branch — both old pins were dead (listed zero valid ids); opencode.json's own default + `fg-chat/opencode` already decide. `CODING_OPENCODE_MODEL` remains the explicit override.
- **Token accounting — the two wires disagree; `total_tokens` means fresh input + output on BOTH now**: Anthropic's `input_tokens` excludes cache reads (additive `cache_read_input_tokens`); OpenAI's `prompt_tokens` includes them. `openAIFreshInputTokens()` (`src/usage-cache.ts`) subtracts `cached_tokens` at the parse boundary on all OpenAI-wire sites so cache columns are additive everywhere. Historical rows were repaired by `scripts/backfill-openai-wire-cache-split.mjs` (idempotency = a marker row in `token_usage_migrations`, not a data heuristic — don't re-run `--apply` expecting it to no-op safely without that marker). **When displaying, use `allTokens()`** (`token-usage.tsx`) = total + cache_read + cache_write; `total_tokens` alone understates real consumption, sometimes by 2+ orders of magnitude for cache-heavy foreground sessions.
- **A bare `claude` session is INVISIBLE to token accounting — always launch via `coding --claude` / `claude-mcp`**: foreground Claude reaches `token_usage` through a file adapter driven by hooks/daemons the wrapper installs **per launch**. A plain `claude` session writes its transcript but nothing reads it — zero rows, dashboards show a flat line. Recovery is lossless: `node scripts/recover-claude-transcript-tokens.mjs [--session=<uuid>] [--since=YYYY-MM-DD] --apply` (safe to re-run — dedup on `(user_hash, tool_call_id)`). Diagnose: last `token-adapter-claude` timestamp far behind `max(timestamp)` while `auto-measure.log` says "0 active session(s) written".
- **`subscription` is NOT an account identity — group by normalized `provider`**: the column holds multiple spellings for the same account and maps many-to-many to `provider` in both directions. Use `normalizeProvider(row.provider)` + `accountLabel()` (`src/lib/providers.ts`) — never group by raw `subscription`.
- **fg/bg split = `user_hash`, via an ALLOW-LIST** (`FOREGROUND_USER_HASHES` in the proxy's `src/token-usage.ts`) — deliberately allow-list rather than "≠ machine hash", so stray/junk hashes default to background (fails toward understating foreground). Exposed as `?scope=fg|bg|both` on `/api/token-usage/summary`, applied to every aggregate so headline and series can't disagree.
- **Never let background out-spend foreground**: a closed-set classifier job routed to `medium`/sonnet instead of `small` (the `taskType` field it claimed used to route on was never read by the proxy — only `complexity`/band matters), plus an idempotency gate that only skipped Insights that already HAD an edge (so a `[]` answer was re-asked every run, 11× redundancy). Both are config/gate mistakes worth checking for in any new bg classifier: (1) band is `small` in `llm-routing.yaml`, not a `taskType` field; (2) the skip condition must cover "already answered, even with an empty result" (e.g. a ledger keyed on a content hash), not just "already has an edge".
- **A local offload target needs its OWN `timeout_ms`, and the PROVIDER value caps the CALLER's — never the reverse**: `providers.<id>.timeout_ms` in `llm-routing.yaml` (values under 1000 refused as "looks like seconds"). `resolveRequestTimeout({callerTimeoutMs, providerTimeoutMs})` in `proxy-bridge/request-timeout.mjs` takes the MIN — a caller may ask for less, never more, so a semantic-offload target declaring 20-30s can't be dragged into a 5-minute wait by a caller's own timeout. Malformed values (`0`, `NaN`, `Infinity`, `'5000'`) count as "not stated", not coerced.
  - **`qwen3.8-27b-dual-normal` is a REASONING model** — spends completion tokens thinking before emitting content (~2× tokens, ~33 tok/s on a V100); `output_tokens` does NOT count reasoning tokens, so a row showing few output tokens against a long timeout is not proof it "worked fine." `medium` is removed from `qwen-local`'s `offload_bands` for this model. A ceiling only helps if it clears the real work — verify against realistic (~6K token) prompts before raising any timeout for it, not against a handful of short-prompt successes.
- **A `from-caller` route reads `reasoning_effort`, which is how pi declares a band**: pi has no `complexity` field, so `proxy-bridge/caller-complexity.mjs` resolves the band from `complexity` > `x-complexity` header > `reasoning_effort`, and `config/agents/pi.sh` maps pi's thinking levels onto band names. Lowering pi's thinking level to `low`/`minimal`/`off` is what routes a turn to the free local model. NOT a classifier — `resolve?…&complexity=<band>` reproduces every decision.
- **The proxy re-decides `HTTPS_PROXY` at RUNTIME (every 30s)** — `proxy-bridge/egress-decision.mjs` can drop a pinned proxy that stops answering even while the coordinator still reports the old network. On corporate, every hop in a fallback chain shares one pin, so fallback depth buys nothing against a stale pin during a VPN drop — diagnose network transitions here before assuming a proxy bug.
- **rapid-llm-proxy needs `npm run build` — its `dist/` is gitignored**: `proxy-bridge/server.mjs` imports compiled `../dist/*.js` from `src/*.ts`; a fresh clone can't start the proxy, and edits to `src/` don't reach the running daemon until rebuilt (same trap as km-core). After editing `_work/rapid-llm-proxy/src/**`: `cd _work/rapid-llm-proxy && npm run build && launchctl kickstart -k gui/$(id -u)/com.coding.llm-cli-proxy`. Editing `proxy-bridge/*.mjs` or `config/*.yaml` needs no build.
- **Provider names are ACCOUNTS, not companies**: `claude-code-max` (personal Max) ≠ `anthropic-api` (metered key) even though both serve Claude models. Always write `<provider>/<model>` (`claude-code-max/claude-opus-5`), never a bare model name.
- **launchd-managed daemons** (auto-respawn on crash/hang): `com.coding.obs-api`, `com.coding.health-coordinator`, `com.coding.llm-cli-proxy`, `com.coding.sub-agent-live-{claude,copilot,opencode}`, `com.coding.sub-agent-sweep`, `com.coding.lsl-lock-sweeper` (clears orphaned `.specstory/history/.git/index.lock`, StartInterval=60, only when no live git holds it AND mtime > 90s). LSL observation resolution now runs in-process inside obs-api (30-min sweep) — trigger manually via `POST /api/observations/resolve-lsl`. Inspect: `launchctl list | grep com.coding`; kickstart: `launchctl kickstart -k gui/$(id -u)/<label>`.
- **`vpn` and `corporate` are ONE network — never compare the two network vocabularies as raw strings**: coordinator speaks `corporate|vpn|open`, proxy's `/health .networkMode` speaks `corporate|public` — `vpn` and `corporate` mean the same thing. The flip-detector logic lives in `lib/network/proxy-mode-flip.mjs` (`settleModeFlip`+`classifyNetClass`, pure/unit-tested); `pollProxyMode()` is the sole writer of `proxy.networkMode` and compares against the last SETTLED class, never the last raw reading. Diagnose a restart-loop with `grep -c 'dispatching restart_llm_cli_proxy' .logs/health-coordinator.log` while ON VPN specifically — on public the bug is invisible because both sides spell it the same.
- **ETM is NOT launchd-managed** — the host coordinator owns every project's ETM uniformly, re-spawning a dead one within 30s. Logs: `.logs/etm-<project>.log` (rotated at 20MB). Watchdog auto-resets `isProcessing` after 60s, emits `[STALL-DETECT]` when no observation has been written for 5min despite fresh jsonl mtime.
- **A wedged ETM does not die** — stalled event loop, so `ps`/Health API look fine while the heartbeat stops and statusline goes `[LSL🔴]`. Diagnose with `sample <pid>` (not `ps`), read `.logs/etm-<project>.log` for the loop.

## Rebuilding After Code Changes

**CRITICAL: This project uses git submodules.** Code changes to submodule TS source do NOT take effect until BOTH steps are done:

1. **`npm run build`** inside the submodule (compiles TS → `dist/`)
2. **Docker rebuild** if the service runs in a container

Forgetting step 1 is a recurring issue — committed source looks correct but `dist/` stays stale and the container runs old code.

**Submodules requiring both steps:**
- `integrations/semantic-analysis`
- `integrations/constraint-monitor`
- `integrations/graphify` (git submodule built into the `coding-services` image; Python — no `npm run build`, but a Docker rebuild is needed to pick up source changes)

**After ANY code change to a submodule:**
```bash
cd integrations/<submodule> && npm run build
cd "$CODING_REPO"/docker && docker-compose build coding-services && docker-compose up -d coding-services
```

**Dashboard** (`integrations/system-health-dashboard/`): Bind-mounted into `coding-services` (`docker-compose.yml:96-102` covers `dist/`, `server.js`, `static-server.js`), so **no `docker-compose build` is needed** — but Docker Desktop's VirtioFS caches bind-mounted files and does NOT pick up host edits live. After editing, you MUST do one of:

```bash
# Frontend (UI bundle) only — rebuild dist/, then restart the frontend service:
cd "$CODING_REPO"/integrations/system-health-dashboard && npm run build
docker exec coding-services supervisorctl restart web-services:health-dashboard-frontend

# Backend (server.js / static-server.js) — restart the whole container to invalidate the FUSE cache;
# `supervisorctl restart web-services:health-dashboard` alone re-reads the STALE cached file:
cd "$CODING_REPO"/docker && docker-compose restart coding-services
```

Symptom of the stale-cache bug: the dashboard backend exits with `SyntaxError: Invalid or unexpected token` mid-line, because Docker serves a truncated snapshot of the file. Verify with `docker exec coding-services wc -lc /coding/integrations/system-health-dashboard/server.js` vs the host — sizes must match.

**Config files** (`integrations/semantic-analysis/config/`): Bind-mounted read-only, no rebuild needed.
