# CLAUDE.md - Coding Project Guidelines

## Mandatory Rules

- **Documentation skill**: ALWAYS invoke `documentation-style` skill before creating/modifying PlantUML, Mermaid, or documentation artifacts
- **PlantUML**: Use `plantuml` CLI command. NEVER `java -jar plantuml.jar`
- **TypeScript**: Mandatory with strict type checking
- **API design**: Never modify working APIs for TypeScript compliance; fix types instead
- **Visual UI verification — use `gsd-browser`**: For any visual smoke / screenshot / click-through against `localhost:3002` / `3032` / `8080` or any local web UI, use the `gsd-browser` CLI (`gsd-browser navigate`, `screenshot`, `click`, `eval`, `select-frame`, `snapshot`). It wraps Playwright with the correct chromium resolution and avoids the `ERR_MODULE_NOT_FOUND` failure mode of inline `chromium.launch()` scripts. The `/playwright-cli` skill is allowed as an entry point but does NOT excuse writing a hand-rolled `node /tmp/foo.mjs` Playwright script — that re-triggers the `prefer-gsd-browser` constraint. For structured E2E tests, place them under `tests/e2e/<area>/<spec>.spec.ts` and run via `npx playwright test`.
- **Constraint dodging is forbidden**: When a constraint blocks a tool call, fix the underlying issue — DO NOT swap to a different API that pattern-matches around the regex (e.g., `process.stderr.write` to dodge `no-console-log`). Switching to a different raw-write API preserves the behaviour the rule prevents and is itself a violation. For legitimate exceptions, include `OVERRIDE_CONSTRAINT: <id>` in the prompt with rationale.
- **km-core scripts**: Any CLI or service that imports `resolveEntities` from `@fwornle/km-core` MUST construct `GraphKMStore` with an `ontologyDir` option — otherwise default-class resolution throws `opts.classes omitted but store has no ontology registry`. Resolve via `import.meta.resolve('@fwornle/km-core')` + walk up to package root. Integration tests pass this explicitly, so absent CLI greps will mask the gap (Phase 41 lesson, commits `87bc2f567` / `fd35c5350`). When authoring a new CLI plan, include an acceptance grep for `ontologyDir` in the script.
- **km-core LLM proxy endpoint**: The local rapid-llm-proxy serves `POST /api/complete` (NOT OpenAI `/v1/chat/completions`) on **port 12435** (host) / **`host.docker.internal:12435`** from inside the coding-services container. The container has `LLM_CLI_PROXY_URL=http://host.docker.internal:12435` pre-set in `docker/docker-compose.yml`. **DO NOT confuse with port 3033** — that's the *Health API*, not the LLM proxy (the Health API will silently return `Cannot POST /api/complete` HTML, masking the wrong-port bug — Phase 42.2 Plan 06 follow-up lesson; submodule commit `7df8773`). Request body: `{ process, messages, complexity? }`; response: `{ content, provider, model, tokens, latencyMs }` — not OpenAI-wrapped, and `provider` is the ACCOUNT id (`gh-copilot`, `claude-code-max`). URL resolution precedence (matches `@rapid/llm-proxy` SDK convention): `RAPID_LLM_PROXY_URL` → `LLM_CLI_PROXY_URL` → `LLM_PROXY_URL` → `http://localhost:${LLM_CLI_PROXY_PORT ?? '12435'}`; append `/api/complete` exactly once. See `scripts/backfill-raw-observations.mjs:40,95` for the canonical host-side client and `integrations/semantic-analysis/src/agents/llm-with-process.ts` for the container-side wrapper. **`taskType` does nothing** — this file used to claim it "routes dedup calls to claude-haiku (cheaper)", but `server.mjs` and `worker-pool.mjs` contain zero references to it and always did; the field was silently ignored. To make a call cheap, give its `bg-<process>` a `complexity: small` route in `llm-routing.yaml`, or send `complexity` per request on a route declared `from-caller`.
- **km-core wiring — hand-made symlink, NOT a package.json dependency**: `@fwornle/km-core` is the `lib/km-core` git submodule, linked in by hand as `node_modules/@fwornle/km-core -> ../../lib/km-core`. It appears in **no** `package.json`, so `npm install` neither creates nor restores it and nothing fails loudly at install time. If the link goes missing (the scope dir `node_modules/@fwornle/` is typically left behind, empty), **every ETM spawn dies instantly** with `ERR_MODULE_NOT_FOUND: Cannot find package '@fwornle/km-core' imported from .../src/live-logging/ObservationWriter.js`. Symptom: statusline shows `[LSL🔴]` and the project's agent letter turns 🟡 **while the Health API still reports green** — this is the ETM, not a service, so health is the wrong place to look. Diagnose: `curl -s localhost:3034/health/state` (the project's `lsl` entry reads `status: stopped`, which `getLSLHealthStatus()` maps to `down`), then `tail .logs/etm-<project>.log` for the real error (the ETM is no longer launchd-managed — see the daemon list below — so `launchctl` tells you nothing about it; the coordinator re-spawns it within 30s, which turns this into a visible respawn loop in that log). Fix: `ln -s ../../lib/km-core node_modules/@fwornle/km-core`, then either wait 30s for the coordinator or `launchctl kickstart -k gui/$(id -u)/com.coding.health-coordinator` to force it. Beware the false all-clear: long-lived daemons that resolved the module *before* it vanished (e.g. obs-api) keep running and only fail on their next restart, so "obs-api is up" does not prove the link exists (2026-08-08).
- **km-core snapshot-restore patch (now upstream — nothing to re-apply)**: `hydrate()` in `store/persistence.js` prefers the JSON export over the LevelDB `graph:state` cache when the JSON has more nodes. **Why**: `persistGraph` only fires on clean `close()`; an obs-api crash during shutdown (we hit a `libc++abi mutex lock failed` on SIGTERM) leaves LevelDB frozen at the prior clean state — *days* behind the JSON exports written by the exporter's 5s-debounced scheduleExport. Without it, `launchctl kickstart com.coding.obs-api` resurrects the stale state (a 2026-06-05 snapshot came back over a 2026-06-11 backfill). This is **no longer a local `node_modules` patch** — but not for the reason this file used to give. It is committed in the submodule **source**, at `lib/km-core/src/store/persistence.ts` (marked "Phase 57-05 lesson: prefer JSON exports"), and it reaches `dist/` only by being rebuilt. **`lib/km-core/.gitignore` line 2 is `dist/`, so NOTHING under `lib/km-core/dist/` is tracked by git** — the earlier claim that the patch "is committed at `lib/km-core/dist/store/persistence.js`" was wrong. Two consequences: (1) since the patch lives in source, `npm run build` regenerates it and cannot wipe it, so disregard any older instruction to re-apply it manually after `npm install`; (2) **a fresh clone or a wiped `dist/` has no built km-core at all**, and since `node_modules/@fwornle/km-core` is a symlink to `lib/km-core` (not an npm install), nothing restores it — you MUST run `npm run build` in `lib/km-core` before any consumer can import it. The same applies to every km-core change you make: it does not travel via git as `dist/`, so each machine has to build it.
- **km-core reads MUST NOT write — pass `readOnly` on any request-scoped open**: `GraphKMStore.close()` persists by default, and `persistGraph` is a single `db.put('graph:state', JSON.stringify(graph))` — **the whole graph as ONE value under ONE key** (the experiment LevelDB contains exactly 1 key). So a store opened purely to READ still rewrites the entire graph when it closes. Harmless for a CLI that opens once; fatal on a polled HTTP route doing open→read→close per request. Any handler that opens a km-core store to read MUST use `openExperimentStore({ readOnly: true })` (which sets `persistOnClose: false`); the default stays `true`, so writers need no change. **Why**: `/api/experiments/runs` is polled every 30s by `performance.tsx:173`, and each poll appends a ~1 MB SST for a graph that exports to 8.3 MB. Left unchecked, `.data/experiments/leveldb` grows to thousands of files and multiple GB backing ~4,000 nodes — 550× amplification — at which point `open()` alone exceeds the container's 4 GiB cgroup limit and the kernel OOM-kills vkb-server on **every** poll; each SIGKILL is an unclean close, so compaction never catches up and the loop sustains itself. Diagnostic signature: `WARN exited: vkb-server (terminated by SIGKILL; not expected)` every ~30s with *clean, fast* startup logs (⇒ request-triggered, not startup). **`docker stats` lies here** — it reports a few hundred MB against the 4 GiB limit because the spike outruns its 1s sampling; read `/sys/fs/cgroup/memory.events` (`oom_kill`) and `memory.peak` instead. Cheapest positive test: **one GET adds one ~1 MB `.ldb` file**; an order-of-magnitude gap between `du -sh` of the LevelDB and its JSON export IS the bug. Recovery: stop vkb-server, `launchctl bootout` the writers (`com.coding.auto-measure-foreground`, `com.coding.measurement-reconciler`), move the leveldb dir aside, then open+close the store once — `hydrate()` rebuilds it from `.data/experiments/exports/*.json`.

## Startup & Services

- **Command**: `claude-mcp` or `coding --claude` (starts all services). Never use bare `claude`
- **Dashboard**: http://localhost:3032 | **Health API**: http://localhost:3033
- **Semantic Analysis SSE**: http://localhost:3848 (workflow execution)
- **VKB**: `vkb` command opens http://localhost:8080
- **rapid-llm-proxy routing** — NOTHING to run at startup. Routing is read from two version-controlled YAML files in the proxy repo and needs no post-start step: `_work/rapid-llm-proxy/config/llm-routing.yaml` (which provider + model) and `config/llm-fallback.yaml` (fallback chains + guards). `scripts/configure-wave-analysis-routing.sh` is **DELETED** — it PUT ~26 `processOverrides` into runtime state at boot, which made routing depend on a script having run, racing the proxy's own startup. A config that will not parse now **aborts proxy boot** instead of being silently skipped. Edit via the dashboard (**Token Usage → Settings**, Routing/Fallback tabs — saves are validated before write and preserve the files' comments) or by hand (reloaded on mtime change, no restart). The third tab, **Flow**, draws the same config as a graph with edge thickness from real `token_usage` traffic, so a thick edge to a provider no route names = work arriving by fallback (the tables cannot show this). Each provider also declares `available_models` — everything that ACCOUNT can serve; the `models` band table is a choice out of it, and a band naming a model outside the catalogue **fails validation at boot** rather than 400-ing on the next call. An empty catalogue constrains nothing (that is how `gaia` stays declarable). Diagnose with `curl -s 'localhost:12435/api/llm/routing/resolve?job=bg-<service>' | jq -r .summary` — add `&tools=true` to apply the capability gate, `&network=corporate` to evaluate the other network's guards. Full reference: `docs/architecture/llm-routing.md`.
- **Semantic offload: two targets, each gated by network AND by fg/bg `scope`**: `semantic_routing` in `llm-routing.yaml` takes a `targets:` list (ordered, first `require_network` match wins), NOT the old single `local_provider` + `require_network` — those two keys are now **refused by name at boot**. Two targets ship: `qwen-local` (the on-prem V100 cluster, corporate only, `scope: [fg, bg]`, ON) and `qwen-laptop` (llama.cpp on this laptop, `127.0.0.1:8081`, public only, `scope: [fg]`, OFF). Before 2026-08-28 there was only the corporate one, so **off-VPN every `small` call went back to a paid account silently**; `offloadSkipped` now distinguishes "no target here" from "the target here is off" from "the target here does not serve this kind of work".
- **The prompt-complexity JUDGE is network-aware, config-driven, and its own service — `config/prompt-classifier.yaml`**: the proxy's `classifier:` block in `llm-routing.yaml` decides WHETHER to ask and which bands a verdict may take; **which model judges and what it is asked live in this repo**, in `config/prompt-classifier.yaml`, read by `scripts/prompt-classifier-service.mjs` (`com.coding.prompt-classifier`, `127.0.0.1:12437`) and **hot-reloaded on mtime**. `backends:` is an ordered, network-guarded list with the same shape and the same first-match-wins rule as `semantic_routing.targets` — `qwen-local` on corporate, `qwen-laptop` on public. **Why it had to become a list**: until 2026-09-02 it was one URL from one env var fixed at boot (the laptop), so inside CN two `--pi` turns recorded `classifier error: classifier HTTP 502` and ran on `gh-copilot/claude-sonnet-5` while the offload *destination* for that network was up and reachable the whole time — the judge was the only part of the path that could not follow the machine between networks. **The judge is never a metered model**: no reachable backend means no verdict, the proxy fails open, and the caller's own band stands. Network comes from the proxy's `/health .networkMode` (cached 60s, fails open to `public`), not sensed again — one source of truth. Validation is `scripts/lib/prompt-classifier-config.mjs`, pure and unit-tested, refusing near-miss key names rather than ignoring them. Edit in the dashboard at **Token Usage → Routing → the offload card ("The judge")**, which also shows per-backend `enabled` vs `reachable` **as separate fields** — "switched off" and "not answering" have opposite fixes — and the rubric itself in an editable box.
  - **A dead judge is now visible in aggregate.** `GET /api/llm/routing/behaviour` returns `classifierNotes` (tallied from `attempt_trail.classifier`), rendered as `judge` rows in **Candidates never tried** with errors in red. Before this the note existed only per row, which is exactly how a judge whose backend had been down for a day looked identical to a policy that had decided not to downgrade anything.
  - **`llama-server` is NOT installed on this machine** (only the GGUF at `~/models/Qwen3.8-27B-GGUF`) and nothing has a launchd job for it, so `qwen-laptop` is declared-but-unreachable and the offload does nothing off-VPN. Corporate is unaffected — the cluster serves both the judge and the destination.
- **`offload_bands` is now `[small, medium]`, and a TARGET may narrow it**: `semantic_routing.targets[].offload_bands` overrides the global list for one endpoint and **must be a subset of it** — the global list states what the policy permits, a target states what that box can take, and a target that could widen policy would let one endpoint opt itself into work excluded everywhere. `qwen-laptop` declares `[small]` because it serves exactly one model and averages 47s. **Without the per-target field, adding `medium` globally FAILS BOOT** on the laptop's missing medium model — turning "let the cluster take medium" into "delete the laptop target". Ladder gate order is now `considered · route-allows · band · target · target-band · scope · transport · offloaded`; **`RUNG_OFFLOADED` moved 6 → 7**, so derive rung numbers from `GATES`/`RUNG_OFFLOADED` and never hardcode them (three test fixtures did, and broke).
  - **Widening to `medium` retired the eval's stated premise.** "Precision on `small` is the only metric that matters, because a wrong `medium`/`high` verdict changes nothing" was exactly true while both lists were `[small]`. It is not now: a wrong `medium` moves real work. `scripts/eval-prompt-classifier.mjs` measures precision **per emittable band and gates on the WORST**, and the labelled corpus grew to 32 cases (10/11/11). **Re-run it against a real model on corporate before trusting the widening** — it has not been run against one since the change.
  - **`scope` (added 2026-08-29) says WHO may be waiting; `offload_bands` says HOW HARD the work may be.** The band alone cannot express "cheap, but only when someone is watching" — which is why switching `qwen-laptop` on used to hand `bg-observation-writer` and `bg-auto-measure-title`, the two highest-volume services on the machine, to an endpoint averaging 47s against `gh-copilot`'s 5.4s. Default is `[fg, bg]`, so omitting it changes nothing. It is per-target because it describes the **box**, not the policy.
  - **`enabled` is separate from `scope` and both default safe** (`enabled: false`, `scope: both`): reachability is not usability, and the 60s probe can only establish the first. Toggle in the dashboard (**Token Usage → Settings → Routing**) or the YAML. The PATCH write is surgical for an enabled-toggle (prose under each target survives); a **reorder** rebuilds the sequence, and it now carries `scope` forward explicitly — before that it would have silently reset the laptop to `[fg, bg]`, restoring the exact bug, from a UI action nobody would connect to it.
  - **`QWEN_LOCAL_API_KEY` MUST live in `_work/rapid-llm-proxy/.env`** — `bin/start-llm-proxy.sh:46` sources exactly that one file. The same key sat in `coding/.env` from 2026-08-28 and the proxy never saw it: `qwen-local` stayed `available: false`, the probe logged `QWEN_LOCAL_API_KEY not set, skipping` **once at boot and never again** (it only logs on transitions), and the whole offload silently did nothing on VPN. Verify with `/bin/ps -Eww -p <proxy pid> | tr ' ' '\n' | grep QWEN_LOCAL`, not by reading a `.env`.
  - **A target is not probed on a network it does not serve** (2026-08-29). The routing guard already refuses to send work off-network, so an off-corp probe of `qwen-local` could only yield a `false` the router will ignore — while opening a connection to `10.143.241.223` and sending the corporate bearer on whatever network the laptop is actually on. `fg-chat/claude` can never be offloaded on any network: it arrives on the Anthropic wire at `/v1/messages` and no local provider carries `fg_transport`.

- **Token accounting: the two wires disagree, and `total_tokens` now means fresh input + output on BOTH**: Anthropic reports `input_tokens` EXCLUDING cache reads (additive `cache_read_input_tokens`); OpenAI reports `prompt_tokens` INCLUDING them (`cached_tokens` is a breakdown, not an addition). The proxy recorded each verbatim, so the column could not be summed across providers. Measured 2026-08-29 over 24h: foreground Claude Code showed **726K** tokens while really consuming **327M** (320.8M of cache reads excluded) — a **450× undercount** — while a background classifier showed its cache hits in full at 51.9M, inverting which dominated. `openAIFreshInputTokens()` (`src/usage-cache.ts`) now subtracts `cached_tokens` at the parse boundary on all three OpenAI-wire sites, so cache columns are additive everywhere. Historical rows were repaired by `scripts/backfill-openai-wire-cache-split.mjs` (25,455 rows; 732M cache tokens moved out of `input_tokens`) — it targets ONLY the pure OpenAI-wire providers (`gh-copilot`, `copilot`, `qwen-laptop`, …), never the file adapters (`token-adapter-opencode` carries BOTH shapes inside one process, so no per-row rule separates them). **Its idempotency is a marker row in `token_usage_migrations`, NOT the data**: after correction 3.4% of rows still satisfy `input_tokens >= cache_read_tokens`, so a second `--apply` would subtract again — it refuses instead. **When displaying, use `allTokens()`** (`token-usage.tsx`) = total + cache_read + cache_write; `total_tokens` alone is not "what this consumed".
- **A bare `claude` session is INVISIBLE to token accounting — always launch via `coding --claude` / `claude-mcp`**: foreground Claude turns reach `token_usage` through the file adapter (`lib/lsl/token/claude-token-rows.mjs`), driven by hooks and daemons the wrapper installs **per launch** (`generate-agent-instructions.sh` reports this as "Claude gets them per-launch via 'coding' (wrapper-scoped)"). A session started with a plain `claude` writes its transcript normally and **nothing reads it** — zero rows, so every board that reports tokens or cost shows a flat line. Measured 2026-08-29: a bare-claude session from 06:16Z–09:44Z accounted for **182M tokens**, more than everything else on the machine combined, while the dashboard showed nothing and called the day background-dominated. The two sessions that morning are a clean control — the `coding`-launched one (`b7a50fb6`) was fully captured, the bare one (`459f082b`) not at all. **Recovery is lossless**: `node scripts/recover-claude-transcript-tokens.mjs [--session=<uuid>] [--since=YYYY-MM-DD] --apply` replays the transcript through the same builder and the same deduped insert the live adapter uses. Safe to re-run — `token_usage` has a UNIQUE index on `(user_hash, tool_call_id)` and `insertTokenRowDeduped` honours it, so an already-captured session adds nothing. Diagnose with: last `token-adapter-claude` timestamp far behind `max(timestamp)` while `auto-measure.log` says `claude pass complete — 0 active session(s) written`.
- **`subscription` is NOT an account identity — group by normalized `provider`**: the `token_usage.subscription` column holds **four spellings for the Claude Max account alone** (`max-oauth-passthrough`, `max-subscription`, `anthropic-subscription`, and empty) and maps **many-to-many** to provider in both directions (`copilot-subscription` spans `copilot`+`gh-copilot`; `max-oauth-passthrough` spans `anthropic`+`claude-code-max`). Any surface grouping by it renders one account as several rows — the same double-counting `PROVIDER_ALIASES` exists to prevent, in a column nobody aliased. The Token Usage card did exactly this until 2026-08-29. **Use `normalizeProvider(row.provider)` + `accountLabel()`** (`src/lib/providers.ts`); there is one identity system, not two.
- **fg/bg split = `user_hash`, via an ALLOW-LIST**: foreground rows carry an agent-adapter hash (`cladpt`, `opnadt`, `opcadt`, `copadt`, `piadpt` — `FOREGROUND_USER_HASHES` in the proxy's `src/token-usage.ts`); background telemetry omits `user_hash` and gets the machine hash. Deliberately an allow-list rather than "≠ the machine hash", so a second machine and the junk hashes a long-lived DB accumulates (`seed-demo`, `fake-process`) do not read as foreground — unknown means background, failing toward understating foreground.
